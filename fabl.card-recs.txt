0. TLDR
--------------------------------------------------------------------------------
All three reports independently reached the same headline conclusions, which
gives us high confidence:

  * Pure CSS + the existing semantic HTML is the right tool. Canvas: rejected
    unanimously. SVG: decoration only, never the list itself.
  * The "selected card goes transparent" bug is the row tints being mixed with
    literal `transparent` instead of the opaque pane color. Unanimous.
  * The chosen/hovered card must be raised with an explicit z-index, not just
    a translateY transform. Unanimous.
  * The gradient instinct (lighter card top -> darker bottom) is correct,
    achievable with color-mix over theme tokens, and theme-safe. Unanimous.

The one substantive disagreement is HOW MUCH real geometric overlap the cards
should have. Recommendation: ship correctness first (no overlap), style the
deck illusion with shadows/gradients/decorative edges second, and offer true
overlap only as an opt-in "compact stack" density mode built on the safe
foundation. Details below.

1. ROOT CAUSE — RECONCILING THE THREE DIAGNOSES
--------------------------------------------------------------------------------
GPT-5 and Fable agree exactly, and the CSS confirms it:

  PRIMARY CAUSE (the stacking itself): `.email-list-pane__list` is a flex
  column; `.email-list-pane__item` has default `flex-shrink: 1` plus an
  explicit `min-height: 4.5rem` (72px). The explicit min-height replaces the
  default `min-height: auto` content floor, so when the folder is full,
  flexbox compresses every row to 72px while its content (~110px: header
  line + 72px cartouche + padding) keeps painting, unclipped, over the next
  row. Density is the trigger, which is why only busy folders stack.

  Grok's report attributes the overlap mainly to the hover translateY without
  z-index promotion. That mechanism is REAL but SECONDARY — it explains a
  ~4px ambiguity at row edges and the wandering hover target, not the ~38px
  card-on-card pile visible in docs/stacking.png with no pointer anywhere
  near. Treat Grok's finding as an amplifier and fix it too, but the
  flex-shrink fix is the load-bearing correction.

  SECONDARY CAUSES (all three reports, combined list):
    a. Transparent state tints: selected = color-mix(accent 10%, transparent),
       unread = 8% info wash, hover = rgba(255,255,255,0.05), loading =
       opacity 0.7. Overlapped content ghosts straight through them.
    b. No z-index elevation on hover/selected/focus (only --menu-open: 30),
       so paint order and pointer ownership follow raw DOM order.
    c. Transform moves paint + hit-testing but not layout, so a hovered card
       vacates a strip of its own layout box (Grok's correct observation).
    d. Cascade order bug (GPT-5's catch, verified): the --selected rule
       appears BEFORE --unread in EmailListPane.css, so an unread row that
       is selected shows the unread wash until the read state flips, then
       snaps — amplifying the "it changed to transparent" impression.

2. WHAT ALL THREE REPORTS AGREE ON — ADOPT WITHOUT DEBATE
--------------------------------------------------------------------------------
  A1. Kill the accidental squash: add `flex-shrink: 0` (or flex: 0 0 auto)
      to `.email-list-pane__item`.
  A2. Make every stateful background opaque by mixing over the base surface,
      never over `transparent`:
        selected: color-mix(in srgb, var(--accent-primary) ~14-22%, var(--secondary-bg))
        unread:   color-mix(in srgb, var(--status-info) 8%, var(--secondary-bg))
        pending:  same pattern with --accent-warning
        hover:    gradient over var(--secondary-bg), not bare 5% white glass
      Always mix against theme tokens so Light/High-Contrast themes keep
      working (Grok risk R4; GPT-5 accessibility section).
  A3. Explicit z-index ladder + `isolation: isolate` on the list container
      (both other reports; GPT-5's concrete ladder is good):
        ordinary 1, selected 3, hover/focus-within 5, menu-open 30,
        popover 20 inside the raised row. Keep menu-open above hover.
  A4. Keep and enrich the "draw a card from the deck" hover: slightly larger
      translateY, tiny scale (~1.005-1.01), a real outer box-shadow so the
      lifted card casts onto the pile, same treatment for :focus-within so
      keyboard users get the identical spatial cue.
  A5. Top-light gradient card face — the product owner's original idea —
      e.g. color-mix(white ~6-8%, --secondary-bg) at the top edge fading to
      color-mix(black ~15-18%, --secondary-bg) at the bottom, plus a 1px
      lighter top border as the "lit card edge".
  A6. Rotation, if any, stays tiny (<= ~0.3deg alternating). All three
      reports warn that real fan angles hurt text legibility in a mail list.
      Verify crispness at 125%/150% Windows scaling before keeping it.
  A7. prefers-reduced-motion: keep transforms disabled (already done), but
      NOTE (Grok, correct): z-index elevation and opaque selection are
      correctness, not decoration — they must survive reduced-motion.
  A8. No canvas. No SVG list. SVG stays where it already is (cartouche art).

3. THE ONE REAL DISAGREEMENT — HOW MUCH TRUE OVERLAP?
--------------------------------------------------------------------------------
  Fable's original report: embrace constant negative-margin overlap; since
    hit-testing follows paint order, a constant exposed "spine" per card
    makes the visible slice exactly the clickable slice, fixing misclicks
    by construction.
  GPT-5: never let interactive content overlap at all; keep card boxes
    vertically separate and fake the deck with opaque gradients, shadows,
    and pointer-events:none pseudo-element "card edges" behind each card.
  Grok: middle path — default density non-overlapping; offer an opt-in
    "compact stack" mode (negative margin + per-index z-index + hover
    expands the card) when count is high or user prefers it.

  RECOMMENDATION (synthesis): do it in stages and let real usage decide.
    * Phase 2 ships GPT-5's safe illusion: fully separate cards, gradient
      faces, lower shadows, optional decorative stacked-edge pseudo-elements
      with pointer-events: none. Zero interaction risk, immediately better
      than today, and honestly delivers most of the "stacked deck" look.
    * Phase 3 (optional, product call) adds Grok's compact mode implemented
      with Fable's spine geometry: constant margin-top overlap tuned so the
      exposed strip is exactly the header line (sender left, date right —
      file-folder tabs), per-index z-index so fan direction is deliberate,
      hover/focus raises AND expands the card. The GPT-5 rule stays law:
      a user must never see text of card A where the pointer belongs to
      card B — with constant overlap + correct z-index, the exposed strip
      of each card is owned by that card, satisfying the rule.
    * Compact mode is a modifier class (.email-list-pane__list--compact),
      trivially removable, and can be gated on message count or a settings
      toggle.

4. UNIQUE POINTS WORTH KEEPING FROM EACH REPORT
--------------------------------------------------------------------------------
  From GPT-5 (adopt):
    - The selected/unread cascade-order fix (see 1.d) — cheap, do in Phase 1.
    - Don't change surface opacity when unread flips to read on select; the
      snap is part of the perceived "vanishing".
    - Long-term semantic cleanup: the row is an <article role="button"> with
      six interactive descendants relying on stopPropagation. Replace with a
      dedicated primary "open message" button layer + real sibling buttons.
      Not required for the visual fix; schedule as tech-debt Phase 4.
    - Its test matrix (folders x densities x scaling x pointer-edge clicks x
      keyboard) is the most complete — adopt it as the acceptance checklist.
  From Grok (adopt):
    - `isolation: isolate` on the list to contain z-index wars with the rest
      of the dashboard.
    - Risk register framing; especially R5: any new hover z-index must keep
      the open row menu on top (menu-open 30 > hover 5 — preserved in A3).
    - Box-shadow cost on low-end GPUs: keep blur radii modest, transitions
      short.
    - Virtualization for very large folders is orthogonal — note and defer.
  From Fable (adopt):
    - The precise root-cause chain (explicit min-height defeats min-height:
      auto's content floor) — worth a code comment on the fix so nobody
      reintroduces it.
    - Spine geometry spec for compact mode: the exposed strip must be the
      existing header band, which the DOM already provides — no JSX
      restructuring needed for Phase 3.
    - Fan-direction control via style={{'--i': index}} + calc'd z-index if
      the deck should read "newest on top".

5. IMPLEMENTATION PLAN (CONSOLIDATED)
--------------------------------------------------------------------------------
  PHASE 1 — Correctness (small diff, ship immediately)
    1. .email-list-pane__item { flex-shrink: 0; }  (+ explanatory comment)
    2. Opaque state backgrounds per A2; reorder rules so selected beats
       unread deterministically.
    3. z-index ladder per A3 + isolation: isolate on the list.
    4. Give hover/focus-within the raised z-index now, even before the
       visual redesign.
    Acceptance: with 50+ mails, no row overlaps; clicking any visible card
    at top/center/bottom edge selects that card; selecting an unread mail
    leaves an obviously solid, highlighted card.

  PHASE 2 — Deliberate deck styling (pure CSS)
    5. Gradient card faces (A5), rounded corners, soft lower shadow, 6-8px
       inter-card gap, lit top edge.
    6. Upgraded hover/focus "draw card" motion (A4) honoring --motion-scale
       and reduced-motion.
    7. Optional decorative stacked-edge pseudo-elements (pointer-events:
       none) and/or micro-offsets; rotation only if it survives the
       Windows-scaling crispness test (A6).

  PHASE 3 — Opt-in compact stacked density (product decision)
    8. .email-list-pane__list--compact: constant negative margin exposing
       the header spine, per-index z-index, hover/focus raises + expands.
       Gate on count threshold or a user setting. Revert is one class.

  PHASE 4 — Structural tech debt (independent)
    9. GPT-5's semantic cleanup of the row's interactive children.
    10. Virtualization for very large folders if pagination limits grow.

  TESTING — use GPT-5's matrix (section "Test matrix" in docs/gpt5.cards.txt)
  as the acceptance checklist for Phases 1-3; add Grok's R3 perf check
  (long-list hover shadows) on the low-end target machine.

6. FINAL VERDICT
--------------------------------------------------------------------------------
Three independent analyses converge: fix the flexbox shrink and the
transparent state surfaces first (that is the entire bug), then rebuild the
happy accident as an intentional, opaque, gradient-lit CSS card deck with an
honest z-index story. Real overlap is a Phase-3 opt-in luxury, not the
foundation. No canvas, no SVG scene graph, no new dependencies — roughly
30-60 lines of CSS for Phases 1-2 and a one-line JSX index variable if the
fan direction ever needs to flip.
