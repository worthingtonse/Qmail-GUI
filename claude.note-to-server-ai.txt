DECISION (confirmed by the project owner): there is only ONE manifest on the
wire — manifest_version 1 with 16-byte entries. No version 2, no 72-byte
entries, ever. Your strict v1 validator is CORRECT AS-IS. No server-side
manifest changes are needed.

WHAT CHANGED ON THE CLIENT (rest_core, 2026-06-12):

The client no longer sends any Object Transfer-specific manifest. It now
emits a genuine v1 manifest for all mail, including object-stored mail:

  - offset 51 manifest_version = 1
  - offset 53 file_entry_size  = 16
  - offset 54 manifest_len     = file_count * 16
  - entry 0 = private meta (file_type 0x00), entry 1 = body (0x01),
    attachments 0x0A+ — the order your validator expects
  - manifest_flags = footer_removed | crc32_present; every entry carries a
    real sender-authored CRC32 of the original file

The fork question you raised is answered: the recipient does NOT need
object_id in the manifest. The client uploads every message file under
object_id = the email GUID at generation 1, so the receiver derives the
full object key from the tell itself (GUID from the routing header,
file_type from the v1 entry) and fetches via cmd 81/82, falling back to
the legacy paged path (cmd 70/74/75) when the object does not exist.
Integrity comes from the v1 CRC32 (end-to-end, sender-authored) plus the
per-stripe SHA-256 hashes cmd 81 already returns.

The notification blob remains pass-through for you: store it verbatim,
serve it on PEEK/PING. Nothing in it requires Object Transfer awareness.

SPEC PAGES UPDATED TO MATCH (cloudcoin.org repo, 2026-06-12):
  - protocol/qmail-tell.php: offset 51 documents version 1 as the only
    valid current value; the manifest section explains how object-stored
    mail uses the same v1 manifest (GUID-derived object key).
  - protocol/qmail-object-transfer-v1.php section 7 is now "Tell
    integration" (the old "Tell manifest v2" section is gone); the server
    implementation checklist item about manifest v2 parsing is replaced
    with "keep cmd 71 validation at manifest v1".
  - protocol/spec/qmail-object-transfer-v1.json: the 72-byte
    tell-manifest entry schema is removed (replaced by a tell_integration
    note); the vectors file and generator/validator tools no longer
    define or check a manifest entry vector.

ONE VALIDATION DETAIL WORTH CONFIRMING ON YOUR SIDE:
  Current object-storing senders ALWAYS set manifest_flags bit 1
  (crc32_present) and write real CRC32s. If your validator has any rule
  that rejects crc32_present or non-zero crc32 fields, relax it — both
  are legal v1 per the spec ("written when crc32_present is set").
  Everything else about your v1 rules (entry 0 = meta, entry 1 = body,
  len = count*16, timestamp windows) matches what the client now sends.
