3. Primary software bug (HIGH) — stale Bank-only guard
------------------------------------------------------
Source of truth (verified in tree):

  core/api_src/api_handlers_locker.c  →  api_handle_locker_upload()

Early guard (~lines 432–441):

  list_bin_files(bank_path, ...)
  if (file_count <= 0) {
      json_error_response_from_string(..., "No coins in Bank", 404);
      return;
  }

This aborts BEFORE any coin selection. But the same handler ALREADY supports
Bank + Fracked:

  - Single-coin mode: Bank first, then Fracked fallback
    (~495–515); error text even says "in Bank or Fracked" (~519).
  - Amount mode: greedy Bank then Fracked + make-change cascade
    (~574–677; Fracked pass ~602–627; comment ~946 on put path:
    "greedy from Bank then Fracked").
  - Snapshot helper locker_snapshot_bank_fracked_denom_counts (~373–393)
    counts Bank + Fracked.
  - Insufficient-funds path (~679–698) uses
    calculate_wallet_balance_units() = Bank + Fracked
    (api_handlers_utils.c).

GPT was right that Bank was empty and the endpoint "requires Bank" at the
guard. Fable was right that this is a *stale* requirement: selection logic
below would spend Fracked, so the guard contradicts its own handler.

Consequence for this session: Bank=0, Fracked=345 → every
GET /api/locker/upload 404s with "No coins in Bank", even though amount-mode
selection would have taken one fracked 10,000-CC coin.

If the guard were relaxed (Bank+Fracked empty only, or removed so selection
errors surface), THIS specific withdraw should succeed without waiting for
heal.

Related sibling endpoint:

  api_handle_locker_put_no_sum (later in same file) has NO equivalent early
  "No coins in Bank" abort; it goes straight to Bank-then-Fracked selection.
  Behavior is inconsistent between locker upload vs put-no-sum.

------------------------------------------------------------

   This wallet: plaintext only; wallet_is_encrypted=false.

B) RAIDA shared-secret FixEncryption (CMD45 / GetEncryptTicket)
   Health: "1 RAIDA broken (no shared secret)" → RAIDA 5; CMD45 fails res=2
   because node is offline. Wire crypto repair, not on-disk Type 10.

train, but the withdraw failure path is the Bank-only guard + empty Bank,
not Type 10 file crypto.

7. Blast radius — other processes that may be affected
------------------------------------------------------
Same *empty-Bank / all-Fracked* wallet state can break or degrade more than
Locker Key withdraw. Severity depends on whether the path is Bank-only or
Bank+Fracked.

A) Directly same bug class (Bank-only early check while Fracked has value)

  - GET /api/locker/upload  (this incident)
    Guard: Bank only → 404 "No coins in Bank"
  - find_breakable_denom_for_gap() in same file (~350–353)
    Scans Bank only; returns -9 if Bank empty. Even AFTER fixing the early
    guard, make-change for non-exact amounts may still fail if all
    breakable coins sit only in Fracked (this 10000 request does not need
    change).

B) Bank-then-Fracked selection (works if Bank empty but Fracked funded)

  - Amount selection inside locker_upload (after guard) and locker put-no-sum
  - qmail_select_coins_for_units (qmail_coin_select.c) — Bank then Fracked
    for QMail send / fee funding (no early "No coins in Bank" on that
    selector). Caveat: qcs_find_breakable_denom_for_gap / largest breakable
    still Bank-only → make-change can stall for awkward amounts when Bank
    is empty.
  - qmail_locker_pool funding helpers that list Bank then Fracked
  - system transfer coin moves that scan Bank + Fracked
  - coins authenticate API (explicit Bank + Fracked load)

C) Bank-only by design (will fail or no-op when Bank empty)

  - /api/transactions/export (.bin File withdraw) — cmd_export_coins is
    documented as selecting from Bank (api_handlers_export.c comments).
    Wallet -> Withdraw -> .bin File likely fails under the same wallet
    state (different error than locker upload, e.g. insufficient funds /
    export failed).
  - Coin consolidate path loads Bank only (api_handlers_coins.c
    consolidate_load_bank).
  - Any UI/API that assumes "balance" implies "exportable Bank coins".

D) Health / identity (related, not the same 404)

  - Boot health cannot regrade Fracked → Bank while RAIDA 5 offline.
  - Mail wallet identity coin SN 5243 also stuck Fracked with same RAIDA 5
    heal failure (second health pass in log).
  - QMail beacon pings to RAIDA 11/14 timing out — separate reliability
    issue; may affect mail more than withdraw.

E) UI surfaces

  - WalletActionModal withdraw shows aggregate balance for both Locker Key
    and .bin File methods — same misleading total for any Bank-gated spend.
  - No proactive "0 Bank / N Fracked" warning before submit.

F) NOT broken by this guard (evidence this session)

  - Locker pool status: upload_available=40, inbox_fee=10 (pre-funded units;
    separate from Default Bank selection).
  - Balance API: correctly reports Bank+Fracked total.
  - Type 10 write-gate: wallet_is_encrypted=false; not involved.


8. Causal chain (updated)
-------------------------
1. Coins live in Fracked (RAIDA 5 fail/offline; heal skips regrade).
2. Balance API / GUI show 2,597,979 CC (Bank+Fracked) — correct.
3. User requests Locker withdraw of 10,000 (fundable from Fracked).
4. api_handle_locker_upload hits Bank-only early guard → 404.
5. Bank+Fracked selection code never runs.
6. UI shows cryptic "No coins in Bank" under a large total.

If step 4 were fixed and amount is exact (one DN4), withdraw can succeed
even while heal remains blocked. Heal still needed for Bank-only features
(export, consolidate) and for long-term health.
