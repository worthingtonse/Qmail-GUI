================================================================================
2. PRIMITIVE-VS-OVERRIDE PATTERN AS APPLIED
================================================================================

All override blocks across 3.2c + 3.2-omnibus follow the same template,
intentionally:

  /* Layout/local overrides on top of .btn .btn--<variant>. */
  .per-file-class {
    /* only the properties that genuinely deviate from primitive */
    padding: ...      (if different)
    border-radius: ...(if different)
    box-shadow: ...   (if different)
    margin: ...       (if needed)
  }
  .per-file-class:hover { /* only deviating hover bits */ }
  .per-file-class:disabled { /* only deviating disabled bits */ }

Background, color, border, cursor, transition, ::before ripple, hover
transform, font-size, font-weight, font-family are NEVER repeated in
the override block — they're inherited from the primitive.

The pattern matches your phrasing from the 3.2a review:
> "keep overrides genuinely layout/local rather than half-redefinitions"

Concrete examples, all live in the tree now:

  MainDashboard.css .logout-button (4 lines override + 2 lines hover)
  MainDashboard.css .change-password-btn (3 lines + 1)
  MainDashboard.css .backup-btn (3 lines + 1 hover + 2 disabled)
  MainDashboard.css .test-cli-btn (2 lines + 1 hover + 2 disabled)
  MainDashboard.css .payout-option (2 lines, nothing else)
  AuthenticateTab.css .browse-button (4 lines + ripple-on-disabled
    suppression + 1 hover + 2 disabled)

3. TWO DESIGN DECISIONS I WANT YOUR READ ON
================================================================================

3.1 AuthenticateTab .browse-button:disabled:hover::before suppression
---------------------------------------------------------------------

The primitive has:

  .btn:hover::before { width: 300px; height: 300px; }

with NO :not(:disabled) qualifier. That means a disabled primitive
button still expands its hover ripple on pointer-over.

Auth's slate-disabled state previously used `:hover:not(:disabled)::before`
to suppress this. After trimming, I added an explicit suppression:

  .browse-button:disabled:hover::before {
    width: 0;
    height: 0;
  }

Two questions:

  (a) Is local suppression the right call, or should the primitive
      itself get the `:not(:disabled)` qualifier on .btn:hover::before?
      (broader change — affects every .btn consumer)

  (b) If we ever extract a `.btn--disabled-slate` modifier later, the
      suppression can move into it. For now it lives on .browse-button.
      OK as a transitional shape?


3.2 ContactsPane toggle-button template collapse
------------------------------------------------

Before (3 JSX sites use this pattern):

  className={`contacts-btn ${currentMode === "contacts" ? "active" : "secondary"}`}

The conditional swapped between `active` (primary-gradient compound)
and `secondary` (shim consumer for glass).

After:

  className={`btn btn--secondary contacts-btn${currentMode === "contacts" ? " active" : ""}`}

Cascade analysis I relied on:
  - .btn--secondary  (specificity 0,1,0)  glass base
  - .contacts-btn.active  (specificity 0,2,0)  primary-gradient when active

The compound wins by specificity in active state. When inactive, only
.btn--secondary applies for the variant surface, plus .contacts-btn
for layout.

Question: is this the right collapse? I considered keeping the
conditional and just adding .btn .btn--secondary unconditionally:

  className={`btn btn--secondary contacts-btn ${currentMode === "contacts" ? "active" : "secondary"}`}

That would leave the redundant `secondary` token alongside .btn--secondary
during the shim period. The collapse drops the redundancy at the cost
of some readability for the conditional. I lean toward the collapsed
form as the cleaner end state. Do you agree, or would you keep the
explicit `secondary` token in the template?


3.3 ServiceSelectionScreen + DicewarePasswordCreator compound retain
--------------------------------------------------------------------

Both files have a real `.X.secondary` compound selector that I LEFT
in place AND added `btn btn--secondary` to JSX alongside the bare
`secondary` token. Resulting JSX:

  className="btn btn--secondary service-button secondary"
  className="btn btn--secondary btn-backup secondary"

Reasoning:
  - .btn--secondary provides border + backdrop-filter (the parts that
    the original button.secondary shim contributed)
  - .service-button (base) / .btn-backup (base) provide their custom
    own-system shape
  - .service-button.secondary / .btn-backup.secondary compound provides
    the local "secondary" bg/color overrides

Without .btn--secondary in the className, dropping the App.css shim
in 3.2i would orphan border + backdrop-filter (the compound only sets
bg/color in those files).

Question: is this triple-class shape OK as a transitional pattern? In
particular, the bare `secondary` token still triggers the live App.css
`button.secondary` shim until 3.2i. After 3.2i, only `.btn--secondary`
contributes that surface; the bare token still triggers
`.service-button.secondary` and `.btn-backup.secondary` compounds.

Alternative: rename the compound (.service-button--secondary BEM) and
drop the bare `secondary` token. That's a bigger change but ends with
a cleaner BEM-like shape. I deferred this thinking — Track F is the
home for the BEM rename pass.

2. Q3.1 — disabled hover ripple on `.browse-button`
---------------------------------------------------
I would fix this at the **primitive** level, not just locally.

Recommended shape:

  .btn:hover:not(:disabled)::before { ... }

Reason:
- disabled buttons should not keep an "interactive" hover animation as a
  primitive default
- Auth is not uniquely special here; it is just the first place where the
  mismatch became visible because the slate-disabled state made it obvious

So my answer is:
- **(a)** prefer the primitive fix
- **(b)** the local suppression is acceptable as a transitional stopgap,
  but once the primitive gets the `:not(:disabled)` qualifier, delete the
  local Auth suppression rule

This is not a blocker for the current handoff, but I would fold it into
3.2i rather than leave it as a permanent per-file quirk.

Your cascade read is correct:

4. Q3.3 — ServiceSelectionScreen / Diceware triple-class transitional shape
