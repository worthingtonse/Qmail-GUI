Decisions resolved during this session (do NOT re-debate)
---------------------------------------------------------
The user resolved these on 2026-05-22. They are locked.

  1. JSON format for custom_theme.txt. NOT YAML. The PHP spec at
     D:\Code\src\PHP\cloudcoin.org-main\commands\system-theme.php
     lists JSON as a documented option (line 446). Schema is in
     plan §2.4. Includes validation rules to prevent CSS injection
     through the <style> tag (regex on token keys; ban on ;/}//* in
     values).
  2. Runtime-first ship order. NOT tokens-first. Phase 0–3 ship the
     runtime; Phase 4 does the giant consolidation. See §5 preamble
     for why (and Gemini's plan now also agrees).
  3. C-core spec discrepancies (§8) are a PARALLEL work-stream, not
     blocking. The GUI's themeService.js (Track D) must accept BOTH
     response shapes and log a one-time warning if it sees the old
     C shape.
  4. CSS consolidation is PHASED + BUNDLED (Phase 4). One file per
     PR. BEM rename happens in the same touch.
  5. Themes live in BOTH the high-contrast theme definition AND the
     custom-theme JSON's "a11y" object. Editor exposes them via UI.
  6. Three standard themes + one custom slot. NOT a preset library.
     Matches the single-file backend constraint.

User PREFERENCES (not gates — look wins over guidelines):
  - Use h1–h6 for headings; do not introduce more levels.
  - Bias toward semantic landmarks (nav, section, header, main,
    footer, article, aside) when promoting from <div>.
  - Spans stay where they are; they're semantic.
  - No new inline style={{...}}; use CSS classes or CSS custom
    properties for dynamic values.
  - Flexbox/grid over nested divs where it doesn't change the look.
  - Reduce raw colour literals; cap total tokens at ~80.
  - **The app must look excellent. Any guideline that visibly
    degrades a screen yields.**

Full rules in plan §13.

Known gotchas / things future-you will trip on
----------------------------------------------

G1. The dark theme is defined in BOTH tokens.css :root AND in
    themes.css [data-theme="dark"]. They contain identical values
    on purpose: :root is the "no attribute set" fallback; the
    [data-theme="dark"] rule is what the FOUC script and
    ThemeProvider explicitly select. Keeping both lets the cascade
    behave consistently even if data-theme is briefly absent. If
    you change a dark value, change BOTH or the dark theme will
    look different from "no attribute set."

G2. The --glow-* tokens were COMMENTED OUT in the old index.css
    (lines 44–47 of the original). Six component files reference
    them. They are now restored to the dark theme's actual values.
    THIS MEANS Phase 0 is NOT a zero-visual-diff change — glow
    effects that were previously invisible are now visible on
    primary/success buttons and active nav tabs. This is the
    intended fix per plan §1.3b / §3.2. If a screenshot regression
    is reported and the diff shows new glow halos, that is
    correct, not a bug.

G3. The new --motion-scale: 0 @media rule in tokens.css does
    nothing for the current codebase — component CSS uses raw
    durations like `transition: all 250ms ease`. Phase 4 will
    rewrite those to `transition: all calc(250ms *
    var(--motion-scale)) ease`. Until Phase 4 lands on a given
    file, that file's animations still play even with OS-level
    reduced-motion ON. The !important block at App.css :549–560
    still works as a fallback for the un-migrated files; do NOT
    delete it before Phase 4 finishes ALL files.

G4. ThemePicker uses `appearance: none` on the radio input to
    hide it visually while keeping it focusable. The custom
    pseudo-radio dot is drawn with ::after. This pattern works
    in Chromium (Electron) but if you ever need Firefox, double
    check.

G5. The localStorage keys are `qmail.theme` (active theme id) and
    `qmail.theme.base` (base for custom themes; not used in P1 —
    will be set by P3 when the user saves a custom theme). The
    FOUC script reads both already, so P3 only needs to write the
    base key when saving.

G6. The light theme placeholder values in themes.css (plan §4.2)
    were not WCAG-verified. Track B is the work item to do that.
    If a user picks "Light" right now, some text/background
    contrast pairs may fail WCAG AAA — flag this in any Track B
    report, but do not block Phase 1 over it.

G7. Phase 0 deliberately did NOT touch the 22 component CSS files.
    All raw colour literals, font-sizes, and px spacing in those
    files are still there. They will keep rendering correctly
    against the dark theme (the values they hard-code happen to
    match the dark theme), but switching to light or high-contrast
    will show "incomplete theming" on un-migrated screens. This
    is BY DESIGN — see §5 preamble. The screens that DO update
    correctly under all three themes today are: anything driven
    solely by global tokens (the body background, scrollbar, h1–h6
    typography) and the new ThemePicker itself.

G8. The C backend deviates from the PHP spec in five places (§8 of
    the plan). The Phase 3 themeService.js must defensively accept
    BOTH shapes. Do not assume the C-team will fix the spec mismatch
    before P3 ships. Track C is the work item to file the C-team
    backlog ticket; not blocking.

G9. The PHP spec says GET creates the file with a default stub
    when it does not exist. The C code returns empty content. The
    GUI must treat `exists:false` as either "newly-created stub"
    OR "permanent absence" depending on which server it talks to.
    Plan §8 D2.
