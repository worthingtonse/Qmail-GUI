Fixes applied in this pass
--------------------------
1. First-poll "ghost arrival" toast.
   QMailDashboard.jsx: the new notification watcher fired its
   "New mail from X" / "N new emails arrived!" toast on the VERY
   FIRST `fetchNotifications` call, including notifications that were
   already pending before the user opened the dashboard. That turns
   the toast into a lie ("new" means just arrived).
   - Pre-Batch-8 behaviour: watcher silently hydrated pendingMails on
     first poll; toasts only came from loadMailCounts's "inbox total
     grew" path.
   - Fix: add an `isFirstPoll` flag scoped to the watcher's useEffect.
     Hydrate pendingMails + pendingMailsRef silently on the first
     poll, then flip the flag in a finally{} so all subsequent polls
     toast genuinely new arrivals. The flag is also flipped on the
     early-return paths so a "no new notifs" first poll still arms
     toasts for the second poll.

2. Trash page-delete error handling.
   QMailDashboard.handleDeleteVisibleTrash had no try/catch. emptyTrash
   Folder itself can't throw (each delete is wrapped per-id and
   results are collected), but the follow-up `loadEmails("trash",
   nextPage)` and `loadMailCounts()` can. If either threw,
   EmailListPane's confirm modal stayed open with isDeletingTrashPage
   reset to false (because the modal's `setShowTrashConfirm(false)`
   only fires AFTER `await onDeleteVisibleTrash`).
   - Fix: wrap the trash deletion / refresh / counts sequence in
     try/catch. On error: log to console, set a user-facing
     notification ("Could not delete these messages. Try again.") and
     fall through so the EmailListPane finally{} closes the modal.
   - This preserves the success / partial-failure notifications that
     were already correct.

Out-of-scope observations
-------------------------
- Multi-arrival toast ("N new emails arrived!") is not clickable
  because there's no single guid/id to focus. The spec doesn't
  require it but a "go to inbox" affordance on the bulk toast would
  be useful.
- focusPendingMail does NOT auto-trigger handleDownloadMail when the
  user clicks the toast — they have to click the row again. The spec
  says "select the matching pending row" so this is intentional, but
  a one-click decrypt-via-toast UX may be worth a future ticket.
- loadMailCounts's fallback "fetch latest 1 inbox row" can produce a
  toast saying "New mail from Unknown Sender" if the API responds
  with an empty list during the race window. The toast is not
  clickable in that case (targetEmailId is undefined) so it dead-ends.

These observations have been appended to docs\cla.bugs.txt.
