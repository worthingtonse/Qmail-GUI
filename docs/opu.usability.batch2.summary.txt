normalizeIdentityForUi helper
=============================
Lives in src\api\qmailApiServices.js (right above hasId).

Design choices worth flagging:
1. Returns BOTH camelCase (preferred for new code) AND snake_case
   aliases (existing consumers read pretty_address, serial_number,
   etc.). This was the explicit v4 plan instruction: "Centralizing
   the construction prevents every consumer from inventing its own
   field-name guesses" and "Returning both shapes means a missed
   consumer still works."

2. Default domain is "qmail.cloud" — the backend response does not
   carry a domain, but existing consumers (AccountPane:460) read
   `${userAccount.address}@${userAccount.domain}` so something has
   to fill the gap. Exposed as opts.defaultDomain in case callers
   want to override.

3. needs_healing defaults to false. The backend has no
   identity-health field yet (CORE-F is the HARD prerequisite per
   FIX-10). Surfacing false here is honest: we don't know the
   identity health, and the v3/v4 plan said don't synthesize it
   from wallet folder counts.

4. Safe with null input: returns null. Callers can check.

5. Handles BOTH the getIdentity() response shape (address,
   serial_number, registered, identity{...}) AND the import-
   credentials response (coins_found, coins_saved, wallet_path,
   mail_wallet_path). The latter doesn't carry identity fields, so
   if you pass it directly, the result will be sparse — callers
   should call getIdentity() first and normalize that, which is
   exactly what ServiceSelectionScreen now does.

Identity propagation flow (after batch 2)
=========================================

Returning user (auto-restore):
  App.useEffect → App.checkIdentity
    getIdentity() succeeds with configured=true
    → normalizeIdentityForUi(raw)
    → setProvisioningData(normalized)
    → setSelectedService(QMAIL)        # was PROVISIONING in v1
  App.renderService → <QMail initialIdentity={provisioningData} />
  QMail.jsx → <QMailDashboard initialIdentity={...} />
  QMailDashboard:
    useState(initialIdentity || null)
    Mount-time useEffect: if null, retry getIdentity() once.

has_id fallback (coins on disk but identity not yet visible):
  App.checkIdentity
    getIdentity() returns null or configured=false
    hasId() returns {has_id: true}
    → setProvisioningData(null)
    → setSelectedService(QMAIL)
  QMailDashboard mount-time useEffect picks up null userAccount
  and retries getIdentity() once.

First-run import:
  ServiceSelectionScreen.handleImport
    importCredentials() succeeds → response has no identity fields
    → getIdentity() (retry once on configured=false)
    → normalizeIdentityForUi(raw)
    → onSelectService('qmail', normalized)
  App.handleSelectService('qmail', data):
    setProvisioningData(data) → setSelectedService(PROVISIONING)
  PROVISIONING → <WalletSetupScreen accountData={normalized} />
    User sees their real address in the welcome screen.
    Clicks "Go to Dashboard" → setSelectedService(QMAIL)
  At this point provisioningData is still set, so <QMail> receives
  it as initialIdentity and QMailDashboard mounts with the real
  identity already in state.

No identity at all:
  App.checkIdentity finds nothing → SERVICES.NONE
  ServiceSelectionScreen renders normally.

Product decision baked in
=========================
"Returning users with a configured identity should go STRAIGHT to
QMAIL, not bounce through WalletSetupScreen on every launch.
WalletSetupScreen remains the first-run-only screen."

Previous behavior: every restart went configured-user → PROVISIONING
→ user clicks Go to Dashboard → QMAIL. Annoying and adds a step.
New behavior: configured users land straight on the dashboard.
WalletSetupScreen is now reached only via post-import flow.

Decisions worth flagging for review
===================================
1. Three-tier identity loading sequence:
     props (initialIdentity)  →  mount-time getIdentity()  →  null
   QMailDashboard initial state is `initialIdentity || null`. The
   mount-time useEffect retries getIdentity() once if state is null.
   If that retry also fails, userAccount stays null. AccountPane
   already handles a missing userAccount gracefully (the Profile
   section just doesn't render — see line 460-ish: `{userAccount &&
   (...)}`). No new "Loading…" placeholder was added, on the
   reasoning that the existing conditional render is already the
   right UX (don't show profile until you have one).
   --> Reviewer: confirm "don't render the Profile section" is
       acceptable, or should I add an explicit "Loading…" state?

2. Snake_case aliases in normalizeIdentityForUi.
   This means callers can keep reading `userAccount.pretty_address`
   and it works. No consumer was updated to read camelCase in this
   batch except WalletSetupScreen (which I touched anyway) and
   QMailDashboard's draft-mapper (which I touched anyway). Other
   consumers like AccountPane still read snake_case and that's
   fine.
   --> Reviewer: is this acceptable as a permanent shape, or do you
       want a follow-up ticket to migrate consumers to camelCase?
       My recommendation: leave it; the indirection has zero cost
       and avoids a flag-day migration.

3. handleSelectService('qmail', data) still routes to PROVISIONING.
   The service argument is currently ignored when `data` is
   provided. After this batch, the ONLY caller passing data is the
   post-import flow in ServiceSelectionScreen, and PROVISIONING is
   the right destination. If a future caller wanted to skip
   WalletSetupScreen (e.g. a "Continue with existing local
   identity" button from FIX-15b), App.handleSelectService would
   need to honor the service argument. Flagged for FIX-15b.

4. Mount-time retry is single-shot, not a polling loop.
   The v4 plan says "retry once after 500ms" for the
   ServiceSelectionScreen import-then-identity flow, which I did.
   For the QMailDashboard mount-time fallback, I only retry once
   (the initial call). Reasoning: if the backend is slow enough
   that getIdentity() fails twice, the user is going to notice
   either way; layering more retries pushes the failure deeper
   into the load and makes "Loading identity…" feel broken. The
   user can refresh manually if needed (Refresh button is right
   there in NavigationPane).
   --> Reviewer: ok to leave at single-shot, or want a 2-3 retry
       loop here too?

5. WalletSetupScreen renders "—" when prettyAddress is missing and
   "Welcome!" (no name) when greetingName is empty. Simple
   placeholders, no spinner. Matches the v4 plan's "Show "—"
   placeholders for any missing field; don't crash on null"
   guidance.

6. handleAccountUpdate spread-on-null guard:
   Before: `setUserAccount((prev) => ({ ...prev, ...newAccountDetails }))`
   After:  `setUserAccount((prev) => ({ ...(prev || {}), ...newAccountDetails }))`
   AccountPane fires this on profile edits; if it ever fires before
   identity hydration completes, we don't want to crash.

Edge cases handled
==================
- Configured user restart → straight to QMAIL with seeded identity
- has_id fallback (coins on disk, identity lagged) → QMAIL, mount-
  time retry fills userAccount
- Successful import + backend lags on identity registration →
  ServiceSelectionScreen retries once after 500ms, advances even
  if still null (toast-less; the dashboard's own retry covers it)
- Import succeeds but identity never appears → user lands on
  WalletSetupScreen with "Welcome!" greeting (no name) and "—"
  address badge. Not great, but not crashed. They can proceed to
  the dashboard which will keep trying.
- handleAccountUpdate fires before userAccount is set → spread-
  on-null guarded
- userAccount.email read in draft mapper (line 303) → uses
  prettyAddress with sensible fallback chain

Five findings, four code-level. All actionable, all genuine bugs.
Gem's review was a clean approval — no conflicts.

Patches applied:

1. (gpt #1, High) Normalizer no longer double-stamps domains.
   Before: `${address}@${domain}` was applied to a raw address that
     already contained '@'. Returning user with backend address
     "Alice.Admin@Developer.C25.Giga" became
     "Alice.Admin@Developer.C25.Giga@qmail.cloud".
   After: if rawAddress.includes("@"), use it AS-IS as prettyAddress.
     The returned `address` field is now the local-part-only (before
     @) and `domain` is derived from the email tail. Bare local-part
     inputs (no @) still get synthesized as `local@defaultDomain`.

2. (gpt #2, High) initialIdentity gated on configured=true.
   Three coordinated changes:
   a. ServiceSelectionScreen.handleImport now passes the normalized
      identity ONLY if normalized.configured === true; otherwise
      passes null. No more raw import metadata downstream.
   b. App.handleSelectService now honors the `service` argument
      (was always routing to PROVISIONING when data was truthy,
      QMAIL when null). Now reads service to decide route, so the
      post-import flow can pass null + 'provisioning' to still
      reach WalletSetupScreen.
   c. ServiceSelectionScreen passes 'provisioning' (not 'qmail')
      so the user always sees the welcome screen, identity-loaded
      or not.
   d. QMailDashboard initial userAccount state is
      `initialIdentity?.configured ? initialIdentity : null` so
      the mount-time retry actually fires for unconfigured inputs.

3. (gpt #3, Medium) WalletSetupScreen no longer falsely claims
   healthy/verified.
   Derives `hasVerifiedIdentity = configured && serial > 0 &&
   prettyAddress`. Status becomes a tri-state ('pending' | 'fracked'
   | 'healthy'). The "pending" state renders a Loader2 spinner with
   text: "Your identity is still loading. You can proceed to the
   dashboard; the app will keep trying to load your details."
   The Heal Identity button is disabled when no verified identity
   (with a tooltip explaining why) — you can't heal what's not
   visible. Make Change stays enabled (it's wallet-side, not
   identity-dependent).

4. (gpt #4, Medium) Mount-time retry strengthened in QMailDashboard.
   Before: single immediate getIdentity() call. If it returned
     unconfigured or threw, no retry.
   After: up to 3 attempts with 500ms / 1000ms backoff (matches
     hydrateDownloadedEmail's pattern). Cancellation flag respected.
     Try/catch per attempt. Only setUserAccount when configured=true.
     If all 3 attempts fail, leave userAccount null and log a warn.
     AccountPane's existing conditional render already handles the
     null case gracefully.

5. (gpt #5, Low) normalizeIdentityForUi now reads raw.identity.
   Before: helper claimed to handle the nested identity object but
     only read top-level fields.
   After: `const nested = raw.identity || {};` and falls back
     through both top-level and nested for address/email, serial/sn,
     display_name, first_name, last_name, class_name, beacon_raida.
