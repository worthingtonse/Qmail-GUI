Your job in the next session
============================

1. Sean reports a bug (verbal description, sometimes a screenshot
   or paste of console/network output).

2. Reproduce or trace the bug:
     - Read the relevant component file(s) before editing.
     - For UI bugs, find the React component that owns the symptom.
     - For API bugs, trace through src/services/qmailApiServices.js
       to the backend endpoint. (Endpoint inventory is in the

     - **Obvious / tiny** (typo, wrong className, missing
       aria-label, off-by-one in copy): fix immediately, no
       confirmation needed.
     - **Non-trivial** (touches state, effects, multiple files,
       changes behavior, alters an API call): post a ONE-LINE
       plan to Sean and wait for "go" before editing. Example:
       "Plan: refactor handleSearch to debounce on input change
       instead of submit — touches QMailDashboard.jsx +
       SearchBar.jsx. OK?"
     - When in doubt, confirm. Sean explicitly chose
       "confirm scope first if non-trivial."

4. Fix it. Follow the existing code style — don't add comments,
   don't refactor unrelated code, don't introduce abstractions.
   Match what's already there.

5. Verify gates before commit:
     - npm run lint    (must be zero warnings — eslint config
                        runs with --max-warnings 0)
     - npm run build   (Vite build must complete cleanly)
   If either fails, fix and re-run. Don't bypass.

6. Commit. One commit per bug fix. Use this shape:

     fix(BUG-NN): one-line summary

     <2-3 sentence body: what was wrong, what changed, why this

Fix-log file format
===================

When you fix a bug, add an entry to docs/opu.bug-fixes.2026-05-24.txt.
First-write the file with this header:

----8<----
QMail-GUI bug fixes — 2026-05-24 session
=========================================
Fixed by: Claude Opus 4.7 (bug-fix phase)
Reviewing models welcome. Each entry covers ONE bug.

Format per entry:

  ## BUG-NN — one-line summary
  Reported by: Sean (manual GUI testing)
  Severity: HIGH / MEDIUM / LOW
  Commit: <git short SHA>

  **Symptom**: what Sean saw.

  **Root cause**: what was actually wrong, with file:line.

  **Fix**: what changed and why this is right. Touched files
  listed.

  **Verification**: how to confirm the fix works (steps a
  reviewer can re-run).

  **Notes** (optional): related bugs, follow-ups, scope
  decisions, anything a reviewer should know.

---
----8<----

Then append one section per fix. Keep entries chronological
(newest at bottom).

If a fix turns out to be wrong and gets reverted, leave the
original entry and add a follow-up: "## BUG-NN follow-up —
reverted, see commit XXXXX." Don't edit the original entry —
the log is append-only so reviewers see the history.

Cross-cutting context (e.g. "BUGs 51, 53, 57 all share a root
cause in EmailListPane's useEffect dependency array") goes in
the entry for whichever bug fixed the underlying cause. Link
forward/backward with "see BUG-NN."
