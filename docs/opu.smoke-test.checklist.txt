How this is split
-----------------
The handoff asked for one manual checklist. After confirming with Sean
the split is:

  AUTO  Claude (this session) runs against the live backends via
        curl/HTTP — no UI involved. Verifies the C1<->C2 mail flow,
        attachments, drafts persistence, contacts CRUD, search,
        folder counts, RAIDA health, etc. Produces a results file.

  MANUAL Sean walks the visual / UX items the handoff explicitly
         called out as needing a human eye: toast-vs-modal routing,
         italic preview weight, unified Refresh spinner sync,
         hover states, etc. These cannot be verified by API alone
         because they assert about what the React UI rendered.

  KNOWN  Items listed in the handoff as "Known broken until backend
         ticket" (CORE-A/E/F/H/J/K) are NOT in either checklist.
         Don't re-test them. See handoff lines 378-396.
         Additional known gaps surfaced by the parallel plans
         (Gemini, GPT) — also do NOT file as bugs:
           CORE-L  Draft recipient detail may be incomplete.
           CORE-M  Attachment paths containing ',' or ';' are
                   rejected by the GUI. Pick paths without them.
           CORE-N  Draft attachment persistence may be incomplete.

Diff vs parallel plans
----------------------
Gemini: docs/gemini.manual-gui-smoke-checklist.md
GPT:    docs/gpt.manual-gui-smoke-checklist.md

Adopted:
  - CORE-L / CORE-M / CORE-N caveats (above) — Gemini surfaced
    CORE-M, GPT surfaced CORE-L and CORE-N.
  - Attachment variety in A3 (text + binary + spaces-in-filename)
    — Gemini.
  - Bidirectional attachment send, new step A3b — Gemini.
  - To-field autocomplete visual check, M-Autocomplete — Gemini
    & GPT both wanted it.
  - Results-file template with Date / Tester / Build / portable
    exe path — GPT. See A12 below.
  - Server count sanity check ("25 servers or absent", not just
    'a list') folded into M-Setup — GPT.

Deliberately kept different:
  - Hybrid split (Claude auto + Sean visual) instead of fully
    manual. Sean confirmed this.
  - Reuse existing E:\Client1\ and E:\Client2\ rig instead of
    building a fresh dated rig under E:\QMail-Smoke\. The handoff
    says the rig is already set up and funded; rebuilding is
    busywork and risks bootstrap bugs unrelated to the smoke
    test. Both Gemini and GPT proposed fresh rigs.
  - FIX-NN / BUG-NN tags kept on every check so failures can be
    filed against the specific shipped fix that regressed —
    important context for a CSS-refactor regression hunt.
  - Visual checks Gemini and GPT both omitted but the handoff
    specifically called out are kept: toast-vs-modal routing
    (BUG-43), Move-to dropdown content (BUG-40), Mark Unread
    visibility rule (BUG-39), page-snap on sort change (FIX-38),
    pending-decrypt weight (FIX-46), server card class colors
    (FIX-45), advanced-options persistence (FIX-40), popular-
    contact checkmark persistence (BUG-44), undo-toast 10s
    expiration. These are the regression surface a CSS refactor
    is most likely to hit, and the value of the smoke test is
    exactly to catch them.
  - Skipping GPT's "Stop Conditions" preamble — useful for a
    human running blind, but Claude can just check at A0 and
    fail-stop on the same conditions inline.
  - Skipping GPT's optional dangerous-attachment / zero-byte /
    oversize tests as out-of-scope for this regression pass.

The MANUAL list assumes the AUTO list ran first and seeded state
(messages in inboxes, contacts saved, a draft sitting in Drafts) —
that lets the visual checks be done by clicking around existing data
rather than re-creating it. Run AUTO first.

PART 1 — AUTO (Claude runs this; you don't need to do anything)
===========================================================

These steps must run top-to-bottom; later checks depend on earlier
state. Setup at the very top.

[A0] Preflight
    - Confirm no stray core.exe is running (kill if any).
    - Start E:\Client1\core.exe; wait for /raida/echo on :8081 to
      respond with array_usable=true.
    - Start E:\Client2\core.exe; wait for /raida/echo on :8082.
    - GET /qmail/local/identity/get on both. Confirm:
        :8081 -> SN 55076, address @chariot.pyramid.byte
        :8082 -> SN 55077, address @chariot.harbor.byte
    - GET /wallets/balance on both. Confirm total_value > 0 on each
      (need funded coins to send). Fail-stop if either is zero.
    - Stage extra attachment files in E:\Client1\ if missing
      (filenames chosen to avoid the CORE-M ',' / ';' rejection):
        qmail_test_attachment.txt        (already present, 2228 B)
        qmail_test_attachment_binary.bin (write 256 bytes 0x00..0xFF)
        qmail_test_attachment_spaces.txt (filename with spaces; small)
      Skip creation if the files already exist with non-zero size.

[A1] Health baseline
    - /raida/echo on both: record total_available, total_error,
      total_timeout. Expect >= 6 reachable per Setup verification.
    - /qmail/local/status on both: confirm topology returns a server
      list. Snapshot for the results file.

[A2] C1 -> C2 plain send (covers FIX-01 backend half)
    - POST /qmail/net/messages/upload_and_tell on :8081 with
      to=@chariot.harbor.byte, subject="AUTO-A2 plain", body="hello".
    - Poll /system/tasks for the returned task_id until status=done
      or 30s timeout.
    - On :8082, POST /qmail/net/beacon/ping then GET
      /qmail/net/beacon/peek. Expect new_mail_count >= 1.
    - GET /qmail/db/notifications/list on :8082; find the
      file_guid for the AUTO-A2 send.
    - POST /qmail/net/messages/download?file_guid=... on :8082;
      wait for decrypt.
    - GET /qmail/db/messages/list?folder=0 on :8082; find a row whose
      subject is "AUTO-A2 plain" and body matches "hello". Record the
      email_id as C2_AUTO_A2.

[A3] C1 -> C2 with attachments (FIX-02 / FIX-19 backend half)
    - POST upload_and_tell on :8081 with the same recipient,
      subject="AUTO-A3 attach", body="see attached",
      and three attachment_file_path[] entries:
        E:\Client1\qmail_test_attachment.txt
        E:\Client1\qmail_test_attachment_binary.bin
        E:\Client1\qmail_test_attachment_spaces.txt
      (Per Gemini's plan: testing one text, one binary, one
      spaces-in-name. Adopted because attachment encoding is the
      kind of thing that quietly breaks on edge inputs.)
    - Repeat the beacon/notification/download dance on :8082.
    - GET /qmail/db/messages/list to find the new email_id; call
      /qmail/db/attachments/list?email_id=...; confirm all three
      attachments are listed with the right filenames.
    - GET each /qmail/db/attachments/get?email_id=...&attachment_id=N;
      compare bytes to the local file. Pass only if all three match.

[A3b] C2 -> C1 with attachment (bidirectional verification)
    - On :8082, send to=@chariot.pyramid.byte, subject="AUTO-A3b
      reverse attach", body="reverse direction",
      attachment_file_path[]=<one small file copied to E:\Client2\
      first, since :8082's core.exe reads from its own working
      directory>.
    - Beacon/download on :8081; confirm the attachment arrived and
      bytes match. (Gemini-suggested addition: catches direction-
      specific encoding bugs that a one-way send misses.)

[A4] C2 -> C1 reply round-trip (covers Phase 2 "Reply" backend half
     and proves the mutual flow)
    - On :8082, send to=@chariot.pyramid.byte, subject="Re: AUTO-A2
      plain", body="ack". (Claude isn't using the GUI's Reply
      builder; just sending a fresh message with the right shape.)
    - Beacon/download on :8081; confirm "Re: AUTO-A2 plain" appears
      in C1's inbox. Record email_id as C1_AUTO_A4.

[A5] Drafts CRUD (FIX-04 backend half; CORE-H not tested)
    - POST /qmail/db/drafts/create on :8081 with subject="AUTO-A5
      draft", body="wip", to=@chariot.harbor.byte.
    - GET /qmail/db/drafts/list; confirm it appears.
    - POST /qmail/db/drafts/update?email_id=... changing body to
      "wip updated"; list again; confirm the update is visible.
    - Leave the draft in place — MANUAL M-Drafts step will re-open
      it and look at the field hydration.

[A6] Mark read / unread (BUG-39 backend half)
    - POST /qmail/db/messages/set-read?email_id=C2_AUTO_A2&is_read=true
      on :8082. GET the message; confirm is_read=true.
    - Same with is_read=false; confirm flipped back.

[A7] Move to folder + trash + permanent delete
    - On :8082, send a throwaway from :8081 first (subject "AUTO-A7
      trashable") so we don't delete the A2 message.
    - DELETE /qmail/db/messages/trash?email_id=... on the throwaway.
    - GET /qmail/db/messages/list?folder=3 (trash); confirm it's
      there.
    - DELETE /qmail/db/messages/delete?email_id=...; list trash
      again; confirm it's gone.

[A8] Folder list + counts (FIX-47 backend half; iconName not tested
     unless backend ships one)
    - GET /qmail/db/folders/list on :8081. Expect at least
      inbox/sent/drafts/trash/starred/archive (handoff says six).
    - GET /qmail/db/folders/counts on :8081 and :8082. Sanity-check
      that inbox unread count matches what /messages/list returns.

[A9] Contacts CRUD (FIX-28 / FIX-29 / FIX-42 backend half)
    - On :8081, POST /qmail/db/contacts/create for Client2's SN
      (55077, first_name="Client", last_name="Two"). Confirm via
      /qmail/db/contacts/list.
    - GET /qmail/db/contacts/list-popular?limit=10; if it returns
      anything, pick a non-Client2 entry and POST /create for it.
    - DELETE the Client2 contact; confirm it's gone from list.
    - Re-add Client2 (MANUAL M-Contacts re-uses this).

[A10] Search (FIX-43 backend half; CORE-K excluded)
    - GET /qmail/db/messages/search?query=AUTO on :8082. Expect at
      least the AUTO-A2 and AUTO-A3 messages in results.
    - GET ?query=zzznomatchzzz; expect count=0.

[A11] Sign-out / sign-in (FIX-15 backend half)
    - There's no explicit sign-out endpoint via REST — sign-out is
      a GUI-state action. Skip auto verification; MANUAL handles it.

[A12] Results write-up

      HTTP status, response body excerpt, expected vs actual.
    - Save as docs/opu.smoke-test.results-2026-05-23.txt per
      handoff lines 414-418. File header (GPT-suggested template):

        Date: 2026-05-23
        Tester: Claude Opus 4.7 (auto) + Sean (manual)
        Build / HEAD: <git rev-parse --short HEAD>
