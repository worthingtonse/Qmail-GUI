## BUG-51 — QMail.exe single-file launch + CLI flags
Fixed by:    Claude Opus 4.7 (1M context)
Reported by: Sean (manual GUI testing)
Severity:    HIGH
Commit:      Qmail-GUI 98c7c0c (combined with BUG-52)
             rest_core  ae2aa22 (CMake mirror + kill-by-name)

**Symptom**: Sean launched E:\Client3\QMail.exe (5/22/2026 build)
and the expected Client_Data folder structure never appeared next
to QMail.exe. Suspected a stale build but also wanted a real
single-file distribution where you don't have to drop core.exe
next to QMail.exe, plus CLI control over the backend port,
core debug logging, and the dev-only RAIDA-11 LAN override.

**Root cause**: Two issues stacked:

  1. The 5/22 E:\Client3\QMail.exe predates current main and
     was definitely stale.
  2. Even on current main, electron.cjs only recognized `--dev`.
     There was no way to ask for a specific port, no way to
     forward core.exe's `-debug` or `-r11ip` flags, and no

  electron-builder's extraResources (electron-builder.config.cjs:
  45-48), and core's cwd is set to PORTABLE_EXECUTABLE_DIR
  (electron.cjs:62-64) so Client_Data lands next to QMail.exe.
  Those mechanisms were correct on current main; the stale build
  was the entire reason Sean couldn't see the folder.

**Fix**: Three changes across two repos.

  1. D:\code\src\C\rest_core\CMakeLists.txt
     - Added kill-by-name (QMail, core) to kill_test_ports.cmake
       PRE_LINK so the post-build mirror can overwrite locked
       binaries when a client is running.
     - Added one more post-build mirror destination:
         D:/code/src/JavaScript/Qmail-GUI/backend/core.exe
       So a `cmake --build build` against rest_core now keeps the
       GUI's bundled core.exe automatically in sync.

  2. D:\code\src\JavaScript\Qmail-GUI\electron.cjs
     - Added parseQMailArgs() with GNU-style long options:
         --port <N>      pin backend HTTP port (1..65535)
         --debug         forward -debug to core.exe
         --r11ip         forward -r11ip to core.exe (dev only)
         --dev           (existing) Vite dev-server mode
         --help, -h      print usage + examples, exit 0
         --version, -V   print app version, exit 0
     - Unknown options print "QMail: unrecognized option …" +
       usage on stderr, exit 2.
     - Malformed --port value prints "QMail: invalid port …" +
       usage on stderr, exit 2 (no silent fallback — if you
       specified a port, you wanted THAT port).
     - boot() uses qmailArgs.port when present, else
       findFreePort() (unchanged default).
     - startBackend() builds core's argv from qmailArgs and
       logs the resolved vector for debuggability.
     - DevTools left at Electron's default behavior — F12 /
       Ctrl+Shift+I work as usual; --debug does NOT auto-open
       DevTools (per Sean A5).

  3. D:\code\src\JavaScript\Qmail-GUI\backend\core.exe
     - Refreshed to today's 5/24 build via CMake post-build
       mirror. Size 3023975, LastWriteTime 2026-05-24 14:39:06.

## BUG-52 — Client_Data created in temp dir, not next to QMail.exe
Fixed by:    Claude Opus 4.7 (1M context)
Reported by: Sean (manual GUI testing, follow-up to BUG-51)
Severity:    HIGH
Commit:      Qmail-GUI 98c7c0c (combined with BUG-51)
             rest_core  4467849 (-data-dir flag)

**Symptom**: After BUG-51 fix, launching QMail.exe still did not
produce a Client_Data folder next to QMail.exe. Each launch
started fresh — no persistence of wallets, mail, or settings
across QMail.exe restarts.

**Root cause**: core.exe uses GetModuleFileNameA(NULL) at
rest_core/api_src/config.c:794-808 to find its own binary
location, then synthesizes <exe-dir>/Client_Data from that.

In an electron-builder portable bundle, the bundled core.exe is
extracted to a per-launch temp directory like
C:\Users\<u>\AppData\Local\Temp\<guid>\resources\backend\core.exe.
core.exe was creating Client_Data NEXT TO ITS RUNTIME BINARY —
i.e. inside that temp dir — and electron-builder's portable
wrapper deletes the entire temp extraction on app quit, taking
the Client_Data with it. Sean's data was being created and
silently destroyed each session.

electron.cjs was setting cwd to PORTABLE_EXECUTABLE_DIR (the
visible folder next to QMail.exe), but core.exe doesn't use cwd
for Client_Data placement — only the binary's path. So the cwd
hint was ignored.

GPT independently diagnosed this from the GetModuleFileNameA
call site while reviewing BUG-51. Credit to them.

**Fix**: Add a `-data-dir <path>` flag to core.exe and have
QMail.exe pass the visible portable folder through it. core.exe
already had the override mechanism (config.c:805 only synthesizes
the default when client_data_path is empty); just needed a CLI
flag to set it.

  1. rest_core/api_src/main_rest.c
     - Added `-data-dir <path>` / `--data-dir <path>` to
       parse_arguments(). Pre-populates g_config.client_data_path
       with "<path>/Client_Data" so config.c:805 sees a non-empty
       value and skips the GetModuleFileNameA-derived default.
     - Added line to print_usage() and the --help output.
     - Removed the now-incorrect "Client_Data directory is always
       created next to the executable" note from print_usage().

  2. rest_core/api_src/config.c — NO change needed.
     bootstrap_create_client_data_directories() already calls
     create_directory_recursive() which does mkdir -p. If the
     parent path doesn't exist (rare but possible if user passed
     a fresh portable path), it gets created. Good.

  3. Qmail-GUI/electron.cjs
     - startBackend() builds coreArgs with '-data-dir', dataDir
       inserted after -port. dataDir is the same value already
       used for cwd (PORTABLE_EXECUTABLE_DIR with fallback to
       dirname(app.getPath('exe'))). One line added; cwd left
       in place as defense-in-depth.

**Verification**:
  Build chain executed:
    a. cmake --build build --config Release (rest_core)   PASS
       - Mirrored new core.exe to all 6 destinations
    b. npm run lint                                         PASS
    c. node --check electron.cjs / preload.cjs              PASS
    d. npm run build-portable                               PASS
       release/QMail.exe = 60,938,666 B, 2026-05-24 23:45:08
    e. Copy release/QMail.exe → E:\Client3\QMail.exe        PASS

  Manual smoke (Sean to run):
    1. Delete E:\Client3\Client_Data\ if present (clean slate).
    2. Launch E:\Client3\QMail.exe.

**Notes**:
  - Standalone core.exe usage is UNCHANGED. Without -data-dir,
    config.c:805 falls back to the historical
    <exe-dir>/Client_Data behavior. Test scripts
    (test_qmail_e2e.py, test_qmail_phases_e2e.py) and direct
    rest_core launches are unaffected.

## BUG-56 - Import-credentials saves locker coin outside graded folders

Severity:       HIGH
Commit:         uncommitted - batch pending

**Symptom**: On first-run import, the user entered a locker code and the coin was downloaded, but it landed in the wrong folder instead of the normal wallet folder flow.

**Root cause**: `rest_core/api_src/api_handlers_qmail_identity.c` handled `/api/qmail/raida/locker/import-credentials` by calling `core_download_locker` and then saving directly with `coin_file_save(mail_path, ...)`. ## BUG-60 — Startup asks for locker code even when Mail ID exists
Fixed by:       GPT-5

**Symptom**: After the Mail wallet already contains a mailbox key in
`Mail/Bank` or `Mail/Fracked`, launching QMail can still show the first-run
welcome screen and ask the user to enter a locker code.

**Root cause**: `src/App.jsx` checked `shouldSkipAutoRestore()` before calling
`getIdentity()` or `hasId()`. That skip flag is persisted in localStorage by
Sign Out, so it could survive a restart and prevent the GUI from asking the
backend whether a Mail ID coin exists. `src/screens/ServiceSelectionScreen.jsx`
also only checked for a local identity when that skip flag was present, which
left no fallback auto-route if the welcome screen was reached without the flag.

**Fix**: Startup now always calls the backend identity APIs first. If
`identity/get` reports a configured identity or `identity/exists` reports a
Mail wallet ID coin, the GUI clears the stale skip flag and routes directly to
QMail. The welcome screen now performs the same local identity check when it is
mounted; it auto-routes only when skipAutoRestore is not set, preserving the
manual same-session Sign Out flow.

**Verification**: `node --check electron.cjs` passed. `node --check preload.cjs`
passed. `git diff --check -- src/App.jsx src/screens/ServiceSelectionScreen.jsx`
passed. `npm run lint` passed. `npm run build` passed.

**Notes**: The backend already exposes the necessary checks: `/api/qmail/local/identity/get`
refreshes identity from the Mail wallet, `/api/qmail/local/identity/exists`
checks for `.bin` files in Mail/Bank and Mail/Fracked, and
`/api/qmail/local/identity/whoami` performs the same wallet refresh/persist

## BUG-61 — RAIDA refresh spinner can spin forever
Fixed by:       GPT-5
Reported by:    Sean (manual GUI testing)
Severity:       HIGH
Commit:         uncommitted — batch pending

**Symptom**: On the main dashboard, pressing the Refresh button above the
RAIDA status grid starts the spinner, but the spinner can keep spinning
forever. The RAIDA dots also continue showing stale red/green status instead
of turning gray while the new echo is in progress.

**Root cause**: `src/qmail/screens/QMailDashboard.jsx` set `isRefreshing=true`
and then awaited several backend operations with no UI-side timeout. If any
fetch never settled, the `finally` block that clears the spinner never ran.
The RAIDA echo also ran after the beacon ping, and `src/qmail/screens/NavigationPane.jsx`
ignored a cleared/null echo snapshot, so the grid had no way to show an
unknown in-progress state.

**Fix**: The refresh flow now clears the RAIDA snapshot immediately, runs the
RAIDA echo first, and wraps each refresh step in a finite timeout so the button
spinner cannot remain stuck forever. NavigationPane now treats a null echo
snapshot or active refresh as unknown health, rendering the 25 dots gray until
fresh `/api/raida/echo` results arrive.

**Verification**: `node --check electron.cjs` passed. `node --check preload.cjs`
passed. `git diff --check -- src/qmail/screens/QMailDashboard.jsx src/qmail/screens/NavigationPane.jsx`
passed. `npm run lint` passed. `npm run build` passed.

## BUG-63 - Contacts search empty when users consensus has no rows
Fixed by:       GPT-5
Reported by:    Sean (manual GUI testing)
Severity:       HIGH
Commit:         uncommitted - batch pending

**Symptom**: In the Contacts area, clicking `Search contacts or DRD alias...`
showed no directory contacts. The test file `E:\Client3\Client_Data\qmail_users.csv`
contained only the CSV header, so the backend had no users to insert into the
contacts database.

**Root cause**: `src/qmail/qmail_users.c` treated any `/service/users` response
containing `Email,` as valid. That allowed a header-only CSV from the normal
RAIDA consensus path to be accepted and saved, preventing fallback to RAIDA11,
which currently has the populated users list.

**Fix**: The users CSV validator now requires the header plus at least one data
row containing an address and comma-separated fields. When normal RAIDA
consensus does not return a non-empty users list, QMail fetches
`https://raida11.cloudcoin.global/service/users` directly, uses that data for
DB sync, and saves it to `qmail_users.csv`. Saved-file fallback also rejects
header-only CSVs.

**Verification**: The RAIDA11 users endpoint returned HTTP 200 with 215 bytes
and 5 CSV lines from this machine. `cmake --build build --config Release`
passed. `npm run build-portable` passed, and the rebuilt executable was copied
to `E:\Client3\QMail.exe`.
