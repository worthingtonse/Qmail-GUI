Fix #1 — numericallyClose now requires identical units (your item 1)
--------------------------------------------------------------------
File: scripts/css-analysis/cluster.mjs (extractNumber + numericallyClose)

Before:
    extractNumber returned just a number; numericallyClose compared
    only scalars. Result: 1rem ≈ 1em ≈ 100% ≈ 100px.

After:
    extractNumber returns { n, unit }.
    numericallyClose:
      - Special-case: pa.n === 0 && pb.n === 0 returns true.
      - Otherwise: pa.unit !== pb.unit → returns false.
      - Same unit: standard 5% tolerance.

    No cross-unit conversion (px ↔ rem) is implemented. Adding it
    later would require an explicit conversion rule (e.g. 1rem = 16px)
    and is deferred. Documented in README known-limitations §3.

Fix #5 (bonus, found while debugging) — single-property fuzzy rule
------------------------------------------------------------------
File: scripts/css-analysis/cluster.mjs (fuzzyEquivalent)

After fix #1, the toolchain still reported 0 fuzzy clusters. Tracing
through revealed why:

My old fuzzy rule required "≥80% of values match exactly". For a
single-property rule-set (e.g. `font-size` alone), the math is:

    1 property, 1 value comparison
    if it's a near-miss: matches = 0, props.length = 1
    matches / props.length = 0 / 1 = 0%  →  fails 80% gate

So fuzzy was structurally impossible for single-property rule-sets.
That's the most common shape (font-size: ..., padding: ..., etc.).

New rule:

  - Single-property rule-set: ANY single near-miss counts as fuzzy.
  - Multi-property rule-set: keep the ≥80% rule, plus require at
    least one near-miss (so exact-duplicate pairs don't pollute
    fuzzy clusters).

This restored 1 fuzzy cluster (5 font-size rows in {1.05rem,
1.1rem, 1.125rem}). Probably the actual number should be higher
once shorthand-spacing parsing exists, but at least the algorithm
works end-to-end now.

Q2. The new single-property fuzzy rule (fix #5) — does relaxing
    the 80% gate for single-property rule-sets feel right?
    --------------------------------------------------------------
    Without the relaxation, fuzzy clustering is mathematically
    impossible for any single-property rule-set (font-size alone,
    padding alone, etc.). With the relaxation, the algorithm fires
    on numeric-near-miss pairs in those sets.

    The risk: false positives where two adjacent rem values are
    semantically different (e.g. `0.75rem` for a small badge vs
    `0.8rem` for a comparable but distinct microtext token). The
    5% tolerance is loose enough that this can happen.

    The alternative would be: "ignore single-property fuzzy; let
    the literal-map drive the consolidation decision instead." That
    keeps fuzzy clustering as a multi-property-only heuristic.

    What's your call?

Q1. Is the 30× outline cluster real, or are we double-counting?
---------------------------------------------------------------
Short answer:
- it is NOT wrong under the current inventory model
- but it IS counting selector occurrences, not unique rule sites

Current model:
- inventory emits one row per selector token, not one row per
  comma-separated CSS rule site
- so a rule like:
    .a:focus-visible, .b:focus-visible, .c:focus-visible { ... }
  becomes 3 inventory rows

For the 30× outline cluster specifically, the current report is:
- 30 selector occurrences
- across 10 unique file:line rule sites

My call:
- keep row-per-selector in the inventory; it is the right shape for
  block grouping, rename blast radius, and collision analysis
- but the cluster report should stop presenting that count as if it were
  a unique edit-site count

Recommendation:
- keep `occurrences`, but rename it in report language to
  `selector_occurrences`
- add `site_count` = unique `file:line`

That gives both useful signals:
- selector_occurrences = semantic spread / rename surface
- site_count = actual CSS edit-site count

So: not a blocker, but I would adjust the wording so reviewers do not
read 30 as "30 separate declaration blocks".


Q2. Is the new single-property fuzzy rule the right move?
---------------------------------------------------------
Yes. Keep it.

Reason:
- without it, Algorithm 2 is mathematically impossible for all
  single-property rule-sets
- those are common in this repo (`font-size`, `padding`, `width`,
  `border-radius`, etc.)
- now that same-unit matching is enforced, the false-positive risk is
  materially lower than before

Important nuance:
- I would treat single-property fuzzy clusters as candidate-review
  output, not auto-collapse output
- but that is already how this tool is being used

So my call is:
- keep the single-property relaxation
- do NOT remove single-property fuzzy matching

One small doc nit remains:

- that is now incomplete, because single-property rule-sets use the
  explicit near-miss exception

Recommendation:

  - multi-property sets use the >=80% rule
  - single-property sets treat one same-unit numeric near-miss as fuzzy

That is a doc fix, not a logic blocker.
