QMail public profile / QCon directory implementation plan
========================================================

Status
------

This document is a plan only. No application or server code has been changed.

Repository findings that affect the design
-------------------------------------------

1. The current QMail address format is four bytes total: a three-byte serial
   number plus a one-byte denomination. This is implemented in
   src/qmail/address/qmailAddress.js and mirrored by rest_core. The proposed
   public-directory key is five bytes total: a four-byte serial plus a one-byte
   denomination. That is incompatible with the current client, parser, contact
   API, database, and avatar code and must be resolved before implementation.

2. The 256 QCon SVG assets already exist as numbered files 000.svg through
   255.svg in public/qmail-avatars/NewAvatars.

3. QmailCartoucheAvatar currently derives one to three symbol indices from the
   three bytes of the user's serial number. There is no stored QCon selection.
   The denomination chooses the cartouche frame.

4. The Edit menu is an Electron native menu in electron.cjs. It already sends
   qmail:menu-command messages through preload.cjs to QMailDashboard.jsx, which
   is the appropriate pattern for opening a Publish Public Profile modal.

5. The local contacts API currently stores/returns names, description,
   denomination and related contact metadata. Its create endpoint does not
   accept inbox_fee or QCon fields, and it is not an upsert endpoint. rest_core
   and its local contact database therefore require changes before the GUI can
   persist downloaded profiles or update an existing/self contact correctly.

6. On 2026-07-01, direct GET requests to all four stated/likely routes returned
   HTTP 404:
     https://raida11.cloudcoin.global/update_users
     https://raida11.cloudcoin.global/update_users.php
     https://raida11.cloudcoin.global/user_hints
     https://raida11.cloudcoin.global/user_hints.php
   The routes may not be deployed yet. Their final names and contracts must be
   confirmed before GUI integration.

Recommended product behavior
----------------------------

The feature should model a public profile as:

  denomination       integer code, currently 0..4
  serial_number       integer in the range agreed for QMail addresses
  qmail_address       canonical display address, returned by the server
  first_name          string
  last_name           string
  inbox_fee           non-negative integer in an explicitly agreed unit
  description         string
  qcon_indices        ordered array containing zero to three unique integers
                      in the range 0..255
  updated_at          server-generated UTC timestamp
  revision            server-generated monotonically increasing value

The denomination and serial number form the immutable identity key. The QMail
address is derived data and must not be accepted as an independent identity if
it disagrees with those fields.

An explicitly selected qcon_indices array overrides the serial-derived symbols
inside the existing denomination frame. If no public QCon data is available,
the existing deterministic serial-derived cartouche remains the fallback. This
preserves current avatars for all users who have not published a profile.

Phase 0 - resolve contracts and security before coding
------------------------------------------------------

1. Resolve the blocking questions at the end of this document.

2. Write and freeze a versioned JSON contract for update_users and user_hints.
   Define request methods, content type, status codes, response envelopes,
   field types, size limits, nullable/empty behavior, pagination, ordering,
   error codes, and authentication/proof fields. Both endpoints should return
   application/json for success and failure.

3. Do not ship an unauthenticated update endpoint. A request containing only a
   denomination and serial number would allow anyone to overwrite anyone
   else's public profile. Define an ownership proof that the PHP server can
   validate. Prefer a short-lived challenge/nonce and a proof produced through
   the local QMail/rest_core identity service. Include expiry and replay
   protection. Never send a CloudCoin secret, AN, wallet file, or reusable
   credential to the PHP server or expose it to renderer JavaScript.

4. Decide whether public-directory HTTP calls go through a narrow Electron main
   process IPC handler or through a new local rest_core proxy. A local rest_core
   proxy is preferred if it must create the identity proof. Direct renderer
   fetches would require correct CORS headers and put more security-sensitive
   protocol handling in the renderer. The current 404 response advertises
   methods but does not include an Access-Control-Allow-Origin header.

5. Use a configurable directory base URL, defaulting to
   https://raida11.cloudcoin.global. Do not scatter a hard-coded hostname
   through components. Define timeouts and allow deployment environments to
   override the URL.

Phase 1 - public PHP service and MySQL storage
---------------------------------------------

1. Create a public_profiles table. The exact serial type depends on the address
   decision:

   - current QMail: MEDIUMINT UNSIGNED, range 1..16777215;
   - proposed four-byte serial: INT UNSIGNED, range 1..4294967295.

   Suggested columns are denomination TINYINT UNSIGNED, serial_number,
   first_name, last_name, inbox_fee BIGINT UNSIGNED, description, qcon_1,
   qcon_2, qcon_3, revision BIGINT UNSIGNED, created_at and updated_at. Use a
   composite primary key on (denomination, serial_number). QCon columns are
   nullable TINYINT UNSIGNED values. Store no wallet secrets or identity proof
   after verification. Add normalized/indexed columns only for supported prefix
   searches.

2. Implement POST /update_users using a JSON request body. POST profile data in
   the body rather than the query string so names and descriptions do not land
   in routine URL logs. Validate the ownership proof, identity key, lengths,
   Unicode, inbox fee, QCon count/range/uniqueness, and unknown fields. Use
   prepared SQL and an atomic INSERT ... ON DUPLICATE KEY UPDATE. Increment the
   revision on every material change. Return the canonical stored profile.

3. Make update requests idempotent. Support an idempotency key or expected
   revision so retries cannot create ambiguous results or silently overwrite a
   newer edit. Return 409 for a revision conflict and 401/403 for failed proof.

4. Implement GET /user_hints with the stated optional parameters:

     first_name_starts_with
     last_name_starts_with
     qmail_address_starts_with

   Add limit and cursor parameters with a small bounded maximum. Escape SQL LIKE
   wildcard characters and use prepared statements. Return a stable sort order,
   result count, next cursor, and complete normalized profile objects. Empty
   criteria should either be rejected or return a deliberately small curated
   page; it must not dump the whole directory.

5. Add an exact lookup using denomination plus serial number, or explicitly
   guarantee that a full canonical qmail_address_starts_with value can be
   filtered to one exact match. Automatic sender/profile resolution needs exact
   identity semantics; a prefix-only result is not safe enough to auto-save.

   If qmail_address_starts_with must be supported efficiently, store or generate
   one canonical qmail_address value from the identity key and index it for
   prefix lookup. The server, not the client, is authoritative for that
   derivation, and it must reject a supplied address that conflicts with the
   denomination/serial key.

6. Add rate limits, request/body size limits, HTTPS-only handling, restrictive
   CORS if renderer access is chosen, audit logging without profile secrets, and
   generic production error responses. Define retention/deletion policy and a
   way for an owner to clear optional fields or unpublish the profile.

7. Add PHP integration tests for create, update, clearing fields, proof failure,
   replay, invalid ranges, Unicode, SQL/LIKE metacharacters, pagination, exact
   lookup, duplicate identity keys, revision conflict, and rate limits.

Phase 2 - extend the local rest_core contact model/API
-----------------------------------------------------

This work belongs in the rest_core repository even though the GUI consumes it.

1. Add inbox_fee, qcon_1, qcon_2, qcon_3, public_profile_revision and
   public_profile_updated_at to the local contacts schema. Use a migration that
   preserves every existing contact and permits null public fields.

2. Include those fields in:

     GET  /api/qmail/db/contacts/list
     POST /api/qmail/db/contacts/create

   Add a dedicated idempotent upsert/update endpoint keyed by denomination plus
   serial_number. A create-only API cannot refresh self data and will fail on an
   existing contact. Avoid delete/recreate because it can lose favorites,
   trust level, and notes.

3. Preserve user-owned local fields during a public-profile upsert. Public data
   may update names, description, inbox fee and QCons, but must not overwrite
   user_notes, is_favorite, trust_level, or other private annotations. Record
   that the public fields came from the directory.

4. Define the local-first rule precisely as: an existing contact row for the
   exact (denomination, serial_number) key prevents any automatic public lookup,
   even if some public fields in that row are empty. This matches the stated
   requirement that the directory is queried only when no local information
   exists. A future explicit Refresh from Public Directory action can bypass
   this rule, but should not be part of the first release without approval.

5. Add core tests for migration, 0-valued denomination and QCon indices,
   unsigned limits, upsert behavior, private-field preservation, self-contact,
   list serialization, and duplicate prevention.

Phase 3 - QMail-GUI API/domain layer
-----------------------------------

1. Add a focused publicDirectoryService module rather than mixing remote calls
   into qmailApiServices.js. It should own contract normalization, validation,
   timeouts, cancellation, error mapping, base URL configuration, exact lookup,
   prefix search, and publish/update calls. It should not log descriptions,
   names, proof material, or full response bodies.

2. Extend qmailApiServices.js contact normalization and addContact/upsert
   payload handling for inboxFee and qconIndices. Keep denomination code 0 and
   QCon index 0 valid; do not use truthiness checks for numeric fields.

3. Add a single public-profile model/validator shared by publishing, downloads,
   contact normalization and avatar rendering. Reject malformed remote records
   rather than partially trusting them.

4. Add a profile resolver/cache keyed by denomination and serial number:

   a. Check the in-memory local-contact map.
   b. If not loaded, query the local contact API for the exact identity.
   c. If a local row exists, return it and do not call the public directory.
   d. If no row exists, issue one exact user_hints lookup.
   e. Validate an exact identity match, upsert it into the local contact DB, and
      update the in-memory map.
   f. Deduplicate concurrent lookups, limit concurrency, and use a short
      negative-result cache so a mailbox with repeated unknown senders does not
      flood RAIDA11.

   Collect and deduplicate unknown identities from each loaded mail page, then
   enqueue them as one bounded background batch after the page has rendered.
   Directory latency must never delay the mail-list response or visible mailbox.
   A negative-cache TTL should be configurable; persisting it trades fewer
   requests for delayed discovery when a user publishes shortly after a miss.

5. Never use a first/last-name prefix response to automatically associate a
   profile with an email sender. Only an exact denomination plus serial identity
   match is safe for automatic persistence.

Phase 4 - Publish Public Profile modal
--------------------------------------

1. Add an Edit menu item such as "Publish Public Profile..." in electron.cjs.
   It sends a new command such as open-public-profile through the existing
   qmail:menu-command bridge. Disable the item when there is no configured QMail
   identity, if practical; otherwise the modal explains the requirement.

2. Handle the command in QMailDashboard.jsx and render a dedicated modal, with
   its open/closed state owned by the dashboard. Do not overload AccountPane or
   AddContactModal.

3. Pre-fill immutable QMail address/identity details from normalized
   userAccount. Pre-fill editable fields from the local self-contact/public
   profile when available. Fields are:

     First name
     Last name
     Inbox fee, with the exact currency/unit shown
     Self description, with a visible character counter
     Up to three ordered QCons

4. Build the QCon picker from the fixed 0..255 asset index, generating URLs with
   getQmailAvatarAssetHref rather than reading a Windows source path at runtime.
   Render a searchable/lazy or virtualized 16-by-16 grid so 256 SVGs do not make
   modal interaction sluggish. Each choice shows its icon and numeric index.
   Support keyboard navigation, visible focus, selected state, remove, and
   reorder. Prevent duplicates and enforce the maximum of three.

5. Show a live cartouche preview using the denomination frame and selected QCon
   order. If none are selected, explain/show the current serial-derived fallback.

6. Validate on the client using the same published limits as the server, but
   treat server validation as authoritative. Disable duplicate submissions,
   support cancellation with AbortController, preserve edits on transient
   failure, and use accessible status/error messages and focus management.

7. Publish sequence:

   a. Obtain the short-lived ownership proof through the chosen trusted layer.
   b. POST the normalized JSON profile to update_users.
   c. Validate the canonical profile returned by the server.
   d. Upsert that returned profile into the local contact database as self.
   e. Update dashboard profile/contact state immediately so all own-avatar
      instances rerender without restarting.

   The two servers cannot provide one transaction. If remote publish succeeds
   but local upsert fails, tell the user "Published, but local refresh failed"
   and retain an idempotent retry action. Do not report the publish itself as
   failed or issue a blind second remote write.

Phase 5 - QCon rendering and local-first downloads
--------------------------------------------------

1. Refactor the avatar model so QmailCartoucheAvatar accepts an optional
   qconIndices override. Valid public selections render in their given order;
   absent public data uses getQmailAvatarSymbolIndices(serialNumber), preserving
   today's behavior.

2. Pass local public-profile QCons to every relevant avatar call site, including
   NavigationPane (self), ContactsPane, sender avatars in EmailListItem and
   ReadingPane, and compose recipient chips where identity data is available.
   Centralize lookup/state rather than making each visual component perform
   network requests.

3. On dashboard/contact initialization, load local contacts once into the
   profile map. Resolve only exact unknown identities through the resolver from
   Phase 3. When a remote profile is saved locally, update the map so all visible
   avatars and profile text rerender in the same session.

   The primary automatic trigger is a successfully rendered page of mail:
   collect its unique sender identity keys, subtract the locally known keys, and
   queue only the remaining keys. Do not await directory resolution in the mail
   loading path. Reading one message may also enqueue its exact unknown sender,
   but must share the same in-flight/cache entry.

4. Keep remote failures non-destructive. A timeout, invalid result or 404 leaves
   the existing serial-derived avatar and sender labels in place. Do not create
   an empty local contact on a miss, because that would permanently suppress
   later directory lookup under the local-first rule.

5. If directory browsing is desired in ContactsPane, run its prefix query only
   after the corresponding local search has no results. Clearly label public
   results and persist one only after an exact identity is selected/confirmed.
   This is separate from automatic exact sender resolution.

6. Treat lookup metadata as a privacy concern: exact queries reveal to the
   directory operator which QMail identities this installation is trying to
   resolve and can therefore expose correspondence relationships. Document the
   behavior, avoid sending message IDs/subjects/timestamps, and decide whether
   automatic lookup requires a user-visible setting before release.

Phase 6 - tests and release checks
----------------------------------

1. Unit tests:

   - profile normalization and all numeric boundary values;
   - update and hint request construction/response mapping;
   - local-first resolver makes zero public calls on a local hit;
   - concurrent misses produce one public call;
   - exact-match enforcement and negative caching;
   - QCon override rendering, ordering, index 0, and fallback rendering;
   - modal validation and selection maximum/uniqueness;
   - Edit menu command handling and listener cleanup.

2. Integration tests:

   - publish -> remote success -> local upsert -> visible self avatar refresh;
   - existing self contact updates without losing notes/favorite/trust;
   - unknown sender -> local miss -> exact hint -> local upsert -> avatar refresh;
   - known sender -> local hit -> no request to RAIDA11;
   - mailbox content renders before slow directory lookups finish;
   - one mail page containing repeated senders creates one lookup per identity;
   - public miss/failure leaves deterministic avatar and does not create a row;
   - remote publish success plus local failure exposes a retryable partial state;
   - restart loads persisted QCons from the local database.

3. Manual checks on Windows Electron and the browser/Vite development path:
   menu availability, modal focus/escape behavior, 256-asset rendering,
   light/dark/high-contrast themes, slow/offline behavior, long Unicode text,
   duplicate clicks, app restart, and packaged relative asset paths.

4. Run npm test, npm run lint, npm run build, and the relevant rest_core/PHP
   suites. Deploy the PHP schema/endpoints before releasing a GUI that exposes
   the menu item. Use a staging base URL for end-to-end testing.

Recommended delivery order
--------------------------

1. Freeze identifier, fee, route, response and ownership-proof contracts.
2. Implement/test MySQL migration and PHP endpoints in staging.
3. Extend/test rest_core local contacts schema and upsert API.
4. Implement/test GUI service, profile resolver and avatar override.
5. Implement/test the Edit menu and publish modal.
6. Run staging end-to-end and failure-path tests.
7. Deploy PHP first, then compatible rest_core and GUI builds.

Blocking questions
------------------

1. Is the public-directory identity intended to use the existing one-byte
   denomination plus three-byte serial (four bytes total), or is QMail itself
   changing to a one-byte denomination plus four-byte serial (five bytes total)?
   The latter is a protocol/database migration much larger than this feature.

2. A selection comes from 256 assets, so its index is naturally one byte
   (0..255). What does "four byte index numbers" mean: a 32-bit integer for each
   selected QCon, four separate indices, or something else?

3. Is the lookup route /user_hints or /update_users? Both named routes currently
   return 404. What are the exact request methods and JSON success/error shapes?

4. What ownership proof will update_users require so one user cannot overwrite
   another user's public profile? Which existing rest_core operation, if any,
   can produce and validate that proof?

5. What unit and allowed range does inbox_fee use (CloudCoin, cents, atomic
   units, or another denomination)? Is zero allowed and does empty mean zero or
   "not published"?

6. What are the maximum lengths and allowed empty/null behavior for first name,
   last name and self description? Can a user clear fields or fully unpublish?

7. Should selected QCons replace the serial-derived symbols inside the existing
   denomination cartouche, as proposed here, or appear as three separate icons?

8. Should unknown senders be resolved automatically when a message is shown, or
   should public-directory access happen only during an explicit Contacts search?
   The plan supports safe exact automatic resolution but needs product approval.

9. If any local contact row exists, should it always win forever, or should a
   user be offered an explicit "Refresh from Public Directory" action? The first
   release plan treats any local row as authoritative and performs no refresh.

10. Automatic exact sender lookup reveals lookup/correspondence metadata to the
    public-directory operator. Should it be always enabled as specified, enabled
    only after notice/consent, or controlled by an account setting?
