To start the two GUIs against these pinned ports, you have two
options.

Option A — Dev mode (recommended for smoke testing)
---------------------------------------------------
The Vite dev server runs the GUI in a browser; the GUI's port-
resolution priority is (qmailApiServices.js:10-14):
  1. ?backendPort=N URL param
  2. VITE_API_PORT env var
  3. 8080 fallback

For two side-by-side dev clients:

  # Terminal 1: Client1 GUI on http://localhost:5173, talks to 8081
  cd /d D:\Code\src\JavaScript\Qmail-GUI
  npm run dev
  # then open: http://localhost:5173/?backendPort=8081

  # Terminal 2: Client2 GUI on http://localhost:5174, talks to 8082
  cd /d D:\Code\src\JavaScript\Qmail-GUI
  npm run dev2
  # then open: http://localhost:5174/?backendPort=8082
  # (dev2 already sets VITE_API_PORT=8082 but the URL param is
  #  authoritative.)

Both browsers can be open simultaneously side-by-side. Each connects
to its own backend. Same source tree, two clients.

This is the simplest setup. You'll be able to refresh the page,
inspect the network panel, and watch React state in DevTools — none
of which is possible inside Electron without enabling devtools.


Option B — Packaged Electron (closer to what a real user sees)
--------------------------------------------------------------
DO NOT use `npm run electron-dev` for two-client testing — it spawns
its OWN core.exe at its OWN auto-picked free port. It would compete
with the manually-launched E:\Client1\core.exe / E:\Client2\core.exe.

Instead: build a packaged QMail.exe and place a copy in each client
folder. The portable build expects rest_core.conf and Client_Data
to live alongside it.

  cd /d D:\Code\src\JavaScript\Qmail-GUI
  npm run build-portable
  # Output: release\QMail-Portable.exe (or similar — check
  # electron-builder.config.cjs for the exact name)
  copy release\QMail.exe E:\Client1\
  copy release\QMail.exe E:\Client2\

Then double-click each QMail.exe. Each one spawns ITS OWN core.exe
sibling at an auto-picked free port. The pinned ports in E:\Client*\
rest_core.conf are NOT used in this mode — Electron picks the port,
not the config. So if you need ports 8081/8082 specifically (for
example to point external tools at them), use Option A.

I'd start with Option A for smoke testing. Option B is for shipping
verification later.


Q2. "Will I need to do the testing manually?"

Yes — for this round.

Reasons:
  1. The Phase 1-3 checklists are heavy on visual verification: "is
     the trash-icon hover state correct?", "does the italic preview
     render only for empty bodies?", "does the unified Refresh
     spinner stay synchronized?". A browser-automation harness can
     check DOM presence but it can't see styling correctness — that
     needs a human eye.

  2. Several flows depend on RAIDA network state that a test harness
     can't easily mock. E.g. the "Send anyway" override after RAIDA
     warning, the pending-message decryption flow, the inbox-fee
     locker. Mocking those out would test a different code path
     than the one users hit.

  3. The two-client smoke test is mutual — Client1 sends to Client2,
     then Client2 replies, then Client1 sees the reply. That's a
     stateful sequence with backend persistence between steps. The
     usual test-harness pattern (per-test reset) doesn't apply.

So: walk the checklist below by hand, side-by-side, with both
clients visible.

Future automation could partially help with:
  - Per-screen smoke (does AccountPane render? does ContactsPane
    render?) — Playwright / Puppeteer could click through.
  - API-level smoke (does sendEmail return success?) — curl scripts
    against the live backends.

Both are valuable for regression after the CSS refactor lands. Not
worth blocking this round on them.


Q3. "Do we need to have Gem do it since it seems it can manipulate
     a browser?"

Reasonable instinct, but I'd skip Gem-driven testing for this round
and revisit after the CSS refactor.

Why not now:
  - Gem's browser tool would have to know what "looks right" looks
    like. Without a known-good baseline (screenshots, snapshot tests,
    or detailed pixel descriptions), it's just clicking buttons. It
    would catch broken flows (button doesn't respond) but not
    regressed flows (button responds but does the wrong thing).
  - The two-client mutual flow is the most important shape of this
    test. Gem can drive ONE browser at a time. Coordinating two
    Gem sessions (or one Gem switching between two windows) is
    fiddly and slower than Sean manually clicking.
  - The CSS refactor is about to happen. If you script a smoke test
    against the current CSS class names, the refactor (which Track F
    is about) will invalidate most of the selectors. Wait for the
    BEM rename to settle before automating.

Why later (after CSS refactor):
  - Once the BEM rename lands, the selectors are stable. Then a
    Playwright suite tied to BEM block names would survive the
    refactor and catch regressions in future refactors.
  - Gem could be the agent that *writes* and *maintains* that
    Playwright suite, which is more valuable than having Gem click
    once.

What to do with findings
========================

If a check fails:
  - File a bug entry in docs/cla.bugs.txt under a new BUG-NN
    appendix. Next BUG number to use is BUG-51.
  - Include: file:line if known, what you did, what you saw, what
    you expected. Severity: HIGH if it blocks a normal email flow,
    MEDIUM for UX regressions, LOW for cosmetic.

If a check passes:
  - No action needed. Don't update individual batch fixes.txt
    files — those are immutable post-shipment.

After the full walkthrough:
  - If everything passes, write a short closure note: "Smoke test
    passed N/M checks, M-N failures filed as BUG-XX..YY." Save as
    docs/opu.smoke-test.results-2026-MM-DD.txt or similar.
  - If significant failures: bundle them in the closure note and
    decide with Sean which to fix vs defer.
