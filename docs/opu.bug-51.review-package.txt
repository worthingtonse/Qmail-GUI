Addition 1A: kill-by-name at PRE_LINK (inside kill_test_ports.cmake)
--------------------------------------------------------------------
The existing kill_test_ports.cmake killed processes BY PORT
(8080/8081/8082). That misses any QMail/core launched from
E:\Client3\ or anywhere else with a random port. I added a
kill-by-NAME block AHEAD of the port loop:

    execute_process(
        COMMAND powershell -NoProfile -Command
            "foreach ($n in @('QMail','core')) {
               Get-Process -Name $n -ErrorAction SilentlyContinue |
                 ForEach-Object {
                   try {
                     Stop-Process -Id $_.Id -Force -ErrorAction Stop;
                     Write-Host \"killed $n PID $($_.Id)\"
                   } catch { }
                 }
             }"
        OUTPUT_VARIABLE _name_out
        ERROR_QUIET
    )
    if(_name_out)
        message(STATUS "${_name_out}")
    endif()

What it does: enumerates every process named QMail or core
(extension-insensitive on Windows), force-kills them, prints
"killed <name> PID <pid>" for each.

Why machine-wide is OK: Sean explicitly chose the simpler version.
Trade-off: if Sean has two QMail.exe builds open and rebuilds
rest_core, both die. Acceptable per his answer to Q-NEW-1.

Why try/catch around Stop-Process: handles the race where a
process exits between the Get-Process snapshot and the Stop-Process
call. Silent on failure (just skips).

Why -ErrorAction SilentlyContinue on Get-Process but Stop:
Get-Process emits a non-terminating error if zero matches — that's
expected (most of the time nothing is running). Stop-Process needs
the explicit -ErrorAction Stop to make the catch fire.

PowerShell quoting: nested triple-escape because CMake's file(WRITE)
embeds it in a here-string that's itself inside a CMake script.
The `\$n` / `\$_.Id` escapes the outer level; the `\\\"` escapes
both levels. I verified by running the build: output included
"killed QMail PID 12892" etc.

Change 2 of 2 — D:\code\src\JavaScript\Qmail-GUI\electron.cjs
==========================================================
Diff stats: +92 -8 (three hunks)

Three pieces:

Piece 2A: new QMAIL_USAGE constant + parseQMailArgs() function
--------------------------------------------------------------
Inserted right after the log() helper, before findFreePort().
Roughly 80 lines including the usage string. Pure addition.

The parser:
  - Slices argv past Electron's own args using
    process.defaultApp ? 2 : 1. Standard Electron pattern.
    (In a packaged build process.defaultApp is undefined/false,
    so we start at index 1; in `electron .` dev mode it's true
    and we start at index 2 to skip the script path.)
  - Handles --help / -h and --version / -V first; both call
    app.exit(0) and return null. The caller (`const qmailArgs =
    parseQMailArgs(...) || {...}`) substitutes a default object
    so subsequent code doesn't crash before exit completes.
  - Three boolean flags: --dev, --debug, --r11ip.
  - --port accepts both `--port 8081` (next arg) and
    `--port=8081` (attached). Validates Number.isInteger and
    range 1..65535. Bad value → "QMail: invalid port '...'" on
    stderr + usage + app.exit(2).
  - Unknown arg → "QMail: unrecognized option '...'" + usage +
    app.exit(2).
  - app.exit(2) (not process.exit) because app.exit allows
    Electron to clean up before terminating.

Piece 2B: replace `const isDev = process.argv.includes('--dev')`
----------------------------------------------------------------
Old code did its own scan. New code reads from the parsed result:
  const qmailArgs = parseQMailArgs(process.argv) || { ... };
  const isDev = qmailArgs.dev;

This centralizes arg parsing in one place. The downstream `isDev`
checks (in startBackend, createMainWindow, read-file IPC) work
unchanged.

Piece 2C: thread args into startBackend() and boot()
----------------------------------------------------
startBackend(port) — replaced the hardcoded args array with a
built one:
  const coreArgs = ['-port', String(port)];
  if (qmailArgs.debug) coreArgs.push('-debug');
  if (qmailArgs.r11ip) coreArgs.push('-r11ip');
  log('Backend args: ' + coreArgs.join(' '));
  ...spawn(backendPath, coreArgs, {...});

boot() — replaced the unconditional findFreePort() call with a
branch on qmailArgs.port:
  if (qmailArgs.port !== null) {
    backendPort = qmailArgs.port;
    log('Using explicit port: ' + backendPort);
  } else {
    try { backendPort = await findFreePort(); ... }
    catch (e) { ... backendPort = 8080; }
  }

When --port is set, no free-port probe — we trust Sean. If the
port is already in use, core.exe will fail to bind and exit;
electron.cjs logs the exit code via the existing
backendProcess.on('exit', ...) handler. Per my plan there's no
special "port already taken" pre-flight — keeping it simple.

GPT review questions for Change 2
---------------------------------
Q2.1: The slice(process.defaultApp ? 2 : 1) idiom — is that
      right for all the modes QMail can launch in? Specifically:
      `electron .` (defaultApp=true → slice 2), packaged
      QMail.exe (defaultApp=undefined → slice 1), and dev via
      `electron-dev` npm script (uses `electron .` so same as
      first). I think yes. Worth a second eye since the wrong
      slice would either eat a real arg or process the script
      path as a flag.

Q2.2: app.exit(0) on --help/--version: any case where Electron
      buffers stdout in a way that the usage string doesn't
      reach the terminal before exit? On Windows this has
      historically been a hazard. Worth changing to
      process.exit(0) after a flush? My take: leave it; the
      writes are sync (process.stdout.write returns true for
      small payloads, no callback needed) and app.exit waits
      for the current tick.

Q2.3: When `--port N` is provided AND N is unavailable, core.exe
      exits within ~1s. The Electron splash stays up, the main
      window loads with backendPort=N in the URL, and the React
      app tries to fetch from it — eventually times out / errors.
      User experience is "splash → main window → broken." Not
      great but not in scope for BUG-51. Would you file a
      follow-up bug or add a 2-second post-spawn health check
      now? I lean toward follow-up bug to keep BUG-51 small.

Q2.4: My handling of the `out` return value when help/version
      exits — the parser returns null, the caller does
      `|| { port: null, debug: false, ... }`. After app.exit(0)
      the rest of electron.cjs still runs synchronously for a
      tick (boot() being async, the queued tasks run). Is this
      a problem? In practice startBackend won't fire because
      app.whenReady() resolves after the exit completes. I
      believe this is safe but it'd be cleaner to early-return
      before app.whenReady().then(boot). Want me to add that?
