- QMailDashboard refresh crash: `handleRefresh` calls `checkForNewMail()` even though that function is commented out/undefined in QMailDashboard.jsx (around the refresh handler). Clicking Refresh throws a ReferenceError and stops the UI from updating.
- USB check never passes: USBCheckScreen initializes local `usbStatus` from the `isUSBDrive` prop once and never updates it when the prop changes. When Wallet detects a USB drive later, the screen still shows the failure state because `currentUSBStatus` stays false.
- Send-status polling stuck: ComposeModal.pollTaskStatus reads `result.data.status`, but `getTaskStatus` returns `state` (with progress flags). Tasks with a `task_id` never reach the “completed” branch, so sending stays in a perpetual sending state even after the backend finishes.
- Attachment paths with delimiters fail: the GUI sends repeated `attachment_file_path` values, but the backend concatenates them into a comma-separated string and later parses with comma/semicolon delimiters. Valid Windows paths such as `D:\Docs\invoice, final.pdf` or `D:\Docs\notes; qmail.txt` can split into invalid paths. Backend refs: `D:/Code/src/C/rest_core/api_src/api_handlers_qmail_messages_send.c` and `D:/Code/src/C/rest_core/src/qmail/qmail_upload_orchestrator.c`.
- Attachment overflow is silent: backend attachment path aggregation uses a fixed buffer and silently stops copying paths when full, so the Compose UI can show more staged attachments than the backend sends. Backend should reject overflow with an explicit error or expose a limit the GUI can enforce. Backend ref: `D:/Code/src/C/rest_core/api_src/api_handlers_qmail_messages_send.c`.
- Reply All is backend-limited: Batch 6 now disables Reply All when recipient lists are unavailable, but `/api/qmail/db/messages/get` still appears to omit full To/Cc/Bcc data for normal downloaded messages. Without those stored recipient lists, the GUI cannot honestly offer Reply All for existing messages. Backend/local DB should persist and return recipient lists for message detail reads.
- Contacts delete uses a browser confirm: ContactsPane still calls `window.confirm()` before deleting a contact. The rest of the app is moving to in-app confirmation modals, and this native dialog breaks the visual/accessibility pattern. Replace with an app-styled modal when Contacts work is in scope.
- Vite build is intermittently flaky on Windows: during Phase 3 Batch 16, the first `npm run build` transformed and rendered chunks, then failed in `vite:build-html` with `RollupError: The "fileName" or "name" properties of emitted chunks and assets must be strings that are neither absolute nor relative paths, received "D:/Code/src/JavaScript/Qmail-GUI/index.html".` An immediate `npx vite build --debug` and then the same `npm run build` both passed. This looks like a build-tool/cache/path-resolution issue outside the compose polish scope.
- DicewarePasswordCreator still uses browser `alert()` dialogs for row-validation errors and cloud-backup tips (`src/wallet/components/DicewarePasswordCreator.jsx:78,255`). That bypasses the app's themed notification/modal patterns and will feel visually inconsistent once the screen is fully themed.
- `--font-size-base` is not a real global token, but it is used in `src/App.css` and `src/qmail/screens/AccountPane.css`. It appears to be defined only locally on `.qmail-dashboard` in `src/qmail/screens/QMailDashboard.css:3-6`, so uses outside that subtree can resolve to an unset custom property and drop the font-size declaration.
- App.css bare-button disabled ripple mismatch: Phase 3 kept the global `button { ... }` fallback for non-`.btn` controls, but `src/App.css` still uses `button:hover::before` without `:not(:disabled)`. Disabled fallback buttons in ComposeModal, AddContactModal, DicewarePasswordCreator, etc. can still animate the ripple on hover even though `.btn` was fixed to suppress that behavior.
