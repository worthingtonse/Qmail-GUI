4. THREE QUESTIONS FOR YOUR FINAL READ
================================================================================

4.1  Was the 3.2i revert (§2 above) the right call?
-----
The 7 reverts moved several JSX sites BACK to bare per-file class names.
The alternative would have been to keep `btn btn--variant` and add
explicit `transform: none; box-shadow: none` suppressions in each
custom button's `:hover` rule.

I went with revert because:
  - These are genuinely custom contextual designs, not CTAs
  - The bare-element `button { ... }` rule provides their interaction
    baseline anyway
  - Suppression in :hover would have been a per-file Band-Aid in 6
    different files
  - The revert keeps the architectural rule "primitive is for CTAs
    only" honest

But the revert means there are STILL ~30 `<button>` elements in the
codebase that don't carry the .btn primitive — they rely on the
bare-element fallback. Is that the right architectural endpoint, or
should Track F eventually fold the contextual buttons into a separate
primitive family (something like .icon-button, .text-toggle,
.contextual-action)?

For now I left this as "out of scope for Phase 3" — the variant
extraction is done; further button taxonomy is a Phase 4 question.
Agree or disagree?

4.2  Is App.css's `button { ... }` baseline rule pulling its weight?
-----
The rule contributes:
  - cursor: pointer
  - border: none
  - border-radius: var(--radius-lg)        (overridden by per-file)
  - font-size: var(--font-size-md)         (overridden by per-file)
  - font-weight: 500                       (overridden by per-file)
  - font-family: var(--font-primary)       (mostly inherited anyway)
  - padding: 12px 24px                     (overridden by per-file)
  - transition: all var(--transition-base) (overridden by per-file)
  - position: relative                     ← needed for ::before ripple
  - overflow: hidden                       ← needed for ripple containment
  - letter-spacing: 0.01em

Plus siblings: `button::before` ripple element, `button:hover`
(transform: translateY(-2px); box-shadow: var(--shadow-lg)),
`button:active`, `button:disabled` (opacity 0.5).

The ONLY consumers benefiting from these are the ~30 non-.btn buttons
in the codebase. The .btn primitive defines its own versions of every
one of these properties in primitives.css, so .btn consumers are
unaffected.

Is the right end state:

  (a) Keep `button { ... }` indefinitely (current — covers any
      future non-.btn button cheaply, single source of "what a button
      looks like by default"), OR
  (b) Migrate every non-.btn `<button>` to either consume .btn or
      define its own complete shape (so the bare-element rule can be
      deleted)?

I lean toward (a) — option (b) is Track F territory and would touch
PasswordScreen, USBCheckScreen, WelcomeScreen, ThemePicker,
NotificationContainer, ThemeEditorModal, AddContactModal, plus the
~10 DicewarePasswordCreator .btn-X bespoke buttons. That's a lot of
churn for the architectural-purity win.

4.3  Anything I missed that should be re-opened before closing Phase 3?
-----
Track-F deferred items I'm aware of:
  - 3.6 (`.upload-box` family) was deferred in v1.2; still deferred.
  - The CTA-vs-contextual button taxonomy from §4.1 above is a Phase
    4 question.
  - `.refresh-btn` is now a shared layout-only rule in MainDashboard.css
    but is consumed by both wallet (TransactionsTab) and qmail
    (AccountPane, ContactsPane). Should it MOVE to primitives.css?
    I left it in MainDashboard.css because (a) it's layout-only so
    audit doesn't penalize it as a collision, (b) moving it would
    require updating the global import chain, and (c) MainDashboard.css
    is already imported globally via the Wallet shell.

  - `.diceware-button` at App.css L156+ is still a one-off rule with
    its own gradient. Lone consumer is DicewarePasswordCreator (and
    it's not the `.btn-backup` family — different class). I left it
    untouched because it has only 1 JSX site and doesn't fit the
    primitive variants. Worth flagging for Track F.

Anything else you'd flag before signing off on Phase 3?

4.1  Was the 3.2i revert the right call?
----------------------------------------
**Yes.**

Reverting those 7 sites away from `.btn btn--variant` was the right move.
Your reasoning is sound:
- those buttons are contextual/custom controls, not CTA primitives
- pushing them through `.btn` and then suppressing primitive behavior in
  six different files would have been backwards
- the revert keeps the primitive taxonomy honest

So I agree with the architectural endpoint:
- CTA buttons → `.btn` family
- contextual/custom buttons → per-file classes + baseline button fallback

If Track F later wants a second primitive family (`.icon-button`,
`.contextual-action`, etc.), that is a separate improvement track, not a
reason to reopen the 3.2i revert.


4.2  Is App.css's `button { ... }` baseline rule pulling its weight?
--------------------------------------------------------------------
**Yes — keep it.** I agree with your option **(a)** for now.

The current tree still has enough real non-`.btn` button consumers that
the bare-element rule is doing meaningful work. Trying to force full
elimination now would create a lot of churn for limited payoff.

So I agree with:
- keep the baseline rule
- let Track F / Phase 4 revisit button taxonomy only if it becomes worth
  the churn


4.3  Anything missed before closing Phase 3?
--------------------------------------------
**Yes — one small but real reopen item.**

You fixed disabled hover ripple on the `.btn` primitive:

  .btn:hover:not(:disabled)::before

But the App.css bare-button fallback still has:

  button:hover::before

with **no** `:not(:disabled)` qualifier.

That means the same semantic bug still exists for the non-`.btn` buttons
Phase 3 now intentionally relies on, including disabled-capable controls
such as:
- ComposeModal `send-button`
- ComposeModal `attach-button`
- ComposeModal `network-retry-btn`
- ComposeModal `attach-files-btn`
- ComposeModal `toggle-advanced-btn`
- AddContactModal buttons
- multiple DicewarePasswordCreator buttons

These sites inherit the global `button::before` ripple and can still be
disabled, so the ripple can animate on pointer-over of a disabled button.
That is the same mismatch we already decided was wrong for `.btn`.

So my recommendation is:

  button:hover:not(:disabled)::before { ... }

in App.css before calling Phase 3 done.

I consider that a real reopen item, not just a doc nit.
