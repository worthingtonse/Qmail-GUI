FIX-42 (Contacts SN ↔ email lookup helper)
  Plan text: "Add SN ↔ email lookup helper in Contacts."
  [x] New "Lookup" mode in the contacts tab bar (line 573-580),
      sitting next to the existing Contacts (line 558-564) and
      Popular (line 565-572) buttons. Activated via switchToLookup
      (line 469-474), which sets currentMode = "lookup",
      clears searchTerm, and does a hidden loadContacts to refresh
      the userContacts cache without flipping the visible list.
  [x] Lookup panel rendered only when currentMode === "lookup"
      (line 624-689). When active, the standard search bar
      (line 591-602) is hidden — the dedicated lookup input
      (line 633-662) takes its place. Clean mode separation.
  [x] handleLookupContact (line 211-276) implements the documented
      precedence:
        1. findLocalContactMatches over userContacts first
           (line 225-233). If anything matches, return "local"
           result with the matches.
        2. If the value matches SERIAL_NUMBER_PATTERN (/^\d+$/),
           call the existing local convertSnToEmail helper
           (line 235-253). Returns "remote" type on success — but
           the message text is honest: "Serial number resolved by
           the local QMail service." — no claim of DRD involvement.
        3. If serial-only lookup misses, return "empty" with copy
           that says the local service did not return an address.
        4. Otherwise (the value is not a serial), return "empty"
           with copy that explicitly states: "Address-to-serial
           lookup is not available yet, and this helper does not
           query the DRD." Matches the summary's "clearly local-
           only" promise.
  [x] API shape matches: convertSnToEmail returns
      { success, email, firstName, lastName } (qmailApiServices.js
      line 1349-1361); JSX destructures result.firstName /
      result.lastName / result.email at lines 244-247. No shape
      mismatch.
  [x] Empty-input guard (line 213-219) returns a friendly error
      result instead of throwing. Lookup form inputs are
      disabled={lookupLoading} (line 647, 653), so Enter-while-
      loading cannot re-fire handleLookupContact.
  [x] Lookup result rendering (line 663-687) shows the explanatory
      message, then maps lookupResult.contacts (when present) into
      name/email/SN rows. Keying uses `${contact.id||email}-name`
      which is stable across the three result shapes.
  [x] No new backend dependency. The ticket note about CORE-C
      (reverse SN lookup) is still relevant — until that lands,
      address→SN is intentionally not implemented, and the UI
      copy says so. Good restraint.
  [x] Existing search behavior unchanged: typing in the regular
      search bar still flips currentMode to "search" and calls
      loadContacts({ displayMode: "search" }). The new lookup
      mode short-circuits the search-debounce effect at line 69-71.

FIX-43 (Default-with-override folder-icon map)
  Plan text: "Treat folderIcons as a default-with-override map so
  new backend folders render with a sensible icon."
  [x] DEFAULT_FOLDER_ICONS (NavigationPane.jsx line 26-33) keyed by
      canonical folder.name: inbox, sent, drafts, trash, starred,
      archive → Inbox, Send, FileEdit, Trash2, Star, Archive.
  [x] ALLOWED_FOLDER_ICONS (line 35-47) is the whitelist for
      backend-provided folder.icon / folder.iconName values. Maps
      both the canonical names and common aliases (draft/drafts,
      send/sent, star/starred, fileedit, mail) → lucide components.
      Whitelist approach prevents a malformed backend payload from
      crashing the render or pulling in an unexpected icon.
  [x] normalizeIconName (line 49-50) lowercases, trims, and strips
      everything non-alphanumeric. So "Star-icon", "STARRED ",
      "star_icon" all collapse to "starred"/"staricon"/"star" —
      the lookup is forgiving without being unsafe.
  [x] getFolderIcon (line 52-59) precedence:
        1. ALLOWED_FOLDER_ICONS[folder.iconName] (preferred)
        2. ALLOWED_FOLDER_ICONS[folder.icon] (compat alias)
        3. DEFAULT_FOLDER_ICONS[folder.name]
        4. Mail (fallback).
      Every branch yields a component, so the JSX <IconComponent />
      at line 128 cannot render undefined.
  [x] No behavior change for known folders. The backend can now
      ship a "labels" or "promotions" folder with iconName: "star"
      and it renders correctly; without that hint, it falls back
      to Mail.

Reviewer BUG Coverage (BUG-44, BUG-47, BUG-48)
----------------------------------------------
BUG-44 (LOW — DRD "Add to My Contacts" saved-state local on remount)
  [x] The local savedDrdContactIds state and the setter that
      populated it are GONE. Grep confirms zero matches for
      savedDrdContactIds in src\.
  [x] isContactSavedLocally (ContactsPane.jsx line 189-198) is the
      derived check — it walks userContacts and compares
      normalized id / email / name tuples to the DRD contact's
      same tuple. Single match counts as saved.
  [x] DRD Add button (line 783-801) reads isSavedDrdContact from
      isContactSavedLocally(contact). On every render. So:
        - Successful add → loadContacts updates userContacts →
          isContactSavedLocally returns true on next render →
          button switches to the Check-icon "Added" state.
        - Delete (via the user-side delete flow) → loadContacts
          removes the row from userContacts → next time the user
          views the DRD list, the Add button is re-enabled.
        - Remount → useEffect at line 61-64 reloads userContacts;
          the saved state is recomputed correctly with no special
          handling.
  [x] No race: userContacts is the source of truth, and it is
      refreshed by every mutation path (handleAddPopularContact at
      line 349, handleConfirmDeleteContact at line 414).

BUG-47 (LOW — Undo onClick fires setContacts after unmount)
  [x] restoreDeletedContact (line 358-370) no longer calls
      loadContacts. The body is now:
        1. addContact(payload) — POSTs the restore to the backend.
        2. showSuccess / showError on the unified provider.
      No setContacts, no setUserContacts. The next ContactsPane
      mount (or a refresh while still mounted) picks up the
      restored contact via the normal loadContacts path.
  [x] handleConfirmDeleteContact (line 415-418) still wires the
      undo notification with the captured `contact` and
      `payload.data`. The closure is now safe across ContactsPane
      unmount — only addNotification / showSuccess / showError are
      called, and those route through NotificationProvider (which
      is mounted at the app level).
  [x] The 10-second undo window (duration: 10000) is preserved
      verbatim from FIX-28.

BUG-48 (LOW — Inline delete-error pattern inconsistency)
  [x] GPT chose option (b) from the bug's FIX PLAN: "Document this
      as an intentional exception." The two inline-error setters
      now each carry the comment:
        // Keep delete errors inline so the confirmation stays
        //   open for retry.
      at lines 407 and 420.
  [x] The comment correctly captures the WHY: a delete preparation
      or backend failure should keep the destructive modal open so
      the user can retry without losing their decision context.
      Routing through showError() + closing the modal would force
      the user to re-open and re-confirm, which is the wrong UX
      for a transient failure.
  [x] No other error path in ContactsPane was changed — the
      pre-existing showError calls in handleAddPopularContact
      (line 339, 345, 352) and restoreDeletedContact (line 362,
      368) still route through the unified system. Inline-error
      is now visibly the EXCEPTION, not the rule.

    delete) — handleConfirmDeleteContact (line 384-425) calls
    await loadContacts() at line 414 AFTER a successful delete.

    delete path instead of the post-delete undo. Suggested fix:
