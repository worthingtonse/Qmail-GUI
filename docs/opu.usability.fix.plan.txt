Purpose

work into phases by priority and risk, gives each ticket concrete

Scope guardrails
----------------
- Most tickets are GUI-side (React/JS), but several have HARD
  backend prerequisites — see "Backend tickets implied by this
  plan" at the bottom for the full list. The HARD ones are CORE-F
  (non-mutating identity-health endpoint), CORE-H (deleteDraft
  endpoint), and CORE-J (starred filter). The GUI-side work for
  FIX-10, FIX-23, and FIX-18 cannot complete without those.
- Tickets that touch Electron / preload / packaging are flagged
  Phase 0B or noted in-place. They cross more process boundaries
  than the renderer-only tickets.
- Don't rewrite layers wholesale. Most tickets are a 10-80 line
  patch in one or two files. The one exception is FIX-05.5
  (composeContext refactor) which crosses ComposeModal and several
  call sites.
- "Dead controls" policy: visibly disabled with "Coming Soon"
  badges (per FIX-16-0A and product decision). NOT silently
  no-op'd, NOT removed wholesale. Delete Account remains hidden
  entirely (safety-critical, doesn't exist, should not be tempting
  to click).

Ticket-naming convention

Each ticket is FIX-NN, severity-tagged [C]/[H]/[M]/[L], and tagged
with the originating finding(s) in the form opu-H1 / gpt-2 / gem-E.

FIX-01 [C] (gpt-2 / R1)  Pending-message download must hydrate the body
  Problem:
    handleDownloadMail in QMailDashboard.jsx:700-766 reads
    responseData.body, but POST /api/qmail/net/messages/download
    returns metadata (email_id, sender_sn, stripes_downloaded,
    stripes_recovered). The body is empty in the reading pane.
  Files to change:
    src\qmail\screens\QMailDashboard.jsx (handleDownloadMail)
    src\api\qmailApiServices.js (downloadEmailContent — leave as is,
       the call is right; the consumer is wrong)
  Approach:
    1. After the download call returns success, take responseData.email_id.
    2. await getEmailById(email_id) for the body and subject.
    3. await getEmailAttachments(email_id) for the attachment list.
    4. Update selectedEmail from those two responses (not from the
       download response).
    5. Remove the row from pendingMails, refresh loadMailCounts and
       loadEmails(currentFolder) so the inbox row flips from pending
       to downloaded.
  Edge cases:
    - Download succeeds but the DB row is not yet visible (race
      between net/download and DB index). Add a short retry (3 tries,
      500ms backoff) on getEmailById before declaring failure.
    - Each getEmailById attempt MUST be wrapped in try/catch (gem
      v2 feedback). The backend can 5xx during a retry window. On
      exception: decrement the retry counter, sleep, and try again.
      If all retries are exhausted, exit with a "Service temporarily
      unavailable" toast and leave the row in pendingMails so the
      user can retry by clicking it again. Do NOT leave selectedEmail
      stuck in a half-loaded state.
    - User clicks a different message before the download completes:
      the existing isDownloadingItem state guard handles this; verify
      it still works after the refactor.
  Verify:
    1. Receive a new mail on the test backend. Click the pending row.
       Confirm the reading pane shows the real subject, body, and
       any attachments — not the placeholder "Encrypted Message".
    2. Resiliency: simulate a backend that 500s on getEmailById.
       Confirm the user sees the "Service temporarily unavailable"
       toast (not a permanent spinner) and the row remains clickable.

FIX-03 [C] (gpt-1 / opu-H31 / R6)  First-run identity is never verified
  Problem:
    Two compounding bugs:
    (a) ServiceSelectionScreen.handleImport hands result.data
        straight to onSelectService('qmail', result.data).
        WalletSetupScreen reads accountData.email_address,
        accountData.pretty_address, accountData.needs_healing —
        fields the import response does NOT contain (it has
        coins_found, coins_saved, wallet_path, mail_wallet_path).
    (b) Even if (a) were fixed, the data still wouldn't reach
        QMailDashboard. App.jsx renders <QMail />, QMail.jsx
        renders <QMailDashboard /> — neither passes provisioningData
        through. The "John Doe" placeholder leaks because the prop
        chain is broken end-to-end.
  Files to change:
    src\screens\ServiceSelectionScreen.jsx
    src\App.jsx
    src\qmail\QMail.jsx
    src\qmail\screens\WalletSetupScreen.jsx
    src\qmail\screens\QMailDashboard.jsx
    src\api\qmailApiServices.js (add a normalizeIdentityForUi helper)
  Approach:
    1. Add normalizeIdentityForUi(raw) in qmailApiServices.js that
       takes a getIdentity() response — fields like address,
       serial_number, registered, identity{...} — and returns a flat
       UI-friendly object containing BOTH camelCase and the
       snake_case aliases that existing consumers read today:
         {
           // camelCase (new convention)
           address, prettyAddress, serialNumber, domain,
           isHealthy, needsHealing,
           // snake_case aliases (preserve compatibility)
           pretty_address, serial_number,
           // misc
           raw, configured,
         }
       Why both shapes: current consumers (AccountPane, WalletSetupScreen)
       read fields like userAccount.pretty_address and
       userAccount.serial_number. Updating every consumer in this
       ticket is possible but risky — easy to miss one. Returning
       both shapes means a missed consumer still works (reads
       snake_case), and new consumers can use the cleaner camelCase
       naming. Centralizing the construction prevents every
       consumer from inventing its own field-name guesses.
    2. ServiceSelectionScreen.handleImport: on successful import,
       call getIdentity() then normalizeIdentityForUi(). Hand the
       normalized object to onSelectService('qmail', identity).
       If getIdentity returns configured=false, retry once after
       500ms (backend can lag right after import). If still nothing,
       advance with a warning toast "Account imported but identity
       not yet visible." Don't hard-block — data is in the wallet.
    3. App.jsx: thread provisioningData into the QMAIL branch:
         case SERVICES.QMAIL:
           return <QMail initialIdentity={provisioningData} />;
       Product decision: returning users with a configured identity
       should go straight to QMAIL, not PROVISIONING. Change
       checkIdentity to setSelectedService(SERVICES.QMAIL) when
       getIdentity says configured=true. PROVISIONING /
       WalletSetupScreen remains the first-run-only screen.
    4. QMail.jsx: accept initialIdentity and pass it through:
         <QMailDashboard initialIdentity={initialIdentity} />
    5. QMailDashboard.jsx: replace the hard-coded John Doe default
       with userAccount initialized from props.initialIdentity (or
       null if absent). Add a useEffect that calls getIdentity() on
       mount when userAccount is null, normalizes, and sets state.
       Render a "Loading identity…" placeholder until set.
    6. WalletSetupScreen.jsx: the existing reads of
       accountData.pretty_address / accountData.email_address etc.
       continue to work because normalizeIdentityForUi() returns
       snake_case aliases. New code in this file should prefer the
       camelCase shape (accountData.address, prettyAddress, etc.).
       Either way: show "—" placeholders for any missing field;
       don't crash on null.
  Compatibility / gem-feedback:
    The AccountPane loading state must not block the NavigationPane
    RAIDA dot grid. NavigationPane runs its own echoRaida call on
    mount; nothing about FIX-03 should change that. Keep the dot
    grid alive throughout the Loading state.
  Verify:
    1. Cold start with no identity. Import a valid locker code.
       Confirm WalletSetupScreen shows the real address.
    2. Click Go to Dashboard. Confirm Account > Profile shows real
       serial number, not John Doe.
    3. Restart the app. Confirm it boots straight to the dashboard
       with the right identity (no WalletSetupScreen flash).
    4. Throughout (1)-(3), confirm the RAIDA dots in the nav pane
       remain interactive.

FIX-04 [C] (gpt-5)  Drafts reopen with empty body and recipients
  Problem:
    /db/drafts/list returns preview metadata only (subject,
    body_preview, recipient_count, timestamps, star state). The GUI
    feeds those rows directly into ComposeModal as editDraft, so the
    user opens a draft and sees no body, no recipients, and no Cc.
    Worse, hitting Save overwrites the persisted draft with the
    empty fields they just looked at.
  Files to change:
    src\qmail\screens\QMailDashboard.jsx (handleSelectEmail's
       isDraft branch ~ line 492)
  Approach (one UI model — hydrate BEFORE mount, one-shot fetch):
    Note: this is a SINGLE fetch, not a polling loop. The retry
    discussed below is bounded (at most 1-2 attempts on transient
    failure) — it's not the long polling pattern from FIX-33.
    1. In handleSelectEmail, when email.isDraft is true:
         - Set a dashboard-level "loadingDraftId" state.
         - Do NOT open ComposeModal yet.
         - try { const full = await getEmailById(email.id); }
           catch (e) {
             // gem v2: handle backend transient failures
             clear loadingDraftId
             showNotification("Could not load draft. Try again.")
             return
           }
         - On success: setEditDraft(mergedFromFetch),
           setIsComposeOpen(true), clear loadingDraftId.
    2. Show a small spinner overlay on the clicked draft row while
       loadingDraftId === draft.id, so the user sees feedback. The
       inbox list stays interactive during the fetch.
    3. ComposeModal does not change for this ticket; it sees a
       fully hydrated editDraft when it mounts.
    4. Draft-id consistency (gem v2): when ComposeModal opens with
       a hydrated editDraft, it MUST set currentDraftId from
       editDraft.id. This already happens at line 73 of the current
       ComposeModal, but verify it still works after FIX-06/07's
       composeContext refactor — a regressed currentDraftId would
       cause Save Draft to spawn duplicate rows instead of updating
       the existing draft.
  Why this model (not the modal-internal spinner alternative):
    Keeping the fetch in the dashboard means ComposeModal stays
    "props-in, behavior-out." Putting an in-modal spinner risks the
    user starting to type before hydration finishes and clobbering
    their own changes when the fetched body lands.
  Dependencies:
    Draft-cleanup-after-send (delete the source draft once it ships)
    moved to a separate ticket (see FIX-23) and explicitly blocked
    on a deleteDraft backend contract (see Backend tickets, CORE-H).
  Verify:
    1. Save a draft with body + To + Cc. Close compose. Click the
       draft in the Drafts folder. Confirm all fields repopulate.
       Edit and save. Confirm the persisted draft matches what's on
       screen.
    2. Draft-id regression: save a draft, reopen, edit the body,
       click Save Draft. Switch to the Drafts folder. Confirm there
       is still exactly ONE draft (not two — i.e. the same id was
       updated, not a new draft created).
    3. Resiliency: simulate a backend that 500s on getEmailById.
       Confirm the user sees a "Could not load draft" toast and the
       inbox list stays interactive (not stuck in a loading state).

FIX-02 [C] (opu-H14 / gem-section-B / gpt-4)  Compose attachment picker
  Problem:
    ComposeModal hard-codes attachments: [] (line 489). Paperclip is
    imported but not rendered. Backend already accepts repeatable
    attachment_file_path params and sendEmail() iterates them.
  Files to change:
    electron.cjs                          (IPC handler + fs.stat)
    preload.cjs                           (expose via electronAPI)
    src\qmail\screens\ComposeModal.jsx    (picker UI, chip list)
  Approach (use the EXISTING electronAPI bridge):
    1. In electron.cjs, register an IPC handler "compose:pickFiles":
         ipcMain.handle('compose:pickFiles', async () => {
           const r = await dialog.showOpenDialog({
             properties: ['openFile', 'multiSelections'] });
           if (r.canceled) return [];
           // Stat each file in the main process so the renderer
           // doesn't need fs access:
           return Promise.all(r.filePaths.map(async (p) => {
             const stat = await fs.promises.stat(p);
             return { path: p, name: path.basename(p),
                      size: stat.size };
           }));
         });
       Handle the canceled case explicitly (return []), not undefined.
    2. In preload.cjs, EXTEND the existing electronAPI exposure
       (do NOT add a second bridge):
         contextBridge.exposeInMainWorld('electronAPI', {
           ...existingMethods,
           pickAttachments: () =>
             ipcRenderer.invoke('compose:pickFiles'),
         });
       If electronAPI doesn't already exist, add it; otherwise merge.
    3. In ComposeModal.jsx:
       - Add useState attachments = [] (array of {path, name, size}).
       - Add an "Attach" button in the footer next to Save Draft,
         icon = Paperclip. onClick:
           const picked = await window.electronAPI?.pickAttachments();
           if (!picked || picked.length === 0) return; // canceled
           // De-duplicate: don't add paths already in the list
           const known = new Set(attachments.map(a => a.path));
           const additions = picked.filter(p => !known.has(p.path));
           setAttachments([...attachments, ...additions]);
       - Render staged files as removable chips above the body
         (filename + size + X to remove). Show total size.
       - In handleSend, pass attachments.map(a => a.path) into
         emailData.attachments instead of [].
    4. Browser fallback: if window.electronAPI is undefined, render
       the button but disable it with title "File attachments
       require the desktop build."
  Edge cases:
    - Paths with spaces / unicode: the IPC handler returns strings
      verbatim; URLSearchParams in sendEmail handles the escape.
      Test with a filename containing a space and a unicode
      character.
    - Cancelled dialog: handler returns []; UI must check for the
      empty array AND defensively handle a null/undefined return
      (in case showOpenDialog rejects). gem v2: do NOT push an
      empty array into state. The snippet above handles this.
    - Re-picking the same file: gem v2 — de-duplicate by path so
      the staged list doesn't accumulate dupes when a user opens
      the picker twice and reselects a file already attached.
    - fs.stat failure (file deleted between dialog and stat): catch
      per file in the IPC handler, drop just that one, log a warning.
    - Backend filesystem access: the backend reads
      attachment_file_path from the host filesystem. In the packaged
      build, paths returned by Electron's dialog point at the host
      OS — confirm the backend process can read them (same user
      context). If not, this needs a staging-upload endpoint
      (escalate to CORE-I, see Backend tickets).
  Verify:
    1. Send a message with one .pdf, one .png, and one
       filename-with-space.txt. Confirm the recipient sees all three
       with correct names and content.
    2. Open the picker, cancel — confirm no error and no chip added.
    3. Build and run the packaged binary; repeat step 1.

FIX-13-0B [C] (opu-H2)  First-run import error messages collapse
  Pulled forward from Phase 1 because it pairs naturally with the
  Phase-0A first-run identity work; without it FIX-03 lands with no
  honest error path. Numbered FIX-13-0B to preserve the original
  number.

  Problem:
    handleImport sets error = result.error || 'Locker is empty or
    invalid' for every failure. No differentiation between 400, 404,
    5xx, and network errors.
  Files to change:
    src\screens\ServiceSelectionScreen.jsx (handleImport)
    src\api\qmailApiServices.js (importCredentials — already
       exposes response.status; promote to structured error)
  Approach:
    1. importCredentials() already returns response.status. Promote
       its error return to { code, message, raw }.
    2. handleImport switch on code:
         400 → "That doesn't look like a valid locker code. Check
               for typos and try again."
         404 → "We couldn't find anything in that locker. It may
               already have been imported, or the code may be wrong."
         5xx → "The QMail backend returned an error. Try again
               in a moment."
