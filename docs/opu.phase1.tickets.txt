WORKING CONVENTIONS
===================
Same as Phase 0. Quick reminders:

- Default to no comments. Only add a comment when WHY is non-
  obvious — a constraint, an invariant, a fix for a specific bug,
  or behavior that would surprise a reader. Don't explain WHAT
  the code does — well-named identifiers handle that. Don't write
  "added for X flow" or "fixes #123" — that belongs in the PR
  description, not the source.

- Every ticket ships with:
    * npm run build passes
    * Per-file ESLint at parity-or-better with pre-change baseline
    * A batch summary at docs\opu.usability.batchN.summary.txt
      following the same shape as the Phase 0 summaries
    * Reviewer-focus questions called out for each non-obvious
      decision

- Wait for BOTH reviewers (gem + gpt) before considering a batch
  done. gpt is the more substantive reviewer; gem's approval alone
  is not sufficient. gpt has caught real bugs in every batch.

- Don't add new ESLint baseline errors. The codebase doesn't use
  prop-types anywhere; if you add a component, add
  // eslint-disable-next-line react/prop-types on its function
  signature.

- normalizeIdentityForUi returns BOTH camelCase and snake_case for
  every field. This is the permanent convention. Don't refactor
  consumers to camelCase-only.

- "Coming Soon" dead controls are visibly disabled, NOT silently
  no-op'd. Delete Account stays hidden entirely.

- Do NOT fake server state in the GUI (no fake Sent rows, no fake
  Mark-as-Read persistence, no synthesized identity health).
  Wait for the backend.

- The composeContext refactor (FIX-05.5) is a HARD CUTOVER per
  product decision — drop the old replyTo / editDraft props
  entirely. This is a beta with no external consumers; no
  compatibility shim.

FIX-05.5 [H] (third-pass feedback)  Prep: composeContext refactor
  Why this is its own ticket:
    v3 buried the ComposeModal refactor inside FIX-06 and FIX-07.
    That's a risky shape — the modal is touched by FIX-04 (draft
    hydration), FIX-22 (send gating), FIX-23 (delete-on-send),
    FIX-27 (post-success disable), FIX-39 (autosave), and others.
    A refactor that changes its prop contract mid-stream causes
    cascading regressions in tickets that ride alongside.
    Make the refactor its own prep ticket, with a regression
    checklist, BEFORE Forward/Reply All land on top of it.

  Architecture target:
    Rather than overloading replyTo with progressively more
    "variants", introduce an explicit composeContext object that
    ComposeModal consumes uniformly:

      composeContext = {
        mode: "new" | "reply" | "replyAll" | "forward" | "draft",
        sourceEmail: <email being replied-to/forwarded/edited>,
        ownIdentity:  <from FIX-03 normalized identity>,
        draftId:      <if mode === "draft", the draft's id>,
      }

    ComposeModal derives subject prefix, body prefill, and recipient
    prefill from `mode`. The current replyTo and editDraft props
    become internal mode branches.

  Files to change:
    src\qmail\screens\ComposeModal.jsx (accept composeContext;
       remove replyTo and editDraft props)
    src\qmail\screens\QMailDashboard.jsx (build composeContext at
       each opener: handleOpenCompose, handleReply, draft click)
  Approach:
    1. Add a single composeContext prop. Remove the old replyTo /
       editDraft props entirely — this is a beta with no external
       consumers, so a hard cutover is fine. Update every call site
       in the same patch. (v3 proposed a compatibility shim; v4
       drops it per product call.)
    2. ComposeModal's mounting useEffect switches on
       composeContext.mode:
         "new":      blank fields, default storage
         "reply":    derive To from sender, "Re: " subject, quoted body
         "replyAll": same plus Cc minus own identity (FIX-07 details)
         "forward":  "Fwd: " subject, body quoted, To blank (FIX-06)
         "draft":    pre-hydrated fields from the hydrated editDraft
       The currentDraftId state is set from composeContext.draftId
       when mode === "draft", preserving the draft-id-consistency
       behavior FIX-04 verified.
    3. QMailDashboard:
         openCompose({ mode: "new", ownIdentity })
         openReply(email)      → mode: "reply"
         openReplyAll(email)   → mode: "replyAll"  (FIX-07)
         openForward(email)    → mode: "forward"   (FIX-06)
         openDraft(hydrated)   → mode: "draft", draftId: hydrated.id
  Regression checklist (third-pass requirement):
    After landing FIX-05.5 and before FIX-06/07/etc. start:
    [ ] New compose: open, type, send (mode: "new")
    [ ] New compose: open, save as draft, close, verify draft
        appears with correct content
    [ ] Reply: open from inbox, send (mode: "reply")
    [ ] Draft hydration (from FIX-04): click draft, edit, save,
        confirm same draft is UPDATED (not duplicated — FIX-04
        regression check #2)
    [ ] Attachment send (from FIX-02): attach a file, send
    [ ] Send-gating (from FIX-22): preflight still gates correctly
    [ ] Post-success disable (from FIX-27): buttons disabled through
        the 1500ms window
    Pre-implementation: if any of these check items already fail
    on current main (i.e. the ticket they belong to hasn't landed
    yet), note "n/a — not yet implemented" rather than treating it
    as a regression.
  Dependencies:
    Blocks FIX-06, FIX-07. Should land AFTER FIX-04 so the draft-
    hydration model is already settled when the refactor happens.
  Verify:
    Complete the regression checklist above. Every applicable item
    must pass before FIX-06 can be merged on top.

FIX-15 [H] (opu-H32)  Durable Sign Out
  Problem:
    Today there is no sign-out path. Per product decision, the
    intended behavior is DURABLE sign-out: after Sign Out, restarting
    the app should land on ServiceSelectionScreen, not auto-restore
    the previous identity.
  Why durable not session:
    App.checkIdentity() runs on every boot and routes any configured
    identity into PROVISIONING or QMAIL automatically. A session-
    only sign-out would be silently undone on restart — confusing
    and a security surprise.
  Files to change:
    src\App.jsx (skip-auto-restore flag check in checkIdentity)

         "Use existing local identity"

       locker-import step.

FIX-17 [H] (opu-H40)  New-mail toast carries no sender preview
  Files to change:
    src\qmail\screens\QMailDashboard.jsx
  Approach:

       notification poller already runs every 10s and tracks new
       items. When a new notification arrives, build the toast from

    2. Only fall back to getMailList('inbox', 1, 0, 'newest') when

       select the matching pending row.
    4. Keep the "N new emails" summary form when growth > 1.
  Why this matters (gpt-13):
    Pending mail is not in the inbox DB list yet, so v1's "fetch
    latest 1 inbox row" would miss the actual new item. Using
    notification data first matches the GUI's actual data flow.
  Verify:

    "New mail from <sender>" within the next 10s poll and is
