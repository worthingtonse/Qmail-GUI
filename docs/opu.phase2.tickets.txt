WORKING CONVENTIONS
===================
Same as Phase 0 / Phase 1. Highlights:

- Default to no comments. Only add a comment when WHY is non-obvious
  (a constraint, an invariant, a fix for a specific bug, or behavior
  that would surprise a reader). Don't explain WHAT — well-named
  identifiers handle that.

- Every ticket ships with:
    * npm run build passes
    * Per-file ESLint at parity-or-better with the pre-change
      baseline
    * A batch summary at docs\opu.usability.batchN.summary.txt
      (or gpt.usability.batchN.summary.txt if GPT is implementer)
      following the shape of the Phase 0 / Phase 1 summaries
    * Reviewer-focus questions called out for each non-obvious
      decision

- Wait for BOTH reviewers (gem + gpt) before considering a batch
  done. gpt is the more substantive reviewer; gem's approval alone
  is not sufficient. gpt has caught real bugs in every Phase 0/1
  batch.

- Don't add new ESLint baseline errors. The codebase still has a
  repo-wide lint failure (73 errors / 4 warnings — see
  docs\cla.bugs.txt BUG-36). Phase 2 work must keep the touched-file
  gate clean and should not GROW the baseline.

- normalizeIdentityForUi returns BOTH camelCase and snake_case for
  every field. This is the permanent convention. Don't refactor
  consumers to camelCase-only.

- "Coming Soon" dead controls are visibly disabled, NOT silently
  no-op'd.

- Do NOT fake server state in the GUI (no fake Sent rows, no fake
  mark-as-read persistence, no synthesized identity health). Wait
  for the backend.

- FIX-22 + FIX-31 is a HARD CUTOVER coupling per the master plan —
  do not split.

FIX-18 [M] (gpt-6)  Reconcile Starred: flag OR folder, not both
  Approach:
    The preferred model — "Starred as virtual view backed by
    is_starred" — REQUIRES backend support. /db/messages/list must
    accept a starred=true filter (or expose a dedicated starred-list
    endpoint). The GUI cannot implement this correctly with local
    filtering, because pagination would silently drop starred
    messages on later pages.
  Dependencies:
    Backend ticket CORE-J: add starred=true filter to
    /api/qmail/db/messages/list.
  Plan:
    (Until CORE-J)
    Remove "Move to Starred" from the ReadingPane move dropdown so
    users don't get the impression that Star and Move-to-Starred are
    separate features. Keep the folder=4 nav link working for now —
    it shows whatever the backend has stored under folder=4.
    (After CORE-J)
    Drop folder=4 from the nav. Drive the Starred view from a
    /db/messages/list?starred=true call.

FIX-19 [M] (gpt-11 / gem-recommendation-2)  Attachment safety
  Approach:
    1. getEmailAttachments() in qmailApiServices.js: map the
       dangerous and warning fields through (they're dropped today).
    2. ReadingPane.jsx: if dangerous === true, render a
       visually-distinct warning chip next to the filename using
       the ShieldAlert icon (lucide-react). Yellow/red treatment.
       If a warning string exists, show it as a tooltip.
    3. QMailDashboard.handleDownloadAttachment: pass attachmentName
       through to downloadMailAttachment as the third argument.
       The current call drops the name, so dangerous-extension
       files save as "downloaded_file" with no clue about their
       real type — the worst possible failure mode.
    4. Confirm modal before downloading a "dangerous" attachment.
       Use the existing modal infrastructure, not window.confirm.
       Modal text: "This file is flagged as potentially dangerous.
       Save anyway?"
  Verify:
    Mock an attachments-list response with dangerous=true and a
    warning string. Confirm the chip, tooltip, confirm modal, and
    real-name save.

FIX-20 [M] (gem-v2 / gpt-10)  Unified Refresh action
  Product decision: one "Refresh" button does the whole stack.
  Non-technical users don't care about RAIDA echo vs beacon ping —
  they want a button that says "go get my mail." Keep the
  underlying helpers separate at the API layer so a future debug
  surface can split them again. SUPERSEDES the earlier gpt-v1
  recommendation to split.
  Approach:
    1. Rename "Check Connection" to "Refresh." RefreshCw icon stays.
    2. handleRefresh in QMailDashboard runs in order:
         a. checkMailNow()            // POST /api/qmail/net/beacon/ping
         b. echoRaida()               // GET  /api/raida/echo
         c. getMailNotifications()    // GET  /api/qmail/db/notifications/list
         d. loadMailCounts()
         e. loadEmails(currentFolder)
       Each step in its own try/catch — one failure should not
       block the next.
    3. Add a checkMailNow() helper in qmailApiServices.js for
       POST /api/qmail/net/beacon/ping. Rename pingQMail() to
       peekBeacon() for clarity (it calls /beacon/peek, read-only).
    4. Spin the RefreshCw icon throughout the full chain so the
       user sees ONE operation, not five.

FIX-21 [M] (opu-M11)  Pending-mail click semantics
  Approach:
    Pick one: auto-download on click (remove the manual button) OR
    manual button only (don't auto-fire). Recommendation is the
    manual model — it respects cost-per-decrypt awareness.

FIX-22 [M] (opu-M16 / gpt-12)  Compose send-gating UX
  MUST SHIP IN THE SAME PATCH AS FIX-31 (remove getParityServer).
  ComposeModal.checkNetworkStatus() currently calls
  getParityServer(); removing it without fixing the gating logic
  would leave a broken import.
  Approach:
    1. Initialize canSend = null ("checking…"); Send button label
       "Checking network…", disabled.
    2. checkNetworkStatus result sets canSend true / false. Drop
       the getParityServer() call entirely; only the RAIDA-
       availability check (>= 6 reachable) remains. See FIX-31.
    3. On false, add a Retry button that re-runs checkNetworkStatus.
    4. Soften the gate: warning banner instead of disabled Send;
       user can override with "Send anyway." The backend remains
       the final authority.
  Verify:
    Block /raida/echo. Confirm Send shows "Checking network…" then
    warning-with-Retry. Restore network and Retry; confirm normal
    behavior returns.

FIX-23 [M]  Delete the source draft on successful send-from-draft
  BLOCKED on CORE-H (deleteDraft endpoint). DO NOT simulate
  deletion by writing an empty draft via updateDraft.
  Approach (once CORE-H lands):
    1. Add deleteDraft() helper in qmailApiServices.js.
    2. In ComposeModal.handleSend success branch: when
       currentDraftId is set, call deleteDraft(currentDraftId)
       before closing the modal. Refresh drafts afterward.

FIX-24 [M] (opu-M8 + M9)  Mark Unread + Archive buttons in ReadingPane
  Approach:
    Two small buttons in the reading-pane action row. Mark Unread
    calls handleMarkAsRead(id, false). Archive calls
    handleMoveEmail(id, 'archive'). Both handlers already exist —
    pure UI surface.

FIX-25 [M] (opu-M12 / gem-v2-section-6)  Search scope + result-cap honesty
  Approach:
    1. Search scope. Ship the cheap option first:
       Change the placeholder to "Search all mail..." so the user
       knows. (Folder-scoped search is the more correct option but
       requires backend support — defer.)
    2. Result cap. searchEmails() currently hard-codes limit=50.
       When result.length === 50, render a small notice above the
       results: "Showing top 50 results. Refine your search to see
       more." Without this, a user searching for an old message
       will see 50 hits, none of them the target, and conclude the
       message is gone.

FIX-33 [M] (opu-M43 + M44 / gem-v2-section-1)  Send-failure UX + poll resiliency
  Approach:
    1. Cap the send-poll loop at 60 seconds (wall-clock deadline,
       not iteration count). On timeout, mark sendingStatus="failed"
       with text "Send is taking longer than expected. Check Sent
       in a few minutes."
    2. Per-call try/catch: wrap each await getTaskStatus call
       individually. On exception, do NOT immediately fail the
       send — the backend may transiently 5xx while the task is
       still in flight. Use a small retry counter (e.g. 3
       consecutive failures) before declaring the poll
       unrecoverable. The 60s deadline still applies.
    3. On final failure (timeout OR retry-counter exhausted): push
       the error to the dashboard-level notification system so it
       persists if the user closes the modal.
    4. The existing cancelledRef.current guard must still break the
       loop on modal close — verify after the refactor.

FIX-34 [M] (opu-M45)  Unify the three notification systems
  Approach:
    Migrate QMailDashboard's setNotification and AccountPane's
    showNotification to the NotificationProvider already wrapping
    App.jsx. One visual style, one timeout policy, one priority
    queue.
  Caution:
    The setNotification objects added in FIX-17 (Batch 8) carry
    targetPendingGuid / targetEmailId for clickable toasts.
    Preserve those payloads in the unified system.
