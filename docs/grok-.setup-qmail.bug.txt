================================================================================
2. Root cause (two independent layers)
================================================================================

LAYER 1 — SOURCE FILES ARE MOVED BEFORE AUTH  [PRODUCT / CODE — HIGH]
--------------------------------------------------------------------
cmd_deposit.c deposit pipeline (deposit_execute):

  Phase 1 MOVE   →  fs_move_file from external path → Default\Import
  Phase 2 UNPACK
  Phase 3 POWN   →  authenticate with RAIDA (may mark counterfeit)
  Phase 4 GRADE  →  Bank / Fracked / Counterfeit / Limbo
  Phase 5+       receipt / legacy upgrade

**Move is permanent and happens first.** Selecting Desktop's Bank folder
as the import source **removes the .bin files from Desktop** before RAIDA
says whether they are good. After grade:

  - If Bank/Fracked: coins live in QMail Default (Desktop still empty)
  - If Counterfeit: coins live in QMail Default\Counterfeit (Desktop empty)

Desktop then shows **Balance Adjustment −11 → 0** because the Bank files
are gone (Desktop is folder-based; no files = zero balance). This matches
Pierre's report exactly: "disappeared from my Desktop wallet altogether."

This is not a Desktop bug. QMail deposit is designed as a **move import**,
not a copy. The UI does not warn that the source folder's coins will leave
the other program. For a support walkthrough (Pierre → Michelle), that is
the catastrophic UX failure: even a successful import looks like theft from
Desktop; a failed (counterfeit) import looks like destruction.


LAYER 2 — ALL 11 NOTES GRADED COUNTERFEIT  [AUTH OUTCOME — NEEDS LOG]
--------------------------------------------------------------------
Deposit totals drove GUI warning via depositReceipts.js:

  counterfeit_count (+ legacy_counterfeit_count) → "11 notes were counterfeit"

Then onboarding always calls provision-from-default:

  wallet_find_highest_eligible_coin(Default, denom 0..4)  // Bank + Fracked only
  → RESULT_NOT_FOUND
  → HTTP 422 "Default has no QMail identity coin worth at least 1 CC"
     (exact string in api_handlers_qmail_identity.c ~434)

Counterfeit notes are **not** eligible for Mail identity. So identity setup
cannot finish. "Retry Identity Setup" only re-POSTs provision; it does **not**
re-read the Desktop Bank (already empty) and cannot succeed without a new
authentic ≥1 CC coin in Default Bank or Fracked.

Why RAIDA/POWN called them counterfeit is **not proven** without Pierre's
QMail main.log / deposit receipt for that task. Candidates:

  (a) True counterfeit / already spent on network (notes last moved 2024).
  (b) Network/RAIDA degradation → excessive fails → grade Counterfeit
      (fail ≥ 13). Same day as other RAIDA trouble on lab installs.
  (c) Encryption-related POWN path (see §3) — possible, not confirmed.
  (d) Legacy upgrade path marking counterfeit (legacy_counterfeit_count)
      if notes were old format and upgrade failed.


================================================================================
3. Encryption hypothesis (reporter + last-build changes)
================================================================================

Pierre: "may have something to do with … checking if the encryption."

Two different "encryption" systems must stay separate:

A) Type 10 **file** encryption (recent GUI/core work)
   - On-disk encrypted .bin; write-gate; password / key_state APIs.
   - Classic CloudCoin Desktop Bank coins are almost always **plaintext**
     legacy/current unencrypted bins — not Type 10.
   - A Type 10 failure typically surfaces as read/key errors, not a clean
     "N notes were counterfeit" deposit warning.
   - **Ruled unlikely as the direct cause of the counterfeit banner**
     unless deposit mis-maps Type 10 read failures into counterfeit counts
     (no evidence of that mapping in depositReceipts.js — it only reads
     counterfeit_count / legacy_counterfeit_count from deposit totals).

B) RAIDA **wire** encryption (POWN / encryption key coin)
   deposit_phase_pown (cmd_deposit.c ~521–556):
     1. encryption_key_select(target wallet)
     2. else encryption_key_select_any_wallet
     3. if still none → **POWN SUM unencrypted** ("first deposit mode")
     4. else regular encrypted POWN with that key coin

   On a brand-new QMail install with empty Default, first deposit usually
   hits (3) POWN SUM — no Type 10, no helper key.

   Hazard if **any** registered wallet already has a bad/counterfeit key coin:
   select_any_wallet may pick it → encrypted POWN with broken key → mass
   RAIDA reject → looks like all counterfeit. Recent encryption-key /
   health changes could make this more common. **Plausible but unproven**
   without log lines:
     "POWN phase: Using encryption key coin SN …"
     vs "using POWN SUM (unencrypted)"
     and "BAD ENCRYPTION KEY" / DetectHash counterfeit patterns seen on
     other installs (e.g. Client16).

Legacy upgrade path (deposit Phase 5) also has encryption-key retry with
ENC_TYPE_NONE when upgrade fails for missing key — separate from Type 10.

**Conclusion on encryption:** Do not dismiss; check Pierre's main.log for
POWN SUM vs key-coin POWN and any BAD ENCRYPTION KEY lines. Do **not**
blame Type 10 file encryption without evidence. The **move-before-auth**
behavior alone fully explains "disappeared from Desktop" regardless of
why grade said counterfeit.

4. Causal chain (Pierre incident)
================================================================================

  1. Fresh QMail install; Set Up QMail → Folder → Desktop **Bank** folder.
  2. deposit_phase_move: 11 .bin files **leave Desktop Bank** → Default\Import.
  3. Desktop balance → 0 (Balance Adjustment −11 at ~2:00 PM).
  4. POWN + GRADE: all 11 → Counterfeit (reason TBD — see log ask).
  5. GUI: "11 notes were counterfeit".
  6. provision-from-default: no Bank/Fracked ≥1 CC → 422 identity error.
  7. Retry Identity Setup cannot fix; Desktop folder still empty.
  8. Coins not "deleted from the universe" if they landed in
     <QMail Client_Data>\Wallets\Default\Counterfeit\ — but they are
     **gone from Desktop** and **unusable as identity/spend** until
     re-evaluated / recovered by support tools.


================================================================================
5. Why this is dangerous for Michelle (and demos)
================================================================================

  - Natural workflow for onboarding help: "point QMail at your Desktop Bank."
  - That **empties** the Desktop wallet even on success.
  - On all-counterfeit (true or false), Desktop is empty AND QMail has no
    identity — worst case for a non-technical user ("my coins disappeared").
  - No in-modal recovery: Retry does not re-import; Cancel leaves them stuck.
  - Matches onboarding dead-end class (fab.onboarding-review FINDING 2),
    worsened by source-folder consumption of a **live second product**.

7. What is NOT the problem

================================================================================
10. Recommended fixes (NOT applied)
================================================================================

P0 — Stop silent destruction of other wallets' Bank
  - Folder/Files deposit: **copy** by default when source is outside
    Client_Data, OR require explicit confirm:
      "These files will be MOVED out of the other program. Continue?"
  - Better: copy into Import, leave originals until grade success; only
    then optional delete — or never delete external sources from UI import.

P0 — Onboarding when depositAddedNothing / all counterfeit
  - Do not call provisionIdentity().
  - Do not offer only "Retry Identity Setup".
  - Offer "Import different coins" / re-enable Folder|Files|Locker.
  - Explain: "Source files were moved into QMail. Counterfeit notes cannot
    become your identity. Check Default\\Counterfeit or restore from backup."

P1 — Encryption/POWN diagnostics
  - Log and surface whether POWN SUM vs key-coin was used.
  - If key-coin POWN fails massively, fall back to POWN SUM once and/or
    refuse to use a key that DetectHash marks bad (avoid false counterfeit).
  - Confirm Type 10 write-gate never classifies unreadables as counterfeit.

P1 — Demo / first-run copy
  - Launch-screen help: do not select another app's live Bank without a copy.
  - Optional "Import from CloudCoin Desktop" wizard that copies Bank first.
