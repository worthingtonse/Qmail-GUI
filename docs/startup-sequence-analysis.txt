QMAIL-GUI STARTUP SEQUENCE ANALYSIS
================================================================================

ROOT CAUSE OF STARTUP DELAY
================================================================================

The backend (core.exe) is BLOCKING on RAIDA health checks before accepting
HTTP requests. The HTTP server does not start listening until ALL initialization
is complete. This is the critical path:

BLOCKING SEQUENCE (rest_core/api_src/main_rest.c):

1. Boot Echo (4+ seconds)
   - File: main_rest.c line 1152-1199
   - Timeout: raida_policy_timeout(RAIDA_TIMEOUT_ECHO) = 4000ms (DEFAULT)
   - Operation: Runs echo ping against all 8 RAIDA servers in PARALLEL
   - Config: src/raida_policy.c line 75 (index 1)
   - Blocking: YES (waits for all to respond or timeout)

2. Health Manager Start (milliseconds)
   - File: main_rest.c line 1210
   - Impact: Minimal, just mutex init

3. Boot Health Check (seconds, varies by wallet count)
   - File: main_rest.c line 1219-1247
   - Operation: Checks all registered wallets for coin health
   - Impact: HIGH if wallets exist, NONE if empty
   - Blocking: YES

4. Encryption Check (fast)
   - File: main_rest.c line 1251
   - Impact: Low, local file scan

5. Unprocessed Coins Scan (seconds)
   - File: main_rest.c line 1254-1284
   - Operation: Scans Suspect and Import folders
   - Impact: Medium (depends on folder count)
   - Blocking: YES

ONLY AFTER all above complete:

6. HTTP Server Init (fast)
   - File: main_rest.c line 1291
   - Operation: Creates socket, binds to port

7. HTTP Server Start (immediate)
   - File: main_rest.c line 1308
   - Operation: Starts accept() thread
   - Message: "REST API server running on http://..." appears here

FRONTEND TIMEOUT
================================================================================

Frontend waits 15 seconds for backend to respond:
- File: src/App.jsx line 61
- Deadline: Date.now() + 15000 (15 seconds)
- Probe: GET /api/system/version-check every 300ms

HTTP CLIENT TIMEOUT
================================================================================

Backend HTTP client read timeout: 15 seconds
- File: api_src/http_server.c line 22
- Define: HTTP_READ_TIMEOUT_MS = 15000
- Applies to: Per-socket read operations, not overall request


OPTIMIZATION STRATEGIES (in order of impact)
================================================================================

PRIORITY 1: SKIP BOOT HEALTH CHECK IF NO WALLETS
   - File: main_rest.c lines 1219-1247
   - Impact: 3-5 seconds savings (if no wallets exist)
   - Changes: Check wallet_registry_count() first; skip entire block if 0
   - Risk: Low (health check is optional on boot)

PRIORITY 2: PARALLELIZE BOOT INITIALIZATION
   - Run boot echo + unprocessed coins scan in parallel threads
   - Start HTTP server AFTER echo only (don't wait for health check)
   - Health check runs in background after server is ready
   - Changes: main_rest.c restructure
   - Risk: Medium (requires threading)

PRIORITY 3: REDUCE ECHO TIMEOUT ON BOOT
   - Lower raida_echo_attempt_timeout_ms from 4000 to 2000ms
   - Config: src/raida_policy.c line 75 (index 1) from 4000 to 2000
   - Or: Add rest_core.conf setting to override default
   - Risk: Low (echo is for health check, not critical path)

PRIORITY 4: MAKE BOOT ECHO NON-BLOCKING
   - Move echo to background thread after HTTP server starts
   - Return qmail_health_init() without seed data (use defaults)
   - First QMail operation will re-check anyway
   - Changes: main_rest.c structure + qmail_health initialization
   - Risk: Medium (changes initialization order)

PRIORITY 5: MOVE HEALTH CHECK TO BACKGROUND (SAFEST)
   - Start HTTP server after echo only
   - Run boot health check in background thread
   - API remains responsive while check completes
   - Changes: Spawn thread at line 1217, remove blocking waits
   - Risk: Low (health check is already idempotent)

================================================================================

- Frontend probe timeout: 15 seconds
- Boot sequence includes untraced wallet/coin scans (unknown duration)

With sound file fix applied but still slow, suggests the issue is backend
initialization sequence, not sound loading.


RECOMMENDATION
================================================================================

For immediate improvement (minimal code changes):
  1. Check if wallet_registry_count() > 0 before boot health check
  2. If 0, skip the entire block (saves 3-5 seconds if no wallets)
  3. Move remaining checks to background threads after HTTP server starts

This requires changes to main_rest.c around lines 1217-1284 to defer health
checks to a background thread spawned AFTER http_server_start().
