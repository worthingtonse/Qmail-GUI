FIX-01: Pending-message download body hydration
================================================
Bug:
  handleDownloadMail read responseData.body from
  POST /api/qmail/net/messages/download, but that endpoint returns
  metadata (email_id, sender_sn, stripes_*), not the decrypted body.
  Result: clicking an encrypted message left the reading pane empty.

Fix:
  - Extracted a new hydrateDownloadedEmail(emailId) helper that
    calls getEmailById + getEmailAttachments in parallel and retries
    up to 3 times (500ms / 1000ms backoff) with try/catch per
    attempt — handles the brief DB-indexing lag the backend can have
    right after a successful network download.
  - Rewrote handleDownloadMail to branch:
      isLocalEmailId (32-char hex, not "pending-")
         → read direct from local DB (fast path for already-
           downloaded messages — no network)
      else (pending guid)
         → POST /net/messages/download (returns metadata only)
         → take responseData.email_id
         → hydrate via getEmailById + getEmailAttachments
  - If hydration fails after all retries, the pending row stays in
    pendingMails so the user can retry by clicking it again. We do
    NOT leave selectedEmail half-loaded.
  - Toast text differentiates the failure modes:
      "Failed to decrypt message."   — download itself failed
      "Service temporarily unavailable. Try opening the message
        again."                       — download ok, hydrate failed
      "Download failed"               — fell into the catch (network)

Decisions worth flagging for review:
  1. The dual-path branch (local short-circuit vs. pending hydrate)
     is preserved from the original code. The original short-circuit
     was correct for already-downloaded messages and there was no
     reason to remove it.
  2. The local-DB short-circuit ALSO now fetches attachments
     (originally it only fetched the body). Without this, opening
     an already-downloaded message from the pending-mail click path
     would have shown the body but cleared the attachment list.
  3. setPendingMails now matches BOTH identifier and email_id, in
     case the download path returns an email_id that differs from
     the guid the user clicked. Defensive, cheap.
  4. Added loadMailCounts() after the inbox refresh so the unread
     badge updates immediately (the original code only called
     loadEmails). Small UX improvement bundled in.

Edge cases tested in code review:
  - User clicks a different message mid-hydrate: the existing
    isDownloadingItem guard still works (set at the top of the
    handler, cleared in finally).
  - Network 5xx during hydrate: each attempt is try/catch-wrapped,
    so the loop continues to the next retry rather than blowing up.
  - User clicks a message that's already-downloaded but whose body
    is empty in the DB: contentRes.success is true but data.body is
    falsy, so the if-block falls through and the function exits via
    "Failed to decrypt message." That matches the original behavior.

What this fix does NOT do:
  - Doesn't add a manual "Download" button to the reading pane
    (FIX-21 in the plan addresses the auto-vs-manual question).
  - Doesn't change the "🔒 Encrypted Message" placeholder text in
    the inbox row (FIX-11a addresses that).
  - Doesn't backfill missing attachment dangerous/warning flags
    (FIX-19 addresses that).
  - Doesn't fix the search-result hydration path (different code
    path, different ticket).

FIX-16-0A: Truly disable dead Security / Settings controls
==========================================================
Bug:
  Six controls in AccountPane were rendered with onClick handlers
  that just console.log()'d (Change Password, 2FA, Backup Wallet,
  Delete Account) or flipped local-only state nothing read (Email
  Notifications, Dark Mode, Auto-Sync, Biometric). The rows looked
  fully interactive: pointer cursor on hover, click registered.
  Per v3 third-pass feedback: not just no-op'd — truly disabled.

Fix:
  - Added two small helper components at module scope:
      ComingSoonAction (for security rows)
      ComingSoonToggle (for settings toggles)
    Both apply the same disabled treatment:
      style: opacity 0.5, cursor: default, pointerEvents: none
      no onClick handler at all
      aria-disabled="true"
      tabIndex={-1}            (Tab nav skips them)
      title="This feature is on the roadmap."
      Visible "Coming Soon" badge next to the title
  - The toggle <button> also gets the native `disabled` attribute
    in addition to aria-disabled.
  - Replaced all four security rows + four toggle rows with calls
    to these helpers. JSX shrunk from ~140 lines to ~25.
  - Delete Account: removed entirely (no Coming Soon badge, no
    placeholder row). Per the plan, this is a safety-critical
    control that doesn't exist and shouldn't be tempting to click.
  - Removed accountSettings state (no longer read anywhere).
  - Removed handleSettingToggle and handleSecurityAction handlers
    (no longer referenced).

Decisions worth flagging for review:
  1. Inline styles for the Coming-Soon visuals instead of new CSS
     classes. Rationale: the existing .security-action and
     .setting-item CSS classes have hover/cursor rules baked in, and
     fighting them with !important would be ugly. Inline wins.
     If the team prefers a CSS-class approach, the move is small:
     add .coming-soon { opacity: 0.5; ... } and reference it from
     the helpers.
  2. Sign Out was NOT added in this batch. That's FIX-15 / FIX-15b,
     a Phase 1 ticket with backend interactions (skipAutoRestore
     flag, re-entry path). 0A only removes the dead controls.
  3. Delete Account hidden, not greyed out. Per the plan: "a safety-
     critical control that doesn't exist should not be tempting
     to click."
  4. The four <ComingSoonToggle> rows still render the toggle-switch
     visually (greyed out, fixed in the "off" position). Could
     instead replace them with a static "Coming Soon" pill and no
     toggle. The current approach preserves the visual real estate
     and the design language — when these get implemented, the
     toggle just becomes live.
  5. Inline `eslint-disable-next-line react/prop-types` on each
     helper component. Rationale: the codebase doesn't use
     prop-types anywhere (not even installed as a dep — checked
     package.json), and every other component has the same lint
     violations sitting in the baseline. Matching the existing
     pattern with localized disables on my new code is honest.

Follow-up (gem batch-1 review)
==============================
Date: 2026-05-21
Reviewer: D:\Code\src\JavaScript\Qmail-GUI\docs\gem.usability.batch1.review.txt
Verdict was "Approved with minor UX observations." Three actionable
items, all in FIX-01. None in FIX-16-0A.

Patches applied:

1. List flicker fixed.
   Before: pending row dropped from pendingMails, then async
     loadEmails() refreshes — leaves a visible gap in displayEmails.
   After: build a hydratedRow synchronously from the hydrate
     response and insertOrUpdate it into emails BEFORE dropping
     from pendingMails. loadEmails() then replaces it with
     canonical server data. No more gap.
   Implementation note: setEmails callback does a findIndex
     against id/guid/hydratedId — replaces in place if the row was
     already present (local-DB short-circuit case where the row is
     already in emails), otherwise prepends. loadEmails refresh
     then resorts.

2. Ineffective ID comparison removed.
   Before: setPendingMails filter compared m.guid against both
     identifier AND hydrated.body.email_id. The second check was
     a no-op (guid = network ID, email_id = local DB ID, different
     namespaces).
   After: filter only on identifier (the actual guid the user
     clicked). Comment added explaining why.

3. Local-DB short-circuit now uses hydrateDownloadedEmail.
   Before: short-circuit called getEmailById + getEmailAttachments
     directly with no try/catch and no retry. Inconsistent with the
     pending path.
   After: short-circuit calls hydrateDownloadedEmail(identifier)
     (same retry-with-backoff helper as the pending path) inside
     its own try/catch. On failure it falls through to the network
     download path, which is the previous fallback behavior — just
     more resilient about deciding when to fall through.

Decisions intentionally NOT changed:
- CSS approach (gem said inline acceptable here).
- Toast wording (gem confirmed "Service temporarily unavailable").
- ComingSoonAction/ComingSoonToggle helpers (no gem feedback).

Follow-up #2 (gpt batch-1 review)
=================================
Date: 2026-05-21
Reviewer: D:\Code\src\JavaScript\Qmail-GUI\docs\gpt.usability.batch1.review.txt

Five findings, all actionable. One required a product call:
gpt's #3 (Repair Now banner) — user authorized removing the wrong
banner trigger NOW as the FIX-10 interim, even though full FIX-10
waits on CORE-F.

Patches applied:

1. (gpt #1, High) Stale-selection race fixed.
   Before: If user clicked message A (pending), download started, user
     clicked B during hydrate, A's completion would overwrite B's
     selectedEmail and emailAttachments.
   After: Added selectedEmailRef (useEffect mirrors selectedEmail
     into it). In handleDownloadMail, after hydration succeeds,
     check if selectedEmailRef.current still matches the identifier
     OR the hydrated email_id. Only call setSelectedEmail and
     setEmailAttachments if the match holds. List updates / pending-
     row removal / loadEmails refresh still happen unconditionally
     — those are correct regardless of selection.

2. (gpt #2, Medium/High) Read state now persisted to backend.
   Before: handleSelectEmail's pending branch returned before the
     normal markEmailRead call. Hydration set isRead in UI state
     only; a refresh could undo it.
   After: After hydration succeeds and the local email_id is known,
     call markEmailRead(hydratedId, true).catch(warn). Fire-and-
     forget — backend correctness without blocking the UI.

3. (gpt #3, High) Repair Now banner removed (FIX-10 interim).
   Per the plan and user decision: drop the banner that triggered on
   walletBalance.folders.fracked.coins > 0. Removed:
     - the entire status-message warning JSX block in AccountPane
     - the handleRepairIdentity handler
     - the repairing state
     - the healWallet import from qmailApiServices
   Replaced with a comment block explaining why and pointing at
   CORE-F + the plan. Identity repair will return as an explicit
   manual action once CORE-F (non-mutating identity-health endpoint)
   provides a safe health source.

4. (gpt #4, Low/Medium) Coming-Soon tooltip now works.
   Before: COMING_SOON_STYLE applied pointerEvents:"none" to the row,
     which suppressed the title-tooltip from firing on hover.
   After: Removed inline pointerEvents:none. Added a new
     .security-action.coming-soon and .setting-item.coming-soon
     CSS class to AccountPane.css that:
       - sets opacity 0.5 and cursor: default
       - overrides the .security-action:hover / .setting-item:hover
         rules (no background change, no transform, no shadow)
     Rows are still non-interactive (no onClick, aria-disabled,
     tabIndex={-1}, button has disabled), but hover works so the
     tooltip fires. Matches gem-batch1's "if hover styles are a
     problem, override with a coming-soon CSS class" suggestion.

5. (gpt #5, Low) Removed unused Trash2 import from AccountPane.
   Was only referenced by the deleted Delete Account row.

6. (gpt non-blocking) Skip trailing sleep in hydrateDownloadedEmail.
   Loop only sleeps between attempts now (500ms, 1000ms — no
   sleep after the final failed attempt).

Decisions worth flagging:
- The Repair Now removal is a deliberate functional regression
  (users with a fracked identity now have no in-app recovery path
  until CORE-F lands). Per the plan and the product decision, this
  is the correct interim — false positives on the wrong signal +
  mutating-as-health-check were worse than no banner.
- The new .coming-soon CSS class moves the disabled-row pattern
  from inline styles to a reusable class. If we add more disabled
  controls elsewhere (e.g. when Sign Out lands in Phase 1), reuse
  this class.
