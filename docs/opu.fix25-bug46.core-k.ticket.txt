TL;DR
-----
1. Today /api/qmail/db/messages/search accepts only `query` and
   `limit` (clamped 1-200, default 50). Returns
   { query, count, results[] }. No offset. No total. No "more
   available" signal.

2. The GUI compensates with a heuristic: if results.length === 50,
   show "Showing top 50 results. Refine your search to see more."
   When there happen to be EXACTLY 50 actual matches with no
   truncation, the notice lies. That's BUG-46.

3. The asked-for change is two additions:
     (a) Accept an `offset` query param. SQL becomes
         `LIMIT ? OFFSET ?`. Standard pagination.
     (b) Internally request `limit + 1` rows; if you got the
         extra row, set `has_more: true` and only return `limit`.
         Standard cursor trick — no second COUNT query, no
         second SQL statement.

4. Response gains two fields: `offset` (echoed) and `has_more`
   (boolean). Existing `count` stays — it now means "rows in
   this page," matching its current semantics.

5. NOT asking for an exact `totalCount`. SQLite FTS5 doesn't
   yield total for free; a second `COUNT(*)` over the FTS index
   would double search latency for every keystroke. `has_more`
   is the right shape for search.

Proposed contract — CORE-K (Option A)
-------------------------------------
Endpoint:
  GET /api/qmail/db/messages/search

Existing params unchanged:
  query  string  required
  limit  int     1-200, default 50

New param:
  offset int     0+, default 0

Response shape — two new fields, otherwise unchanged:

  {
    "success": true,
    "rid": "...",
    "query": "<echo>",
    "count": <rows returned in THIS page>,   (unchanged)
    "limit": <echo>,                          (NEW — echo for parity
                                                with /messages/list)
    "offset": <echo>,                         (NEW)
    "has_more": <bool>,                       (NEW)
    "results": [ ... ]                        (unchanged shape)
  }

  count semantics: same as today — number of rows in `results`.
  has_more: true iff there is at least one more row beyond this
            page. false on the last page (or empty results).
  limit/offset: echoes; matches /messages/list's response shape so
                callers can reuse the same pagination state.

The internal trick: request `limit + 1` rows from SQL. If you
got `limit + 1`, set has_more=true and discard the trailing row
before serializing. Otherwise has_more=false. No second query.

File: src/qmail/qmail_db.c

Step 1: Extend qmail_db_email_search signature:

  result_t qmail_db_email_search(const char *query, int limit,
                                  int offset, bool *has_more_out,
                                  qmail_email_t **emails_out,
                                  int *count_out);

  Inside:
    if (limit <= 0) limit = 50;
    if (offset < 0) offset = 0;
    *has_more_out = false;

    const char *sql =
        "SELECT ... FROM qmail_emails e "
        "JOIN qmail_emails_fts fts ON e.rowid = fts.rowid "
        "WHERE qmail_emails_fts MATCH ? "
        "ORDER BY rank LIMIT ? OFFSET ?";

    sqlite3_bind_text(stmt, 1, query, -1, SQLITE_STATIC);
    sqlite3_bind_int(stmt, 2, limit + 1);   /* peek-ahead */
    sqlite3_bind_int(stmt, 3, offset);

    /* loop: collect up to limit rows; if you stepped to a
       (limit+1)-th row, set *has_more_out = true and stop. */
    int idx = 0;
    while (sqlite3_step(stmt) == SQLITE_ROW) {
        if (idx >= limit) {
            *has_more_out = true;
            break;
        }
        read_email_row(stmt, &list[idx]);
        idx++;
    }

  Existing capacity/realloc loop stays the same. Just bound the
  inner step loop by limit (not limit+1) and check for the extra
  step before assigning.

Rejected alternatives
---------------------
Option B — Return exact totalCount via a second SQL query
  Add a `SELECT COUNT(*) FROM qmail_emails_fts WHERE
  qmail_emails_fts MATCH ?` before the main SELECT. Response
  gains a `total` integer.

  Why this was rejected:
  - FTS5 COUNT queries are slower than ordinary COUNT queries —
    they have to evaluate the MATCH expression across the whole
    index, not just the top-K rows. We'd pay this cost on every
    keystroke (the GUI debounces at 500ms; multi-keyword
    queries can be expensive).
  - Search isn't a folder. Users don't need "Page 7 of 23" —
    they need "more results available." Pagination widgets
    typically don't show 1-of-N for search results.
  - If a user really wants to know the total, they can keep
    paging until has_more=false. Most users will refine the
    query long before that.

  Option B IS achievable if the backend owner thinks search
  performance is fine. The GUI patch is mostly the same; only
  the cap-notice copy changes ("X results found" vs "more
  results available"). Flag it during review if you disagree
  with my read on the cost.

Option C — FTS5 rank cursor (continuation token)
  Instead of OFFSET, the response includes a continuation
  cursor (the rank or rowid of the last row returned). The next
  page request passes that cursor; SQL becomes
  `WHERE rank > ? AND MATCH ? ORDER BY rank LIMIT ?`.

  Why this was rejected:
  - OFFSET in FTS5 is O(offset+limit) — you pay for all the
    skipped rows. For shallow pagination (page 1, 2, 3) this is
    fine. For deep pagination it gets slower.
  - But the GUI does not deep-paginate search. The 500ms debounce
    and the "refine your query" UX both discourage going past
    page 2 or 3 in practice. Standard OFFSET handles that
    comfortably.
  - Cursors are more complex on both sides — the GUI has to
    track an opaque token per page, the backend has to validate
    it. Not worth the complexity for the actual usage pattern.

  Option C is the right answer IF search performance under deep
  pagination becomes a real complaint. Until then, OFFSET is
  the simpler, more standard, and easier-to-debug shape.

Option D — Just fix BUG-46, skip pagination
  Add a `has_more` field via the peek-ahead trick, but don't
  add offset. The GUI replaces the exact-50 check with the
  authoritative has_more bool and keeps the "Showing top 50
  results. Refine to see more." notice.

  Why this was rejected:
  - The peek-ahead change is the same backend work as Option A.
    OFFSET is one more bind + one more clamp parse, ~3 LOC.
    Skipping it leaves the user with no way to ever see results
    51+, even if they really want them.
  - The GUI's existing pagination widget is already designed
    for limit/offset. Wiring it up to search is the natural
    next step.

  Option D is a viable smaller-scope ship if the backend owner
  wants to land the BUG-46 fix immediately and defer pagination.
  Tell me which way you'd prefer and I'll adjust the GUI patch.

src/api/qmailApiServices.js

  Update searchEmails to pass offset and surface has_more:

    export const searchEmails = async (query, limit = 50, offset = 0) => {
      try {
        if (!query || query.trim() === "") {
          throw new Error("Search query is required");
        }
        const encodedQuery = encodeURIComponent(query);
        const url =
          `${API_BASE_URL}/qmail/db/messages/search` +
          `?query=${encodedQuery}` +
          `&limit=${limit}` +
          `&offset=${offset}`;
        const response = await fetch(url);
        const data = await handleResponse(response);
        if (data) {
          return {
            success: true,
            data: {
              query: data.query || query,
              results: data.results || [],
              count: data.count || 0,
              limit: data.limit || limit,
              offset: data.offset || offset,
              hasMore: data.has_more === true,
            },
          };
        }
        throw new Error("Invalid response from email search endpoint");
      } catch (error) {
        console.error("Email search failed:", error);
        return { success: false, error: `Error: ${error.message}\n\nFailed to search emails.` };
      }
    };
