3. DEVIATIONS FROM PLAN v1.1 — YOUR REVIEW SHOULD FOCUS HERE
===============================================================================

I made two judgment calls that depart from the v1.1 plan. Both are
documented in their commit messages but I want explicit sign-off.

3.1  fadeIn keyframe extraction DEFERRED (plan §3.5 / Q4 said
     "extract identical keyframes")
     ---------------------------------------------------------
     The plan said to extract fadeIn alongside .status-message.
     Cross-file inspection found two distinct @keyframes fadeIn
     definitions sharing the same name:

       Pure fade (0→1 opacity only):
         AuthenticateTab.css:559
         LockerTab.css:434

       Rise+fade (0→1 opacity + translateY(20px)→0):
         App.css:613
         ExportTab.css:7
         (MainDashboard.css consumers expect this too)

     If primitives.css hosts the pure-fade as canonical, the rise+
     fade consumers visually regress (6+ animation sites). If
     primitives.css hosts the rise+fade, .status-message's fade
     gets unwanted vertical motion.

     Decision: leave fadeIn keyframes per-file for this commit.
     A separate sub-phase can rename the rise+fade variant to
     fadeInUp (a name already used in the codebase) and THEN
     primitives.css can safely host the canonical pure fadeIn.

     What I want you to check: is "look wins over guidelines"
     the right framing here, or do you want a different approach
     (e.g. ship primitives.css with both keyframe names)?

3.2  .progress-bar SCOPE TIGHTENED from plan (plan §3.3 said "3+1
     files with the 3 already-identical")
     -----------------------------------------------------------
     The plan said "3 already-identical definitions (Export, Auth,
     Locker) + 1 commented-out MainDashboard Bootstrap variant."
     That was wrong on Export.

     Three lineages found, not three identical shapes:

       30px Bootstrap-style:  MainDashboard.css (live, not commented)
       8px slim:              ExportTab.css
       12px medium + pulse:   AuthenticateTab.css + LockerTab.css
                              (byte-identical)

     User chose "conservative" — extract only Auth/Locker's shape;
     leave Export and MainDashboard alone for Phase 4 per-file
     review. This collapses 2 sites instead of the 4 the plan
     implied.

     Below the formal ≥3-files rule but follows the plan's
     "primitive owns shape" principle. If a third file ever grows
     the canonical 12px+pulse pattern, the primitive is already
     there.

     What I want you to check: is the conservative scope right,
     or should I have proposed modifiers (.progress-bar-container--
     thin/--thick) to absorb Export and MainDashboard now?

4. AUDIT-TOOL REPORTING NUANCE (DOCUMENT, DON'T FIX)
===============================================================================

After primitive extraction, the audit's "collisions" report can
mislead. Primitives.css is in the audit's scope per config.json,
so it counts as a "file" for collision-detection purposes.

Example: after Phase 3.3, the audit reports

  .progress-bar  (3 files, naming-collision)
  .progress-bar-container  (2 files, naming-collision)

That looks like a remaining problem, but it's actually:
  primitives.css      (the canonical owner — what reviewers should
                       look at first)
  MainDashboard.css   (a documented intentional variant)
  ExportTab.css       (a documented intentional variant)

The verdict "naming-collision" fires because the declarations
DIFFER between primitives.css and the per-file variants — which is
the intent for an intentional variant, but the audit can't tell
that from a real collision.

This is the same shape as plan v1.1 §Q3 (gradient end-stops as
literals in primitives.css show as raw debt in the audit). Per
GPT review item 5 (your earlier review), defer the audit-tool
exemption to Phase 5 cleanup. No code change needed now.

What I want you to verify: is "document, don't fix" still the
right disposition? My read: yes, because changing the audit
tool's collision-counting logic is a non-trivial change that
should ride with other Phase 5 audit-tool polish (the proposed
primitives-css-allowlist from Q3 + maybe a "verdict: primitive-
owned-variant" status). One change covers all four nuances.

Main feedback
-------------
I found one real issue, but it is a **comment/doc inconsistency**, not a
logic or styling bug:

- In `src/styles/primitives.css`, the 3.3 section says:
  - "The progressPulse keyframe stays per-file-defined..."

So the implementation is fine, but that comment should be corrected
before the next related commit to avoid confusing future readers.


Q1. fadeIn deferral approach
----------------------------
I agree with the deferral.

You found the key point correctly:
- there are two different animations currently named `fadeIn`
- choosing one canonical meaning right now would create a visual change
  in whichever family loses

So my call is:
- **do not** make rise+fade the canonical `fadeIn`
- **do not** force pure fade into primitives.css yet
- keep the current per-file definitions for now

The right cleanup path is the one you described:
1. rename the rise+fade lineage to `fadeInUp` (or another explicit name)
2. then extract a canonical pure `fadeIn` if it is still shared enough

That is cleaner than shipping a silent behavior change under an existing
animation name.


Q2. .progress-bar conservative scope
------------------------------------
Yes, the conservative 2-site extraction was the right call.

I would **not** introduce thin/thick modifiers yet.

Reason:
- Export and MainDashboard are not just size variants
- they also differ in visual intent and decoration
- adding modifiers now would pretend we already understand the variant
  taxonomy, when really we only know Auth + Locker are identical

So:
- extracting the canonical Auth/Locker medium+pulse shape now is good
- leave Export and MainDashboard for later per-file or later primitive
  work


Q3. Audit-tool primitives.css exemption
---------------------------------------
Still defer.

I agree with "document, don't fix" for now.

The reporting noise is real, but not yet severe enough to justify a
Phase-3 detour into audit semantics. The current behavior is at least
truthful:
- primitives.css owns one shape
- component files own intentional variants
- the audit sees different declarations and reports a collision

That is noisy, but understandable once documented.

So my call is:
- no config/audit-tool change now
- bundle this with the broader Phase 5 audit polish you already named


Q4. Ordering — what next?
-------------------------
I agree with your sequencing:

1. **3.4** `.results-grid` family
2. **3.6** `.upload-box` family
3. then **3.2** `.btn` family

That is the right risk order.

Why:
- 3.4 and 3.6 are smaller and lower-risk
- they grow `primitives.css` in understandable ways
- they let you validate the composition pattern a bit more before the
  much larger JSX-heavy `.btn` extraction

I would not move 3.2 earlier.
