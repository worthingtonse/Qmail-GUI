1.4  Backend endpoint — canonical spec
--------------------------------------
The endpoint contract is defined in:
    D:/Code/src/PHP/cloudcoin.org-main/commands/system-theme.php

Summary of the contract the GUI must satisfy:
    GET    /api/system/theme
           If the file does not exist yet, the server *creates* it with a
           default stub (a "# Custom Theme Configuration" header) and
           returns exists:false to indicate "newly created with defaults."
           Returns:
             { success:true, command:"get-theme",
               file:"custom_theme.txt",
               path:"Data/Themes/custom_theme.txt",
               content:string, size:int, exists:bool }
    POST   /api/system/theme
           Body: raw text (Content-Type may be text/plain or
           application/json — the server treats it as an opaque blob).
           413 Payload Too Large if body > 8192 bytes.
           400 Empty request body if body is empty.
           Returns:
             { success:true, command:"update-theme",
               file:"custom_theme.txt",
               path:"Data/Themes/custom_theme.txt",
               bytes_written:int,
               message:"Theme configuration updated successfully" }
    DELETE /api/system/theme
           Clears the file in place (keeps zero-byte file).
           404 if the file never existed.
           Returns:
             { success:true, command:"theme",
               action:"cleared",
               message:"Theme file cleared successfully" }

Important constraints flowing from the contract:
  * Only one custom theme slot exists on disk (custom_theme.txt). The
    plan below uses *one* slot — we do not need to extend the backend.
  * 8192-byte cap is enforced server-side. Our serialisation has to fit
    (the editor must show a live byte count and disable Save above the
    limit; surface a 413 toast if a save sneaks past).
  * The file is opaque to the server (no parsing, no execution). The
    GUI owns the schema. The PHP spec lists YAML as "Recommended" but
    also explicitly lists JSON (Option 2 at system-theme.php :446) as
    valid. This plan uses **JSON** — see §2.4 for the reasoning. Note
    in the project README that the file is JSON not YAML, so users
    hand-editing don't follow the spec's first example by mistake.
  * Path is "Data/Themes/custom_theme.txt" in the spec (in the C
    implementation this becomes Client_Data/Themes/custom_theme.txt
    relative to g_config.client_data_path — see §8 about the discrepancy).
  * No theme service exists in src/api/. apiService.js (pattern at
    src/api/apiService.js:1–80) is the existing convention: a small helper
    module exporting async fns that call fetch against `${API_BASE_URL}/...`.
    The new module (themeService.js) belongs here and uses the same
    handleResponse() helper for error extraction.

2.1  Token layer (file: src/styles/tokens.css — new)
----------------------------------------------------
Move the :root block out of index.css into its own file. Add the tokens that
are currently missing or commented-out:

    --glow-primary, --glow-secondary, --glow-success    (re-enable)
    --font-scale        : 1          (multiplier; large-print theme = 1.25)
    --font-size-base    : calc(16px * var(--font-scale))
    --font-size-xs      : calc(12px * var(--font-scale))
    --font-size-sm      : calc(14px * var(--font-scale))
    --font-size-md      : calc(16px * var(--font-scale))
    --font-size-lg      : calc(20px * var(--font-scale))
    --font-size-xl      : calc(24px * var(--font-scale))
    --font-size-2xl     : calc(32px * var(--font-scale))
    --glass-blur-amount : 16px       (so themes can set it to 0 to flatten)
    --glass-blur        : blur(var(--glass-blur-amount))
    --motion-scale      : 1          (animation/transition multiplier;
                                     see auto-apply rule below)

Auto-apply rule for --motion-scale: an OS-level reduced-motion
preference must override the active theme's --motion-scale, so users
get the accessibility behaviour without picking the high-contrast
theme. Add this once in tokens.css:

    @media (prefers-reduced-motion: reduce) {
      :root { --motion-scale: 0; }
    }

This means: dark/light themes set --motion-scale: 1; the high-contrast
theme sets it to 0; and the @media rule above forces it to 0 anywhere
the OS asks, regardless of theme. Folds the !important block currently
at App.css :549–560 into the token, so we have one source of truth.

The calc() pattern (borrowed from Gemini's plan) is the key trick: every
component CSS file references `var(--font-size-md)` etc., never a raw px
value. Changing --font-scale at the theme level scales the entire type
ramp without any per-component code change. Same trick is used for
--motion-scale by writing transitions as
    transition: all calc(var(--transition-base-ms) * var(--motion-scale)) ease;
so the high-contrast theme's `--motion-scale: 0` collapses every transition
to zero duration in one place.

Every existing token from index.css :5–83 stays, with names unchanged, so the
22 component CSS files keep working without edits during phase 1.

2.4  Custom theme file format (what we POST to /api/system/theme)
-----------------------------------------------------------------
Keep it small — 8192-byte cap. The PHP spec lists JSON as a valid
format (system-theme.php :446, "Option 2: JSON Format"). This plan
chooses JSON over the spec's "Recommended" YAML because:

  * Native browser support — JSON.parse / JSON.stringify avoid pulling
    in (or writing) a YAML parser, and JSON's tighter grammar means we
    won't accept ambiguous user input.
  * Stricter validation — invalid YAML fails in subtle ways (whitespace
    significance, type coercion); invalid JSON fails immediately at the
    quote level, surfacing errors earlier.
  * The same editor that produces the file can also pretty-print it,
    keeping the human-readable surface YAML offers without the parser.

A theme file is a JSON document with metadata + a flat "tokens" map
keyed on CSS custom-property names:

    {
      "schema":  "qmail-theme/1",
      "name":    "My Theme",
      "author":  "sean",
      "base":    "dark",          // one of: dark, light, high-contrast
      "a11y": {
        "reduced_motion": false,
        "large_print":    false
      },
      "tokens": {
        "--accent-primary": "#22c55e",
        "--secondary-bg":   "#0a0a0a",
        "--font-scale":     "1.1",
        "--radius-md":      "6px"
      }
    }

(JSON itself does not support comments — the "// one of: dark, ..."
inline is illustrative for this doc only. The editor will surface allowed
values via UI dropdowns and a separate help panel, not via file
comments.)

Why this shape:
  * `base` lets a user start from light/dark/high-contrast and only
    override a few things — keeps the payload tiny and forward-
    compatible if we add new tokens later.
  * `tokens` is a flat map of CSS custom-property name to literal
    value, so serialising it to a <style> block is one line per entry:
        :root[data-theme="custom"] { --accent-primary: #22c55e; ... }
  * `schema: "qmail-theme/1"` is our version marker. Unknown schemas →
    fall back to the named `base` theme; never throw.
  * `a11y` flags are first-class so users can tick "reduced motion" or
    "large print" without knowing the underlying token names. The
    ThemeProvider translates these into the corresponding token
    overrides (--motion-scale, --font-scale) before injecting the
    <style> tag.

The 8192-byte cap is generous: at ~40 bytes per override, the user
can override ~150 tokens after the JSON header — far more than the
editable subset (§2.5) ever exposes.

Validation rules (enforced before POST and before injecting overrides):
  * Token keys must match /^--[a-z0-9-]+$/.
  * Token values must be string scalars containing no semicolon (;),
    no closing brace (}), and no slash-asterisk (/*). This prevents
    CSS injection through the <style> tag.
  * `base` must be one of dark, light, high-contrast.
  * Unknown top-level fields are ignored (forward compatibility).

2.6  Service layer — src/api/themeService.js (new)
--------------------------------------------------
Three thin functions, in the apiService.js style:

    export async function fetchUserTheme()         // GET   -> {exists,content}
    export async function saveUserTheme(obj)       // POST  body = JSON.stringify(obj)
    export async function clearUserTheme()         // DELETE

fetchUserTheme parses content (which is the raw file the server returned) as
JSON and validates {version, base, tokens}. On parse failure it returns a
neutral { exists:false } and logs — a corrupted theme file must never break
the GUI.

3.  CONSOLIDATION PLAN  (the "easier to change" part of the request)
===============================================================================

This is mechanical work, mostly done file-by-file. Each step is independent
and reviewable on its own.

Step 3.1 — Inventory hex / rgba literals per file
  Tool:  ripgrep '#[0-9a-fA-F]{3,8}\b|rgba\(' per file.
  Already counted (§1.3a) — totals 547 raw colour literals across 22 files.
  For each unique literal, decide: (a) maps to an existing token? rename.
  (b) is a one-off accent for a specific component? leave it, but add a
  per-component token like --compose-attachment-pill-bg into themes.css and
  reference *that* from the component CSS.

Step 3.2 — Restore the commented-out glow tokens (index.css :44–47)
  Required before phase 4 — App.css already references them.

Step 3.3 — Drive the type scale through one variable
  Tokens are already defined (§2.1) as
    --font-size-* : calc(<base-px> * var(--font-scale))
  so per-file work is purely substitution: replace each raw font-size with
  the closest --font-size-* token. The 282 declarations break down roughly
  as: 91 in MainDashboard.css, 34 AuthenticateTab, 31 LockerTab, 29 each
  in DicewarePasswordCreator/ExportTab — heavy files first.
  pass A: top-level layouts (App.css, index.css, ServiceSelection)
  pass B: QMail screens
  pass C: Wallet screens (MainDashboard is the big one)
  pass D: tabs and modals
  After each pass, toggle high-contrast at 1.25x and confirm no per-component
  CSS still hard-codes a px value that fails to scale.

Step 3.4 — De-duplicate the update-modal block in App.css
  App.css :598–804 is a self-contained chunk that uses raw hex (#1a1f2e,
  #3b82f6, #2563eb, #f59e0b, #10b981). Move to src/components/UpdateModal.css,
  swap literals for tokens (--secondary-bg, --accent-secondary, etc.), and
  drop the second fadeIn/slideIn @keyframes copies (App.css :771–789).

Step 3.5 — Extract glass-morphism utility classes
  .glass-pane, .glass-card, and .glass-overlay are reimplemented at least
  half a dozen times across the heavy CSS files (search for `backdrop-filter`
  combined with `rgba(255, 255, 255` / `var(--glass-bg)`). Move the canonical
  versions into tokens.css and have the per-component files compose them via
  `@extend`-style class composition in JSX (className="glass-pane email-row").

Step 3.6 — Sweep the dead code
  MainDashboard.css and AccountPane.css both contain commented-out blocks
  from earlier iterations. Delete those before phase 1 finishes; they're
  noise that makes the cross-file audit harder.

Step 3.7 — Rename classes to BEM convention (done during Phase 4)
  Current naming is ad-hoc and inconsistent — `.account-confirm-overlay`,
  `.update-modal-header`, `.nav-tab.active`, `.glass-sound-btn`. Three
  different patterns (kebab-case-with-context, no-context kebab, modifier-
  via-second-class) appear within ten lines in App.css alone.

  Adopt BEM (Block__Element--Modifier) as we touch each file in Phase 4:
      .account-pane                       (block)
      .account-pane__confirm-overlay      (element)
      .account-pane__confirm-overlay--open (modifier)
      .nav-tab                            (block)
      .nav-tab--active                    (modifier; was .nav-tab.active)
      .btn                                (block)
      .btn--primary, .btn--ghost          (modifiers; were .primary etc.)

  Rules of engagement for the rename:
  * Each renamed class must be searched-and-replaced across both the CSS
    file *and* every JSX that references it. ripgrep both before merging.
  * Keep the old class name as a comment in the CSS for one release cycle
    (e.g. `/* was: .account-confirm-overlay */`) so reviewers can map
    PRs back to git history. Remove these comments in the release after.
  * Don't bulk-rename across files — do one file's classes + their JSX
    references in one PR, so each rename is reviewable in isolation.
  * Component-namespaced blocks (.account-pane, .compose-modal) prevent
    the cross-file collision risk of bare element names.

  This is bundled into Phase 4 deliberately: we're already touching every
  CSS file to tokenise, and JSX files only need to be touched if we also
  rename classes — so doing both at once halves the file churn.

    --font-scale            : 1.25          (multiplies the type scale)
    --radius-sm/md/lg/...   : keep, but optionally reduce for sharper edges

Acceptance: all text/background pairs above clear WCAG AAA (7:1).

5.  PHASING (deliverable per phase — each is mergeable on its own)
===============================================================================

Note on ship order
------------------
Both peer plans (Gemini, GPT) put the tokenisation sweep *before* React
plumbing — Gemini's Phase 1 is "Tokenization and Cleanup," GPT explicitly
calls this plan out for "leaning too quickly into a specific React
architecture before the CSS token cleanup is fully mapped." That is a fair
critique and we take it seriously, but we are deliberately going the other
way for one reason:

  * Tokenisation is mechanical and large (~547 raw colours + ~282 font-
    sizes). It will take weeks. During those weeks no user can see a
    different theme, because there is no runtime. Risk: the work stalls
    and ships in a giant unreviewable PR.
  * The React runtime is small (a Provider, a `<style>` tag, an inline
    bootstrap script in index.html) and *doesn't depend on the tokenisation
    being complete*. Whatever is already token-driven (which is most of
    the layout, all of the spacing, most of the borders) will react to a
    theme change today. Hardcoded values stay frozen at their dark-theme
    values until phase 4 mops them up.

So phases 0–3 land the runtime and a real picker first, and phase 4 does
the long tokenisation sweep against a stable runtime that is already in
production. This makes the per-file token migration small and reviewable
("convert AccountPane.css → click switch → confirm light theme looks
right") instead of a single mega-PR.

Acceptance criterion for this choice: at the end of phase 3, switching
to "light" should leave roughly the App-shell and the picker itself
looking right; per-screen visual debt is acknowledged and tracked in
phase 4 tickets. If that's not acceptable to product, fall back to
Gemini's ordering.


Phase 0 — Plumbing (no visible change)
  * Create src/styles/tokens.css; move :root block from index.css into it;
    import it from index.css so the existing import order is preserved.
  * Create src/styles/themes.css with one rule:
       [data-theme="dark"] { /* re-applies the same values */ }
    so the cascade is consistent once we attach data-theme on <html>.
  * Add the FOUC-prevention inline script to index.html that reads
    localStorage.qmail.theme and sets <html data-theme=...> before React
    mounts.
  * Restore the --glow-* tokens (§3.2).
  * Verify zero visual diff against main.

Phase 1 — ThemeProvider + light theme
  * Add src/theme/{ThemeProvider.jsx, themeContext.js, themes/light.css,
    themes/dark.css}.
  * Wrap <App/> in <ThemeProvider> in main.jsx.
  * Ship the radio-button picker in AccountPane (replace the Dark Mode
    placeholder). At this point the user can toggle between dark and light.

Phase 2 — High-contrast / large-print
  * Add themes/high-contrast.css with values from §4.3.
  * Add the --motion-scale wiring so animations actually disable
    (search-and-replace any hard-coded transition durations to use the token
    or multiply by --motion-scale via calc()).
  * Run a WCAG check on every screen.

Phase 3 — Custom theme + backend
  * Add src/api/themeService.js (§2.6).
  * On startup, if active theme === "custom", fetch and inject overrides

  * Build ThemeEditorModal: pickers for the subset of editable tokens in §2.5,

  * Show the user the raw JSON in an "Advanced" disclosure (pretty-

Phase 4 — Consolidation sweep
  * Steps 3.1, 3.4, 3.5, 3.6 from §3 — token-ise the 547 raw colour

  * Step 3.7 — rename classes to BEM in the same pass, since we're

  * One file at a time, one PR each. Reviewers can verify each rename

Phase 5 — Polish

6.  RISKS & WATCHPOINTS
===============================================================================

R1  FOUC on first paint.
    The data-theme attribute must be on <html> before React mounts.  Solve
    with an inline script in index.html (no module, no import) that reads
    localStorage synchronously. The "custom" theme can't avoid an async
    /api/system/theme fetch, so on first paint we render the *base* theme
    from the JSON's "base" field — we duplicate that field into localStorage
    on every save for exactly this reason.

R2  Tokens used inside linear-gradient() and box-shadow stops.
    var() works in those positions in all current Electron / Chromium builds,
    but @keyframes interpolation does not animate var() changes smoothly.
    Currently we only animate transform/opacity in keyframes, so no
    regression — but the theme audit (Phase 4) should flag any future
    keyframe colour interpolation.

R3  Backwards compatibility of the on-disk theme file.
    custom_theme.txt is opaque to the server. The "schema: qmail-theme/1"
    line in §2.4 gives us forward compatibility. fetchUserTheme() must
    treat an unknown schema as "ignore, fall back to base" and surface a
    one-time toast — never throw, never block startup.

R4  8192-byte cap.
    Generous for our token surface, but the editor must show a live byte
    count and disable Save above the limit (don't rely on the server 400 —
    surface it earlier).

R5  Custom theme corrupted on disk.
    If JSON.parse fails or the schema is unrecognised, fetchUserTheme
    returns { exists:false } so the GUI silently falls back to dark. We
    also surface a *non-blocking* toast on the next settings open:
    "Your custom theme could not be loaded; falling back to the dark
    theme. [View raw] [Reset]". The token-validation rules in §2.4
    must run on every token before the override <style> is injected —
    a malformed value containing "; }" could break out and inject
    arbitrary CSS.

R6  prefers-reduced-motion vs. high-contrast.
    The OS-level @media (prefers-reduced-motion: reduce) block in App.css
    :549–560 currently sets all animation durations to 0.01ms via !important.
    Resolved by §2.1's auto-apply rule: a single @media block in tokens.css
    drives --motion-scale to 0, the rest of the codebase reads the token,
    and the !important block is deleted as part of Phase 4. One source of
    truth, no scattered overrides.

R7  Touch-cursor block in App.css :565–582 changes background and transform
    on button:active. Verify the high-contrast theme still has visible focus
    rings on touch — the outline-only fallback in App.css :585–595 should be
    sufficient but worth a screen check.

8.  C IMPLEMENTATION vs. PUBLIC SPEC — DISCREPANCIES TO RESOLVE
===============================================================================

The canonical contract is the PHP reference page
(D:/Code/src/PHP/cloudcoin.org-main/commands/system-theme.php). The current
C implementation in
(D:/Code/src/C/rest_core/api_src/api_handlers_system.c :964–1048)
does not match the spec in five places. None of these blocks Phase 0–2 work,
but they need to be picked up before Phase 3 ships, because the GUI's
themeService.js will be coded against the spec.

D1  Storage path.
    Spec  : Data/Themes/custom_theme.txt
    Code  : g_config.client_data_path + "/Themes/custom_theme.txt"
            (the prefix depends on runtime config)
    Action: confirm with whoever owns the C core whether the spec means
            "wherever Data/ resolves to" or whether the C code should be
            renaming the root from Client_Data to Data. The GUI doesn't
            care which path the server uses (it never sees the absolute
            path beyond logging) — but the spec's `path` field in the
            response should match reality.

D2  GET when file is missing.
    Spec  : server creates the file with a default stub
            ("# Custom Theme Configuration\n# Add your theme settings here\n",
             68 bytes) and returns exists:false.
    Code  : returns content:"", size:0, exists:false; does NOT create.
    Action: make the C handler create-on-GET, with the same default stub
            as the spec. The GUI assumes the file always exists after the
            first GET (it relies on exists:false to mean "newly created,
            show first-run defaults," not "permanent absence").

D3  Response field names.
    Spec  : { success, command, file, path, content, size, exists }   on GET
            { success, command, file, path, bytes_written, message } on POST
            { success, command, action, message }                     on DELETE
    Code  : { status, exists, size, content }                          on GET
            { status, action:"saved", size }                           on POST
            { status, action:"cleared", message }                      on DELETE
    Action: rename the C json_success_response keys to match the spec.
            The GUI's handleResponse() in apiService.js looks for `success`,
            `message`, `error`, `detail`, `details` — `status` is not in
            that list, so without this fix error extraction degrades to the
            HTTP-status fallback. Until D3 is fixed, themeService.js will
            be defensive (accept either `success` or `status === "success"`)
            and log a one-time warning if it sees the old shape, so we know
            when the server upgrade lands.

D4  Oversize POST.
    Spec  : 413 Payload Too Large
    Code  : 400 (json_error_response_from_string "Theme too large (max 8192
            bytes)")
    Action: change the HTTP status to 413. The GUI surfaces the error
            message either way, but matching the spec lets us write
            `if (response.status === 413) showOversizeToast()` cleanly.

D5  DELETE of a never-existed file.
    Spec  : 404 with message "Theme file does not exist"
    Code  : matches (good).

These are server-side fixes, listed here so they're scoped together when the
C core gets touched. The GUI plan does not depend on any of them being
resolved before Phase 0 starts — it depends on D2 and D3 being resolved
before Phase 3 ships.

10. RESPONSIVE DESIGN & SIZING  (currently invisible in all three plans)
===============================================================================

10.1  Why this section belongs in the theme plan
------------------------------------------------
The accessibility "large print" theme works by multiplying every type
size by --font-scale. That only works correctly if the layout *also*
scales when the type does — otherwise an oversized font overflows a
fixed-width container. Layout and type sizing are joined at the hip;
the theme system has to acknowledge that.

This is also the right moment to standardise responsive sizing because
the Phase 4 sweep is already going to touch every CSS file.

10.2  Current state — measured
-----------------------------
  * 49 uses of clamp() across 21 files, no consistent floor/ceiling.
    Examples: index.css h1 uses clamp(2rem, 5vw, 3rem); MainDashboard
    uses ten separate clamp() calls with different scaling factors.
  * Five different breakpoints in use today, by file:
        640px   App.css, WelcomeScreen, PasswordScreen, USBCheckScreen
        768px   DicewarePasswordCreator, MainDashboard (3x)
        968px   MainDashboard (1x)
        1024px  MainDashboard (1x)
        1200px  MainDashboard (1x)
    There is no document explaining why these specific widths were
    chosen — they appear to be picked per-component when something
    visibly broke.
  * Mix of px and rem throughout. Modals declare max-width in px
    (App.css :619 = 480px; WelcomeScreen = 500–650px), while heading
    sizes use rem via clamp() (good). Spacing tokens (--space-*) are
    px, which means they don't scale with --font-scale.

The inconsistency itself is the problem. None of it is unsafe; all of
it makes the theme system harder to reason about.

10.3  Standards this plan adopts
--------------------------------
(a) Breakpoint tokens (add to tokens.css):

      --bp-sm:  640px    /* phone / very narrow window           */
      --bp-md:  1024px   /* tablet / standard laptop sidebar     */
      --bp-lg:  1440px   /* large laptop / desktop default       */
      --bp-xl:  1920px   /* full HD external monitor             */

    CSS Custom Properties don't work directly inside @media queries
    (a spec gap), so the *values* live as comments in tokens.css for
    documentation and we keep them as bare literals in @media:
        @media (min-width: 1024px) { /* --bp-md */ ... }

    During Phase 4, every existing media query is rounded to the
    nearest breakpoint above. So 968 → 1024 and 1200 → 1440. We
    accept a few pixels of visual drift to get one consistent ruler.

(b) rem everywhere for sizes that should scale with --font-scale.
    Convert the --space-* tokens from px to rem:
        --space-xs: 0.25rem    (was 4px)
        --space-sm: 0.5rem
        --space-md: 1rem
        --space-lg: 1.5rem
        --space-xl: 2rem
        --space-2xl: 3rem
    The browser's base rem = 16px, so today's px values map 1:1. The
    change is invisible until --font-scale moves; then padding,
    gaps, and margins scale with the type and modals don't burst.

(c) Modal/container max-widths stay in px (or move to rem with the
    same rule). Either is fine; pick one per Phase 4 sweep. Current
    `max-width: 480px` becomes `max-width: 30rem` for the same
    visible result on default font-size.

(d) Document the clamp() convention. The pattern in use today —
    `clamp(<min-rem>, <preferred-vw>, <max-rem>)` for headings — is
    correct and worth keeping. Make it explicit:
        h1: clamp(1.5rem, 3vw, 2.5rem)
        h2: clamp(1.25rem, 2.5vw, 2rem)
    Headings are the only place clamp() is *needed* in this app
    (the Electron window is the viewport — most other elements live
    inside fixed-width containers). Remove clamp() from anywhere
    it's used unnecessarily.

(e) Container queries (@container) are *not* added in this pass. The
    QMail UI doesn't have component-level reflow needs that media
    queries don't solve. Revisit if the app gains an embeddable mode
    or a resizable side panel.

(f) Minimum window size. The Electron window has a configurable
    minWidth/minHeight (in electron.cjs). The smallest breakpoint
    we'll *design for* is --bp-sm (640px). The smallest the window
    is *allowed* to be should match — set minWidth: 640 in
    electron.cjs (currently no min; check during Phase 4).

10.4  Tracking
--------------
Phase 4 owns the breakpoint normalisation (folded into the same
per-file sweep as tokenisation and BEM renaming). Phase 0–3 don't
need to do anything responsive — they just don't add new hardcoded
breakpoints to the codebase.

12. PARALLEL WORK-STREAMS
===============================================================================

12.1  Coordination model
------------------------
  * One agent owns one file at a time. No two agents touch the same
    CSS file or the same JSX file concurrently — even though the CSS
    changes are isolated, JSX files often import multiple CSS files
    so two CSS-renames against the same component cause merge pain.
  * Sequential merges. Opu merges in arrival order. If two PRs touch
    overlapping JSX, the second rebases.
  * Status file at docs/theme.status.txt is the source of truth for
    "who is doing what right now." Claim a track by editing one line.
    Format and seed entries are created alongside this revision.
  * No track may start (other than Track A docs/research) until
    Phase 0 has merged. Phase 0 creates tokens.css and themes.css —
    every other track imports from these files.

13.1  Overriding principle
--------------------------
The site must look excellent. Every rule below is a preference that
yields when applying it would visibly degrade a screen. Phase 4 is
already a large mechanical sweep; we use that touch to nudge markup
toward standards rather than initiating a separate refactor that
might break working components.

If a guideline below conflicts with the look, the look wins. Note the
exception in the PR description with one line: "kept .foo as <div>
because <section> introduced a margin collapse on Safari" or similar.

13.3  Heading levels — restrict to h1–h6
----------------------------------------
  * Use h1–h6 for all titles. Do not introduce `<div class="title">` or
    `<p class="section-heading">` patterns. If a "heading-style" piece
    of text is not actually a heading (e.g. a label above an input),
    keep it as a `<label>`, `<p>`, or `<span>` — not a styled div.
  * Honour document outline: one h1 per screen (the screen's title).
    Children of that screen use h2 for major sections, h3 for
    subsections, and so on. Do not skip levels to get a font-size.
    Font-size lives in CSS, not in tag choice.
  * If six levels feel insufficient, look first at whether the screen
    has the wrong outline. Six is enough for QMail's screen depth.

13.4  Semantic landmarks — bias toward, don't force
---------------------------------------------------
  Promote a `<div>` to a semantic tag when its role is clearly one of
  these:

    <header>    Top bar of a screen, a card's title region.
    <nav>       The navigation tabs in NavigationPane and the wallet's
                tab strip in MainDashboard.
    <main>      The primary content region of each screen — exactly
                one per screen.
    <section>   A self-contained block with its own heading. Account
                pane's "Account Information" / "Settings" blocks fit.
    <article>   A self-contained piece of content (email list item,
                contact card). EmailListItem and ContactCard are
                strong candidates.
    <aside>     Sidebar / supplementary content. NavigationPane fits.
    <footer>    Bottom bar of a screen or a card.

  Do *not* promote a `<div>` to a landmark when it's purely a layout
  wrapper for flex/grid alignment. A wrapper that exists only to add
  display:flex stays as `<div>`.

  Spans are exempt: `<span>` for inline text formatting is correct
  semantic HTML. Don't replace inline spans with anything.

13.5  Reduce div nesting via flexbox/grid
-----------------------------------------
  The codebase has many places where two or three nested `<div>`s
  exist to achieve a layout that one flex/grid container could
  handle. Examples (look for these patterns during a Phase 4 PR):

    <div class="row">                  →  one flex container
      <div class="row__left">
        <div class="row__title">...</div>
        <div class="row__subtitle">...</div>
      </div>
      <div class="row__actions">...</div>
    </div>

  becomes:

    <article class="row">              (or stays <div> if not an article)
      <header class="row__head">
        <h3>...</h3>
        <p>...</p>
      </header>
      <menu class="row__actions">...</menu>
    </article>

  Rules of engagement:
    * Drop a wrapping div only when one *function* (the wrapper does
      nothing besides containing). A wrapper that adds padding or a
      background can stay.
    * `display: contents` is *not* a substitute for removing the div
      — accessibility-tree exposure varies. Just remove the div.
    * Don't collapse a div if removing it changes the cascade for
      child styles. Verify visually after.

13.6  Inline styles — extract to CSS
------------------------------------
  The 58 `style={{...}}` blocks must go. Replacement options in
  priority order:

  1. Existing class in the component's CSS file — add to it.
  2. New class in the component's CSS file with a BEM name.
  3. Inline CSS custom property if the value is dynamic (state-
     driven): `style={{ '--row-color': severity.color }}` is
     acceptable because the *style sheet* still owns the rule
     that reads --row-color. This is the only inline-style pattern
     that survives.

  Dynamic values that need to flow into CSS go through custom
  properties; never via `style={{ color: severity.color }}` directly.

13.7  Palette reduction
-----------------------
  The 51 CSS variables in index.css are not the problem — they
  define an intentional palette. The 547 raw colour literals that
  bypass them are the problem.

  During each E-track:
    1. Collect every distinct colour literal in the file.
    2. Each colour either (a) maps to an existing token (most do —
       look for a 0–10% lightness delta and use the existing token),
       or (b) is a true component-specific accent that needs a new
       token in themes.css.
    3. If a file introduces more than 2 new tokens, that's a smell —
       the component is probably reinventing existing palette colours.
       Prefer mapping to existing tokens with a small visual
       compromise to introducing new ones.

  Cap target: total distinct tokens in tokens.css + themes.css stays
  under 80. We're at ~51 today; the audit should add at most ~30 new
  ones across all 22 files combined. If a single component wants to
  add 10 new tokens, push back.

13.8  Verification per PR
-------------------------
  Before opening a Phase 4 PR, the agent runs:

    rg '<div\b'         <touched.jsx>   # counts div uses
    rg 'style=\{\{'     <touched.jsx>   # must be empty (or only
                                          custom-property pattern)
    rg '<h[1-6]\b'      <touched.jsx>   # confirm heading levels
    rg '#[0-9a-fA-F]+|rgba\(' <touched.css>  # must be empty

  PR description includes the delta:
    "div: 23 → 14, semantic landmarks: 0 → 3, inline styles: 2 → 0,

  Reviewers verify by opening the screen in dev mode and toggling
