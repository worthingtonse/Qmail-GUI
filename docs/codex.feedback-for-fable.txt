Feedback on docs/fab.qcons.txt
================================

Overall assessment
------------------

The plan maps the request to the current repository accurately and is useful as
an implementation inventory. Its strongest additions are the concrete Edit-menu
routing, the exact avatar call sites, and the proposal to collect unknown mail
senders, deduplicate them, and resolve them without blocking mailbox display.

The plan should not be implemented as written until the identifier, endpoint,
ownership-proof, inbox-fee, and local-schema contracts are resolved. Several of
its provisional choices should be tightened as described below.

What is strong
--------------

1. It correctly identifies the central protocol mismatch: the current QMail
   implementation uses a three-byte serial while the request describes a
   four-byte serial.

2. It correctly treats a QCon as an index into the existing 000.svg-255.svg
   assets and reuses getQmailAvatarAssetHref instead of hard-coding asset paths.

3. It uses the existing Electron Edit-menu -> qmail:menu-command -> dashboard
   path instead of introducing a second command mechanism.

4. It preserves the existing serial-derived cartouche as the fallback and
   proposes public QCons as an optional override. That is the least disruptive
   rendering model if the product confirms the semantics.

5. It identifies exact denomination/serial lookup as necessary for automatic
   sender resolution. Client-side exact filtering after a full-address prefix
   query is an acceptable compatibility fallback, though a real exact endpoint
   is preferable.

6. It explicitly keeps directory failure from blocking mail and proposes
   request deduplication and negative caching. Those are required for usable
   mailbox behavior.

Required corrections
--------------------

1. Do not assume CORS is a non-issue in packaged Electron.

   The BrowserWindow uses the normal webSecurity default. Renderer fetches are
   still subject to Chromium origin/CORS behavior, including from a packaged
   file origin. The server must return a correct Access-Control-Allow-Origin and
   handle preflight, or the remote call should go through a narrow Electron-main
   IPC handler/local rest_core proxy. The trusted layer is also the better home
   for ownership-proof generation. This must be tested rather than inferred.

2. Do not ship an unauthenticated "trusted alpha" update path.

   An unauthenticated upsert lets anyone overwrite any profile and poisons every
   client that imports it. Avoid an "AN-derived token" unless a cryptographic
   protocol owner specifies it; deriving or transmitting reusable material from
   a CloudCoin AN could expose the identity secret. Use a short-lived challenge,
   expiry, replay protection, and a proof validated by the server without
   transmitting wallet/AN material.

3. Prefer JSON POST and a versioned response contract.

   Form encoding can work, but a JSON body gives explicit array semantics for
   qcons and a cleaner evolvable contract. update_users should return the full
   canonical stored profile, revision, and server timestamp, not only
   {"status":"success"}. The GUI must locally persist and render the server's
   normalized result, not its unconfirmed request object.

4. Do not assume GUI-side sidecar/localStorage as the first release design.

   A sidecar splits contact truth across two stores, is easy to clear or corrupt,
   complicates multi-instance behavior, and leaves rest_core unable to expose
   inbox fee/QCons through its contacts API. Packing public fields into notes or
   description is worse because it corrupts user-owned data. Extend the rest_core
   contact schema and add an idempotent public-profile upsert before enabling
   download/publish in a release. A temporary sidecar is suitable only for a
   disposable UI prototype, not production persistence.

5. addContact/create is insufficient for self and existing contacts.

   The plan says to optionally call addContact for self, but create can reject a
   duplicate and cannot safely refresh public fields. Add a local upsert keyed by
   (denomination, serial_number). It must preserve private fields such as notes,
   favorite, and trust level. Do not delete/recreate an existing contact.

6. Make local-first semantics exact and composite-keyed.

   Address strings can have formatting variants. Determine contact existence by
   denomination plus serial number. If any local row exists for that exact key,
   automatic public lookup must not run, even when its public fields are blank,
   unless the product explicitly defines a manual refresh operation.

7. Batch background lookups after rendering.

   The proposed trigger is good, but it should be more explicit: render the mail
   page first, collect unique sender identity keys, subtract a local-contact map,
   and enqueue a bounded background batch. Do not put awaited remote calls in
   getMailList/getEmailById mapping. Share in-flight and negative-cache entries
   between list and reading-pane triggers.

8. Account for lookup privacy.

   Exact sender lookups reveal to RAIDA11 which identities the installation is
   trying to resolve and can expose correspondence relationships. Never send
   subject, message ID, or timestamp. The product owner should decide whether
   automatic lookup is always on, requires notice/consent, or has a setting.

9. Harden user_hints behavior.

   Do not allow a parameterless request to dump the directory. Require at least
   one bounded criterion or return only a deliberately curated page. Add cursor
   pagination, stable ordering, maximum limit, rate limits, LIKE wildcard
   escaping, and an exact (denomination, serial_number) path. A first/last-name
   prefix result must never be auto-associated with a mail sender.

10. Tighten the MySQL model.

   qcon1/qcon2/qcon3 can be nullable TINYINT UNSIGNED, not signed SMALLINT.
   inbox_fee should use a range chosen after its unit is defined; BIGINT UNSIGNED
   is safer if it represents atomic units. Add revision and created_at, validate
   QCon uniqueness in application code, and use a canonical generated/stored
   qmail_address only if prefix lookup needs it. The identity key remains the
   composite numeric key.

11. Define empty QCon semantics.

   Distinguish "field absent/no published profile," an explicit empty array
   meaning "use deterministic fallback," and nullable slots. Preserve order,
   allow index 0, reject duplicates/out-of-range values, and return a single
   normalized qcons array in JSON even if MySQL uses three nullable columns.

12. Treat the endpoint routes as unavailable until deployed.

   Direct checks on 2026-07-01 returned HTTP 404 for /update_users,
   /update_users.php, /user_hints, and /user_hints.php. The apparent user_hints
   URL typo and the final no-extension rewrite rules need confirmation before
   GUI integration.

Suggested delivery order
------------------------

1. Freeze serial width, QCon semantics, fee unit/range, routes, JSON schemas,
   and ownership proof.
2. Implement and integration-test the PHP/MySQL service in staging.
3. Extend the rest_core contact schema/list/upsert API and migrate existing data.
4. Implement the GUI service/resolver and QCon model with unit tests.
5. Implement the modal/menu and background sender-resolution queue.
6. Run failure-path, privacy, CORS/IPC, multi-instance, packaging, and restart
   tests before enabling the menu in production.

Specific changes worth carrying into the GPT plan
-------------------------------------------------

I incorporated Fable's useful mail trigger into docs/gpt.qcons.txt: resolve a
deduplicated batch of unknown senders only after the mail page renders, keep
reading-pane requests on the same cache, and test that remote latency never
blocks mailbox display. I also added canonical-address indexing detail and the
directory-lookup privacy decision that both original plans needed.
