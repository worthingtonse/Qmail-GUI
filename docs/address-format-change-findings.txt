PART 0: THE SETTLED SPEC (Phase 1)
================================================================================

ADDRESS STRUCTURE (4 bytes total)
    byte 1..3 : serial number (3 bytes, big-endian as displayed)
    byte 4    : denomination code
    Denomination codes (existing table in coin_denom.c KEPT):
        0 = bit  (1 cc)      3 = mega (1000 cc)
        1 = byte (10 cc)     4 = giga (10000 cc)
        2 = kilo (100 cc)
    Fractional denominations (0xFF = .1cc, 0xFE = .01cc, ...) are NOT
    valid qmail addresses in Phase 1 - reject them.
    Serial number 0.0.0 is RESERVED - never a valid address.

ACCEPTED INPUT FORMS (what a user may type in To:)
    a) 0.51.254.0      full numeric: 3 serial bytes + denom code
    b) 51.254.0        leading zero serial bytes dropped (any number of
                       them): parser counts groups from the RIGHT -
                       last group = denomination code, the rest are the
                       low serial bytes.  "254.0" and even "254.4" valid.
    c) 51.254@bit      serial groups (zeros dropped) + '@' + denom WORD.
                       "254@bit" valid.
    - groups are decimal 0-255, no leading '@', no name part.
    - invalid input -> MODAL dialog explaining the valid forms (not just
      an inline error).

CANONICAL DISPLAY FORM (inbox, reading pane, contacts, everywhere)
    51.254@bit     (zeros dropped, @ + denomination word)

CARTOUCHE (avatar)
    - symbols come from public/qmail-avatars/NewAvatars/000.svg-255.svg
      (256 symbols; files 256.svg-259.svg in that folder are unused extras)
    - symbol count mirrors the zero-dropping of the text address:
        serial byte1 != 0           -> 3 symbols (byte1, byte2, byte3)
        byte1 == 0, byte2 != 0      -> 2 symbols (byte2, byte3)
        byte1 == 0 and byte2 == 0   -> 1 symbol  (byte3)
    - border/frame color = denomination (reuse existing frames/ assets)
    - goal: each of the 256 symbols has its own distinct color

NAMES & CONTACTS (the only aliasing in Phase 1)
    - the canonical address has NO name part (First.Last@ prefix is gone)
    - first time a user composes to a new dotted-decimal address, offer to
      associate a first/last name -> creates a contact
    - To: field behavior: typing digits = direct address entry; typing a
      letter filters a dropdown of contacts by first/last name; choosing a
      contact fills in their address (display can show the name)

EXPLICITLY OUT OF SCOPE FOR PHASE 1 (planned Phase 2)
    - DNS aliases (A-record style: Sean.raidatech.com -> 0.51.254.0) and a
      custom root DNS with bit/byte/kilo/mega/giga TLDs
    - the published user directory (qmail_users.csv) - REMOVED in Phase 1
    - no transition/backward compatibility needed (no beta released);
      word-list system is removed outright; assume all clients are new

PART 4: DECISIONS LOG (all questions resolved)
================================================================================
1. Serial is 3 BYTES + 1 denomination byte (4 total). Earlier 4-byte-serial
   assumption withdrawn.
2. Denomination codes keep the EXISTING mapping: 0=bit 1=byte 2=kilo
   3=mega 4=giga. (The example "0.51.254.1 = bit" in discussion was per
   the old assumption; with 0=bit the address is 0.51.254.0.)
3. Phase 1 = whole-cc notes only; fractional denom codes rejected.
4. Canonical display = "51.254@bit" (@word form).
5. Numeric input may drop ALL leading zero serial bytes; groups counted
   from the right (last = denomination code).
6. No leading '@'. Invalid input -> explanatory modal.
7. Canonical address has no name part; names live in user-created
   contacts only (first-compose prompt creates them).
8. Cartouche shows 1-3 symbols mirroring zero-dropping; border color =
   denomination.
9. qmail_users.csv user directory: removed for Phase 1.
10. Word lists (RAIDA services, caches, embedded defaults, GUI assets):
    removed outright; no transition, no cleanup staging - all clients new.
