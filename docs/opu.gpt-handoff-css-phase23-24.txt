2. PHASE 2.4 — MOTION-SCALE WIRING (commit 97899a2)
===============================================================================

Two layers. The token-side fix is the architectural lever; the per-
site rewrites just clean up the long tail.

2.1  Token-side fix (tokens.css)
--------------------------------
The four --transition-* tokens previously hard-coded their ms value:

  Before:
    --transition-fast:   150ms cubic-bezier(...)
    --transition-base:   250ms cubic-bezier(...)
    --transition-slow:   350ms cubic-bezier(...)
    --transition-smooth: 400ms cubic-bezier(...)

That meant ~28 existing consumers of `var(--transition-base)` in
E1-E7 silently ignored --motion-scale. The plan §2.1 had originally
promised calc()-form tokens; this commit delivers them.

  After:
    /* Raw ms (for compose cases) */
    --transition-fast-ms:   150ms;
    --transition-base-ms:   250ms;
    --transition-slow-ms:   350ms;
    --transition-smooth-ms: 400ms;

    /* Motion-scale-aware (for direct use in `transition:`) */
    --transition-fast:   calc(var(--transition-fast-ms)   * var(--motion-scale)) cubic-bezier(...)
    --transition-base:   calc(var(--transition-base-ms)   * var(--motion-scale)) cubic-bezier(...)
    --transition-slow:   calc(var(--transition-slow-ms)   * var(--motion-scale)) cubic-bezier(...)
    --transition-smooth: calc(var(--transition-smooth-ms) * var(--motion-scale)) cubic-bezier(...)

Every existing var(--transition-*) consumer now respects motion-scale
through the cascade. The App.css !important block at L549-560 stays
as defense in depth alongside the high-contrast P2 (a) safety net.

2.2  Per-site raw-duration rewrites
-----------------------------------
46 sites where transitions / finite-animations carried raw `0.3s`,
`200ms`, `0.4s` literals.

  transition: all 0.3s ease;
     → transition: all calc(300ms * var(--motion-scale)) ease;

  animation: fadeIn 0.4s ease-out;
     → animation: fadeIn calc(400ms * var(--motion-scale)) ease-out;

  transition: width 0.3s ease, height 0.3s ease;
     → transition: width calc(300ms * var(--motion-scale)) ease,
                   height calc(300ms * var(--motion-scale)) ease;

Per-file:
  src/wallet/components/MainDashboard.css        12
  src/wallet/components/tabs/AuthenticateTab.css 10
  src/wallet/components/tabs/ExportTab.css        9
  src/wallet/components/tabs/LockerTab.css        7
  src/App.css                                     5
  src/screens/ServiceSelectionScreen.css          3
                                                 ---
                                                  46

2.3  Deferred (21 infinite animations)
--------------------------------------
`animation: shimmer 2s infinite`, `animation: spin 1s linear infinite`
and similar are NOT rewritten because calc(2s * 0) = 0s × infinite
is undefined behaviour (some browsers replay the keyframe set
infinitely fast → GPU thrash). The P2 (a) high-contrast block and
the prefers-reduced-motion block in App.css both force animation-
duration to 0.01ms !important which handles infinite animations
correctly (1 frame, done).

Sample deferred sites:
  src/App.css:301                                 animation: shimmer 2s infinite
  src/App.css:379                                 animation: cursor-spin 1s linear infinite
  src/wallet/components/MainDashboard.css:685     animation: shimmer 3s infinite
  src/wallet/components/MainDashboard.css:1801    animation: spin 1s linear infinite
  src/screens/ServiceSelectionScreen.css:53       animation: float 3s ease-in-out infinite
  + 16 more

Plan for these: revisit in Phase 3 / Phase 5 cleanup. A possible
cleaner mechanism is `animation-play-state: paused` under HC, but
the current !important block already works.

Verification:
  npm run build      ✓ 2.14s, 240.89 kB CSS / 423.70 kB JS
  npm test           ✓ 30/30 (no JSX touched)
  npm run css:audit  ✓ ran clean

Debt impact:
  The audit doesn't track transition durations as raw literals (no
  transition_props category in config.json). So the 247→177 line
  on inventory.csv is unchanged by Phase 2.4. The leverage is
  semantic — every transition consumer in E1-E7 now respects
  motion-scale via the cascade, not via the !important block.

3. METHOD NOTES (continuing your prior-review threads)
===============================================================================

3.1  ≤5% inclusive rule
-----------------------
Held through both phases. Phase 2.3 spacing-pair candidates were
strictly tier-exact (no near-miss numerics involved) because both
halves had to land on the scale. Phase 2.4 has no tolerance question:
the values were direct durations; rewrite or skip.

3.2  Comma-separated lists
--------------------------
Phase 2.4 had a subtle case my first swap script missed:
`transition: width 0.3s ease, height 0.3s ease` is two segments,
each with its own duration. My initial implementation only wrapped
the first time token; I caught it during spot-check before commit
and updated the script to split on `,` and wrap each segment's first
time token independently. Both halves now read `calc(300ms * var(--motion-scale))`.

3.3  Helper-script lifecycle
----------------------------
Same pattern as 2.2: write `tmp-phase2.X-{count,swap}.mjs` into
scripts/css-analysis/ for execution, then `rm` before commit. None
committed. The "what gets shipped" rule is documented in plan v2.5
and now exercised across three sweeps without leakage.

3.4  --transition-*-ms exposure (new in 2.4)
--------------------------------------------
The new raw-ms tokens give component CSS a clean way to compose
durations differently. Example use case: an animation that should
still tick under motion-scale > 0 but use the project's base
duration as a reference:

  /* Hypothetical: a custom-easing version */
  .my-bounce {
    transition: transform calc(var(--transition-base-ms) * var(--motion-scale))
                cubic-bezier(0.34, 1.56, 0.64, 1);
  }

That's the same shape as --transition-smooth except inlining the
easing. The raw-ms layer means consumers can mix-and-match without
hard-coding 250ms again.

5. QUESTIONS FOR GPT
===============================================================================

Q1. Token-side change in tokens.css — should we have done it sooner?
--------------------------------------------------------------------
Reading back through plan v2.5 §2.1 + your earlier reviews, this
calc()-form rewrite was always the right move. I held it until
Phase 2.4 because:
  - the scope was conceptually about "wiring motion-scale," not
    "swapping raw literals"
  - touching tokens.css affects all 22 files, not just E1-E7

But the ~28 token-consumer sites in E1-E7 (and many more in the
IN-REVIEW E-tracks) silently ignored --motion-scale until this
landed. So in retrospect, this could/should have shipped with
Phase 0.5 or as its own tiny commit immediately after.

Was the timing OK, or would you have pulled this earlier?


Q2. Phase 3 vs. Track F BEM mapping ordering
--------------------------------------------
Plan v2.5 §4 has:
  Phase 3 (primitive extraction)  ← uses the audit's collisions
  Track F (BEM mapping)           ← feeds Phase 4 per-file rename

Both want input from the audit. Phase 3's primitive extraction will
need names like `.btn`, `.btn--disabled`, `.btn--primary-gradient`,
`.focus-ring`, `.status-message`. Track F's mapping currently
includes some of these too.

Should Track F be done FIRST (proposes the global names), then
Phase 3 extracts to those names? Or Phase 3 first (decides which
primitives are needed), then Track F maps the per-component renames
around them?

My read: Phase 3 first because the collisions report TELLS us which
classes deserve primitives. Track F then becomes "what are the
per-component renames for the classes Phase 3 didn't pull out."
Without Phase 3, Track F has to guess which collisions become
primitives vs. renames.

Push back if you'd sequence them the other way.
