# Gemini CLI Feedback on QMail-GUI Usability Fix Plan
Date: 2026-05-21
Reviewer: Gemini CLI

## 1. Overall Assessment
The plan provided in `opu.usability.fix.plan.txt` is excellent—it is technically grounded, well-sequenced, and addresses the most critical "trust-eroding" issues identified across all model audits. The grouping into phases correctly prioritizes functionality (Phase 0) followed by customary email actions (Phase 1).

## 2. Technical Feedback by Phase

### Phase 0: Critical Fixes
- **FIX-01 (Body Hydration)**: **Strongly Agree.** The proposed retry logic (3 tries, 500ms backoff) is a vital addition to handle potential indexing lag in the backend DB. This is a common pitfall in distributed systems.
- **FIX-02 (Attachments)**: **Strongly Agree.** Moving the file picker to the Electron layer via IPC is the correct architectural choice for a desktop app. The browser fallback is a proactive measure for environment parity.
- **FIX-03 (Identity Verification)**: **Strongly Agree.** This is essential to kill the "John Doe" ghost. Suggestion: Ensure the "Loading..." state in `AccountPane` doesn't block access to the RAIDA status dots, as users may want to check connectivity even if their identity is slow to load.
- **FIX-04 (Draft Hydration)**: **Crucial.** Loading the full draft body before opening the modal prevents accidental data loss during saves.

### Phase 1: High Priority
- **FIX-08 (Sent Folder)**: **Validation Required.** While the plan correctly notes this as "Primarily Backend," I recommend the GUI implement a "Local-Only Outbox" or temporary success state if the backend change (CORE-A) is delayed. A user needs immediate visual confirmation that their mail is no longer just in their head.
- **FIX-09 (Contact Schema)**: **Agreement with Caveat.** If `sn-from-address` (CORE-C) isn't ready, the GUI should emphasize that SNs are required for now. A "Lookup" tool (as mentioned in FIX-42) should be accelerated to "High" if CORE-C is delayed.
- **FIX-16 (Hide Dead Controls)**: **Recommendation: Approach B (Coming Soon).** I prefer greying out features like "Change Password" over total removal. It communicates that the app *will* be a full suite eventually, whereas removal might make the app feel "barren." However, "Delete Account" should definitely be hidden as proposed.

### Phase 2 & 3: Polish & Backlog
- **FIX-22 (Send Preflight)**: The move to `canSend = null` (Checking...) is a major UX win over the current "Optimistic" behavior.
- **FIX-31 (Remove Parity)**: **Agreed.** Removing parity UI is the right move for v2 to reduce noise and confusion.

## 3. Recommended Additions / Considerations
1.  **Poll Rate Configuration**: While FIX-47 mentions wiring `checkForNewMail` back in, we should consider if the 10s/60s intervals should be user-configurable in a "General Settings" tab later.
2.  **Attachment Security**: For FIX-19, ensure the "dangerous" flag UI is visually distinct (e.g., using `Lucide-ShieldAlert`) to prevent users from accidentally clicking executable files.

## 4. Final Verdict
**Approved for Execution.** The manual-verification checklist at the end of the plan is the correct "Definition of Done." I recommend starting with Phase 0 immediately, specifically focusing on the body hydration (FIX-01) and identity verification (FIX-03) to stabilize the primary user journey.
