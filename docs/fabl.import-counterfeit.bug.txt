SYMPTOM (user report, meeting prep for Michelle)
------------------------------------------------

FIRST THINGS FIRST: THE COINS ARE NOT DESTROYED
-----------------------------------------------
The deposit pipeline MOVES files, it never deletes them:
  1. Phase 1 "MOVE" relocates every file from the user-picked folder into the
     QMail wallet's internal Import folder (cmd_deposit.c:998, 1033-1037).
     THIS is why CC Desktop's folder emptied — its own reconciliation then
     logged the -11.0 "Balance Adjustment" (that entry is CC Desktop noticing
     the files vanished, not a network spend).
  2. After the legacy pipeline declared them counterfeit, the ORIGINAL files
     were moved byte-for-byte, unmodified, to:
        <user's QMail data>\Client_Data\Wallets\Default\Counterfeit\CCv2\
     (cmd_upgrade.c:222-248 upgrade_disposition_file; subfolder built at
     306-318). If they instead took the non-legacy route, they are in
     Counterfeit\ directly. Either way: intact, ANs untouched — the failed
     shard-switch never re-keys legacy coins (RESULT_ERROR aborts before any
     CCv3 notes are written).
  RECOVERY: copy the files from Counterfeit\CCv2\ back into the CC Desktop
  wallet's Bank folder. CC Desktop's balance returns on its next scan.

WHAT ACTUALLY HAPPENED (pipeline trace, verified in source)
-----------------------------------------------------------
GUI "Folder" import -> /api/transactions/deposit (folder) -> core deposit:
  MOVE -> UNPACK. UNPACK classifies each .bin by its FIRST BYTE:
    0x00 -> legacy CloudCoin v2 file -> parked in Import\CCv2\ for the
    upgrade pipeline (cmd_unpack.c:77 -> cmd_convert.c:250-276).
  CC Desktop 23.11.28 writes v2-format files, and every CCv2 coin is worth
  exactly 1 CC (cmd_convert.c:560-562) — 11 files x 1 CC = the user's 11.0
  balance. The legacy route is all but confirmed by that arithmetic.

  UPGRADE then converts parked coins via RAIDA (GetSNs + SwitchShardNoSum,
  cmd_convert.c). The counterfeit label is only applied on a REAL verdict:
    - >=13 RAIDAs answering ALL_FAIL (status 242) forms a counterfeit quorum
      (cmd_convert.c:1252-1259), or a per-coin pass-vote bitmap below 13
      (cmd_convert.c:1272-1278).
    - Timeouts / unexpected statuses / encryption rejections count as
      ERRORS and abort retryably — they can NEVER mark coins counterfeit
      (cmd_convert.c:1222-1230, 1260-1267; cmd_upgrade.c:261-264).
  So >=13 RAIDAs actively rejected the ANs that were presented for these 11
  coins. The question is why — the user's own history shows these coins
  working through Feb 2024 (deposits, locker codes). 11/11 uniform rejection
  smells like systematic corruption of what we SENT, not 11 real fakes.

  Downstream cascade: with 0 coins surviving, identity provisioning finds no
  coin >= 1 CC -> the second error banner. Not a separate bug.

ROOT-CAUSE HYPOTHESES (ranked)
------------------------------
H1 [PRIME SUSPECT — parser ignores the legacy header, incl. its encryption
    flag]: legacy_parse_cc2_file reads the 32-byte CCv2 header and then
    IGNORES it entirely ("Header validation is done by legacy_detect...",
    cmd_convert.c:513-521 — and detection only looks at byte 0, explicitly
    ignoring other header bytes, 260-273). It then reads raw bytes at body
    offset 16 as plaintext ANs (543-570). CloudCoin Desktop wallets support
    password protection, which encrypts the AN section on disk. If the
    user's CC Desktop wallet is password-protected, we sent AES-encrypted
    bytes as ANs -> every RAIDA correctly rejects -> "counterfeit".
    This connects to the "encryption checking" hunch — but it is the OLD
    password encryption being ignored, not the new Type 10 work.
H2 [POSSIBLE — format variant]: if CC Desktop 23.11.28 writes a v2 body
    layout that differs from our assumptions (SN 3-byte BE at offset 0,
    ANs at offset 16, 416-byte body), parsing garbage has the same outcome.
    One hexdump of a quarantined file settles H1 vs H2 instantly.
H3 [POSSIBLE — server side]: the RAIDA legacy shard-2 records for these SNs
    were lost/migrated since 2024 -> genuine ALL_FAIL despite valid files.
    Would hit Michelle identically; needs a server-team check of shard-2
    data for the SNs in the quarantined files.
H4 [RULED OUT as cause — the new Type 10 / file-encryption changes]:
    - The new "reject encrypted Type 9" gate (coin_file.c:428-440, commit
      9e7c85d Jul 30) only fires for files whose first byte is 0x09. CCv2
      files (0x00) never reach it — they branch to the legacy path first.
    - Unpack quarantines encrypted NATIVE files to Encrypted\ with a log
      warning — counted as neither counterfeit nor imported
      (cmd_unpack.c:435-448). Not the observed message.
    - Fresh install -> no encryption key -> GetSNs returns NOT_FOUND ->
      deposit retries unencrypted BY DESIGN (cmd_deposit.c:1177-1188).
      And if RAIDAs rejected unencrypted requests, that maps to error_count
      -> retryable abort, not counterfeit.
    Sean's hunch was reasonable — the timeline fits (Type 10 codec Jul 30,
    session/write-gate Jul 31, Z-folder Aug 3, CCv1/CCv2 import rework
    Jul 29 — all in the last build) — but the code paths do not connect the
    Type 10 work to a counterfeit verdict on 0x00-format files.

RECOMMENDED FIXES (NOT applied — for the next round)
----------------------------------------------------
1. [HIGH, core] Non-destructive import for external folders: COPY files into
   Import\ and leave the originals until the deposit fully succeeds; or
   restore-on-failure. A first-run user pointing at ANOTHER program's live
   wallet must never end with that wallet emptied.
2. [MED, core] legacy_parse_cc2_file: honor the CCv2 header — detect the
   password/encryption flag and refuse with a specific error ("This CC
   Desktop wallet is password-protected. Remove the password in CC Desktop,

3. [MED, GUI] The counterfeit warning should say where the files are
   ("moved to the wallet's Counterfeit folder") and what to do next; the
   follow-on "no identity coin" banner should be suppressed when the import
   itself failed for all coins.
4. [LOW, GUI] Pre-flight notice when legacy v2/v1 files are detected in a
   chosen folder: "These are older CloudCoin files; they will be converted."
5. [Server/team] Verify legacy shard-2 data integrity for the affected SNs
   once the quarantined files are in hand (H3).

WHAT THIS IS NOT
----------------
- Not coin destruction: originals are quarantined intact in
  Counterfeit\CCv2\ inside the QMail Default wallet.
- Not the Type 10 file-encryption feature (H4 above) — timeline fits, code
  paths do not.
- Not the withdraw/locker bug fixed earlier today (fabl.withdraw.bug.txt) —
  unrelated pipeline (deposit/upgrade vs. locker spend).
- Not RAIDA availability: a counterfeit quorum needs >=13 RAIDAs actively
  answering ALL_FAIL; pure outages/timeouts abort retryably instead.
