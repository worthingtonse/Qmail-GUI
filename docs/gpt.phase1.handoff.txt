Batch 5 follow-up note
----------------------
GPT found attachment bugs after the Electron picker landed:

  1. Paths with comma or semicolon delimiters could be broken by backend parsing.
  2. The backend aggregate attachment buffer can silently drop paths on overflow.
  3. Save Draft does not persist staged attachments.

Opus says the GUI follow-up has been applied in ComposeModal:

  - Reject attachment paths containing "," or ";" before staging.
  - Cap attachment count at 50 and combined path length at 12000 bytes.
  - Show a warning that attachments are sent but not saved with drafts.
  - Track the real backend fixes as CORE-M and CORE-N in the master plan.

When starting Phase 1, preserve those attachment guards and the draft warning.
Attachment send remains an important regression check for any ComposeModal work.

Start here: Batch 6
-------------------
The first useful implementation session should start with Batch 6.

FIX-05.5 is the prep refactor:

  - Replace ComposeModal's replyTo/editDraft props with one composeContext prop.
  - Hard cutover only. No compatibility shim.
  - Shape:

      composeContext = {
        mode: "new" | "reply" | "replyAll" | "forward" | "draft",
        sourceEmail: <email>,
        ownIdentity: <normalized identity>,
        draftId: <draft id for draft mode>
      }

  - QMailDashboard should construct the context for every opener:
      new compose, reply, reply all, forward, and hydrated draft open.
  - ComposeModal derives recipients, subject prefix, quoted body, and draft id
    from composeContext.mode.
  - Preserve currentDraftId behavior from Batch 3/4 so editing an existing draft
    updates the same draft instead of creating a duplicate.

FIX-06 adds Forward:

  - Add the button in ReadingPane near Reply.
  - Subject should be "Fwd: <subject>" without double prefixing.
  - Body should include a forwarded-message quote.
  - To should be blank.
  - Disable Forward for undownloaded/pending messages with an honest tooltip.

FIX-07 adds Reply All:

  - Add the button in ReadingPane near Reply.
  - To should include the sender.
  - Cc should include original To/Cc minus the current user's own identities.
  - Own-address filtering must compare serial number, address, auto_address, and
    display/pretty address forms from the normalized identity.
  - If recipient data is not stored, disable Reply All with a tooltip rather
    than guessing.

Important conventions
---------------------
- normalizeIdentityForUi returns both camelCase and snake_case fields. Keep that
  convention. Do not simplify consumers to only one style.
- Do not synthesize fake server state. No fake Sent rows, fake mark-read
  persistence, or fake identity health.
- Coming Soon/dead controls should be visibly disabled or hidden, not silent
  no-ops.
- Use the existing UI style. Keep the app tool-like and dense, not marketing-like.
- Do not introduce new lint categories. Existing lint is noisy, so compare
  touched-file lint against baseline when possible.
- The worktree has many user/Opus changes and untracked docs. Do not reset,
  checkout, or revert unrelated files.

Open hazards to keep in mind
----------------------------
- docs\gpt.bugs.txt currently tracks several broader bugs. Some may have been
  fixed by Opus after the review; verify current code before acting on them.
- Attachment backend issues CORE-M/CORE-N remain real even with GUI guards.
- Sent persistence and Repair Now are backend-blocked. Do not ship GUI-only
  behavior that pretends those server facts exist.
- Reply All quality depends on recipient data actually being present in the
  hydrated message. If the backend does not return full To/Cc/Bcc for a message,
  the honest behavior is to disable Reply All or fall back to plain Reply.
