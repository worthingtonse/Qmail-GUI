4. The consensus-fetch mechanism (already exists)
-------------------------------------------------
rest_core/src/raida_servers.c:75-107 already calls
raida_consensus_fetch("raida_servers", ...) on every boot:
  - 3 attempts of 3 fetches each
  - Requires 2-of-3 consensus per round
  - Iterates: https://raidaN.cloudcoin.global/service/raida_servers
    (DNS_URL_TEMPLATE = "raida%d.cloudcoin.global" — defined in
    rest_core/include/api/api_rest.h:155)
  - On success, REWRITES raida_ips.csv with the fetched list

So the canonical-source download IS happening — but it must be
failing to reach consensus for Sean. Possible reasons:
  (a) The same stale RAIDAs the GUI sees timing out are the
      ones serving the consensus list. If the consensus
      fetcher's HTTP timeout is also short, it fails before
      enough valid RAIDAs respond.
  (b) DNS for raidaN.cloudcoin.global might point at the same
      stale IPs (or be unresolved for the renamed RAIDAs).
  (c) The consensus fetch is succeeding but writing a stale
      list because the CONSENSUS itself ratifies the wrong
      IPs — i.e., a majority of the central servers also have
      the old IPs. Unlikely but possible during a rollout
      transition.
  (d) The HARDCODED list is "good enough" to get consensus on
      most entries but agrees on the wrong IP for some,
      because the same wrong IP is the historical default
      everywhere.
  Diagnostic: need to read rest_core's main.log around startup
  to see whether "Consensus found! Updating server list."
  appears, or whether all 3 attempts log "No consensus."

5. Echo timeout — is 3000ms too short?
--------------------------------------
GUI calls handleEchoTest at
src/wallet/components/tabs/SettingsTab.jsx:20. The endpoint is
core.exe's /api/raida/echo or similar; per-RAIDA timeout is
the executor's `config.timeout_ms`. From main_rest.c:240,
QMAIL_HEALTH_REFRESH_ECHO_TIMEOUT_MS = 3000 (the background
health refresh — separate from the GUI button but same value
class).

3 seconds is on the short side for transatlantic RAIDA hops
under load. But IF the IP is correct and the RAIDA is up, a
healthy echo should complete in well under 1s. 3s timing out
strongly suggests dead IPs, not slow ones. Bumping the timeout
to 6-10s might mask a few flaky-but-alive RAIDAs but won't
help the dead-IP cases.

Recommendation: fix IPs first. If failures persist after IP
freshness is confirmed, then raise timeout.


Root cause (in priority order)
==============================
1. **PRIMARY**: rest_core's stored raida_ips.csv AND its
   hardcoded fallback list are both stale by ~6 IPs. The
   on-boot consensus fetch is supposed to refresh this but
   either isn't running, isn't reaching consensus, or is
   ratifying a stale-but-popular list.

2. **SECONDARY (potential)**: If `-r11ip` is being passed by
   QMail.exe (or by the user via the new --r11ip flag from
   BUG-51), RAIDA 11 is forced to a LAN IP (192.168.1.102)
   that doesn't host anything on Sean's current network. The
   working client uses 96.86.143.105 for RAIDA 11. The flag
   needs to be REMOVED per Sean.

3. **TERTIARY**: 3-second echo timeout is borderline but
   probably not the root cause — fix IPs first, re-measure.

What this means
---------------
The central distribution itself is stale. The consensus
mechanism is doing exactly what it's designed to do: ask the
central RAIDAs, take majority, write that out. The data on
the central RAIDAs is wrong.

The working desktop client (`._id6.guardians`, last modified
~1 hour before this test) tracks a DIFFERENT and apparently
fresher list than `raida11.cloudcoin.global/service/raida_servers`
returns. So:
  - Either the working client uses a different update source
    (something other than the consensus-fetch endpoint), OR
  - The working client is no longer auto-updating and its list
    is "frozen-correct" from before the central data went
    stale, OR
  - The working client has manual overrides that it persists.

Updating the hardcoded list in rest_core (PHASE 2) IS still
correct as a future-proofing measure — when the consensus
fails (e.g. all 3 attempts return no consensus, or the central
RAIDAs are unreachable), the hardcoded list is the fallback.
But it doesn't help today because consensus is succeeding with
bad data.

Available paths forward (Sean's decision needed)
------------------------------------------------
A. **Diagnose the working client.** Find out where
   ._id6.guardians is sourced from. If there's a different
   update endpoint or scheme, point rest_core at the same
   one. This is the right long-term fix but needs Sean to
   share info about the working client's update logic.

B. **Patch the consensus output before writing.** Add a
   per-RAIDA cross-check: after consensus produces a result,
   echo each IP and only accept the consensus IP if it
   responds. Stale IPs in the consensus result get replaced
   by either the hardcoded fallback or the previously-stored
   IP. Code-intrusive, but it would make the system
   self-healing against bad-central-data scenarios.

C. **Disable the consensus overwrite for now.** Comment out

   With the file deleted and the new hardcoded values landed

   intervention would be needed.

D. **Refresh the central RAIDAs.** Update the data on the
   actual central servers so consensus returns the right
   answer. Out of GUI / rest_core scope; that's network ops.

E. **Hybrid: hardcoded list + opt-in consensus.** Add a
   config flag (rest_core.conf or CLI) like
   `raida_consensus_refresh=false` so the default behaviour
   trusts the hardcoded list. Users / dev environments who
   want auto-refresh enable it explicitly. Best of A+C: safe
   default, opt-in to the broken-today refresh.

My recommendation: (E) for the immediate user-visible fix,
plus (A) as a parallel investigation. (C) is the
quick-and-dirty version of (E).

What this means for the diagnosis
---------------------------------
The architectural direction is "RAIDAs ARE the source of truth."
The current bug is therefore NOT a design flaw — it's a data
freshness problem at the RAIDA layer. The RAIDAs are serving
stale `service/raida_servers` responses. Specifically:

  - The working desktop client's `._id6.guardians` shows the
    "correct" IPs because the guardians are independent
    third-party watchers with their own update process.
  - The RAIDAs themselves, when queried via
    `https://raida<N>.cloudcoin.global/service/raida_servers`,
    return a list with stale IPs for RAIDAs 4, 8, 10, 11, 18.
  - rest_core's consensus correctly aggregates the (stale)
    RAIDA responses → writes stale data back to raida_ips.csv.
  - rest_core is doing its job. The data upstream is wrong.

Sean's manual reconnaissance reinforces this: he checked the
raida_servers endpoint on all 25 RAIDAs and ALL of them had
correct IPs EXCEPT RAIDA 4. So:

  - **The RAIDA-4 entry IS legitimately stale in the central
    data**, on every RAIDA. That's a deploy-side fix, not
    something rest_core can solve.
  - **The other timeouts (RAIDA 8, 10, 11, 18) per Sean's
    inspection have CORRECT IPs in the central data** — yet
    rest_core is still using stale IPs for them.

That contradiction needs explaining. Two possibilities:

  (a) The 2-of-3 consensus is succeeding on a minority of
      stale-RAIDA responses by accident. The fetch picks
      3 random RAIDAs and requires 2 to match. If the random
      sample happens to include 2 RAIDAs that haven't been
      updated yet, those 2 "win" the consensus even though
      the other 23 RAIDAs have the right data.

  (b) The consensus IS receiving the right data, but the
      RESPONSE PARSING or WRITE path has a bug that
      preserves old IPs. Less likely given the file change
      Sean observed (RAIDA 18 wrote a NEW-but-wrong IP, not
      the old hardcoded fallback).

Per Sean's observation about RAIDA 18 going to 24.23.27.180
(neither the old hardcoded value 24.23.26.36 nor the
authoritative 24.10.63.29), (a) is more likely. The
consensus IS getting updates but only from a minority of
RAIDAs and ratifying them.

Also: Sean observed rest_core wrote to raida_ips.csv while
he had the file open in an editor. That's the
raida_servers.c consensus-success branch (lines 92-98)
rewriting the file every boot. Causes confusion + risks
data loss if the user is hand-editing.

Revised recommendation
----------------------
Three things, each independently shippable:

  **A. Sample more RAIDAs in consensus (the real fix).**
     Change `consensus_cfg.fetch_count` from 3 to something
     larger like 9 or 15, and `consensus_needed` from 2 to a
     supermajority like 7 or 11. With 25 RAIDAs total and
     most having correct data, a larger sample plus higher
     threshold reduces the chance that a minority of
     stale RAIDAs wins. Touches one line each in
     raida_servers.c and qmail_servers.c.
     Estimated: ~4 lines edits, low risk.
     Caveat: increases boot HTTP traffic ~3-5x but each fetch
     is small JSON. Acceptable.

  **B. Refresh the hardcoded fallback list (already drafted
     in PHASE 2).** Keep as-is. When consensus FAILS entirely
     (all 3 attempts return no consensus), the hardcoded list
     is what gets used. The current 6 IPs are stale and need
     correction whether or not (A) is implemented. The 5 IPs
     I already corrected from `._id6.guardians` are the right
     values per Sean's audit, except possibly RAIDA 4 which
     even the central data has wrong — leave the hardcoded
     value matching `._id6.guardians` (57.128.255.93) since
     that's the authoritative working IP per the desktop
     client.

  **C. Don't write raida_ips.csv unless it changed.** The
     current code writes the file on every consensus success
     regardless. Add a content compare: if the new content
     equals the existing file content, skip the write. Fixes
     Sean's "file changes while I'm editing it" annoyance
     AND removes a class of "did anything change?" debugging
     friction. Same fix should apply to qmail_servers.json.
     Estimated: ~15 lines per file.

  **D. (NOT recommended) Stopgap: disable consensus
     overwrite.** Would give 22/25 today but bake in the
     assumption that the hardcoded list never needs updating.
     The whole architecture is "RAIDAs are the source of
     truth" — disabling consensus contradicts that. Reject.
