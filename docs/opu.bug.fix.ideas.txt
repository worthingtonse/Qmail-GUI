BUG-51 — File structure not implemented on first launch
==========================================================
Reported by: Sean (manual GUI testing, 2026-05-24)
Status:      Proposed plan, awaiting Sean's "go"
Severity:    HIGH  (blocks one-file-distribution goal)

Sean's report (paraphrased)
---------------------------
QMail.exe should be a single-file distribution. Currently the user
has to put core.exe next to QMail.exe for the folder structure
(Client_Data, sub-folders, etc.) to be created on first launch.
Goal: ship JUST QMail.exe; on first launch QMail.exe creates the
runtime layout and starts core.exe with the right args.

Sean's brain-storm bullets:
  a. Maybe QMail.exe extracts core.exe next to itself on first run
  b. Pass through QMail.exe's own CLI args to core.exe
  c. Let QMail.exe set the backend port via arg, else random (default)
  d. Toggle core debug mode from QMail.exe args
  e. Toggle the dev-only "RAIDA 11 fix" (r11ip) from QMail.exe args
  f. Acknowledged the bundle test may be stale — newest builds may
     already do (a) — please confirm

What I found in the code (current behavior)
-------------------------------------------
electron.cjs and electron-builder.config.cjs already implement
most of Sean's goals. The actual gap is narrower than the report
suggests.

ALREADY WORKS:
  - core.exe IS bundled inside QMail.exe.
    electron-builder.config.cjs:43-50 has:
      extraResources: [{ from: "backend/core.exe",
                          to: "backend/core.exe" }]
    Portable mode unpacks it on launch under
    process.resourcesPath\backend\core.exe.

  - electron.cjs:60-65 spawns it from there in packaged mode,
    so users do NOT need to copy core.exe next to QMail.exe.

  - Free port is picked by the OS by default
    (electron.cjs:25-35, findFreePort). Bug-51 (c) default.

  - core.exe creates Client_Data/ next to its cwd
    (rest_core/api_src/main_rest.c — help text line 424:
     "Client_Data directory is always created next to the
     executable").

  - cwd for core.exe in packaged mode is
    PORTABLE_EXECUTABLE_DIR (next to QMail.exe), with a fallback
    to dirname(app.getPath('exe')).
    electron.cjs:62-64. So Client_Data lands NEXT TO QMail.exe.
    This is the "data persists next to the portable for USB-stick
    use" pattern Sean asked for in earlier handoffs.

  - cwd is mkdir'd defensively (electron.cjs:81-88) so a fresh
    directory works without the user pre-creating anything.

GAPS that match Sean's report:
  1. **QMail.exe accepts only --dev** (electron.cjs:13). It does
     not parse:
       --port <N>       set backend port explicitly
       --debug          pass -debug to core.exe
       --r11ip          pass -r11ip to core.exe (dev RAIDA-11 fix)
     core.exe DOES accept all of these (main_rest.c:437-456).
     So Sean's (c), (d), (e) goals need GUI-side arg plumbing.

  2. **No second-process detection or arg pass-through**.
     If you launch QMail.exe twice and want two backends on
     specific ports (instead of two random ports), there is no
     way to tell the second instance which port to use.

  3. **Self-extraction "next to QMail.exe" is NOT implemented**.
     core.exe lives inside the portable-extracted temp dir under
     process.resourcesPath. It does NOT get materialized as a
     sibling of QMail.exe. So if Sean's mental model is "I should
     SEE core.exe appear next to QMail.exe on first launch," that
     never happens — and may be why he thinks the bundle is broken
     when it's actually working.

  4. (Speculation, needs Sean's confirmation) **The bug Sean is
     actually seeing** could be one of:
       (i)   The QMail.exe in E:\Client1\ is built from an older
             commit where core.exe wasn't bundled. Sean's PS in
             the report acknowledges this is possible.
       (ii)  PORTABLE_EXECUTABLE_DIR is unset on his launch (e.g.
             running release/win-unpacked/QMail.exe directly), so
             dataDir falls back to dirname(app.getPath('exe')) =
             the win-unpacked folder, NOT the user's E:\ location.
             Then Client_Data is created in the wrong place and
             looks "not implemented."
       (iii) Sean is launching the .exe and seeing no
             Client_Data appear because he's looking next to
             QMail.exe but the launch was through a context
             (start menu, .lnk shortcut) where the cwd /
             PORTABLE_EXECUTABLE_DIR is not the QMail.exe dir.

Proposed fix (assuming answers: Q3=no-self-extract, Q4=names OK)
-----------------------------------------------------------------
Minimal-touch fix, two files:

  electron.cjs
    - Add CLI parsing for --port <N>, --debug, --r11ip.
      Keep --dev unchanged.
    - findFreePort() only runs when --port not given.
    - Build core.exe args:
        const coreArgs = ['-port', String(port)];
        if (coreDebug) coreArgs.push('-debug');
        if (r11ip)     coreArgs.push('-r11ip');
      Pass to spawn instead of the hardcoded ['-port', ...].
    - Log the resolved args at startup so it's obvious in
      backend logs which switches were active.

  docs/bugfix-log.2026-05-24.txt
    - BUG-51 entry per STANDARD 1 format.

Estimated diff: ~30 lines added in electron.cjs, ~50 lines log

Out of scope for this fix (would defer to a separate bug):
  - Self-extracting core.exe next to QMail.exe (Sean bullet (a)).
    If Sean answers Q3 with "yes I want it visible," add as

  - Multi-instance discovery (e.g. a second QMail.exe finding the

  - Migrating away from `--dev` flag style toward yargs. Not

Risk assessment
---------------
LOW. The changes are additive — default behavior with no args is
unchanged (random port, no debug, no r11ip). Existing dev/dev2
npm scripts continue to work because they don't pass these args.
The flags only TURN ON behaviors that already work in core.exe
today.

The one subtle risk: if Sean passes --port 8081 and another
process already owns 8081, core.exe will fail to bind. Current
random-port flow never has that failure mode. Mitigation: log a
clear error in electron.cjs when core.exe exits non-zero within
the first few seconds, pointing at port conflict as the likely
cause.

Verification plan
-----------------
1. `npm run build-portable` → release/QMail.exe
2. Copy to a CLEAN folder (no Client_Data, no sibling core.exe)
3. Launch with no args. Expect:
   - Splash appears
   - Client_Data/ appears NEXT TO QMail.exe
   - Backend log shows random port
   - GUI loads and works
4. Launch a second copy in a DIFFERENT clean folder with
   `QMail.exe --port 8081 --debug --r11ip`. Expect:
   - Same as above but on port 8081
   - backend log shows "Debug mode: ENABLED"
   - core.exe overrides RAIDA-11 to LAN IP (debug log line)
5. Launch with `QMail.exe --port 8081` while step-4 instance is
   still running. Expect: clear error in electron log saying
   port 8081 is in use, splash stays up briefly, app exits.

If all five pass, the fix is good.

Convention I'll follow (GNU long-option style)
----------------------------------------------
Long flags use -- prefix, lowercase, hyphen-separated. Short
flags use single - prefix and a single letter. Values can be
attached with = or space. Standard --help / --version are
expected. Unknown args print "unknown option" then usage and
exit non-zero.

Adopted flag names for QMail.exe (FINAL):
  --help, -h              Print usage + examples and exit 0.
  --version, -V           Print QMail + bundled core version, exit 0.
  --port <N>              Pin backend (core) HTTP port to N.
                          Range 1..65535. Default: random free.
  --debug                 Forward -debug to core.exe AND enable
                          DevTools in the renderer (F12 to open).
  --r11ip                 Forward -r11ip to core.exe (dev-only
                          RAIDA-11 LAN IP override). Hidden from
                          --help unless --debug also present? No,
                          show always; just label as "(dev only)".
  --dev                   EXISTING. Vite dev-server mode. Keep.

(Notes on the names: I'm mirroring core.exe's flag names
verbatim — `--debug`, `--r11ip` — instead of inventing aliases
like `--core-debug` or `--raida11`. Reasoning: anyone who
already knows core.exe's flags will recognize them on QMail.exe.
The pass-through is 1:1. If we ever need a flag that has
different meaning on each side, we'll prefix it then.)

Unknown-arg behavior: print "QMail: unrecognized option '<arg>'"
on stderr, print short usage, exit 2 (matches GNU conventions —
e.g. `bash --foo` exits 2).

Malformed --port behavior (per gpt's suggestion, slightly
modified): print "QMail: invalid port '<value>' (expected 1..65535)"
on stderr, exit 2. Strict, not silently fall back. Sean's mental
model is "random or specified" — silently swapping in 8080 would
break that. If you want a port, you want THAT port.
