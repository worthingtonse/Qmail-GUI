HOW CODEX FEEDBACK WAS INCORPORATED
-----------------------------------
Adopted:
 - JSON POST body; update_users returns the full canonical stored profile,
   and the GUI persists the SERVER's normalized result, not its own request
   object (codex #3).
 - CORS is handled explicitly, not assumed: the PHP endpoints send
   Access-Control-Allow-Origin and answer OPTIONS preflight (the JSON body
   makes POST non-simple, so preflight WILL happen). webSecurity is at its
   default in electron.cjs createMainWindow, so renderer fetches are
   CORS-constrained (codex #1, verified in code).
 - Local-first is composite-keyed on exact (denomination, serial_number),
   never on address strings (codex #6).
 - Lookups are batched AFTER mail renders; no awaited remote calls inside
   getMailList/getEmailById mapping; list + reading pane share one
   in-flight/negative cache (codex #7).
 - user_hints requires at least one criterion, escapes LIKE wildcards,
   caps limit, has an exact (denomination, serial_number) path (codex #9).
 - qcon columns TINYINT UNSIGNED NULL; inbox_fee BIGINT UNSIGNED; revision
   + created_at columns; canonical qmail_address generated server-side for
   prefix search (codex #10).
 - Empty-qcon semantics defined: absent record = no profile; empty array =
   published but deterministic fallback; server returns one normalized
   `qcons` array; order preserved; duplicates rejected; index 0 valid
   (codex #11).
 - No AN-derived token invented. v1 reserves an `auth` field in the
   contract; the challenge/proof protocol is deferred to the protocol
   owner (codex #2, partially - see DIVERGENCES).
 - Privacy: auto-lookup is gated behind a user setting stored with the
   local public-profile data; only denomination+serial is ever sent -
   never subject, message id, or timestamps (codex #8).

Divergences (deliberate, flagged for review):
 - D1: v1 ships WITHOUT cryptographic ownership proof. Codex says do not
   ship unauthenticated; the product spec provides no auth mechanism and
   the RAIDA-validated challenge protocol does not exist yet. The contract
   carries a reserved `auth` object so the wire format won't break when
   proof lands. The Edit-menu publish dialog shows a "directory is public
   and unverified in this release" notice. Sean owns this call.
 - D2: inbox_fee + qcons persist in a GUI-side store (localStorage,
   wrapped in one module), NOT the rest_core contacts DB. Codex prefers
   extending rest_core first; that is a different repository/binary
   (backend/core.exe) and would block this feature indefinitely. The
   store is isolated behind src/qmail/publicProfile/publicProfileStore.js
   so a later rest_core migration touches exactly one file. Names and
   descriptions DO go into the real contacts DB via the existing API.
 - D3: contacts/create is create-only; no upsert exists in the backend.
   For the self-contact after publish, v1 does create-if-absent and
   otherwise leaves the row alone (never delete/recreate). A rest_core
   upsert endpoint is the fast-follow.

FROZEN v1 CONTRACT (Phase 0 output - review this first)
-------------------------------------------------------
Identity key: (denomination 0..4, serial_number). Server stores serial as
INT UNSIGNED (4-byte capable, forward-compatible with the requested 5-byte
key); the GUI keeps today's 3-byte serial range per qmailAddress.js. If
the protocol later widens serials, only server DDL already accommodates it.

qcons: ordered array, 0..3 UNIQUE integers, each 0..255 (index into
public/qmail-avatars/NewAvatars/NNN.svg). Wire format is a JSON array of
numbers; the "four byte index numbers" phrase is interpreted as each index
being carried as a plain (up to 32-bit) integer.

inbox_fee: non-negative integer, unit deliberately opaque to v1 (displayed
as entered; no currency math). Range 0..2^53-1 client-side.

Field limits: first_name <=64 chars, last_name <=64, description <=512.

POST https://raida11.cloudcoin.global/update_users
  Content-Type: application/json
  { "denomination": 0, "serial_number": 9506,
    "first_name": "Pat", "last_name": "Nash",
    "description": "...", "inbox_fee": 5,
    "qcons": [12, 200, 3],
    "auth": null }                       <- reserved, ignored in v1
  200: { "status":"success", "profile": { ...canonical stored record,
         including server-derived "qmail_address", "revision",
         "updated_at" } }
  4xx/5xx: { "status":"error", "message":"..." }

GET https://raida11.cloudcoin.global/user_hints
  Optional params (>=1 required):
    first_name_starts_with, last_name_starts_with,
    qmail_address_starts_with,
    denomination + serial_number (together = exact lookup),
    limit (1..50, default 25)
  200: { "status":"success", "count": n, "results":[ {profile...} ] }
  Profile object (both endpoints):
  { "denomination":0, "serial_number":9506, "qmail_address":"37.34@bit",
    "first_name":"Pat", "last_name":"Nash", "description":"...",
    "inbox_fee":5, "qcons":[12,200,3], "revision":3,
    "updated_at":"2026-07-01 12:00:00" }

Both endpoints: application/json responses always; CORS headers
(Access-Control-Allow-Origin: *, OPTIONS preflight support); prepared
statements; LIKE % _ escaping; parameterless user_hints rejected (400).

    with raida11 default; single module, no scattered hostnames.
  - publishPublicProfile(profile): validates locally (limits above,
    explicit checks that keep 0 valid - no truthiness), POSTs JSON,
    10s AbortController timeout, returns {success, profile} where profile

  - Never logs names/descriptions/response bodies.

  - Map keyed "denomination:serial_number" ->

  - getProfile(denom, sn), setProfile(...), getQcons(denom, sn),
    subscribe(listener) - useSyncExternalStore-compatible so avatars
    rerender live.
  - Negative cache: "qmail.directoryMisses.v1", TTL 24h,
    isNegativeCached()/markMiss().
  - Auto-lookup consent flag: getAutoLookupEnabled()/setAutoLookupEnabled()
    (default ON per product spec; surfaced in the publish dialog).

      2. Extract unique (senderDenominationCode, senderSn) keys from the
         rendered page (fields already produced by withSenderFields in

         on miss -> markMiss().

      6. Sends ONLY denomination+serial. No subject/msg-id/timestamps.
  - Module-level in-flight set shared by all triggers.
