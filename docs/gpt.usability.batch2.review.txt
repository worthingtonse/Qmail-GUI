Findings:

1. HIGH - normalizeIdentityForUi can produce double-domain QMail addresses.

The backend identity endpoint already returns a complete QMail address in both `email` and `address`. In `D:\Code\src\C\rest_core\api_src\api_handlers_qmail_identity.c:53-54`, it writes `id.email` to both fields. `getIdentity()` preserves that as `data.address` in `src/api/qmailApiServices.js:1378-1396`.

`normalizeIdentityForUi()` then sets `address = raw.address || raw.email || raw.email_address || ""` and synthesizes `prettyAddress` as `${address}@${domain}` at `src/api/qmailApiServices.js:1433-1442`.

Effect: a real address like `Alice.Admin@Developer.C25.Giga` can become `Alice.Admin@Developer.C25.Giga@qmail.cloud` for returning users and imported users. That malformed value feeds WalletSetupScreen, AccountPane, and draft sender display.

Recommended fix: only append a default domain when the source value is known to be a local part. If `address.includes("@")`, use `address` as-is. Given the current backend shape, prefer `raw.pretty_address || raw.prettyAddress || raw.email || raw.address` before inventing a domain.

2. HIGH - unresolved identity data is truthy, so the dashboard retry is skipped.

`ServiceSelectionScreen` retries `getIdentity()` once, but it normalizes whatever comes back even when `identity.configured` is still false (`src/screens/ServiceSelectionScreen.jsx:44-50`). If the endpoint returns the normal unregistered payload, `normalizeIdentityForUi()` returns a truthy object with `configured: false`, `serial_number: 0`, and blank address fields. If `getIdentity()` returns null, the fallback passes raw import metadata via `normalized || result.data` (`src/screens/ServiceSelectionScreen.jsx:59`).

`App.handleSelectService()` treats any truthy data as provisioning data (`src/App.jsx:118-122`). After WalletSetupScreen, QMailDashboard receives the same value as `initialIdentity` (`src/App.jsx:132-144`). QMailDashboard then initializes `userAccount` from any truthy value (`src/qmail/screens/QMailDashboard.jsx:90`) and skips its mount-time `getIdentity()` because `if (userAccount) return` (`src/qmail/screens/QMailDashboard.jsx:166-174`).

Effect: if backend identity indexing takes longer than 500ms, the promised dashboard retry does not run. The user can be left for the session with placeholder or raw import data instead of a real identity. AccountPane can show blank fields or `undefined@undefined` because it expects identity fields.

Recommended fix: only pass an identity object to App/QMailDashboard when `normalized?.configured` is true and it has a serial/address. Otherwise pass `null` or an explicit pending marker that QMailDashboard does not treat as loaded. Do not pass raw `importCredentials()` metadata as `initialIdentity`.

3. MEDIUM - WalletSetupScreen can tell users an unverified identity is healthy and verified.

WalletSetupScreen initializes `status` to healthy unless `accountData?.needs_healing` is true (`src/qmail/screens/WalletSetupScreen.jsx:17`), and then renders "Your identity is healthy and verified." at `src/qmail/screens/WalletSetupScreen.jsx:51-54`.

With the unresolved identity paths above, `accountData` can be null, incomplete, `configured: false`, or raw import metadata. In those cases the screen can show `Welcome!`, an address badge of `-`, and still claim the identity is healthy and verified.

Recommended fix: derive a `hasVerifiedIdentity` flag from `accountData?.configured`, a positive serial number, and a non-empty pretty address. Show an "identity still loading" or "identity unavailable" state when that is false, and do not present the healthy/verified success copy for placeholders.

4. MEDIUM - the has_id fallback retry is probably too weak.

The App has_id path is specifically for "coin files exist, but identity endpoint may not have loaded yet" (`src/App.jsx:55-64`). QMailDashboard then makes only one immediate `getIdentity()` call on mount (`src/qmail/screens/QMailDashboard.jsx:162-182`). If the endpoint is still lagging at that moment, there is no retry loop, no user-visible error, and no retry button.

Recommended fix: use the same retry/backoff discipline as the import path, preferably a few short retries with cancellation, then surface an account identity retry affordance if all attempts fail.

5. LOW - normalizeIdentityForUi says it handles nested `identity`, but it does not read it.

The comments and summary say the helper handles the `getIdentity()` shape including the nested `identity` object. The implementation only reads top-level fields such as `raw.address`, `raw.email`, and `raw.serial_number` (`src/api/qmailApiServices.js:1433-1478`).

Current `getIdentity()` also spreads the important fields top-level, so this is not breaking today. It is still a mismatch with the stated contract and makes the helper less robust for any caller that passes `raw.identity` directly or receives a nested-only response.

Recommended fix: add `const identity = raw.identity || {};` and fall back through both top-level and nested fields for address/email, serial number/sn, display name, names, class, and beacon RAIDA.

Recommended minimum before marking batch 2 done:
- Fix pretty address normalization for full backend addresses.
- Gate `initialIdentity` on a verified/configured identity.
- Treat unresolved identity as pending, not healthy/verified.
- Add a small normalizer test/table for: configured backend response, unregistered backend response, raw import response, and a full email address.
