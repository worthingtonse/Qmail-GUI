5. METHOD NOTES (incorporating your prior review feedback)
===============================================================================

5.1  Source of truth for counts
-------------------------------
Per your Phase 2.1 review: I used the audit's parsed-declaration data
(`docs/css-audit/literal-map.md`) as the canonical impact reference,
not raw grep. Grep totals are used during execution only (the swap
script regexes against on-disk text), and the post-swap audit re-run
confirms whether the change took.

5.2  Longest-first regex ordering
---------------------------------
The swap helper processed values in order:

    0.875rem  →  1.25rem  →  1.05rem  →  1.2rem  →  1.5rem  →
    0.75rem  →  0.95rem  →  0.85rem  →  0.9rem  →  1rem  →
    16px  →  14px

The key reason for this order: `1rem` must NOT match inside `1.5rem`,
`1.25rem`, `1.05rem`, `1.2rem`. By processing the multi-digit cases
first, every later regex sees clean text. Additionally each regex
uses a lookahead `(?=\s*(?:;|!|$))` so partial-token matches are
also impossible.

I verified empirically: post-swap, the literal-map shows zero
remaining `1rem`, `1.05rem`, `1.2rem`, `1.25rem`, `1.5rem`, `0.75rem`,
`0.85rem`, `0.875rem`, `0.9rem`, `0.95rem`, `14px`, `16px`. No
collateral damage.

5.3  Temporary helper scripts
-----------------------------
I created two helpers in scripts/css-analysis/ during execution:
  tmp-phase2.2-count.mjs   (pre-swap site enumeration)
  tmp-phase2.2-swap.mjs    (the batch swap)

Both were removed before the commit. The css-analysis/ folder is back
to its committed shape: README.txt, lib.mjs, config.json,
inventory.mjs, canonicalize.mjs, cluster.mjs, report.mjs.

For future sweeps the same pattern works; a small temp file in the
folder is fine, just don't commit it.

5.4  Tolerance band stayed strict
---------------------------------
Per the user's directive: ≤5% only. 28 sites that would have flipped
at ≤10% (1.125rem → lg, 1.1rem → md, 0.8rem → sm, 13px → sm) sat
untouched. Phase 3 will see them in context.

6. QUESTIONS FOR GPT
===============================================================================

Q1. The 0.95rem (28×) and 1.05rem (3×) boundary swaps
-----------------------------------------------------
Both sit at exactly -5% / +5% from --font-size-md. Inside the
"≤5%" band but at the boundary. The visual difference between
0.95rem and 1rem is roughly 1px of body-text x-height — typically
not noticeable side-by-side, but a careful reader might catch it.

Did I read the threshold rule right? My take was "≤5% inclusive";
your prior framing in the README addendum was "within 5%". Inclusive
seemed right because the audit's clustering uses the same form.

If you'd push for "<5% strict", the 28 + 3 = 31 boundary swaps
would have deferred and the sweep would be 124 swaps instead of
155. Push back if "strict <5%" was your intent.


Q2. Should I have flagged each swap with /* was: 0.95rem */ comments?
---------------------------------------------------------------------
Plan §13.7 says BEM renames keep `/* was: .old-name */` comments
for one release. I didn't apply the same rule to value swaps
because:

  - 155 site-level comments would bloat the file diff substantially.
  - The post-swap audit recomputes everything from scratch on each
    run, so traceability isn't needed for the tool.
  - `git blame` on the swap commit serves the rollback need.

But if you'd prefer the BEM-style ledger for value swaps too, I
can produce a docs/css-audit/phase22-rename-ledger.md (one row
per site: file:line, raw → token) without polluting CSS. That's
a 5-minute add and doesn't require touching the commit.

Worth doing?

  `18px`, `28px` which are NOT on the scale.

  motion-scale: 0 collapse works. Small scope (~30-40 sites).

Phase 3 — at which point we'll know what's left.
