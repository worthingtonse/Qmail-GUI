Credit
------
This plan is heavily informed by GPT-5's independent diagnosis in
docs/gpt.raida-availability.txt. GPT identified three things I
originally missed and that changed my plan:

  1. cmd_echo.c hardcodes timeout_ms=3000 in both serial and
     parallel paths. The REST `?timeout=` parameter is silently
     ignored. (cmd_echo.c:139 and :216)
  2. There are TWO hardcoded RAIDA IP lists in rest_core, not one.
     I had only updated src/raida_servers.c. The list that actually
     populates raida_ips.csv on first boot lives in
     api_src/config.c:429-435, AND it disagrees with raida_servers.c
     in the very entries that are causing user-visible timeouts
     (RAIDA 18 = "24.23.27.180" in config.c is exactly the
     "mysterious" IP I couldn't explain in my earlier empirical test).
  3. platform_get_client_data_dir() in src/platform.c ignores the
     -data-dir CLI flag — it derives from the running binary's path
     via GetModuleFileNameA. So raida_initialize_server_list()
     writes/reads in a Client_Data folder under Electron's temp
     extraction, NOT next to QMail.exe. config.c's load_raida_servers()
     correctly reads from g_config.client_data_path. Two code paths,
     two different folders, only config.c's path wins for the runtime.

Plus two additional findings from GPT that ship with this fix:

  4. qmail_servers.c parses "ip" but the live RAIDA-served JSON
     uses "ip_address". The locally-stored qmail_servers.json had
     the correct shape (because DEFAULT_JSON uses "ip"), but any
     consensus-fetched data loses IPs in the parse. Real bug in its
     own right.
  5. Sean's RAIDA-10 sentinel test confirmed the periodic echo
     path does NOT rewrite raida_ips.csv. Overwrites only happen
     at boot/bootstrap. Narrows the search and means a fix to
     consensus is one-shot per launch, not continuous.

Root cause (one-line)
=====================
The runtime echo path (api_src/transport_adapter.c → g_config.servers[])
is fed by api_src/config.c, NOT by src/raida_servers.c's consensus
refresh. config.c writes a hardcoded stale list to raida_ips.csv on
first boot from a 25-entry array of literal strings, and that's what
the GUI's dashboard echoes against. raida_servers.c does its own
consensus work to a different (and effectively orphaned) Client_Data
location.


Implementation plan (5 phases)
==============================

PHASE A — Refresh BOTH hardcoded RAIDA-IP lists
-----------------------------------------------
Two source-of-truth tables, both currently stale on the same 6
entries (RAIDAs 4, 8, 10, 11, 17, 18). Update both to the live
endpoint (raida11.cloudcoin.global/service/raida_servers, which
matches ._id6.guardians per GPT's cross-check):

  File 1: api_src/config.c:429-435
    const char *default_ips[] = {
        ..., "57.128.255.93", ..., "172.209.208.162", ...,
        "20.200.53.14",  "96.86.143.105", ..., "193.108.114.189",
        "24.10.63.29",   ...
    };

  File 2: src/raida_servers.c:17-23
    static const char *HARDCODED_IPS[RAIDA_COUNT] = { same 6 IPs };

NOTE: I already changed File 2 in an uncommitted edit during the
previous session. File 1 is the new edit that closes the gap GPT
found.

Even though Phase B will route consensus through the right file
path, Phase A is the immediate-correctness fix: on a clean rig
launch, the first boot writes the hardcoded list to
raida_ips.csv BEFORE any consensus runs. Phase A alone takes the
user from 17/25 to 22/25 on a clean Client_Data, regardless of
whether consensus succeeds.

Estimated diff:  ~12 line changes across 2 files.
Risk:            very low. Pure data fix.
User-visible:    immediate (after delete + relaunch).

PHASE B — Make raida_initialize_server_list() respect -data-dir
---------------------------------------------------------------
GPT's core insight. Two acceptable fixes:

  Option B1 (minimal): change raida_initialize_server_list() to
  use g_config.client_data_path directly instead of calling
  platform_get_client_data_dir(). Three lines edited.

  Option B2 (broader): change platform_get_client_data_dir() to
  return g_config.client_data_path when it's set, falling back
  to the executable-derived path. Affects every caller of
  platform_get_client_data_dir(), but they're all in code paths
  that ALSO want the visible Client_Data (password_verifier,
  filesystem, api_handlers_wallet). Cleaner long-term.

I recommend **B2**. The function is misnamed if it doesn't
return the actual Client_Data location. Other callers like
api_handlers_wallet are also victims of the same bug (they
probably look at the wrong folder for wallet state). The fallback
to executable-derived keeps standalone core.exe behavior intact
when -data-dir isn't passed.

After Phase B, raida_initialize_server_list() writes to
E:\Client3\Client_Data\raida_ips.csv (same file config.c writes).
That eliminates the orphaned write entirely.

There's also a sequencing question GPT raised: in rest_init(),
raida_initialize_server_list() runs BEFORE create_folder_structure().
If Client_Data doesn't exist yet, the file write inside
raida_initialize_server_list will fail (which it does today —
boot log "Failed to write initial RAIDA file!" confirms it).
With Phase B the dir will exist by the time the write happens,
but only because config.c creates it. Order of operations should
move create_folder_structure() ahead of the transport init, or
raida_initialize_server_list should mkdir-p its own target dir.

Estimated diff:  Option B1: ~5 lines. Option B2: ~10 lines + the
                 sequencing tweak.
Risk:            B1 low. B2 medium (touches a shared helper).
User-visible:    Makes Phase D actually take effect. Not visible
                 on its own.

PHASE C — Wire echo timeout through cmd_echo
--------------------------------------------
Both cmd_echo_serial() (cmd_echo.c:117-) and cmd_echo_parallel()
(cmd_echo.c:193-) hardcode config.timeout_ms = 3000 — ignoring
any caller value. The REST handler accepts ?timeout=N, threads
it through command_adapter, then it's dropped on the floor.

Fix: add a timeout_ms parameter to both functions; pass it from
the wrappers in api_src/command_adapter.c; preserve the 3000
default by using a sentinel like timeout_ms<=0 → 3000.

This is independent of the IP fix but lands with it because (a)
GPT specifically identified it, (b) it lets the dashboard probe
slow-but-alive RAIDAs (e.g. if 13/15 are sometimes slow rather
than fully down, we want to be able to see that), and (c) test
harnesses already pass `timeout=` expecting it to work.

Verification: after fix, `curl /api/raida/echo?timeout=6000`
should produce total_time_ms ~6000 when RAIDAs are timing out,
not ~3000.

Estimated diff:  ~15 lines across cmd_echo.c + command_adapter.c.
Risk:            low. Backward-compatible (default unchanged).
User-visible:    only if Sean wants to bump the dashboard's
                 default timeout. Right now the dashboard uses
                 no timeout param, which means 3s persists.

PHASE D — Bigger / better consensus sample
------------------------------------------
Today: fetch_count=3, consensus_needed=2 for raida_servers.
Cap MAX_FETCH_COUNT = 10 (raida_consensus_fetch.c:33).
GPT proposes: fetch_count=10, consensus_needed=7.

Reasoning: with the cap at 10 we can sample up to 40% of all
RAIDAs (10/25). Requiring 7-of-10 means a minority of stale
RAIDAs can't ratify on their own. If we ever need >10, the cap
itself has to move — separate change.

Same parameters for qmail_servers consensus (qmail_servers.c).

Note: Phase D becomes meaningful only AFTER Phase B routes the
consensus to the right file. Today, even a perfect consensus
result is being written to the wrong location.

Estimated diff:  ~4 lines across 2 files (raida_servers.c +
                 qmail_servers.c).
Risk:            low. Increases boot HTTP traffic ~3-5x but each
                 fetch is small JSON.
User-visible:    on subsequent boots after consensus converges
                 correctly — keeps the file fresh against future
                 RAIDA IP changes.

PHASE E — Don't rewrite files when content is unchanged
-------------------------------------------------------
Sean's "the program changed my file while I was editing it"
observation. Today raida_servers.c:92-98 rewrites raida_ips.csv
on every consensus success regardless of whether anything
changed. Same pattern in qmail_servers.c.

Fix: before writing, read the existing file, compute a content
hash (or just memcmp), and skip the write if identical. ~15
lines per file.

Eliminates file timestamp churn, eliminates the "did rest_core
change this?" debugging confusion, and prevents the user from
losing manual edits during the brief window between read-it-up
and write-it-back. (Manual edits to raida_ips.csv aren't part
of the supported workflow, but Sean's sentinel-IP test
demonstrates it's something he actually does.)

Estimated diff:  ~30 lines total.
Risk:            very low.
User-visible:    no more "file changed under my cursor"
                 surprises.

PHASE F (optional, defer) — Fix qmail_servers.c JSON parser
-----------------------------------------------------------
GPT finding #4. qmail_servers.c:149 parses "ip" but the live
JSON returned by raidaN.cloudcoin.global/service/qmail_servers
uses "ip_address". After Phase B routes consensus correctly,
the parsed IPs for qmail_servers come back as empty strings.

Fix: accept both keys. ~5 lines.

I'm calling this PHASE F (optional, defer) because:
  - It doesn't drive the user-visible dashboard (which uses
    raida_servers, not qmail_servers).
  - qmail_servers is more complex per GPT's investigation
    (upstream consensus currently picks a stale RAIDA 11 IP
    because RAIDAs 1, 12, 23 all serve the old value).
  - Worth its own focused fix later, possibly with the
    upstream-data piece Sean would need to address.

If the diff is dead simple after I do Phases A-E I'll bundle
it. If it grows, separate bug.


Implementation order
====================

Single commit per phase, two commits per repo split (rest_core
+ Qmail-GUI), per STANDARD 4. -r11ip changes already drafted
locally — fold them into the same Phase A commit since both
are stale-RAIDA-IP related.

Order matches dependency chain:
  1. PHASE A  (data fix — both hardcoded lists)
  2. PHASE B  (route consensus to right path)
  3. PHASE D  (bigger consensus sample — now does work)
  4. PHASE E  (skip write-if-unchanged)
  5. PHASE C  (echo timeout — independent, can be any order)
  6. PHASE F  (only if trivial)

Most user-visible result drops after PHASE A alone (22/25 on a
clean rig). PHASES B+D+E are what makes the system
self-correcting against future IP drift without manual edits.

After all phases:
  - Clean rig launch → consensus runs against the right file
    → writes correct IPs (assuming the live network agrees).
  - Echo dashboard: 22/25 (RAIDAs 13, 15, 17 still down).
  - No file rewrite if nothing changed.
  - Dashboard echo timeout configurable per-request via
    ?timeout= query string (still defaults to 3s, but extensible).


Build / stage / verify steps
============================

Per the now-established workflow:
  1. Each phase: edit → cmake --build (mirrors new core.exe to
     Qmail-GUI/backend) → cmake --build verifies link.
  2. After C-side phases done: npm run lint + build-portable.
  3. Stage release/QMail.exe to E:\Client3\QMail.exe (kill
     stale procs first per STANDARD 9).
  4. Sean smoke-tests: delete E:\Client3\Client_Data\
     entirely, launch QMail.exe, hit echo, expect 22/25.
  5. Each phase logged in docs/bugfix-log.2026-05-24.txt as
     a sub-entry under BUG-58, with commit SHA filled in
     after commit.


Open questions for Sean before I implement

Q3. Phase F (qmail_servers JSON key): bundle with this fix
    if trivial, or always defer to its own bug? My lean is
    bundle-if-trivial.

Q4. Bundling preference per STANDARD 4: each phase as a
    separate commit, or all five (A-E) in one BUG-58 commit
    since they're tightly related? My lean is one commit per
    phase for cleaner revertability if a later phase regresses.
