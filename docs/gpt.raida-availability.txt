Why rest_core is not self-healing the RAIDA IP file
---------------------------------------------------
There are two RAIDA server-list paths in the current code:

1. src/raida_servers.c
   - Has raida_initialize_server_list().
   - Downloads /service/raida_servers via raida_consensus_fetch().
   - Uses platform_get_client_data_dir(), which is based on the directory of
     core.exe.

2. api_src/config.c
   - create_default_files() writes E:\Client3\Client_Data\raida_ips.csv from
     a hardcoded stale list.
   - load_raida_servers() loads E:\Client3\Client_Data\raida_ips.csv into
     g_config.servers[].

In the packaged app, core.exe is extracted under a temp resources directory,
but QMail passes:
  -data-dir E:\Client3

The transport refresh path is therefore not the same as the runtime data-dir
path. The current running temp backend directory does not even have:
  resources\backend\Client_Data\raida_ips.csv

The actual echo send path is api_src/transport_adapter.c, which uses
g_config.servers[] loaded from E:\Client3\Client_Data\raida_ips.csv. That is
the stale file.

There is also an ordering problem in rest_init():
  command_adapter_init()
  transport_adapter_init()
  create_folder_structure()
  create_default_files()
  network_init()
  load_raida_servers()

So raida_initialize_server_list() runs before the visible Client_Data folder
is guaranteed to exist, and before config.c creates the stale default file.
Then config.c loads the stale -data-dir file into g_config.servers[].

Recommended fix sequence
------------------------
1. Fix the RAIDA server source of truth used by echo.
   - Make RAIDA server refresh use the same Client_Data path as -data-dir.
   - Do not use platform_get_client_data_dir() for the packaged runtime RAIDA
     list unless it is taught to respect g_client_data_path.
   - Prefer changing raida_initialize_server_list() to accept a data_dir
     argument and have rest_init() call it after create_folder_structure().
   - Load the refreshed result directly into g_config.servers[] or write/read
     the same E:\Client3\Client_Data\raida_ips.csv file.

2. Update stale fallback defaults.
   - api_src/config.c create_default_files()
   - src/raida_servers.c HARDCODED_IPS
   - Use the live raida11 /service/raida_servers list, which matches Sean's
     working ._id6.guardians file.

3. Remove -r11ip from rest_core.
   - Remove g_r11ip, RAIDA_11_LAN_IP, argument parsing/help, and the block
     that rewrites raida_ips.csv.
   - GUI source already has forwarding disabled, but rest_core should reject
     or ignore the obsolete flag consistently.

4. Wire the echo timeout correctly.
   - Add a timeout_ms parameter to cmd_echo_serial() and cmd_echo_parallel(),
     or add explicit timeout variants.
   - Pass the REST timeout through instead of hardcoding 3000.
   - After the IP list is fixed, retest RAIDA 13 and 15. If they still miss
     at 3000 ms but pass at 6000 ms, then set the dashboard/default echo
     timeout higher.

5. Fix qmail_servers parsing and upstream consistency separately.
   - Teach qmail_servers.c to read "ip_address" as well as "ip".
   - Ask Sean/upstream to update /service/qmail_servers on enough RAIDA
     endpoints so consensus no longer returns 67.181.90.11 for RAIDA 11.

QMail.exe packaging behavior. Per the bugfix standards, this should be done
with an explicit one-line plan before editing.

Revised interpretation
----------------------
Sean's new information does not change the main conclusion that the dashboard
is using stale RAIDA IPs. It strengthens it.

The important distinction is now:
  - cloudcoin_desktop uses guardian consensus and a local 72-hour cache.
  - rest_core/QMail uses raida_ips.csv plus RAIDA /service/raida_servers
    consensus.

Because QMail is intentionally moving toward the RAIDAs as source of truth,
I do not recommend copying the guardian mechanism into QMail. I would use the
desktop guardian file only as a known-good comparison while fixing rest_core's
RAIDA-based path.

The next implementation should focus on rest_core:
  1. Update api_src\config.c default raida_ips.csv list. This is the first
     file written in the visible E:\Client3\Client_Data path on first boot.
  2. Update src\raida_servers.c fallback list. This protects the transport
     initializer when no server file exists.
  3. Make raida_initialize_server_list() use the same -data-dir Client_Data
     path as rest_core's visible runtime data, or move its call after
     create_folder_structure().
  4. Increase RAIDA-service consensus sampling above 2-of-3. The shared
     fetcher currently caps MAX_FETCH_COUNT at 10, so a practical first
     change is fetch_count=10 and consensus_needed=7 for raida_servers and
     qmail_servers.
  5. Avoid rewriting raida_ips.csv/qmail_servers.json when the consensus
     content is byte-for-byte unchanged. This prevents confusing file
     timestamp churn while testing.

Expected result after a correct fix:
  - 4, 8, 10, 11, and 18 should stop timing out if their current IPs are used.
  - 13, 15, and 17 may still time out because Sean says they are known down.
  - The dashboard should therefore improve from 17/25 to about 22/25.
