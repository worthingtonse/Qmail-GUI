SYMPTOM
-------
Withdraw modal (Default Wallet, 2,597,979 CC shown), amount 10000, Locker Key
mode -> red banner "No coins in Bank".
main.log 14:27:58: GET /api/locker/upload -> 404 {"message":"No coins in Bank"}

TWO-LAYER ROOT CAUSE
--------------------
There are two independent defects stacked on top of each other. Fixing either
unblocks the user; both should be fixed.

LAYER 1 — PROXIMATE, CODE BUG  [SEVERITY: HIGH]
  core/api_src/api_handlers_locker.c, api_handle_locker_upload(), lines 435-442:
      int file_count = list_bin_files(bank_path, &files, MAX_BIN_FILES);
      if (file_count <= 0) { ... "No coins in Bank", 404; return; }
  The guard checks ONLY Bank and aborts before coin selection runs — yet the
  SAME handler fully supports spending Fracked coins:
    - single-coin mode Fracked fallback (495-515);
    - amount mode greedy Bank-THEN-Fracked with make-change cascade (574-677,
      Fracked pass at 602-627);
    - the "Insufficient funds" check (679-698) uses Bank+Fracked balance.
  git blame: the guard AND the Fracked fallback both date to commit 73fd8842
  (2026-02-12) — the guard has contradicted the handler's own selection logic
  from day one. It is NOT from the recent file-encryption work (see below).
  Had the guard not fired, this exact withdrawal (10,000 CC) would have been
  satisfied by one fracked denom-4 coin, no make-change needed.
  Proof it's stale: api_handle_locker_put_no_sum (line 898) — the same
  operation minus receipt summing — has NO such guard and goes straight to
  Bank-then-Fracked selection.

LAYER 2 — SYSTEMIC, ENVIRONMENT + HEAL DESIGN  [SEVERITY: HIGH, wider scope]
  Why Bank is empty in the first place: RAIDA 5 is offline.
    - raida_stats.csv: raida 5 -> is_available=0, 291 timeouts (verified).
    - Boot health 13:29:52: 345 coins (Bank=0, Fracked=345); every coin
      detects pass=24 fail=0 (RAIDA 5 skipped as "marked offline").
    - Grading (core/src/commands/cmd_grade.c:75): Bank requires
      auth == 25 && fail == 0 && unknown == 0. 24/25 -> Fracked. Always.
    - Heal finds the 345 fracked coins, gets 24/24 tickets, then:
        "Fix RAIDA 5: skipped" -> "Fix complete: 0 RAIDA fixed ... 1 skipped"
        -> "Heal: No RAIDA were fixed — skipping persist and regrade"
        -> fracked_fixed=0/345, graded=0.
  DEADLOCK: while any one RAIDA is down, NO coin can ever reach Bank grade,
  heal can never repair the one failing RAIDA (it skips offline ones), and
  every new deposit/make-change output lands in Fracked too. Bank drains to
  zero and stays there. Same pattern repeated for the Mail identity coin
  (SN 5243).

FILE ENCRYPTION (TYPE 10): RULED OUT AS CAUSE, ONE HAZARD NOTED
----------------------------------------------------------------
- Boot log: "BOOT: no encrypted .bin files; 346 plaintext coin file(s)" and
  "Type 10 write-gate cache refreshed (wallet_is_encrypted=false)". Zero
  encrypted coins in play.
- The guard predates the encryption project by ~6 months (Feb 12 vs Aug 3).
- Note: the running backend IS a current build (packaged resources/backend —
  boot prints Type-10-era messages). The E:\20.123@giga\core.exe dated Jul 8
  is NOT what runs (electron.cjs:929 uses resourcesPath/backend); it's a
  stray copy — mildly confusing during debugging, verify nothing references
  it before cleaning it up.
- HAZARD for encrypted wallets (future incident waiting): coin_file_read
  returns RESULT_LOCKED for Type 10 files without a session key. Every
  selector/balance scanner (scan_folder_balance, locker selection,
  qmail_coin_select) SILENTLY SKIPS unreadable coins, while the line-438
  guard counts FILES. So a locked encrypted Bank passes the guard, then
  selection finds nothing -> "Insufficient funds" with balance shown as 0
  even though coin files exist. Different symptom, same family (file-count
  vs readable-coin mismatch). Worth a deliberate "wallet is locked" error.

BLAST RADIUS — WHAT ELSE IS AFFECTED (checked in source)
--------------------------------------------------------
Broken by the SAME guard (all funnel into api_handle_locker_upload):
  /api/locker/upload, /api/locker/put, /api/locker/put-one-coin, and the
  three /api/transactions/locker/* aliases (api_handlers.c:95-104; put and
  put-one-coin are thin wrappers, locker.c:1240-1252). GUI callers hitting it:
    - QMail Wallet -> Withdraw -> Locker Key (qmailApiServices.js:3368) [this bug]
    - Wallet section Locker Upload tab (apiService.js:1525 via
      LockerUploadTab.jsx:113) — will fail identically while Bank is empty.

Same disease, second organ — make-change gap scans are Bank-only [MEDIUM]:
  cmd_make_change itself picks its break coin from Bank THEN Fracked
  (cmd_make_change.c:225-256, comment explicitly warns a "Bank-only search
  would wrongly report no coin"). But the callers that decide WHETHER/WHAT to
  break scan Bank only:
    - api_handlers_locker.c:553-567 (largest_breakable ceiling) and :640
      find_breakable_denom_for_gap(bank_path, ...) in amount mode;
      also :952-965 in put_no_sum;
    - qmail_sdk_support.c:108-126 (find_breakable_denom_for_gap);
    - qmail_coin_select.c:111-146 (qcs_largest_breakable_in_bank,
      qcs_find_breakable_denom_for_gap).
  Consequence: with Bank empty, the cascade budget computes from "no
  breakable coins" and the gap scan returns -9, so make-change never fires —
  even though Fracked holds 258 breakable 10,000s. Concrete failure after the
  Layer-1 guard is fixed: withdraw 999 CC. Fracked sub-1000 inventory is
  ~979 CC (6x1 + 7x10 + 9x100 + fractions), so a 1,000 must be broken; the
  Bank-only scan says nothing is breakable -> "Cannot make exact change".
  Affects locker upload, put-no-sum, and QMail locker-pool replenish alike.

Verified NOT affected (they already do Bank+Fracked):
  - .bin File withdraw tab -> /api/transactions/export -> cmd_export_coins
    scans Bank + Fracked (cmd_export.c:424-434). The OTHER tab of the same
    modal would have worked.
  - QMail send affordability gate: wallet TOTAL = Bank + Fracked + ready
    lockers (api_handlers_qmail_messages_send.c:2322-2347).
  - QMail locker-pool funding: fund_locker_batch ->
    qmail_select_coins_for_units, Bank-then-Fracked selection
    (qmail_coin_select.c:241+) — subject only to the make-change scan issue.
  - system_transfer, DRD auth-coin lookup, qmail identity/payments: all
    already search Bank and Fracked.

Related anomaly to investigate separately [LOW/UNKNOWN]:
  "Echo: 0/25 pass, 24 rejected" every ~5 min, yet "QMail health updated:
  24/25 RAIDAs reachable". Per logging.c:699-705, "rejected" = RAIDA replied
  with a NON-SUCCESS status (e.g. 34 = encryption validation failed) — so all
  reachable RAIDAs currently reject the echo command while answering
  pown/detect fine, and health counts rejectors as reachable. Given the
  recent encryption changes, worth a quick look at what status the echoes
  return (also: FixEncryption CMD45 to RAIDA 5 fails res=2, expected while
  it's offline).

ROOT CAUSE 2 — SERVER-SIDE TYPE-0 GATE (raidax R-23)  [SEVERITY: CRITICAL]
--------------------------------------------------------------------------
raidax commit 706fafc (2026-08-03, "Tier A pen-test remediation"):
  validate_header now REJECTS Type 0 (unencrypted) requests with
  ERROR_INVALID_ENCRYPTION (status 34) unless the node's allow_type0
  config is on — and it defaults OFF (config.c: "Type 0 OFF by default
  (R-23)"). Deployed to the fleet via CI-CD phase2 auto-ship.
The desktop client still sends ENC_TYPE_NONE on several commands:
  - core_put_locker            cmd_locker.c:419   <- THIS failure
  - core_put_locker_no_sum     cmd_locker.c:966   <- QMail locker-pool
    funding (send fees) presumably broken fleet-wide too
  - third locker call site     cmd_locker.c:1132
  - Echo (executor default ENC_TYPE_NONE, executor.c:87) <- explains the
    all-day "Echo: 0/25 pass, 24 rejected" anomaly flagged in v2
  - cmd_detect_hash (POWN SUM first-deposit mode, detect_hash.c:212-215)
    <- fresh-install deposits have no coin key BY DEFINITION
  - FIX2 healing (cmd_fix_protocol.c:215, cmd_fix_encryption.c:344)
    <- heal cannot fix fracked coins on updated nodes AT ALL (independent
    of the RAIDA 5 outage)
  - cmd_count.c:155; legacy convert unencrypted retry (cmd_convert.c:692,
    1095; cmd_deposit.c:1177-1188)
Contrast: commands that already encrypt (Detect, GetTicket, QMail ping)
pass with the SAME key coin (SN 35144) in the same session — confirming
the shared secrets are fine and only Type-0 traffic is rejected.

Design tension to resolve: R-23 exists because a client must not be able
to force cleartext (pen-test finding). But several Type-0 paths are
BOOTSTRAP paths that cannot have a coin key yet (first deposit, echo
before any wallet exists). Locker ops have a ready answer: Type 2
locker-derived keys — core_peek_locker already implements exactly the
needed pattern (Type 1 coin key, Type 2 fallback; cmd_locker.c:486-521)
and peek works against the updated fleet.

RECOMMENDED FIX (locker scope): make core_put_locker / put_no_sum /
batch use the same Type 1 -> Type 2 selection as core_peek_locker.
Follow-up work orders needed for: echo, POWN SUM deposits, FIX2 heal,
legacy convert retry, count.

Cross-check vs the import-counterfeit bug (fabl.import-counterfeit.bug.txt):
the R-23 gate rejects in validate_header BEFORE dispatch, so type-0
GetSNs/SwitchShard get status 34 -> mapped to error_count -> retryable
abort, never the >=13 ALL_FAIL counterfeit quorum. R-23 therefore breaks
fresh-install legacy imports (abort) but does NOT explain the customer's
"11 counterfeit" verdict — H1 (password-encrypted CC Desktop ANs) stands.
