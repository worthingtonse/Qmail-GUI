## BUG-51 - Packaged QMail does not create the expected file structure on startup

Current repo state observed
---------------------------
- `electron-builder.config.cjs` already includes `backend/core.exe` as an
  `extraResources` payload. A freshly built portable `QMail.exe` should therefore
  carry the backend binary inside the Electron portable package.
- `electron.cjs` already starts the packaged backend from
  `path.join(process.resourcesPath, "backend", "core.exe")`.
- `electron.cjs` already chooses a random free local port and starts core with:
  `core.exe -port <port>`.
- In packaged mode, `electron.cjs` sets `cwd` for core to
  `PORTABLE_EXECUTABLE_DIR` when available, otherwise `path.dirname(app.getPath("exe"))`.
  This is intended to make core create `Client_Data` beside the visible portable
  `QMail.exe`, not in Electron's extracted temp resources directory.
- `D:\Code\src\C\rest_core\api_src\main_rest.c` documents and parses:
  - `-port <number>` / `--port <number>` for the HTTP server port.
  - `-debug` / `--debug` / `-d` for debug logging.
  - `-r11ip` / `--r11ip` for the RAIDA 11 LAN IP override.
- Core's built-in default HTTP port is `8080` when no port flag is supplied.

This means the build Sean tested may be stale if it required a manually copied
`core.exe` beside `QMail.exe`. A current `npm run build-portable` build should be
tested before changing the startup design.

Sean decisions recorded after first draft
-----------------------------------------
- Do not build a fresh `QMail.exe` yet. CSS work is active and would make the
  program difficult to debug until that phase is finished.
- If a QMail-supplied port is bad, try again without passing any port flag to
  core so core chooses its built-in default.

Recommended target behavior
---------------------------
1. Keep the product as one user-facing executable: `QMail.exe`.
2. Continue bundling `backend/core.exe` with Electron Builder as an internal
   resource. Do not require the user to place `core.exe` next to `QMail.exe`.
3. Start bundled core from the internal resource path, but set core's working
   directory to the portable launcher directory so core creates:
   `Client_Data/` and its subfolders beside `QMail.exe`.
4. Port behavior:
   - If QMail is launched with a valid explicit port, pass `-port <number>` to
     core and pass the same port into the renderer URL as `backendPort`.
   - If QMail is launched without an explicit port, either keep the existing
     random free port behavior or intentionally omit `-port` and use core's
     built-in default `8080`; this needs one final product decision because it
     affects multi-instance launches.
   - If QMail is launched with a malformed explicit port, omit the core port flag
     and use core's built-in default `8080`.
5. Add explicit QMail launcher arguments for manual testing and development:
   - `--port <number>` or `--port=<number>`: use a specific core/API port.
   - `--core-debug`: forward core's `-debug` flag.
   - `--raida11-fix`: forward core's `-r11ip` flag.
6. Log the resolved core path, data directory, and argument vector at startup so a
   packaged smoke tester can diagnose whether the wrong binary or wrong directory is
   being used.

Implementation idea
-------------------
The smallest GUI-side implementation should stay in `electron.cjs`:

1. Add a small CLI parser near the top of `electron.cjs`.
   - Parse only QMail-owned flags.
   - Validate explicit port as integer `1..65535`.
   - On malformed port input, log a clear warning and mark the launch as
     "use core default port".
2. Change `boot()` so:
   - if an explicit port was provided, use it;
   - if the explicit port was malformed, use `8080` for the renderer and do not
     pass `-port` to core;
   - if no explicit port was provided, follow the final product decision: current
     random free port behavior, or core default `8080` with no `-port`.
3. Change `startBackend(port)` so it builds `coreArgs` from:
   - optional `["-port", String(port)]`;
   - optional `-debug`;
   - optional `-r11ip`.
4. Keep packaged `backendPath = path.join(process.resourcesPath, "backend", "core.exe")`.
   This is better than copying `core.exe` beside `QMail.exe` because Electron's
   portable target already extracts internal resources for execution, and copying
   a mutable executable next to the launcher creates version-staleness risk.
5. If testing proves core creates `Client_Data` next to its executable instead of
   respecting `cwd`, fix core to base its data root on `GetCurrentDirectory()` or
   add a core argument such as `-data-dir <portable dir>`. Do not paper over that in
   the GUI by copying binaries around unless core cannot be changed.

Verification plan
-----------------
1. Build a fresh portable package from current source:
   `npm run lint`, `npm run build`, `node --check electron.cjs`,
   `node --check preload.cjs`, then `npm run build-portable`.
2. Copy the new `release/QMail.exe` into `E:\Client1\QMail.exe` and
   `E:\Client2\QMail.exe`, leaving existing `Client_Data` folders untouched unless
   Sean explicitly wants a clean first-run test.
3. For a clean first-run test, use a folder with no `core.exe` beside `QMail.exe`
   and no existing `Client_Data`.
4. Launch `QMail.exe` normally and confirm:
   - no external `core.exe` is needed beside `QMail.exe`;
   - `Client_Data` appears beside `QMail.exe`;
   - QMail reaches the first usable screen;
   - the app talks to core on the port shown in Electron startup logs.
5. Launch with an explicit port after the CLI parser is implemented:
   `QMail.exe --port 8081`
   and confirm the renderer uses `backendPort=8081`.
6. Launch with a malformed explicit port and confirm Electron logs the warning,
   starts core without `-port`, and the renderer uses `8080`.
7. Launch with the development-only flags and verify Electron forwards `-debug`
   and `-r11ip` in the logged backend argument vector.

Open questions before code changes
----------------------------------
1. Final product decision: when QMail is launched without `--port`, should it keep
   the current random free port behavior, or omit `-port` and use core's default
   `8080`? Random free port supports multiple QMail instances; core default is
   simpler but two simultaneous instances will conflict.
