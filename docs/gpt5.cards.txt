QMAIL MESSAGE CARDS: STACKING FAILURE AND FANNED-CARD DESIGN REPORT
=================================================================

Scope
-----

This report analyzes docs/stacking.png and the current Inbox/Sent message-list
implementation in:

  - src/qmail/screens/EmailListPane.jsx
  - src/qmail/screens/EmailListItem.jsx
  - src/qmail/screens/EmailListPane.css
  - src/qmail/screens/QMailDashboard.jsx

No visual implementation is included in this report. The purpose is to explain
the defect and recommend a safe way to preserve and refine the card/deck effect.


Executive summary
-----------------

The current appearance is not a deliberate stack. It is the result of flexbox
shrinking each message's layout box below the height required by its contents.
The contents then paint outside their own boxes and over neighboring messages.
The user sees one card but may be pointing at the hit box of a different card.
That is why clicking a visually apparent message can select the one above or
below it.

The effect should be rebuilt with ordinary semantic HTML and CSS. Canvas and
SVG would make text rendering, scrolling, focus, screen-reader support, menus,
and correct hit testing substantially harder without adding useful capability.

Recommended direction:

  1. Fix the geometry first with flex-shrink: 0 (or flex: 0 0 auto) so every
     message owns all the space occupied by its content.
  2. Make each message an opaque, rounded card with a subtle top-to-bottom
     gradient and shadow.
  3. Suggest a fan with tiny horizontal offsets, shadow layers, and at most a
     very small rotation. Do not create the fan by allowing sibling content to
     overflow into another sibling's hit area.
  4. Raise the hovered, keyboard-focused, selected, and menu-open card with an
     explicit z-index. Use pseudo-elements for decorative cards behind it and
     give those pseudo-elements pointer-events: none.
  5. Replace the selected row's transparent background with an opaque blended
     surface so selecting/marking a message read does not look like the card
     vanished.


What the screenshot shows
-------------------------

In docs/stacking.png:

  - A sender/header strip appears at a regular interval.
  - The avatar, envelope/trash controls, subject, and preview from one message
    extend into the visual territory of the next sender/header strip.
  - Horizontal separators pass through content belonging to adjacent messages.
  - Some dark card surfaces cover parts of other cards, while their text and
    avatars remain visible in different layers.
  - The scrollbar itself behaves normally; the corruption is inside the list,
    not a failure to make the pane scrollable.

This is characteristic of content overflow from flex items whose allocated
heights have been compressed. It is not simply a z-index mistake.


Root cause
----------

1. The scrolling list is a column flex container.

EmailListPane.css defines .email-list-pane__list as:

  display: flex;
  flex: 1;
  flex-direction: column;
  min-height: 0;
  overflow-y: auto;

2. Every message is a flex item with the default flex-shrink: 1.

.email-list-pane__item does not set flex or flex-shrink. A flex child therefore
defaults to "flex: 0 1 auto" and is allowed to shrink when all messages do not
fit in the pane.

3. The explicit min-height is much smaller than the complete card content.

The row has min-height: 4.5rem. However, it contains:

  - a separate header row;
  - padding and gaps;
  - a body row;
  - an avatar/cartouche that is itself 4.5rem high;
  - subject and preview content;
  - sometimes tags and additional controls.

The natural row height is therefore substantially greater than 4.5rem. Because
an explicit min-height is present, flexbox can compress each item toward that
minimum. The inner content is not clipped, so it paints outside the compressed
item.

4. Painted content and hit areas no longer communicate the same structure.

The article's clickable area follows the compressed/transformed flex-item box.
Overflowing child content may be visible over a neighboring article, but the
neighboring article can be later in paint order and can own the pointer target.
The visible subject/avatar is consequently not a reliable indication of which
article receives the click.

5. Hover makes the ambiguity more noticeable.

The current hover rule applies:

  transform: translateY(calc(-1 * var(--space-xs)));

That is the pleasing "card picked from a deck" motion. But there is no explicit
hover z-index. Transformed siblings create stacking contexts, and later siblings
can still paint or receive input over an earlier card. Moving a card upward also
moves it farther into the preceding card's region.


Why the selected message appears transparent
--------------------------------------------

There are two related state changes:

  - An unread message has a translucent information-colored background.
  - Selecting an unread message immediately marks it read in
    QMailDashboard.handleSelectEmail, which removes the unread class.

The selected rule then uses:

  background: color-mix(in srgb, var(--accent-primary) 10%, transparent);

This is intentionally mostly transparent. In a normal flat list it may look
like a faint selection wash. In the corrupted overlapping layout, it makes the
selected card appear to lose its surface and exposes the visual layers beneath
it. The sudden removal of the unread tint amplifies the impression that the
clicked message became transparent.

There is also a cascade issue worth avoiding: the selected rule appears before
the unread rule, so while both classes exist the unread background wins. When
the read state changes, the selected appearance changes abruptly.

The selected surface should instead blend the accent into an opaque base, for
example conceptually:

  color-mix(in srgb, var(--accent-primary) 14%, var(--secondary-bg))

This maintains a solid card while clearly showing selection.


Technology comparison
---------------------

CSS + semantic HTML (recommended)

Advantages:

  - Keeps every message, link, star, menu, and attachment control as a native
    DOM target.
  - Browser scrolling, text selection, tooltips, focus, and screen readers keep
    working.
  - Gradients, shadows, transforms, pseudo-elements, perspective, sticky
    elements, hover/focus states, and reduced-motion support are sufficient for
    the entire visual treatment.
  - It is the smallest change to the existing React components.
  - GPU-composited transforms can animate a hovered card inexpensively.

Risks:

  - Intentional negative margins can recreate ambiguous overlap if the visible
    overlap is also clickable.
  - Excessive rotation makes text less crisp and makes a narrow list feel
    unstable.

SVG

SVG is useful for a decorative deck illustration, but not for the message list
itself. Rendering each message as SVG text would require custom wrapping,
truncation, focus management, controls, and accessibility. Embedding HTML in
SVG foreignObject retains DOM complexity while adding browser/layout edge
cases. SVG can be used for a small decorative edge or mask, but offers no
benefit over CSS pseudo-elements here.

HTML5 Canvas

Canvas would turn the entire list into pixels. The application would then need
to rebuild hit testing, keyboard navigation, screen-reader descriptions,
scrolling/virtualization, high-DPI text rendering, hover states, menus, and
individual action controls. It is especially unsuitable because the current
bug is already a mismatch between visible geometry and input geometry. Canvas
would make that mapping entirely manual.

Canvas is justified for thousands of rapidly animated objects or freeform
drawing, neither of which applies to a paged list of at most 50 messages.

CSS 3D transforms / old "cover flow" techniques

CSS perspective, transform-origin, rotateX/rotateZ, and preserve-3d can create
a dramatic fan. They are longstanding and supported techniques, but the full
cover-flow style would reduce legibility and complicate hit testing. A restrained
2D version produces the desired material/deck feeling with fewer drawbacks.


Recommended visual design
-------------------------

Use a "fanned stack illusion," not physically collapsed cards.

Base card

  - flex: 0 0 auto (the essential correctness fix).
  - A small vertical gap between cards, approximately 6-8px.
  - Rounded corners, an opaque border, and an opaque gradient surface.
  - Top of card 5-8% lighter than the bottom.
  - A soft lower shadow to imply that the next card sits beneath it.
  - overflow: visible only for menus; normal content must remain within the
    card's measured box.

Fan illusion

  - Repeat three or four tiny horizontal offsets, for example 0px, 2px, 4px,
    and 1px, based on row index.
  - Optionally repeat rotations no greater than roughly -0.15deg to +0.15deg.
    Test text crispness at Windows display scaling before retaining rotation.
  - Add ::before and/or ::after pseudo-elements offset behind the card to look
    like thin card edges. These decorations must use pointer-events: none.
  - Keep the actual card rectangles vertically separate. The shadow or
    decorative edge can overlap; interactive content should not.

Hover/focus (the card being chosen)

  - transform: translateY(-3px) translateX(2px) scale(1.005).
  - z-index higher than ordinary and selected cards.
  - Stronger shadow and border highlight.
  - Keep motion near 150-200ms and respect the existing --motion-scale token.
  - Apply the same elevation for :focus-within so keyboard users get the same
    spatial cue.

Selected card

  - Opaque accent/base gradient, not a transparent wash.
  - Accent-colored leading border plus a modest outer glow.
  - z-index above ordinary cards but below the actively hovered/focused card
    and below an open action menu.
  - Do not change opacity when the message changes from unread to read.

Unread card

  - A subtle opaque cool-toned gradient and stronger subject weight.
  - Selection must override or deliberately combine with unread styling; it
    should not depend on which rule happens to appear later in the stylesheet.


Suggested stacking model
------------------------

Use explicit layers rather than relying on DOM paint order:

  ordinary card       z-index: 1
  selected card       z-index: 3
  hover/focus card     z-index: 5
  open-menu card       z-index: 30 (already used)
  row menu popover     z-index: 20 within the elevated row

Each card should use isolation: isolate so its pseudo-elements, content, and
shadow form a predictable local stack. Decorative pseudo-elements belong behind
content but inside that isolated stacking context.


Interaction and semantic recommendations
----------------------------------------

The current <article role="button" tabIndex="0"> contains multiple interactive
descendants: action-menu button, copy button, envelope/read control, trash,
attachment button, and star. Event propagation is manually stopped for those
controls. It works in many cases, but it increases the chance of accidental row
selection and is not ideal button semantics.

A future cleanup should make the article a non-button container with:

  - one dedicated primary message-opening button/link covering the content
    region; and
  - separate real buttons for menu, copy, read state, trash, attachments, and
    star above that primary layer.

This gives every action a native focus target and makes pointer ownership
explicit. It is not required for the first CSS correction, but it is the best
long-term complement to the card treatment.

If any intentional geometric overlap is retained, the overlap band should be
decorative and pointer-events: none. A user must never see text or a control
from card A in an area whose pointer target belongs to card B.


Accessibility and motion
------------------------

  - Preserve a strong :focus-visible outline that is not clipped by the scroll
    container or adjacent cards.
  - Do not encode read/selected state only with gradients; retain font weight,
    leading border, and appropriate ARIA state.
  - Ensure text/background contrast remains sufficient at both ends of the
    gradient in Dark, Light, and High Contrast themes.
  - In prefers-reduced-motion, remove lift/scale/rotation transitions while
    keeping the static gradient, border, and shadow hierarchy.
  - At 200% browser or Windows scaling, cards must expand naturally and remain
    independently clickable.


Implementation sequence
-----------------------

Phase 1: correctness

  1. Add flex: 0 0 auto or flex-shrink: 0 to .email-list-pane__item.
  2. Verify the list itself remains the sole vertical scroll container.
  3. Add explicit hover/focus/selected z-index values.
  4. Change selected and unread backgrounds to opaque base blends.
  5. Verify all nested controls still stop row selection.

Phase 2: controlled card styling

  1. Add card margins, radius, opaque vertical gradient, and shadow.
  2. Add index-based fan offsets through a CSS custom property set by the React
     map index, or use :nth-child patterns if pagination elements cannot disrupt
     the pattern.
  3. Add pointer-inert pseudo-card edges.
  4. Tune hover lift without negative-margin sibling overlap.

Phase 3: semantic cleanup (recommended)

  1. Separate the primary open-message control from the article container.
  2. Keep all secondary controls as sibling buttons with explicit layers.
  3. Test keyboard order, Enter/Space behavior, and screen-reader names.


Test matrix
-----------

Layout:

  - 1, 2, 10, and 50 messages.
  - Inbox, Sent, Drafts, Trash, and Archive.
  - Messages with tags, long sender names, long subjects, attachments, pending
    decryption, and action menus.
  - Narrow pane, full-width responsive pane, 100%, 150%, and 200% scaling.

Pointer behavior:

  - Click the top, center, and bottom edge of every visible card.
  - Click while a neighboring card is hovered.
  - Click menu/copy/read/trash/attachment/star without opening the message.
  - Open a row menu near the bottom of the viewport and scroll.

State behavior:

  - Select an unread message and confirm the same card remains visibly selected
    after it becomes read.
  - Move between selected cards rapidly.
  - Refresh or change sort while a card is selected.

Accessibility:

  - Navigate every card and secondary action using only the keyboard.
  - Verify focus rings remain visible above adjacent cards.
  - Verify reduced-motion and High Contrast themes.


Conclusion
----------

The accidental visual has genuine design potential, but the current overlap
must not be preserved as-is because it divorces painted content from pointer
ownership. CSS is the correct tool. First prevent flex shrinking; then recreate
the deck impression with opaque gradients, shadows, tiny offsets, decorative
pseudo-elements, and explicit stacking levels. This retains the appealing
"choose a card from the deck" hover behavior while making every visible card
and every click unambiguous.
