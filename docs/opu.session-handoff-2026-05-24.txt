PATTERNS THAT WORK — and shouldn't get re-litigated
================================================================================

Things both GPT and the user signed off on across Phase 3 reviews.
Re-applying these patterns in Phase 4 is safe; deviating from them
needs explicit sign-off:

1. **Primitive-vs-override shape:**
     Primitive owns surface, typography, interaction baseline.
     Per-file class owns ONLY genuine local deviations
     (padding, border-radius, custom shadow tier, slate-disabled
     gradient). Never repeat background/color/border/cursor/transition
     in the override block — primitive provides them.

2. **Conservative-extraction threshold for primitives:**
     ≥3 consuming files, semantic name, byte-identical signature
     across consumers. Anything else stays per-file.

3. **Keyframe extraction rule:**
     Extract a keyframe to primitives.css ONLY if the name has a
     single semantic meaning across the codebase.
     `progressPulse`, `fadeInUp` — extracted.
     `fadeIn`, `popIn` — NOT extracted (name collision between
     files with different motion shapes).

4. **Look wins over guidelines:**
     If the audit/plan says X but the actual file says Y, Y wins.
     Always grep/read before recommending; never trust memory of
     "X exists in file Y."

5. **GPT review cadence:**
     Pause for a GPT review handoff after each sub-phase
     (primitive landing, then adoption, then closeout). Write the
     handoff doc, user appends GPT's response inline, Opus applies
     fixes and ships the next sub-commit alongside the review doc.
     Don't batch reviews — keeps each cycle small enough to act on.

6. **JSX adoption decision rule:**
     Adding `btn btn--variant` is correct WHEN the button is a CTA
     (gradient surface, hover lift, ripple). It is WRONG when the
     button is a contextual control (icon close, text disclosure,
     warning-tinted retry, custom blue/purple gradient). For the
     latter, leave the JSX alone — the per-file rule plus the
     `button { ... }` baseline cover it.

7. **Commit scoping with the dirty working tree:**
     Always commit by path, never `git add .`. The user has 30–40
     unrelated dirty files across sessions (gemini.*,
     gpt.manual-bugfix-*, qmail/* WIP, raidax C files, etc.). The
     auto-memory at `project_qmail_gui_dirty_tree.md` captures this.
