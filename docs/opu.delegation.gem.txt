Track B — Light + high-contrast WCAG values
===========================================

Required reading from the plan:
  §4.2  light theme palette          (lines 488–509)
  §4.3  high-contrast theme palette  (lines 510–535)
  §13.1 "look wins over guidelines"  (lines 1272–1283)

What to deliver:
  File: docs/theme.wcag-values.md
  Contents: a table for the light theme AND a table for the high-contrast
  theme. Each table lists every text/background pair the user might
  actually encounter in the UI, with:

      Pair (text token / bg token)
      Hex resolved values
      Measured WebAIM contrast ratio (e.g. "4.82:1")
      AA normal (>=4.5:1)    pass/fail
      AA large  (>=3:1)      pass/fail
      AAA normal (>=7:1)     pass/fail
      AAA large  (>=4.5:1)   pass/fail
      Notes / proposed fix if any AA pass fails

  Then a "Proposed adjustments" section showing the exact token values
  that should replace the current ones in src/styles/themes.css to
  achieve AAA where reasonable, with the rationale for each change
  (e.g. "raise --accent-primary to #5b21b6 to pass AAA on white").

  Acceptance: AAA where reasonable, AA minimum on every pair. If a pair
  has to stay below AAA for aesthetic reasons (look-wins-over-guidelines
  per §13.1), note it explicitly.

Text/background pairs to measure (minimum set):
  --text-primary   on --primary-bg
  --text-primary   on --secondary-bg
  --text-primary   on --card-bg
  --text-secondary on --primary-bg
  --text-secondary on --secondary-bg
  --text-tertiary  on --primary-bg
  --text-tertiary  on --card-bg
  --text-muted     on --primary-bg          (will likely fail AAA — note)
  --accent-primary on --primary-bg          (button text on bg)
  --accent-primary on --secondary-bg
  white            on --accent-primary      (button label)
  white            on --accent-secondary
  white            on --accent-success
  white            on --accent-error
  --accent-error   on --primary-bg
  --accent-success on --primary-bg

For the light theme, the resolved hex values are in plan §4.2 (look at
the comments — most are pure hex; --text-muted and rgba() borders use
alpha and need compositing against the parent bg before measuring).

For the high-contrast theme, see §4.3 (continues past line 535 — read
through to the end of section 4). The palette is black/yellow with
explicit border shorthands; WCAG AAA should be easy to hit but worth
verifying that focus rings and large-print sizing actually achieve the
3:1 non-text contrast target.

Tools: WebAIM Contrast Checker (https://webaim.org/resources/contrastchecker/)
or compute relative luminance manually from the WCAG 2.x formula.
For rgba composited values, blend against the parent bg first.

Why this matters: blocks Phase 2 (high-contrast refinement). Opu cannot
finalise the high-contrast theme until your numbers land.


Track A — Editable-token doc
============================

Required reading from the plan:
  §2.5  Settings UI + ThemeEditorModal     (lines 366–384)
  §13.6 inline styles / custom-property pattern
  §13.7 token-cap rationale                (cap = ~80 total)
  §2.1  full token list with calc() forms  (lines 219–262)

What to deliver:
  File: docs/theme.editable-tokens.md
  Contents: a table covering the SUBSET of tokens the ThemeEditorModal
  will expose to end-users (NOT every token in tokens.css — only the
  ones a non-technical user would want to tweak).

  Starting list (from §2.5):
      --accent-primary
      --accent-secondary
      --secondary-bg
      --text-primary
      --radius-md
      --font-scale
      --glass-blur-amount
      --motion-scale

  For each token, document:
      Token name             (the CSS custom-property)
      User-facing label      (the radio/picker label in the editor UI)
      Allowed format         (e.g. "hex color #rrggbb", "number 0.5–2",
                              "px integer 0–24")
      Default in DARK theme
      Default in LIGHT theme
      Default in HIGH-CONTRAST theme
      One-sentence description (what visually changes)
      Sketch / ASCII diagram of what the token affects on screen

  Then a short "What is NOT editable and why" section listing 3–5
  tokens deliberately kept out of the editor (e.g. typography ramp
  --font-size-* — driven by --font-scale; raw shadow tokens — too
  niche; per-component pill tokens — should be derived).

Why this matters: becomes the help-panel content inside the
ThemeEditorModal (P3 work). Without it the modal will ship with no
guidance for the user.

Open question Opu wants Gem's read on (optional)
------------------------------------------------
The light-theme palette in §4.2 was written from feel, not from
measurement. If you find that hitting AAA requires moving more than 2–3
tokens significantly, flag whether the proposed fixes still feel like a
"light theme" or whether they slide into a high-contrast variant. The
user's principle is "look wins over guidelines" — so where AAA conflicts
with look, propose the best AA-compliant value instead and call it out.
