NEW BOOTUP OPTIONS: CLOUDCOIN FILE/FOLDER DEPOSIT ON THE LAUNCH SCREEN
=======================================================================

Date: 2026-07-04
Author/model prefix: fab (Claude Fable 5)
Scope: investigation note only; no application code was changed.
Cross-review: docs/gpt.new-bootup-options.txt was reviewed against the actual

GOAL
====

Today a first-time user (no coin file in Wallets/Mail/Bank or Mail/Fracked)
lands on ServiceSelectionScreen and gets only:

  - I Have a Locker Code
  - Buy Locker Code

Requested: add the same coin-source choices the dashboard's "+ Add Funds"
button offers, so the launch screen presents:

  1. Locker key
  2. CloudCoin files
  3. CloudCoin folder
  4. Purchase

FEASIBILITY: Yes. All transport pieces exist. The GUI work is confined to
src/screens/ServiceSelectionScreen.jsx (+ CSS + tests). BUT this is not a
copy-paste of the dashboard modal — the wallet target and the post-deposit
routing are different, and there are product decisions to settle first
(see OPEN DECISIONS).


WHAT ALREADY EXISTS (verified against code)
===========================================

Renderer API — src/api/qmailApiServices.js:
  - depositCloudCoinFiles(filePaths, memo, walletPath)   line ~2632
  - depositCloudCoinFolder(folderPath, memo, walletPath) line ~2665
  - waitForTaskCompletion(taskId, opts)                  (task polling)
  - lookupMailWalletPath()                               line ~2538
  - getIdentity(), normalizeIdentityForUi(), hasId()
  - Client-side extension gate: .bin, .stack, .zip, .png (line ~2624)

Native pickers (no new IPC needed) — preload.cjs / electron.cjs:
  - window.electronAPI.pickWalletCoinFiles()  -> Array<{path, name, size}>
  - window.electronAPI.pickWalletCoinFolder() -> {path, name}
  These return host filesystem PATHS. The backend consumes paths, not bytes,
  so a plain <input type="file"> in a browser build is NOT a substitute.
  The launch screen must degrade gracefully outside Electron (same message
  WalletActionModal uses: picker "only available in the QMail desktop app").

Dashboard reference implementation — src/qmail/screens/WalletActionModal.jsx:
  - Locker / Folder / Files method tabs, picker handlers (lines ~408-432),
    deposit + task-progress handling (~440-504), receipt display.
  - Note: the boot-time POWN flow in QMailDashboard.jsx (~1095) already calls
    depositCloudCoinFolder with an EXPLICIT wallet path and a 300s task
    timeout — that is the pattern to copy, not the modal's default-wallet call.

Backend — D:/Code/src/C/rest_core:
  - GET /api/transactions/deposit takes repeated file=... params OR one
    source_folder=..., plus wallet_path and memo; returns a task_id.
  - cmd_deposit.c MOVES source files into the wallet (fs_move_file at lines
    169/204/235 of the move phase). Verified. The user's originals disappear
    from their chosen location. The UI must say so.
  - Folder scan is non-recursive (top-level files only).
  - REST handler caps explicit file lists at 256, but because the request is
    a GET, many absolute Windows paths can blow the request-line limit well
    before 256. Keep first-run selections small or add a POST contract.


THE CRITICAL DIFFERENCE FROM "+ ADD FUNDS" (bug to avoid)
=========================================================

Verified in qmailApiServices.js: when walletPath is null/omitted, both deposit
helpers route through addWalletPathParam() -> resolveDefaultWalletPathForOperation(),
i.e. the DEFAULT wallet. That is correct for the dashboard's Add Funds, and
WRONG for first-run identity setup:

  - App.jsx boot check (hasId) and the backend identity refresh look ONLY at
    the Mail wallet (Mail/Bank first, then Mail/Fracked).
  - A launch-screen deposit that omits walletPath would "succeed" while
    leaving the user exactly where they started: no identity, coins stranded
    in Default.

So the launch-screen handlers MUST resolve the Mail wallet explicitly:

  const mail = await lookupMailWalletPath();      // fail actionably if absent
  depositCloudCoinFiles(paths, "QMail identity import", mail.path)
  depositCloudCoinFolder(path,  "QMail identity import", mail.path)

(The gpt note flags the same thing; I independently confirmed it in the code.
This was also a defect in my own first draft of this document.)


POST-DEPOSIT ROUTING (do not trust result.success alone)
========================================================

The deposit task can complete "successfully" with zero authentic coins
(counterfeit, duplicates, or legacy coins parked for the upgrade pipeline).
Advancing on success alone would strand the user on a broken dashboard.

Correct sequence after the task completes:

  1. Inspect the task result totals; if no authentic/fracked coins landed,
     stay on the launch screen and show the breakdown (reuse the receipt
     totals logic from WalletActionModal's RECEIPT_TOTAL_ROWS).
  2. Call getIdentity() with bounded retries (the backend identity cache can
     lag; QMailDashboard's mount-time hydration uses 3 attempts with
     500ms/1000ms backoff — reuse that discipline). Require configured=true.
  3. normalizeIdentityForUi(), attach mailWalletPath / mail_wallet_path
     (both spellings, matching what handleImport does at
     ServiceSelectionScreen.jsx ~191-204), clearSkipAutoRestore(), then:
        onSelectService('provisioning', enrichedIdentity)
     Routing to 'provisioning' (WalletSetupScreen) mirrors the locker flow
     and gives the user the Heal / Make Change affordances — do NOT jump
     straight to 'qmail'.
  4. Extract the shared tail of handleImport into a small
     finishProvisioning(identity, mailWalletPath) helper so the locker path
     and the new file/folder paths verify and route identically.

OPEN DECISIONS (settle before shipping)
=======================================

1. Multiple authentic coins -> ambiguous identity. The deposit API happily
   accepts many coins, but QMail identity is singular and the backend picks
   the first .bin it finds in Mail/Bank (unsorted scan). A .zip/.png can
   contain several coins, so a GUI file-count check is insufficient.
   Safe MVP: after deposit, surface the chosen serial/address on the
   provisioning screen so the user sees which coin became their identity.
   Robust fix: a dedicated backend identity-import op that selects exactly
   one note deterministically and routes surplus value to Default.

2. Move vs copy. fs_move_file is destructive from the user's viewpoint.
   Either the confirmation step warns plainly ("files will be moved"), or the
   backend grows a preserve-source/copy option for onboarding.

3. Minimum denomination. Launch copy says the locker needs a note worth more
   than 10 CC; the backend identity refresh accepts denominations 0-4. Decide
   whether the >10 rule is real and enforce it consistently (locker, files,
   folder, purchase copy, backend) — not only in UI text.

4. Purchase target. CloudCoins (CloudCoin.com/Pay/) vs QMail address/locker
   (distributedmailsystem.com/register). If CloudCoins: after opening the URL,
   hint the user to come back and use Files/Folder — closing the loop with
   this very feature.

5. Legacy coins (.stack / CCv1 / CCv2) are parked for the upgrade pipeline and
   do not immediately produce a Mail/Bank .bin. The onboarding error must
   distinguish "legacy coin needs upgrade" from "counterfeit"/"network".

6. Signed-out re-entry. ServiceSelectionScreen is reachable after Sign Out
   while a local identity still exists (localIdentityAvailable state). A new
   file/folder import in that state could silently add a second Mail identity.
   Keep "Use existing local identity" primary and require explicit
   confirmation before importing over it.


DIFFERENCES FROM / AGREEMENT WITH docs/gpt.new-bootup-options.txt
=================================================================

Verified and adopted from the gpt note (all checked against source):
  - Mail-wallet-vs-Default targeting (confirmed in addWalletPathParam /
    resolveDefaultWalletPathForOperation).
  - fs_move_file destructive move (confirmed in cmd_deposit.c).
  - GET request-line risk before the 256-file cap (confirmed: deposit
    helpers build GET URLs with repeated file params).
  - Purchase-URL duplication (confirmed at ServiceSelectionScreen.jsx:261
    and NavigationPane.jsx:34).
  - Route to 'provisioning' after verified identity, not straight to 'qmail'.

Additions in this note beyond the gpt note:
  - QMailDashboard's boot-POWN caller (line ~1095) as the concrete in-repo
    precedent for "deposit with explicit wallet path + 300s task timeout" —
    copy that call shape rather than WalletActionModal's.
  - QMailDashboard's mount-time identity hydration (3 retries, backoff) as
    the exact retry discipline to reuse for step 2 of post-deposit routing.
  - Safe-MVP framing for decision #1: display the chosen identity coin on
    the provisioning screen rather than blocking on a new backend endpoint.

No claims in the gpt note were found to be wrong. Its recommendation to keep
the first implementation narrow (two picker handlers in
ServiceSelectionScreen, no WalletActionModal reuse) matches my read: the
modal carries Default-wallet, withdraw, and receipt behavior onboarding
doesn't want.
