Out-of-scope bugs noted during Batch 6 review (2026-05-22):

- Reply/Reply All/Forward quote race: handleReply / handleReplyAll / handleForward in QMailDashboard capture `selectedEmail` at click time. If the user clicks the action before the post-select getEmailById merge completes, ComposeModal quotes the 100-character preview (from the listing) instead of the full message body. Visible as a quoted reply ending mid-sentence with no ellipsis. Flagged for Batch 8 polish.
- Forward header shows raw serial number: handleForward in QMailDashboard does NOT call convertSnToEmail on a numeric senderEmail, unlike handleReply / handleReplyAll. When the original sender's senderEmail is still a serial-number string, the "From:" line in the forwarded-message header renders the bare SN instead of a resolved QMail address.
- Dead code in ComposeModal: `loadDraftIntoCompose` is defined (line ~526) but never called from anywhere. The drafts-list rendering inside the modal was commented out earlier, so the helper has no remaining callers. Safe to delete in a future cleanup pass.
- ComposeModal `loadDrafts` is essentially dead for the same reason: still invoked in the "new" branch of the mounting useEffect, but the result is never displayed (the drafts panel inside the modal is commented out). Network call without a consumer.
- ReadingPane / QMailDashboard duplicate `hasReplyAllRecipientData`: the same predicate (Array/string check across to/To/to_addresses/cc/CC/cc_addresses) is implemented inline in both files. Hoist to a shared helper to avoid drift if backend field aliases change.
- Pending-row "Forward" button tooltip placement: ReadingPane wraps the disabled Forward button in a `<span title="...">` (correct, since disabled buttons swallow native tooltips), but the button itself has no `title` attribute, so keyboard-focus tooltips still don't fire on accessibility tools that read button titles directly.
