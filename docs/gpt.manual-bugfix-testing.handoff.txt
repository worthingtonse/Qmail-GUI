Important next-session operating rule
When the user reports a manual bug:
1. Capture the report in docs\gpt.manual-bugfix-fixes.md before or during the fix.
2. Reproduce from the user's steps when feasible, using code inspection or dev mode if a
   live packaged repro is not practical.
3. Fix the smallest coherent GUI-side cause.
4. Run targeted checks, then the static gates that make sense for the touched area.
5. Update docs\gpt.manual-bugfix-fixes.md with files changed, verification, and residual
   risk.
6. Build a fresh portable QMail.exe when the user is ready to retest a batch.
7. Commit coherent batches from time to time, after confirming what should be included if
   unrelated dirty files are present.

Bug triage guidance
- Prefer real GUI fixes over hiding backend failures.
- If the issue is backend-blocked, document it clearly and update docs\opu.note-to-backend.txt
  only when there is a concrete backend ask.
- If the issue is out of scope for the active manual smoke bug, append it to docs\gpt.bugs.txt
  instead of expanding the patch.
- Known backend gaps from the smoke handoff should not be counted as GUI regressions unless
  the backend ticket is known to be complete and integrated:
  - CORE-A: Sent folder persistence may still be incomplete.
  - CORE-E / FIX-26: Detailed send-progress stages may not be exposed.
  - CORE-H / FIX-23: Draft source cleanup and deleteDraft may still be incomplete.
  - CORE-J / FIX-18: Starred filter is backend-blocked.
  - CORE-K / BUG-46: Search pagination beyond the backend cap is unavailable.
  - CORE-L: Draft recipient detail may be incomplete.
  - CORE-M: Attachment paths containing commas or semicolons are rejected by the GUI.
  - CORE-N: Draft attachment persistence may be incomplete.

Recommended verification before packaging a retest build
Run from D:\Code\src\JavaScript\Qmail-GUI:
1. npm run lint
2. npm run build
3. node --check electron.cjs
4. node --check preload.cjs
5. git diff --check
6. npm test, when the bug touches logic covered by tests or when risk justifies it.

Recommended retest packaging flow
1. Decide whether a retest build is needed now. Build when the fixed bug blocked testing of
   other bugs, or when the user asks for a new manual retest build.
2. If rest_core changed, compile rest_core first.
3. Confirm or locate the latest core.exe source. The expected default is E:\core.exe after
   rest_core/CMake builds it.
4. Copy the confirmed core.exe into backend\core.exe, unless the rest_core CMake post-build
   step already did it.
5. Run the verification gates above.
6. Run:
     npm run build-portable
7. Confirm release\QMail.exe exists and record its size/time.
8. Copy release\QMail.exe into fresh isolated manual test folders, for example:
     E:\QMail-Smoke\<date>\client1\QMail.exe
     E:\QMail-Smoke\<date>\client2\QMail.exe
9. Do not point client1 and client2 at the same Client_Data.

Commit guidance
- Commit coherent batches only after user approval. A batch can be one bug fix or a small
  related set of bug fixes, plus the matching update to docs\gpt.manual-bugfix-fixes.md.
- Do not include unrelated dirty files unless the user explicitly asks.
- Before each commit, run:
    git status --short
    git diff --stat
    git diff --check
- If unrelated changes are present, either stage only the touched files or ask the user what
  should be included.
- Useful commit message shape:
    Fix QMail manual smoke BUGFIX-YYYYMMDD-NN

Manual tester loop
The expected loop is:
1. User manually tests packaged QMail.exe.
2. User reports a bug.
3. Assistant logs the bug and fixes it.
4. Assistant verifies and updates the fix log.
5. Assistant rebuilds QMail.exe with the latest core.exe when the fix blocked further
   testing or the user asks for a retest build.
6. Assistant commits a coherent batch after user approval.
7. User manually retests.
