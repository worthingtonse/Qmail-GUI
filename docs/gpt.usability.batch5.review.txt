Findings:

1. HIGH - Valid attachment paths containing commas or semicolons break in the backend.

ComposeModal passes staged absolute paths through unchanged (src/qmail/screens/ComposeModal.jsx:580-591), and sendEmail appends each one as a repeated attachment_file_path parameter (src/api/qmailApiServices.js:1200-1204). That frontend shape is good.

However, the backend upload_and_tell handler immediately concatenates those repeated params back into a comma-separated string (D:/Code/src/C/rest_core/api_src/api_handlers_qmail_messages_send.c:1556-1574). qmail_upload_orchestrator then parses that string with strtok_r(att_buf, ",;", ...) (D:/Code/src/C/rest_core/src/qmail/qmail_upload_orchestrator.c:357-374).

Effect: a user-selected file like:
  D:\Docs\invoice, final.pdf
or
  D:\Docs\notes; qmail.txt
is split into invalid fake paths, causing send failure or missing attachments even though the UI accepted the file and showed it as staged.

Recommended fix: keep attachments as an array through the backend instead of serializing to comma/semicolon text. If backend array plumbing is too large for this batch, the GUI should temporarily reject paths containing comma/semicolon with a clear message before staging them.

2. HIGH - The UI can show attachments that the backend silently drops.

The Electron picker and ComposeModal have no count or total-path-length limit. The backend upload_and_tell args store all attachment paths in a fixed char buffer, `attachments[MAX_PATH_LEN * 4]` (D:/Code/src/C/rest_core/api_src/api_handlers_qmail_messages_send.c:123), then the param-copy loop silently `break`s when adding the next path would exceed that buffer (D:/Code/src/C/rest_core/api_src/api_handlers_qmail_messages_send.c:1566-1574). There is no error returned to the renderer for the omitted files.

Effect: if a user attaches enough files, or a few long Windows paths, the compose UI can show N chips but the backend may send fewer than N attachments. That is a data-loss UX bug because the user gets no warning.

Recommended fix: make the backend reject overflow with a 400 and an explicit message, or expose/enforce a frontend limit that matches the real backend capacity. The backend already has UPLOAD_MAX_ATTACHMENTS, but the fixed aggregate string buffer is the tighter practical limit here.

3. MEDIUM - Save Draft silently discards staged attachments.

The summary calls out that attachments are not persisted with drafts, and that is acceptable as a first implementation only if users are told. Today, the same modal can show staged attachment chips and still offers Save Draft, but handleSaveDraft does not include the staged attachments in the draft payload (src/qmail/screens/ComposeModal.jsx:319-366). Reopening the draft clears attachments on modal open (src/qmail/screens/ComposeModal.jsx:169-173).

Effect: a user can attach files, save the draft, and reasonably expect those files to be saved with the draft. They are silently lost.

Recommended fix: either disable Save Draft while attachments are staged, show a warning that attachments are send-only and will not be saved, or add backend draft-attachment metadata support before advertising attachment drafts as a normal workflow.
