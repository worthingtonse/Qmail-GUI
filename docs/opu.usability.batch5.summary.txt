FIX-02: Compose attachment picker
=================================
Bug:
  ComposeModal hard-coded `attachments: []` when calling sendEmail.
  The backend supported attachment_file_path params and the API
  helper already iterated emailData.attachments (per the existing
  v3 follow-ups), but there was no UI to populate it. The Paperclip
  icon was imported and never rendered.

Fix:
  Three layers wired together:

  1. electron.cjs — new IPC handler 'compose:pickFiles'.
     Opens dialog.showOpenDialog with openFile + multiSelections.
     For each returned filePath, runs fs.promises.stat in the main
     process so the renderer (which can't fs.stat under
     contextIsolation) receives enriched metadata.
     Returns Array<{ path, name, size }>, or [] on cancel/dialog-
     error. Per-file stat failures drop just that file from the
     result and log; the picker as a whole still resolves so the
     renderer can use whatever survived.

  2. preload.cjs — extended the existing window.electronAPI bridge.
     Added pickAttachments() which invokes 'compose:pickFiles'.
     No second contextBridge — uses the existing exposure pattern
     consistent with checkUSBDrive, runCommand, etc. (gpt-batch1
     architectural feedback honored: do NOT create a second
     renderer bridge.)

  3. ComposeModal.jsx:
     a. attachments state (Array<{path,name,size}>) reset on modal open.
     b. attachmentsSupported: derived from window.electronAPI presence.
        Browser/Vite build returns false → button renders disabled
        with explanatory tooltip.
     c. handleAttachClick: calls pickAttachments(), de-duplicates
        by absolute path so re-picking the same file doesn't
        accumulate copies, handles canceled (empty array) silently.
     d. handleRemoveAttachment: drops a chip by path.
     e. formatAttachmentSize: B / KB / MB display.
     f. UI: an "Attach files" button beneath the message textarea,
        followed by chips for each staged file (name + size + X to
        remove). Button label shows the count when files are staged.
     g. handleSend: passes attachments.map(a => a.path) into
        emailData.attachments. sendEmail() already iterates and
        appends one attachment_file_path query param per entry.

Edge cases handled
==================
- User cancels the picker → handler returns [], UI no-ops.
- User picks the same file twice → de-duplicate by path.
- fs.stat fails on a file (deleted between picker and stat) →
  drop that file from the result, log a warning, keep the others.
- Browser/Vite build (no electronAPI) → button renders disabled
  with tooltip "File attachments require the desktop build."
- Modal closed mid-send → existing isSending guards keep the send
  in flight; staged attachments aren't lost until the close
  completes (next open clears them).
- Path with spaces / unicode → handler returns the absolute path
  verbatim; URLSearchParams in sendEmail handles the escape.
- Long filenames → chip uses CSS ellipsis (whiteSpace: nowrap,
  textOverflow: ellipsis, max-width 320px); the absolute path is
  available via the chip's title (hover tooltip).

Decisions worth flagging for review
===================================
  1. Inline styles on the attachment UI rather than new CSS classes.
     Rationale: the chip + button block is self-contained and uses
     theme variables for colors/spacing so dark-mode/theming still
     works. If the design system prefers classes, it's a small
     refactor (similar to the Retry button extraction in batch 4
     follow-up).

  2. Attachments are NOT persisted with drafts in this iteration.
     Each compose session starts with an empty staged list. A draft
     re-opened later has no record of files the user picked in the
     prior session. Persisting attachments alongside drafts would
     require backend cooperation (CORE-M-or-similar). Flagged as
     a follow-up; not blocking.

  3. The Attach button sits BENEATH the body textarea rather than
     in the modal footer next to Send/Save Draft. Two reasons:
       (a) The footer is busy with Send/Save Draft/Sending status.
       (b) Putting the chips near the body keeps them visible while
           composing; in the footer they'd be below the fold.
     If the design team prefers the footer position, easy to move.

  4. Filename rendering is local-OS-native. dialog.showOpenDialog
     returns absolute paths in whatever encoding the OS uses
     (Windows backslashes, etc.). The backend reads these paths
     directly via attachment_file_path. In the packaged Electron
     build the renderer + main + backend all run on the same OS
     so this is consistent; the cross-host case (path → some other
     server) isn't applicable to this app.

Follow-up (gpt batch-5 review)
==============================
Date: 2026-05-22
Reviewer: D:\Code\src\JavaScript\Qmail-GUI\docs\gpt.usability.batch5.review.txt

Three substantive findings, all real bugs. Gem approved batch 5
with no actionable changes; gpt caught three GUI-side defenses
that should land before relying on the picker in the wild.

Patches applied (all in ComposeModal.jsx):

1. (gpt #1, High) Reject attachment paths with ',' or ';'.
   Root cause: upload_and_tell concatenates the picker's repeated
   attachment_file_path params into a single string, then
   qmail_upload_orchestrator splits that string with
   strtok_r(att_buf, ",;", ...). A path containing either delimiter
   gets mangled into invalid sub-paths.
   Fix: handleAttachClick now filters out picked entries whose path
   contains ',' or ';' BEFORE adding to state. Rejected entries
   surface in attachError with the filename and reason. The user
   can rename the file and re-pick.
   The real fix is backend-side — tracked as CORE-M.

2. (gpt #2, High) Defensive count + combined-path-length cap.
   Root cause: upload_and_tell stores all attachment paths in a
   fixed char[MAX_PATH_LEN * 4] = 16384-byte buffer and silently
   `break`s the copy loop when the next path would overflow. No
   error returned to the renderer. UPLOAD_MAX_ATTACHMENTS = 245.
   Fix: GUI caps total count at 50 (well below 245) and total
   combined path-length at 12000 bytes (well below 16384 with
   margin for the comma separators). Overflows surface in
   attachError. Both numbers are intentionally conservative to
   leave room for any future backend buffer changes.
   The real fix — return a 400 from the backend on overflow, or
   stop using a fixed buffer — is part of CORE-M.

3. (gpt #3, Medium) Draft + attachment mismatch warning.
   Root cause: handleSaveDraft doesn't include the staged
   attachments in the saveDraft/updateDraft payload, and reopening
   the draft clears them on mount. Users could attach files, save
   the draft, and reasonably expect those files to come back.
   Fix: an inline amber warning between the body textarea and the
   footer, visible only when attachments.length > 0:
     "Attachments are sent with this message but are NOT saved
      with a draft. Save the draft first, then re-attach files
      when you're ready to send."
   Save Draft stays enabled (a user with body changes shouldn't
   be blocked from saving body work just because they staged a
   file). The warning is the discoverable contract.
   The real fix — persist attachment metadata with drafts — is
   tracked as CORE-N. The GUI will pick up persisted attachments
   automatically once that ships (saveDraft already receives the
   list via the touchedFields machinery from gpt-batch3).

Backend tickets added to the plan:
  CORE-M: stop comma/semicolon-serializing attachment paths in
          upload_and_tell. Keep them as an array. Unblocks the
          GUI-side delimiter rejection and length cap.
  CORE-N: persist attachment metadata with drafts. Closes the
