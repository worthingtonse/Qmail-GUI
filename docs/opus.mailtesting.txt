GOAL
----
Drive two real QMail clients (the portable QMail.exe builds) entirely through
their local REST API — no GUI clicking — to prove that:

  Test 1: a small TEXT message sends from client A and is received by client B.
  Test 2+: the same WITH an attachment, escalating file size each round.

DIRECTION: ONE WAY ONLY (A=37.34@bit -> B=25.165@giga). We only need to prove a
message can be sent and received; no reverse-direction rounds.

2. HOW THE CLIENTS LAUNCH (CRITICAL)
================================================================================
QMail.exe is an Electron wrapper. At launch it spawns the embedded backend
(core.exe, extracted to a temp dir) with:

    core.exe -port <N> -data-dir <dir-containing-QMail.exe>

Key consequences (verified in electron.cjs):

  * The "-port" flag OVERRIDES rest_core.conf's http_port. To get a DETERMINISTIC
    port for curl, launch with --port:

        "D:\...\37.34@bit\QMail.exe"  --port 41844
        "D:\...\25.165@giga\QMail.exe" --port 23320

    (Using the same numbers as each conf keeps things consistent. Any free port
    works as long as the test script targets the one it launched with. The two
    MUST differ.)

  * -data-dir defaults to the directory of QMail.exe, so Client_Data is picked up
    automatically. Do not pass -data-dir; the wrapper handles it.

  * A GUI window WILL open for each client. That is harmless — the test drives the
    REST API directly. (There is no documented headless flag; do not invent one.)

  * AUTH TOKEN CAVEAT: the Electron wrapper generates a RANDOM per-launch
    QMAIL_API_TOKEN and passes it to the backend via env. ONLY the object-transfer
    progress endpoints (/qmail/net/object-transfers/*) require it as
    "Authorization: Bearer <token>". The test plan below DELIBERATELY AVOIDS those
    endpoints and uses /system/tasks for completion instead, so NO token is needed.
    If you ever must hit an object-transfer endpoint, the token is unknowable from
    outside the process — ask the owner to surface it, or skip that check.

Startup readiness (poll until ready, ~30-60s budget):
    GET {BASE}/qmail/local/identity/get   -> expect { registered:true, serial_number>0 }
  Also confirm identity matches expectation:
    A -> address "37.34@bit"   B -> address "25.165@giga"
  If identity is not registered, the client's wallet/identity coin is missing —
  STOP and report; this is an environment problem, not a send/receive bug.


================================================================================
3. THE SEND API (what the GUI actually does)
================================================================================
Single endpoint, URL-encoded form body (backend parses POST body as query params):

    POST {BASE}/qmail/net/messages/upload_and_tell
    Content-Type: application/x-www-form-urlencoded

    Body params:
      to        = <recipient address>      (repeatable; e.g. 25.165@giga)
      cc        = <addr>                    (repeatable, optional)
      bcc       = <addr>                    (repeatable, optional)
      subject   = <text>
      body      = <text>
      duration  = <weeks>                   (default 4)
      attachment_file_path = <ABSOLUTE local path>   (repeatable, optional)

  Attachment notes (from sendEmail() + object-transfer checklist):
    - attachment_file_path is an ABSOLUTE filesystem path the BACKEND reads
      directly (NOT multipart, NOT base64). The file must exist on the machine
      running that client.
    - Backend path-list limits: max 50 files; combined path strings <= 12000 UTF-8
      bytes; paths containing ',' or ';' are dropped by the serializer (our test
      paths are safe).
    - Large files are chunked/striped by the backend automatically. The ~65 KB
      "stripe" cap is an internal RAIDA packet limit, NOT a per-attachment cap;
      do not confuse them.

  Response JSON (success shape):
      { success:true|status:"success"|"accepted",
        file_guid:"<32hex|null>", task_id:"<id|null>",
        operation_id:"<32hex|null>", operation_ids:[...],
        message:"...", timestamp:<ms> }

  Treat send as ACCEPTED when any of: success===true, status in
  {success,accepted}, file_guid present, task_id present.

  COMPLETION POLL (this is the real pass/fail for the SEND side):
      GET {BASE}/system/tasks?task_id=<task_id>
      -> { status:"success", payload:{ id, status, progress, message, data } }
      Terminal states:  completed, success, failed, error, cancelled, timeout
      Success states:   completed, success
    Poll every 1s. Budget: 60s for text/small; scale up generously for big files
    (e.g. 10 min for 100 MB+, 30+ min for the 958 MB stress file). If no task_id
    was returned (pure synchronous send), the message is already accepted on the
    wire; proceed to verify on the receiver.


================================================================================
4. THE RECEIVE API (what the recipient client does)
================================================================================
A recipient becomes aware of mail two ways; for a script, POLL notifications:

  (a) Discover the new mail:
      GET {B BASE}/qmail/db/notifications/list
      -> { success, count, notifications:[ { file_guid, sender_sn,
           sender_address, sender_name, ... } ] }
      Poll every ~3-5s until a notification with the expected sender appears, or
      until a timeout (e.g. 120s for small; longer for big). The beacon round-trip
      (RAIDA PING/PEEK) means receipt is NOT instant — allow time.
      (SSE alternative: GET {B SSE}/events streams a "new-mail" event with
       {guid|file_guid|email_id}. Polling notifications/list is simpler for a
       script and is what we use here.)

  (b) Download + decrypt the message (synchronous form returns the content):
      POST {B BASE}/qmail/net/messages/download?file_guid=<guid>
      -> { success, status:"success", email_id:"<32hex>", subject, body,
           sender_sn, sender_address, ... }
      Capture email_id for the next steps. (Add &async=1 for 202 async mode that
      completes via SSE — NOT needed here; use the synchronous form.)

  (c) Read the stored message (confirms it landed in the DB correctly):
      GET {B BASE}/qmail/db/messages/get?email_id=<email_id>
      -> subject, body, sender_address, sender_sn, sender_denomination_code, ...
      ASSERT: subject and body match what A sent; sender_address == "37.34@bit".

  (d) Attachments — list metadata:
      GET {B BASE}/qmail/db/attachments/list?email_id=<email_id>
      -> { count, attachments:[ { attachment_id, name, extension, size_bytes,
           storage_mode, dangerous, warning } ] }
      ASSERT: count == number sent; name + size_bytes match the source file.
      storage_mode: 0=internal blob, 1=external file, 2=PENDING on-demand.

  (e) Attachments — download bytes on demand and verify integrity:
      GET {B BASE}/qmail/db/attachments/get?email_id=<email_id>&attachment_id=<id>
      -> raw file bytes (Content-Disposition: attachment; filename="...").
         Save with: curl ... -o out.bin
      ASSERT: byte length == source size, AND sha256(out.bin) == sha256(source).
      This is the definitive attachment pass/fail.

5. TEST PROCEDURE (deterministic, per round)
================================================================================
Conventions:
  - Use a UNIQUE subject per send so the receiver can disambiguate, e.g.
    "OPUS-TEST <round> <epoch>". (Pass a timestamp in; don't rely on wall clock
    inside any restartable harness.)
  - Clear/rotate logs before each round to reduce noise (see Section 7).
  - One round at a time. Verify fully before the next.

DIRECTION: every round is ONE WAY, A (37.34@bit) -> B (25.165@giga). No reverse.

PRE-FLIGHT (once):
  1. Launch A:  "D:\...\37.34@bit\QMail.exe" --port 41844
  2. Launch B:  "D:\...\25.165@giga\QMail.exe" --port 23320
  3. Wait for both /qmail/local/identity/get to report registered:true with the
     expected addresses. Abort with a clear message if not.

TEST 1 — small text, A -> B:
  1. POST upload_and_tell to A:
       to=25.165@giga, subject="OPUS-TEST t1 <ts>", body="hello from bit",
       duration=4
  2. If task_id: poll {A}/system/tasks until success (<=60s). Fail on terminal
     non-success.
  3. Poll {B}/qmail/db/notifications/list until a notif from 37.34@bit appears
     (<=120s). Capture file_guid.
  4. POST {B}/qmail/net/messages/download?file_guid=<guid>. Capture email_id.
  5. GET {B}/qmail/db/messages/get?email_id=... ; ASSERT subject+body+sender.
  PASS if all asserts hold.

TEST 2..N — text + ONE attachment, escalating size, A -> B:
  Same as Test 1 but add attachment_file_path=<abs path to the round's file>,
  walking the size list in Section "GOAL" smallest-first.
  After step 5 also do:
    6. GET {B}/qmail/db/attachments/list?email_id=... ; ASSERT count/name/size.
    7. GET {B}/qmail/db/attachments/get?...&attachment_id=<id> -o out ; ASSERT
       size + sha256 match source.
  Scale poll timeouts with file size (Section 3/4). STOP the whole escalation on
  the first failing round and proceed to investigation (Section 6). The 958 MB
  Anaconda file is OPTIONAL — only run it last, after every smaller round passes.

6. WHEN A TEST FAILS — INVESTIGATION WORKFLOW
================================================================================
Do NOT edit product code. Investigate, then write a bug doc + (optionally) a note
to the server AI.

  1. Capture the failing HTTP response verbatim (status code + JSON body).
  2. Read the backend log for that client around the failure:
       <ClientDir>\Client_Data\main.log
     (rotated copies under Client_Data\OldLogs\*.zip).
     Note the last task/transfer state, any error strings, RAIDA command numbers,
     and timestamps.
  3. Cross-reference the local backend source (available on this machine):
       D:\Code\src\C\rest_core
     Relevant areas:
       - send/upload + tell:  src around upload_and_tell handler, qmail upload,
         protocol.c (packet framing / 65 KB stripe limit).
       - receive/download:    messages/download handler, manifest v1 parsing,
         object fetch (cmd 81/82) with legacy paged fallback (cmd 70/74/75).
       - attachments:         attachments/list + attachments/get handlers,
         storage_mode handling, on-demand download.
     See also client-side context:
       - docs/qmail-object-transfer-v1-client-checklist.md
       - claude.note-to-server-ai.txt   (tell manifest v1 resolution)
       - docs/cod.upload-stripe-limit.findings.txt (65 KB stripe limit)
  4. Decide whether the fault is:
       (a) CLIENT/rest_core bug (local source) — describe the exact function/line.
       (b) SERVER/RAIDA-side issue — write a note to the server AI (Section 8).
       (c) ENVIRONMENT (missing identity, no funds in locker pool, file path,
           network) — report and stop; not a product bug.
  5. WRITE THE BUG DOCUMENT:  docs/opus.mailbug.<short-name>.txt
     Include: which test/round/size, exact request, exact response, relevant
     main.log excerpt, the suspected root cause with file:line, a PROPOSED fix
     (do not apply it), and how to reproduce. Then stop and request approval.

Common things to check first:
  - Is the recipient address exactly right (37.34@bit / 25.165@giga)?
  - Did the send return task_id but the task ended "failed"/"error"? Read
    payload.message + payload.data.error.
  - Locker/payment: wallets are assumed FUNDED. A send rejected for lack of funds
    is therefore UNEXPECTED — capture the locker/payment error from main.log and
    report it as a real failure (don't dismiss it as expected environment state).
  - For attachments: did upload_and_tell drop the path (',' or ';' in it, or file
    not found by the backend)? Confirm the file exists and the path is absolute.
  - Receiver got the tell but download fails: likely manifest/object-fetch on the
    server — capture the cmd numbers from main.log and note to server AI.

7. LOG HYGIENE (optional but recommended per round)
================================================================================
Before each round, truncate the active log so the round's events are isolated:
    <ClientDir>\Client_Data\main.log    (for BOTH clients)
A simple truncate-in-place is fine (e.g. PowerShell: Clear-Content main.log).
Don't delete the file while the client is running; just clear its contents. The
backend rotates old logs into Client_Data\OldLogs as zips on its own.

  --data-urlencode "body=see attached" ^
  --data-urlencode "duration=4" ^
  --data-urlencode "attachment_file_path=C:\Users\User\Downloads\Test Attachements\test-24MB.bin"

# poll send task (sender side)
curl "http://localhost:41844/api/system/tasks?task_id=<TASK_ID>"

# receiver: discover, download, read, list+fetch attachment
curl http://localhost:23320/api/qmail/db/notifications/list
curl -X POST "http://localhost:23320/api/qmail/net/messages/download?file_guid=<GUID>"
curl "http://localhost:23320/api/qmail/db/messages/get?email_id=<EMAIL_ID>"
curl "http://localhost:23320/api/qmail/db/attachments/list?email_id=<EMAIL_ID>"
curl "http://localhost:23320/api/qmail/db/attachments/get?email_id=<EMAIL_ID>&attachment_id=0" -o out.bin

NOTE: ^ is the cmd.exe line-continuation. In PowerShell use backtick ` or put it
all on one line. --data-urlencode is preferred so spaces/specials are encoded.
