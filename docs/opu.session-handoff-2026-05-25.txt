THE ACCEPTANCE-CRITERIA GATES (the Opu review protocol)
================================================================================

When GPT (or anyone) hands you an E-track for review, run THESE seven
checks. Every E-track this session was reviewed with this exact set:

  G1 (color literals)
      rg '#[0-9a-fA-F]{3,8}\b|rgba\(' <file.css>
      Expected: zero matches.

  G2 (font-size literals)
      rg 'font-size:\s*[0-9.]+(px|rem|em)' <file.css>
      Expected: zero matches.

  G2-bonus (bad token refs)
      rg 'font-size:\s*var\(--text-' <file.css>
      Expected: zero matches. (The token tier prefix is --font-size-*,
      not --text-*. This used to be a real bug class.)

  G3 (rename markers)
      rg '/\* was:' <file.css>
      Expected: N markers, where N >= roughly the number of selectors
      renamed in the pass.

  JSX inline-style
      rg 'style=\{\{|style=\{' <file.jsx>
      Expected: zero matches, OR a small handful that match either:
        - §13.6 custom-property pattern: style={{ '--block-prop': value }}
        - a deterministic modifier-class palette pattern (see
          feedback memory on inline-style alternatives)

  JSX old class names
      rg 'className="[^"]*\b(<list-of-old-names>)\b' <file.jsx>
      Expected: zero matches.

  CSS old unprefixed selectors
      rg '^\.(<list-of-old-names>)\b' <file.css>
      Expected: zero matches outside `/* was: */` comments.

If all seven pass: flip the status row to REVIEWED, normalize the
parenthetical to "(opu YYYY-MM-DD; visual smoke pending)", refresh the
"Last updated" line, and append a section to opu.E-track-review.txt.

PATTERNS WORTH KNOWING (carry-overs from this session)
================================================================================

1. **The REVIEWED-status convention.**
   Status row format that worked across E1-E12:
     E#  REVIEWED  gpt  <file path/desc> (opu YYYY-MM-DD; visual smoke pending)  <line-count>
   The "Last updated" line names what changed (e.g., "E# reviewed:
   G1/G2/G3 + JSX pass").

2. **GPT writes "repo gates passed", normalize to "opu gates passed".**
   GPT consistently writes "repo gates passed" in status rows. It's a
   label preference, not a substantive disagreement. Normalize during
   the flip-to-REVIEWED step. (Saw this on E1, E3, E4, E5 over the
   session.)

3. **GPT often bundles structural improvements into Phase 4 rename
   passes.** Across E1-E12, GPT routinely caught and fixed: dead-code
   deletions, missing-token correctness bugs (e.g. --accent-danger
   undefined on E7), inline-style→class refactors (E3 file-input, E5
   COMING_SOON_BADGE_STYLE, E11 avatar tones). All were net wins.
   Don't push back on these; the rename pass is the right place to
   surface and fix this kind of adjacent rot.

4. **Avatar-tone pattern for per-instance variation under the
   no-inline-style gate.** Saved as a memory:
     feedback_qmail_gui_inline_style_alternatives.md
   Summary: prefer a deterministic modifier-class palette
   (.block__el--tone-0 ... --tone-N) over either inline style or the
   §13.6 custom-property exception when per-instance visual variation
   comes from a discrete palette rather than a continuous value.

5. **State-class localization is a real structural improvement.**
   `loading-state`, `empty-state`, `error-message`, `form-group` used
   to be generic cross-cutting classes. Phase 4 migrated each to
   block-local equivalents (`__loading-state`, `__empty-state`, etc.).
   Applied on E5, E9, E11, E12. The codebase no longer depends on
   these generic class names.

6. **Cross-component renames are tractable in a single pass.** E8
   renamed ComposeModal's base classes AND rewired AddContactModal.jsx
   (its shared-base consumer) in the same pass. Did not break. Same
   approach is safe for any future shared-base rename.
