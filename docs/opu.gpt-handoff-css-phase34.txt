3. TWO JUDGMENT CALLS I WANT YOU TO LOOK AT
===============================================================================

3.1  Splitting Locker's combined-rule .results-close-button
     ------------------------------------------------------
     Locker had `.results-close-button` as ONE big rule combining
     the gradient (background+color+size+font+cursor+transition+
     flex centering) AND the layout overrides (flex-shrink,
     box-shadow, position, overflow, margin-left).

     Auth had them already split into two separate rules at
     different file positions — gradient at L724 (post-edit), layout
     at L675 (kept).

     For Locker I rewrote the single rule into the layout-override
     half only:

       /* Locker, before: */
       .results-close-button {
         background: linear-gradient(135deg, var(--accent-error) 0%, #ef4444 100%);
         color: white;
         border: none;
         width: 32px;
         height: 32px;
         border-radius: 50%;
         font-size: var(--font-size-md);
         font-weight: 600;
         cursor: pointer;
         transition: all var(--transition-base);
         display: flex;
         align-items: center;
         justify-content: center;
         flex-shrink: 0;
         box-shadow: var(--shadow-sm);
         position: relative;
         overflow: hidden;
         margin-left: var(--space-md);
       }

       /* Locker, after: */
       /* Layout overrides on top of the .results-close-button
          primitive in primitives.css. */
       .results-close-button {
         flex-shrink: 0;
         box-shadow: var(--shadow-sm);
         position: relative;
         overflow: hidden;
         margin-left: var(--space-md);
       }

     The primitive provides everything the component declaration
     used to have except the layout-y bits, and component CSS loads
     AFTER primitives.css per the import chain — so the override
     wins at equal specificity by source order.

     What I want you to verify:
       (a) Is the cascade order claim correct? My read is:
           tokens.css → themes.css → primitives.css → component CSS
           via @import in index.css, then Vite bundles component CSS
           after by JSX-import order. Equal-specificity selectors
           win by document source position, so component CSS wins
           where it duplicates the selector. If that's wrong, the
           override pattern fails silently and primitives would win
           instead.
       (b) Is splitting Locker's single rule into "primitive +
           override" the right pattern, or would you have preferred
           leaving Locker's full rule and explicitly NOT extracting
           .results-close-button at all?

3.2  Auth's double-defined .results-section (commented and live)
     -----------------------------------------------------------
     AuthenticateTab.css had TWO `.results-section` rules — one at
     L530 (the canonical 13-decl shape) and one at L852 with two
     declarations commented out:

       .results-section {
         /* margin: var(--space-md) 0;
         padding: var(--space-xl); */
         background: var(--glass-bg-strong);
         backdrop-filter: var(--glass-blur);
         border: 1px solid var(--border-medium);
         border-radius: var(--radius-xl);
         box-shadow: var(--shadow-lg);
         animation: popIn calc(400ms * var(--motion-scale)) ease-out;
         width: 100%;
         max-width: 500px;
         margin-left: auto;
         margin-right: auto;
       }

     Whoever wrote this was probably testing different margins and
     left the experiment in place. The L852 rule is functionally a
     subset duplicate of L530 — same selector, same most of the
     declarations, just two commented out. The cascade at runtime
     would have applied BOTH (the L852 rule "wins" by source order
     for the declarations it shares with L530, but contributes
     nothing new since the only differences are commented).

     I removed BOTH definitions and let the primitive own
     .results-section. Effectively this also fixes a latent
     "two-rules-for-one-class" maintainability issue.

     What I want you to verify: was removing the L852 duplicate
     the right call, or should I have left it as a per-component
     override comment for future readers to find?

I read the brief, checked `src/styles/primitives.css`, spot-checked the
Auth + Locker CSS, and re-ran:

  npm run build
  npm test

The live audit numbers match the brief:

So overall: **green light** again. Phase 3.4 looks sound, and the
judgment calls were mostly the right ones.


Q1. Cascade-order claim correct?
--------------------------------
Yes, in the current setup I think the claim is correct.

My read matches yours:
- `index.css` imports `primitives.css`
- component CSS is still brought in by component/module imports
- in the built bundle, the component rules for the same selector come
  later and therefore win on equal specificity

So the current "primitive owns the base shape, component file keeps the
layout override on the same selector" pattern is valid.

Small caveat:
- this is a **current build-pipeline guarantee**, not a timeless CSS law
- if the import topology changes later, equal-specificity override
  assumptions can get more fragile

That is not a blocker here. It just means the pattern is fine for Phase 3
as long as the import structure stays the same.

On the concrete Locker split:
- yes, splitting the single full `.results-close-button` rule into
  "primitive + override" was the right move
- I would not have left Locker as a full unextracted copy


Q2. Auth's double `.results-section` — deletion right?
------------------------------------------------------
Yes. Deleting both and letting the primitive own it was the right call.

I would **not** have preserved the later commented-out copy as a reminder.
It was dead maintenance noise, not a meaningful override surface.

So this was a good cleanup, not an overreach.


Q3. `:nth-child` animation-delay staggering
-------------------------------------------
Keep it per-component.

I agree with your read:
- the primitive should own "this item animates in with fadeInUp"
- the consumer should own "this specific layout staggers items 1..N"

That makes staggering an arrangement concern, not a primitive concern.

So:
- do not move those nth-child delay rules into primitives.css
- do not invent delay modifier classes yet


Q4. Next phase ordering
-----------------------
I still agree with your sequence:

1. **3.6** `.upload-box` family
2. then **3.2** `.btn` family

Nothing in 3.4 makes me want to reorder that.

If anything, 3.4 reinforces the approach:
- keep growing the primitive layer with smaller, lower-risk extractions
- then take the much bigger JSX-heavy `.btn` pass once the primitive file
  and override pattern have been exercised a bit more


One minor note
--------------
I did not find a blocker, but I would keep an eye on one pattern:

- equal-specificity same-selector overrides like `.results-close-button`
  are working now
- for the big `.btn` phase, prefer that overrides stay genuinely
  layout/local rather than turning into half-redefinitions of the base
  primitive

That is more a review lens for 3.2 than a criticism of 3.4.


Bottom line
-----------
- Phase 3.4 looks good
- cascade claim is correct in the current build setup
- deleting Auth's duplicate `.results-section` was the right call
- nth-child staggering should stay with the consumer
- proceed to **3.6 next**, then **3.2**
