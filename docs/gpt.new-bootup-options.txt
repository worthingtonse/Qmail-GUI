========================================================

Review date: 2026-07-04
Reviewer/model prefix: gpt (GPT-5)
Revision basis:
  - User decisions supplied after the first review
  - Cross-review of docs/fab.new-bootup-options.txt
  - Current Qmail-GUI and D:/Code/src/C/rest_core source
Scope: investigation and implementation note only; no application behavior

REVISED CONCLUSION
==================

The user's decisions materially change the recommended flow. Uploaded coins
must first use the normal "+ Add Funds" deposit path into:

  Client_Data/Wallets/Default

After the deposit and any legacy conversion finish, QMail must move exactly one
eligible coin - the highest-value coin - from Default to the matching folder in
the Mail wallet:

  Default/Bank    -> Mail/Bank
  Default/Fracked -> Mail/Fracked

The remaining coins stay in Default as spendable funds. This removes the main
ambiguity in the original gpt/fab findings: the whole deposit must NOT target
Mail. It also makes reuse of the existing WalletActionModal preferable because
that modal already targets Default and already supplies native selection,
progress, task polling, result handling, and deposit receipts.

One additional promotion step is required after Add Funds completes. No GUI or
API helper currently performs the full operation "choose the largest eligible
Default coin, move it to the same-grade Mail folder, and refresh QMail identity"
as one transaction. The backend has nearly all of the component functions, and
an existing wallet-transfer endpoint can implement an MVP, but a small dedicated
identity-promotion endpoint would be safer and easier to test.


DECISIONS NOW TREATED AS SETTLED
================================

1. Deposit destination

   File/folder imports go to the registered Default wallet, using the same
   behavior as dashboard Add Funds. Do not pass the Mail wallet to
   depositCloudCoinFiles() or depositCloudCoinFolder().

2. Progress and receipt

   Show progress and a receipt. Reuse/adapt WalletActionModal rather than
   rebuilding its deposit receipt and progress UI in ServiceSelectionScreen.

3. Identity selection

   After deposit, move one highest-value eligible coin from Default to Mail.
   Preserve its grade: Bank remains Bank; Fracked remains Fracked.

4. Move semantics

   Files and the selected identity coin must be moved, not copied.

5. Minimum identity value

   The minimum is 1 CC. In the current denomination system this means an
   identity candidate must have denomination code >= 0. QMail's current address
   code accepts denomination codes 0 through 4, so the precise eligibility
   range should be 0..4 (1 through 10,000 CC) unless QMail address support is
   expanded for larger denominations.

6. Purchase option

   Defer it. When implemented, use https://CloudCoin.com/Pay/ and show a hint
   telling the user to return and choose Files or Folder after downloading the
   purchased coins.

VERIFIED MOVE BEHAVIOR
======================

The required move behavior is already implemented correctly at the filesystem
layer:

  D:/Code/src/C/rest_core/src/filesystem.c
  D:/Code/src/C/rest_core/include/filesystem.h

fs_move_file(src, dst):

  1. Attempts rename() for an efficient same-volume move.
  2. If rename fails (including a cross-volume move), copies the file.
  3. Verifies the destination size matches the source.
  4. Deletes the source only after verification.
  5. If source deletion fails, removes the destination copy to prevent a
     duplicate.

The deposit pipeline already uses fs_move_file() when taking selected files or
top-level files from a selected folder into Default/Import. The identity
promotion must also use fs_move_file(), directly or through the existing wallet
transfer code. No renderer-side copy/delete implementation should be added.

The UI should still say that selected files will be moved from their original
location. This is now a confirmed requirement, not an open decision.


FORMAT SUPPORT - CURRENT SOURCE FINDINGS
========================================

The GUI picker and qmailApiServices currently allow all four requested suffixes:

  .bin, .stack, .zip, .png

The current rest_core implementation does not fully support all four, despite
the extension allow-list:

  .bin
    - Current CCv3 single/multi-coin files are unpacked and deposited.
    - Legacy CCv2 .bin files are detected, converted inline, graded, and included
      in the final deposit task/receipt.

  .stack
    - Legacy CCv1 stacks are detected, converted inline, graded, and included in
      the final deposit task/receipt.

  .zip
    - The extension is accepted and detected, but unpack_zip_file() currently
      logs "ZIP extraction not implemented" and returns an error. The source is
      then moved to the wallet's Corrupted folder.

  .png
    - The extension is accepted and detected, but unpack_png_file() currently
      logs "PNG extraction not implemented" and returns an error. The source is
      then moved to the wallet's Corrupted folder.

Therefore the launch screen should currently advertise/accept only .bin and
.stack, OR zip/png extraction must be implemented in rest_core before the four
formats are promised. The existing dashboard picker/API allow-list should be
corrected at the same time so it does not claim nonfunctional zip/png support.

Fab's note says legacy files are parked for a separate later pipeline. That was
true of an earlier stage, but it is not the complete behavior of the current
cmd_deposit.c. Current deposit execution parks CCv1/CCv2 during unpack and then
runs upgrade_phase_convert() in the same asynchronous deposit task. It retries
without an encryption key only for the specific missing-key case, grades the
converted CCv3 coins, merges converted/expired/legacy-counterfeit counts, writes
one final receipt, and only then completes the task. CCv1 and CCv2 should work
in this proposed flow, subject to integration testing against live RAIDA.


HIGHEST-VALUE IDENTITY PROMOTION
================================

The current backend already exposes useful pieces:

  GET /api/wallets/show-coins?wallet_path=<Default>&folder=Bank
  GET /api/wallets/show-coins?wallet_path=<Default>&folder=Fracked

These responses include denomination/value, serial number, folder, and POWN.

  GET/POST /api/transactions/transfer
    from_wallet=<Default path>
    to_wallet=<Mail path>
    amount=<highest denomination value>
    memo=QMail identity assignment

api_handlers_system_transfer.c already:

  - Scans Default/Bank and Default/Fracked.
  - Sorts denomination descending.
  - Prefers Bank over Fracked when denominations tie.
  - Uses fs_move_file().
  - Sends Bank to Mail/Bank and Fracked to Mail/Fracked.
  - Returns the amount, count moved, source, destination, and transaction ID.

If the requested amount is exactly the value of the largest coin, the greedy
selector chooses one largest coin and stops. This makes the existing endpoint a
viable MVP after the GUI first queries both show-coins folders to learn the
largest eligible value.

However, the two-query-plus-transfer sequence has weaknesses:

  - Selection and movement are not one atomic semantic operation.
  - Equal-value coins in the same folder have no explicit serial-number tie
    order.
  - The generic transfer endpoint accepts an amount and is capable of selecting
    multiple coins/making change; onboarding requires exactly one existing coin.
  - The GUI would need new show-coins and transfer helpers.
  - It does not itself refresh and return the QMail identity.

Recommended production implementation:

  Add a narrow backend endpoint such as:

    POST /api/qmail/local/identity/promote-from-default

  Behavior:

    1. Resolve registered Default and Mail wallet paths in the backend.
    2. Refuse replacement if Mail already contains an identity unless an
       explicit replace operation was requested.
    3. Scan Default/Bank and Default/Fracked using wallet_scan_folder().
    4. Ignore candidates below 1 CC and outside QMail's supported denomination
       range (currently codes 0..4).
    5. Select exactly one maximum-denomination candidate.
    6. Recommended deterministic ties: Bank before Fracked, then lowest serial
       number.
    7. Move it with fs_move_file() into the matching Mail folder.
    8. Call qmail_identity_refresh().
    9. Return serial number, denomination/value, source/destination folder,
       address, and success/error details.
   10. If identity refresh fails after the move, move the coin back to its exact
       Default folder before returning failure.

This endpoint composes existing scan, denomination, move, and identity-refresh
functions; it does not need a new coin-file implementation.

REVISED END-TO-END ALGORITHM
============================

1. User selects Files or Folder on ServiceSelectionScreen.

2. Open WalletActionModal in onboarding mode.

3. Use the existing native picker. Cancellation is a no-op.

4. Show supported formats and warn that supported source files will be moved.
   Folder import is currently top-level/non-recursive; say so.

5. Start the existing deposit without a Mail wallet override:

     depositCloudCoinFiles(paths, "QMail first-run deposit")

   or:

     depositCloudCoinFolder(path, "QMail first-run deposit")

   The omitted walletPath deliberately resolves registered Default.

6. Poll with waitForTaskCompletion(), using a five-minute ceiling. Continue to
   display MOVE, UNPACK, POWN, GRADE, UPGRADE, and COMPLETE messages supplied by
   the task. Legacy conversion is part of this same task.

7. Display the structured Default-wallet deposit receipt. If no authentic or
   fracked coin worth at least 1 CC is available after deposit, remain in the
   modal and explain why an identity could not be assigned. Do not move
   counterfeit, limbo, expired, duplicate-only, or fractional coins into Mail.

8. Invoke the backend identity-promotion operation. Show a separate
   "Assigning QMail identity..." phase.

9. Verify identity by calling getIdentity() with bounded retries. Require
   configured=true, a nonzero serial, and a nonempty address. Normalize with
   normalizeIdentityForUi().

10. Show the promotion summary and enable "Continue". On Continue, clear the
    skip-auto-restore flag and call:

      onSelectService("provisioning", normalizedIdentity)

11. WalletSetupScreen shows the address and offers Heal when the chosen highest
    coin came from Default/Fracked.

12. On restart, App's existing Mail/Bank or Mail/Fracked check should route
    directly to QMail.


RECEIPT DETAILS
===============

The existing deposit task already writes one JSON receipt in Default/Receipts
and embeds the same receipt in task data. It includes:

  - Bank, Fracked, Limbo, Counterfeit, Duplicate, and Error totals
  - Converted, expired, and legacy-counterfeit totals
  - Values by grade and total deposited
  - Per-coin detail when not truncated

That receipt records the Add Funds operation before identity promotion. The UI
should add a clearly separate identity-assignment result rather than rewriting
the signed/completed deposit receipt. A future backend enhancement may write a
second Mail/identity transaction receipt, but it is not necessary to show the
user what happened in the first implementation.

The final screen should make the accounting explicit:

  - Total authenticated into Default
  - Identity coin moved to Mail (value, serial, Bank/Fracked)
  - Remaining spendable value in Default

REMAINING QUESTION
==================

Does "the coins should all go into Default" also apply to the existing locker
code path?

Current first-run locker behavior uses importCredentials(), which downloads
directly into Mail and applies QMail-specific replacement/refresh behavior. If
the new Default-first rule applies to locker imports too, the cleaner final
design is to use the Add Funds modal's general locker download into Default,
then run the same largest-coin promotion used by Files and Folder. That would
make all three sources consistent, but it is a deliberate change to the current
locker workflow and should be confirmed.

FINAL ASSESSMENT
================

The requested workflow fits the existing architecture well after the
Default-first clarification. Reusing Add Funds is now the recommended approach,
not merely an option. The deposit, progress, receipt, legacy conversion, and
cross-volume move machinery already exist. The missing production-quality seam
is a deterministic, rollback-safe operation that promotes exactly one largest
eligible Default coin into the matching Mail grade and refreshes identity.

The legacy concern is largely resolved by current code: CCv1 and CCv2 conversion
already runs inside the deposit task. ZIP and PNG are the actual unsupported
formats today; their unpack functions are stubs and should not be advertised
until implemented.
