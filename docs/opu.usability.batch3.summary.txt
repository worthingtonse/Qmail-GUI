FIX-04: Draft hydrate-before-mount
==================================
Bug:
  /db/drafts/list returns preview metadata only (subject preview,
  body_preview, timestamps, star state — NOT full body, NOT
  recipients). The previous QMailDashboard.handleSelectEmail isDraft
  branch passed the preview row straight into ComposeModal as
  editDraft. The modal saw an empty body and empty To/Cc/Bcc. Worse,
  a Save Draft on that empty state would persist the empty fields,
  clobbering the original full draft.

Fix:
  1. Added loadingDraftId state in QMailDashboard.
  2. In handleSelectEmail's isDraft branch:
     - Set loadingDraftId = email.id
     - Try { res = await getEmailById(email.id) }
     - On success: setEditDraft({ ...email, ...res.data }) then
       open the modal.
     - On failure: setNotification("Could not load draft. Try
       again.") and don't open the modal.
     - Finally: clear loadingDraftId.
     - Re-clicks while a hydrate is in flight are ignored.
  3. Threaded loadingDraftId through EmailListPane to EmailListItem
     as isLoadingDraft.
  4. EmailListItem renders a Loader2 spinner in place of the draft-
     selection checkbox when isLoadingDraft is true, and ignores
     row/checkbox clicks during that window. The row gets opacity
     0.7 and aria-busy for screen readers.

Known API limitation flagged for reviewers:
  /db/messages/get currently returns { id, from, subject, body,
  timestamp, isRead, folder } — it does NOT return to/cc/bcc/
  subsubject for draft rows. So even after this fix, draft recipients
  remain empty unless the backend either:
    (a) extends /db/messages/get to include recipient fields when
        folder==drafts, or
    (b) ships a dedicated /db/drafts/get?email_id=X endpoint, or
    (c) /db/drafts/list itself starts returning the full draft data.

  FIX-04 still helps in a real way today: the body is now populated
  (it was empty before — the draft mapper's `draft.body || ""` was
  effectively always ""). When a backend ticket lands to expose
  recipients, no GUI change is needed; the spread in
  setEditDraft({ ...email, ...res.data }) picks them up automatically.

Decisions worth flagging for review:
  1. Spinner placement (inside the draft checkbox slot) reuses the
     existing column rather than adding a new visual. Less layout
     disruption. Alternative: replace the whole row with a skeleton
     during hydrate. Current choice is lighter weight.
  2. We ignore re-clicks (`if (loadingDraftId) return;`) rather than
     queueing them. A user mashing the same draft repeatedly waits
     for the first fetch.
  3. Failure path keeps the modal CLOSED and shows a toast. v4 plan
     said the user can "try again" — clicking the draft a second
     time re-runs the hydrate.
  4. The `currentDraftId` consistency check from FIX-04 verify step 2
     (save → reopen → edit → save → confirm one draft, not two) is
     covered by ComposeModal's existing line 73 which sets
     currentDraftId from editDraft.id on mount. Verified by reading;
     should be confirmed in manual testing.

Follow-up (gpt batch-3 review)
==============================
Date: 2026-05-22
Reviewer: gpt (review delivered inline by the user)

Two findings: one high (draft save can still clobber recipients),
one medium (stale hydrate can pop modal after user moved on). Both
genuine bugs that gem missed in her batch 3 review. Fixing both
before considering FIX-04 closed.

Patches applied:

1. (gpt #1, High) Draft save no longer clobbers unhydrated recipients.
   Root cause: updateDraft() always serialized to/cc/bcc/subsubject
     as `field || ""`, and the backend treats provided-but-empty
     to/cc as "clear the existing recipient rows" (per
     api_handlers_qmail_drafts.c:313). A body-only edit on a draft
     whose recipients weren't surfaced by /db/messages/get (the
     known CORE-L limitation) would wipe them.
   Three coordinated changes:
   a. ComposeModal: added touchedFields state {to, cc, bcc,
      subsubject}. A field is "touched" if it has a non-empty
      initial value (from editDraft or replyTo) OR if the user
      typed into it. Untouched fields are NOT sent in the
      updateDraft payload.
   b. ComposeModal.handleSaveDraft: builds draftData with
      `subject`, `body` always, plus only the touched
      recipient/subsubject fields.
   c. qmailApiServices.updateDraft: payload no longer applies
      `|| ""` defaults to optional fields. Only `subject` and
      `body` are always sent; to/cc/bcc/subsubject are sent only
      if `typeof draftData.X === "string"`.

   Verified edge cases:
   - Open existing draft (no recipients surfaced) → type body →
     save: payload contains subject + body only. Backend
     preserves recipients. ←—— gpt's main bug, fixed.
   - Open existing draft → type into Cc field → save: payload
     contains subject + body + cc. Other recipient fields stay
     preserved.
   - Reply to a message: To is pre-populated, touched=true. Save
     persists To.
   - New compose (no editDraft): all fields untouched until the
     user types. Save on a new draft creates it with whatever
     was typed; missing fields are simply omitted (no harm — no
     existing data to preserve).
   - User opens draft, clears the To field intentionally: To was
     marked touched on open (it had content), so save sends the
     now-empty to=" " — clearing as intended.

2. (gpt #2, Medium) Stale draft hydrate no longer pops modal.
   Root cause: handleSelectEmail awaited getEmailById then
     unconditionally setEditDraft + opened the modal. If the user
     clicked a different message or changed folder during the
     fetch, the stale result still appeared.
   Three guards added:
   a. New draftHydrateRequestRef counter in QMailDashboard.
      Bumped before each await; the post-await success branch
      checks `draftHydrateRequestRef.current === requestId` and
      drops the result silently if stale.
   b. handleFolderChange bumps the counter and clears
      loadingDraftId so a draft hydrate from the previous folder
      can't bleed through.
   c. handleSelectEmail's non-draft branch (clicking a regular
      message during a draft hydrate) also bumps the counter,
      so the draft modal won't pop after the user has selected
      a different message.

   The finally clause only clears loadingDraftId if the request
   id is still current — prevents the stale finally from
   clobbering a newer hydrate's loading state.
