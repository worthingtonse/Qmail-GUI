Cross-model comparison update
-----------------------------
After comparing this report with gem.usability.findings.txt and
opu.usability.findings.txt, I kept the original API-completeness findings and
expanded them with the missing user-facing workflow gaps called out by the
other reports. The main additions are onboarding/new-identity gaps, missing
message actions, compose/send feedback issues, account/session controls, and
notification behavior.

Bottom line
-----------
The GUI is much closer to the current QMail API than the older GUI/API
findings. The main send endpoint, duration parameter, task polling, Mail-wallet
credential import preference, RAIDA status aliases, Sync Directory removal, and
duration default have all been addressed.

However, a normal user still cannot rely on the GUI as a complete email client.
The largest remaining problems are user-workflow mismatches: first-run identity
state is not verified/displayed correctly and there is no in-GUI new-identity
path, pending message download does not load the stored body after the backend
decrypts it, sent mail is not saved into Sent, drafts cannot be reopened with
full content/recipients, core mail actions such as Forward/Reply All/Empty
Trash are missing, starred mail is split between a flag and a folder, contacts
cannot be reliably created from the visible form, outgoing local-file
attachments have no UI path, and account/status/notification surfaces still
present static or non-actionable state.

Findings
--------

1. High: first-run import does not verify or display the imported QMail identity.

   User workflow affected:
     A first-time user enters a locker code and expects to land in a working
     account showing their QMail address and identity health.

   Missing/broken customary behavior:
     After import, an email client should verify that the account identity is
     actually registered and should display the real address. The GUI trusts the
     import response and proceeds to WalletSetupScreen, but that response does
     not contain the fields WalletSetupScreen renders.

   GUI files/functions involved:
     ServiceSelectionScreen.jsx handleImport calls importCredentials() and then
     onSelectService('qmail', result.data).

     WalletSetupScreen.jsx reads accountData.email_address,
     accountData.pretty_address, and accountData.needs_healing.

     App.jsx only calls getIdentity() on startup, not immediately after a
     successful locker import.

     QMailDashboard.jsx accepts initValues but does not use them; QMail.jsx does
     not pass provisioning data into QMailDashboard.

   Backend/API call that exists or is missing:
     Exists:
       GET /api/qmail/raida/locker/import-credentials
       GET /api/qmail/local/identity/get
       GET /api/qmail/local/identity/exists

     The import endpoint currently returns operation/count/path fields such as
     coins_found, coins_saved, wallet_path, and mail_wallet_path. It does not
     return email_address or pretty_address.

   Suggested fix:
     After importCredentials() succeeds, call /api/qmail/local/identity/get or
     /api/qmail/local/identity/exists before advancing. Pass the verified
     identity into the provisioning/dashboard views. Remove the fake John Doe
     default from QMailDashboard/AccountPane or replace it with live identity
     state.

2. Critical: pending encrypted-message download does not load the readable body.

   User workflow affected:
     A user sees a pending encrypted message, clicks it, and expects to read it.

   Missing/broken customary behavior:
     The backend download call decrypts/stores the message and returns the local
     email_id, but the GUI treats the same response as if it already contained
     the final body and attachments. The selected message can become a
     "downloaded" pending item with an empty body and no attachment list. The
     pending rows are also all rendered as generic "Encrypted Message" items,
     so multiple new messages are hard to distinguish before download.

   GUI files/functions involved:
     QMailDashboard.jsx handleSelectEmail auto-calls handleDownloadMail() for
     pending messages.

     QMailDashboard.jsx handleDownloadMail() calls downloadEmailContent(), then
     reads responseData.body and responseData.attachments.

     QMailDashboard.jsx maps pending notifications to generic list rows; the
     reading pane then also shows a manual Download Message button, creating an
     unclear auto-download/manual-download split.

     qmailApiServices.js downloadEmailContent() correctly calls:
       POST /api/qmail/net/messages/download?file_guid=...

   Backend/API call that exists or is missing:
     Exists:
       POST /api/qmail/net/messages/download?file_guid=...
       GET  /api/qmail/db/messages/get?email_id=...
       GET  /api/qmail/db/attachments/list?email_id=...

     The backend download handler returns fields including email_id, subject,
     sender_sn, stripes_downloaded, and stripes_recovered. The full body is then
     available through /db/messages/get.

   Suggested fix:
     After a successful download, use responseData.email_id to call
     getEmailById(email_id) and getEmailAttachments(email_id), update
     selectedEmail to that stored message, and refresh counts/list. Keep the
     pending item selected only while the download is actually in progress. Use
     any available sender/subject/timestamp metadata in the pending row, and
     make one download control the source of truth.

3. High: Sent is exposed as a normal folder, but successful sends do not create
   a sent-mail row.

   User workflow affected:
     A user sends a message and later opens Sent to confirm what was sent.

   Missing/broken customary behavior:
     A sent message should appear in Sent. The GUI refreshes wallet/drafts/counts
     after send, but there is no GUI step or evident backend send path that saves
     the sent body into qmail_emails with folder=Sent.

   GUI files/functions involved:
     ComposeModal.jsx handleSend calls sendEmail().

     QMailDashboard.jsx handleSendEmail closes compose and refreshes counts.

     NavigationPane.jsx exposes Sent as a folder from /db/folders/list.

   Backend/API call that exists or is missing:
     Exists:
       POST /api/qmail/net/messages/upload_and_tell
       GET  /api/qmail/db/messages/list?folder=1

     In the reviewed rest_core source, receive saves inbox messages through the
     local DB, but the upload_and_tell/send path appears to write receipts, not a
     Sent-folder message row.

   Suggested fix:
     Decide whether Sent should be backed by qmail_emails or receipt files. If
     qmail_emails is the intended mailbox model, save a sent copy after
     upload_and_tell starts or completes. If receipts are the intended source,
     add a GUI/API adapter that renders Sent from receipts.

4. High: outgoing attachments are API-plumbed but unavailable to users.

   User workflow affected:
     A user composes mail and wants to attach a local file.

   Missing/broken customary behavior:
     Compose has no file picker, no attachment list, no remove action, and no
     upload/stage flow. ComposeModal always sends attachments: [].

   GUI files/functions involved:
     ComposeModal.jsx imports Paperclip but does not render an attachment
     picker. handleSend builds emailData.attachments: [].

     qmailApiServices.js sendEmail() appends repeatable attachment_file_path
     values if attachments are present.

   Backend/API call that exists or is missing:
     Exists:
       POST /api/qmail/net/messages/upload_and_tell
       repeatable attachment_file_path=<server-side path>

     Missing/unclear for GUI:
       A browser-safe way to stage local files into server-side paths accepted by
       upload_and_tell.

   Suggested fix:
     Add a supported staging/upload endpoint or desktop file-path bridge, then
     add Compose controls for choosing, listing, and removing attachments. Do not
     expose a Paperclip affordance until it can actually attach files.

5. High: saved drafts cannot be reopened with their full content and recipients.

   User workflow affected:
     A user saves a draft, opens Drafts later, edits it, and sends or saves it.

   Missing/broken customary behavior:
     Draft list rows only carry preview metadata. The GUI opens ComposeModal
     directly from the list row, so body, to, cc, and bcc are often empty. Saving
     from that compose session can overwrite the draft with incomplete data.

   GUI files/functions involved:
     QMailDashboard.jsx loadEmails('drafts') maps getDrafts() rows to draft
     list items and uses draft.body/draft.to/draft.cc when present.

     QMailDashboard.jsx handleSelectEmail opens ComposeModal for isDraft without
     fetching /db/messages/get.

     ComposeModal.jsx initializes fields from editDraft.body/to/cc/bcc.

   Backend/API call that exists or is missing:
     Exists:
       GET  /api/qmail/db/drafts/list
       GET  /api/qmail/db/messages/get?email_id=...
       POST /api/qmail/db/drafts/update?email_id=...

     /db/drafts/list is intentionally preview-oriented. It returns email_id/id,
     subject, body_preview, timestamps, recipient_count, and star state, not the
     full body or recipient addresses.

   Suggested fix:
     When a draft is selected, call /db/messages/get for the draft email_id and
     load full subject/body/recipient fields before opening ComposeModal. After
     sending an edited draft, either delete/move the draft or mark it as sent so
     it does not remain as a stale draft.

6. Medium: Starred is modeled as both a flag and a folder, so star actions do
   not reliably populate the Starred view.

   User workflow affected:
     A user clicks the star icon and expects the message to appear in Starred.

   Missing/broken customary behavior:
     Starred mail should be one coherent virtual view. The GUI toggles
     is_starred via set-star, but folder navigation maps "starred" to folder ID
     4 and lists /db/messages/list?folder=4. Those are different concepts in
     the current code path.

   GUI files/functions involved:
     qmailApiServices.js folderNameToId maps starred -> 4.

     qmailApiServices.js starEmail() calls /db/messages/set-star.

     QMailDashboard.jsx handleToggleStar updates email.starred but does not move
     the message to folder 4.

     ReadingPane.jsx also offers "Move to Starred" as a folder move.

   Backend/API call that exists or is missing:
     Exists:
       POST/GET /api/qmail/db/messages/set-star?email_id=...&starred=...
       GET      /api/qmail/db/messages/list?folder=4
       POST     /api/qmail/db/messages/move?email_id=...&folder=4

   Suggested fix:
     Pick one model. Prefer making Starred a virtual view backed by is_starred
     and adding an API/list mode for starred=true, or make set-star also maintain
     folder/count semantics. Avoid exposing "Move to Starred" if starring is a
     flag.

7. Medium: contacts can be listed, but add/search/autocomplete are not enough
   for normal recipient discovery.

   User workflow affected:
     A user wants to find a recipient, save them, and use them in compose.

   Missing/broken customary behavior:
     Add Contact asks for name and "Email Address", but the backend create API
     requires a real serial_number. The GUI sends serial_number "0" when the form
     does not provide one, which the backend rejects as invalid. Search text says
     it searches DRD aliases, but loadContacts() fetches /contacts/list and
     filters client-side. Compose suggestions only use local contacts and only
     fill the To field.

   GUI files/functions involved:
     AddContactModal.jsx collects only name and email.

     ContactsPane.jsx handleAddContact sends newContact.serial_number || "0".

     ContactsPane.jsx searchTerm calls getContacts(searchTerm), which filters
     local contacts client-side.

     ComposeModal.jsx loadContacts()/handleContactSelect only use getContacts()
     and replace the whole To field.

   Backend/API call that exists or is missing:
     Exists:
       GET  /api/qmail/db/contacts/list
       POST /api/qmail/db/contacts/create?serial_number=...
       DELETE /api/qmail/db/contacts/delete?serial_number=...
       GET  /api/qmail/db/contacts/list-popular
       GET  /api/qmail/local/address/from-sn?sn=...

     There is no current GUI flow that converts a pasted QMail address to the
     required serial_number before creating a contact.

   Suggested fix:
     Add an address/SN parser or lookup flow before contacts/create. For search,
     either relabel it as local-contact search or wire a real DRD/user search.
     In compose, support suggestions for To/CC/BCC and preserve already-entered
     comma-separated recipients when selecting a suggestion.

8. Medium: email search exists, but the UI scope/pagination are misleading.

   User workflow affected:
     A user searches a mailbox with more than 50 matches or searches inside one
     visible folder.

   Missing/broken customary behavior:
     The placeholder says "Search inbox" or the current folder name, but
     searchEmails() queries /db/messages/search across the mailbox. Search
     results overwrite the current list without updating totalEmailCount, and no
     search offset/pagination is provided.

   GUI files/functions involved:
     EmailListPane.jsx renders folder-scoped placeholder text.

     QMailDashboard.jsx handleSearch() calls searchEmails(query, 50, 0), but
     qmailApiServices.searchEmails() accepts only query and limit. It does not
     update totalEmailCount from result.count.

   Backend/API call that exists or is missing:
     Exists:
       GET /api/qmail/db/messages/search?query=...&limit=...

     Missing for full UI:
       Offset/pagination support is not documented for search.

   Suggested fix:
     Make the UI label honest ("Search all mail") or add folder filtering if the
     API supports it. Reset pagination during search and display result count.
     If large mailboxes matter, add backend offset support or a "show more"
     strategy.

9. Medium: account/status view misrepresents service, identity, and removed
   parity behavior.

   User workflow affected:
     A user opens Wallet/Account to understand whether QMail is healthy enough
     to send and receive.

   Missing/broken customary behavior:
     Status should distinguish service process health, RAIDA availability,
     wallet funding, QMail identity health, and removed/unsupported features.
     AccountPane hardcodes service health to healthy/version 1.0.0, renders fake
     profile data from QMailDashboard, shows a Parity Server Configuration
     section even though getParityServer() always returns failure, and keeps
     account/security/settings controls that only mutate local state or
     console.log. There is also no Sign Out or Switch Identity action, and the
     repair warning is based on fracked wallet coins rather than a direct QMail
     identity-health signal.

   GUI files/functions involved:
     QMailDashboard.jsx initializes userAccount to John Doe.

     AccountPane.jsx initializes serverHealth to static healthy data.

     AccountPane.jsx renders Parity Server Configuration while
     qmailApiServices.js getParityServer() returns "Parity server endpoint
     removed".

     AccountPane.jsx handleSecurityAction only console.logs; accountSettings are
     local-only toggles.

     AccountPane.jsx shows Server Details with raidaServers.slice(0, 10), while
     the service has 25 RAIDA statuses elsewhere.

   Backend/API call that exists or is missing:
     Exists:
       GET /api/qmail/local/identity/get
       GET /api/qmail/local/identity/exists
       GET /api/qmail/local/status
       GET /api/raida/echo
       GET /api/wallets/balance
       POST /api/qmail/raida/identity/heal

     Removed:
       Parity server endpoint.

   Suggested fix:
     Replace the static account view with live identity and health calls. Remove
     or hide the parity section and no-op account/security actions. If
     healWallet() is meant to heal the Mail identity coin, ensure the GUI or
     backend targets the registered Mail wallet, not the Default wallet. Add an
     explicit Sign Out/Switch Identity flow or hide account switching language
     until it exists.

12. Low/Medium: send preflight is useful but still optimistic at modal open and

       GET /api/qmail/local/status

       GET /api/wallets/balance
       POST /api/qmail/net/messages/upload_and_tell

   Suggested fix:
     Initialize canSend=false until network status is known. Consider surfacing

     upload_and_tell as the final authority. Add a retry/recheck path and make

Positive coverage observed
--------------------------
These areas are wired well enough at the static-review level:

  - Compose can send To/CC/BCC, subject, body, and duration through
    /api/qmail/net/messages/upload_and_tell.
  - sendEmail() uses the current duration parameter and supports repeatable
    attachment_file_path values if the caller ever provides server-side paths.
  - Compose polls /api/system/tasks?task_id=... and surfaces backend task
    message/progress/error state.
  - Inbox/Sent/Drafts/Trash/Starred/Archive navigation is present.
  - Folder list/count, list pagination, unread/read toggle, move, trash,
    permanent delete, and archive move APIs are present.
  - Selecting an already-downloaded message fetches full body and attachments
    with /db/messages/get and /db/attachments/list.
  - Single-recipient Reply flow resolves numeric sender serials through
