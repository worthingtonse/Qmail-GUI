GOAL
----
Let a QMail user publish public profile information (first name, last name,
inbox fee, self description, and up to three "qcon" icon indexes) to a public
directory hosted at raida11.cloudcoin.global, and let the QMail-GUI
automatically pull other users' published info into the local contacts
database when a contact is not already known locally.

Record key: 5 bytes = 1-byte denomination code + 4-byte serial number.
(NOTE: the current GUI address code, src/qmail/address/qmailAddress.js, treats
serial numbers as 3 bytes; see OPEN QUESTIONS #1.)

qcon pool: the 256 SVGs in public/qmail-avatars/NewAvatars/ (000.svg-255.svg).
A qcon index is one byte (0-255); a user may publish up to three.


================================================================================
PART A - SERVER SIDE (raida11.cloudcoin.global, PHP + MySQL)
================================================================================

Two PHP pages (no .php extension in the URL):

A1. /update_users   (write endpoint)
-------------------------------------
Method: POST (form-encoded).
Proposed parameters:
    denomination   int 0-4        (0=bit 1=byte 2=kilo 3=mega 4=giga)
    serial_number  uint32
    first_name     varchar(64)
    last_name      varchar(64)
    description    varchar(512)
    inbox_fee      int (units TBD - see OPEN QUESTIONS #4)
    qcon1          int 0-255  (optional)
    qcon2          int 0-255  (optional)
    qcon3          int 0-255  (optional)

Behavior: atomic UPSERT (INSERT ... ON DUPLICATE KEY UPDATE) keyed on
(denomination, serial_number), prepared statements only.
Response: JSON {"status":"success"} or {"status":"error","message":"..."}
so the GUI can reliably detect success before updating local state.
Ideally the success response echoes the canonical stored record so the GUI
persists exactly what the server saved.
Server hygiene: request-size limits, basic per-IP rate limiting, HTTPS only,
and (if the renderer calls it directly - see B4) an
Access-Control-Allow-Origin header for the dev origin.

Proposed MySQL table:

    CREATE TABLE public_users (
        denomination   TINYINT UNSIGNED NOT NULL,
        serial_number  INT UNSIGNED     NOT NULL,
        first_name     VARCHAR(64)      DEFAULT '',
        last_name      VARCHAR(64)      DEFAULT '',
        description    VARCHAR(512)     DEFAULT '',
        inbox_fee      INT UNSIGNED     DEFAULT 0,
        qcon1          SMALLINT         DEFAULT NULL,
        qcon2          SMALLINT         DEFAULT NULL,
        qcon3          SMALLINT         DEFAULT NULL,
        updated_at     TIMESTAMP DEFAULT CURRENT_TIMESTAMP
                                 ON UPDATE CURRENT_TIMESTAMP,
        PRIMARY KEY (denomination, serial_number),
        INDEX idx_first (first_name),
        INDEX idx_last  (last_name)
    );

SECURITY WARNING: as specified, anyone can POST an update for any
(denomination, serial_number) and overwrite someone else's public record.
See OPEN QUESTIONS #2 - we should decide on some proof of ownership
(e.g., an authenticity-number-derived token, or a challenge validated
against the RAIDA) before this goes live.

A2. /user_hints   (read endpoint)
-------------------------------------
Method: GET. All parameters optional (prefix matching):
    first_name_starts_with=P
    last_name_starts_with=na
    qmail_address_starts_with=3
Also (needed for the GUI's exact-lookup use case, cheap to add):
    denomination=<0-4>&serial_number=<uint32>   -> exact match

"qmail_address_starts_with" matches against the canonical dotted-decimal
address string (e.g. "37.34@bit"), so the server should store or compute
that string for LIKE 'x%' matching.

Response: JSON array of records:
    [{"denomination":0,"serial_number":9506,"address":"37.34@bit",
      "first_name":"Pat","last_name":"Nash","description":"...",
      "inbox_fee":5,"qcons":[12,200,3],"updated_at":"..."}]

Server should cap results (e.g. LIMIT 50) since prefix queries can be broad,
escape SQL LIKE metacharacters (%, _) in the user-supplied prefixes, use
prepared statements, and reject/curate an empty-criteria query rather than
dumping the whole directory.

IMPORTANT for the auto-download flow: only an EXACT (denomination,
serial_number) match may ever be auto-saved as a contact. Name-prefix
results are for human-driven search UI only - never for automatically
associating a profile with a mail sender.

(NOTE: the request said user_hints is "found at .../update_users" - assumed
to be a typo for https://raida11.cloudcoin.global/user_hints. OPEN Q #3.)

PART B - GUI: PUBLISH FLOW (Edit menu -> form -> upload -> local update)

B1. Edit menu item
------------------
File: electron.cjs, buildApplicationMenu() (lines ~984-1134).
Add to the Edit submenu (lines ~1006-1036):
    { label: 'Publish Public Profile...', click: () =>

(~line 2763): new case 'publish-profile' sets state to open the new modal.

B2. PublishProfileModal.jsx (new file, src/qmail/screens/)
----------------------------------------------------------
Modeled directly on AddContactModal.jsx (same compose-modal__* CSS pattern,
isOpen/onClose props, role="dialog", Loader2 spinner, error state).

Fields:
    - First name        (text, prefilled from identity firstName)
    - Last name         (text, prefilled from identity lastName)
    - Inbox fee         (number, prefilled from a new stored value, default 0)
    - Self description  (textarea, prefilled from identity description)
    - Qcons             (up to 3 slots; each opens the qcon picker below)
    - Read-only display of the user's own address (from
      normalizeIdentityForUi: prettyAddress / serialNumber / denomination)

Identity source: getIdentity() / normalizeIdentityForUi()
(src/api/qmailApiServices.js:2749 / 2801); the dashboard already holds this
in userAccount state (QMailDashboard.jsx ~603), pass it into the modal.

B3. Qcon picker (new component, e.g. QconPicker.jsx)
----------------------------------------------------
A grid of all 256 icons from public/qmail-avatars/NewAvatars/.
Asset URLs via the existing helper getQmailAvatarAssetHref('symbol', n)
(src/qmail/avatar/qmailAvatar.js:69) - do NOT hardcode paths.
Behavior: click a slot -> grid opens (scrollable, 16x16 or lazy-rendered
rows to keep 256 inline SVG loads cheap) -> click an icon -> slot filled.
Allow clearing a slot. Enforce max 3 selections.

B4. Upload call (new function in src/api/qmailApiServices.js)
-------------------------------------------------------------
Follow the checkVersion() pattern (qmailApiServices.js:2326-2341): a plain
renderer fetch() directly to the external host (deliberately NOT proxied
through core.exe; CORS is a non-issue in the packaged Electron build but
should be verified in dev mode - the Vite dev server origin will trigger
CORS preflight, so the PHP page should send Access-Control-Allow-Origin:*).

    const PUBLIC_DIRECTORY_BASE =
        import.meta.env.VITE_PUBLIC_DIRECTORY_URL ||
        'https://raida11.cloudcoin.global';   // configurable, not scattered

All calls get an explicit timeout (AbortController, ~10s) and must be
best-effort: a directory failure never blocks mail display or the UI.
Numeric fields (denomination, qcon index) can legitimately be 0 - use
explicit null/undefined checks, never truthiness (the existing addContact
code at qmailApiServices.js:1652-1666 already shows the falsy-0 pitfall
with denomination).

    publishPublicProfile({denomination, serialNumber, firstName, lastName,
                          description, inboxFee, qcons})
        -> POST `${PUBLIC_DIRECTORY_BASE}/update_users`
           body: URLSearchParams (form-encoded)
        -> resolve/reject on the JSON status

    fetchUserHints({firstNameStartsWith, lastNameStartsWith,
                    qmailAddressStartsWith, denomination, serialNumber})
        -> GET `${PUBLIC_DIRECTORY_BASE}/user_hints?...` (only params given)
        -> returns parsed array

B5. After a successful upload - update local state
---------------------------------------------------
1) Persist the new fields locally so the form re-opens prefilled and the
   dashboard can render the chosen qcons:
      - firstName/lastName/description already live in backend identity;
        if there is an identity-update endpoint on core.exe use it,
        otherwise (and for inboxFee + qcons, which have no backend field
        today) persist a small JSON blob via a new IPC-backed settings file
        or localStorage:  qmail.publicProfile = {inboxFee, qcons, publishedAt}.
        (See OPEN QUESTIONS #5 for the storage decision.)
2) Optionally upsert the user into their own contacts DB via addContact()
   (qmailApiServices.js:1650) - per the request "calling the contacts api
   for themselves (I think)". CAVEATS:
     - contacts/create has NO inbox_fee or qcon fields (fields enumerated
       at lines 1652-1666), so this only covers name/description unless
       the backend schema is extended (OPEN Q #5);
     - contacts/create is create-only, NOT an upsert. Re-publishing when a
       self-contact row already exists needs either a backend update/upsert
       endpoint or a check-then-skip. Do NOT delete/recreate the row -
       that would destroy is_favorite, trust_level and user_notes.
3) Refresh the dashboard so the user's own avatar/qcons update (B6).
4) Partial-failure UX: the remote server and local DB cannot be updated in
   one transaction. If the remote publish succeeds but the local update
   fails, report "Published, but local refresh failed" with a retry for
   the local half only - do not report the publish as failed and do not
   blindly re-POST.

B6. Rendering chosen qcons on the dashboard
-------------------------------------------
Today avatars are 100% deterministic from the serial number:
    getQmailAvatarSymbolIndices(serialNumber)  (qmailAvatar.js:38)
rendered by QmailCartoucheAvatar.jsx (used in NavigationPane.jsx:438,
ContactsPane.jsx:880, ComposeModal.jsx:1829, and the email list).

Change: getQmailAvatarModel({serialNumber, denominationCode, qcons}) accepts
an optional qcons array (1-3 indexes). If present, it overrides the
serial-derived symbol indices; the denomination frame logic is unchanged.
QmailCartoucheAvatar gets an optional `qcons` prop; call sites pass the
published qcons when known (self: from the stored public profile; contacts:
from wherever contact qcons are stored - OPEN Q #5). Fallback when absent:
current deterministic behavior, so nothing breaks for unpublished users.


================================================================================
PART C - GUI: AUTO-DOWNLOAD FLOW (directory -> local contacts)
================================================================================

Rule: only consult the public directory when the address is NOT already in
the local contacts DB. Never overwrite existing local contact data.

C1. Lookup trigger points
-------------------------
Primary: when mail is loaded/displayed and the sender's address does not
resolve to a local contact. Concretely, in QMailDashboard after getMailList /
getEmailById mapping, collect sender addresses, diff against getContacts()
(qmailApiServices.js:1551), and enqueue unknown ones.
Secondary (nice-to-have, can be phase 2): a manual "Search directory" box in
ContactsPane / AddContactModal using the prefix parameters
(first_name_starts_with, last_name_starts_with, qmail_address_starts_with).

C2. Lookup + add
----------------
For each unknown (denomination, serial_number):
    1. fetchUserHints({denomination, serialNumber}) - exact match preferred;
       if the server only supports prefix matching, use
       qmail_address_starts_with=<full canonical address> and then filter
       client-side for the exact address.
    2. If a record comes back, call addContact() (qmailApiServices.js:1650)
       with serial_number, denomination, first_name, last_name, description
       (class_name/trust_level defaults as ContactsPane.buildContactPayload
       does today, line ~353).
    3. Store inbox_fee + qcons for that contact (pending OPEN Q #5 storage
       decision), then refresh the contacts list so avatars update.

C3. Politeness / caching
------------------------
- Debounce and de-duplicate lookups (one in-flight request per address; keep
  an in-memory "not found" set with a TTL, e.g. 24h persisted alongside the
  publicProfile blob) so the GUI does not hammer raida11 on every inbox
  refresh for users who never published.
- All directory calls are best-effort: network failure must never block or
  delay mail display (fire-and-forget with try/catch, log only).
- On a directory miss, do NOT create an empty local contact row. Under the
  local-first rule an empty row would permanently suppress future lookups
  for that address. Misses live only in the TTL'd negative cache.
- "No information in the local database" means: no contact row exists for
  the exact (denomination, serial_number) key. An existing row - even one
  with empty name fields - blocks automatic lookup. (A manual "refresh from
  directory" action could bypass this later; not in the first release.)

OPEN QUESTIONS (blocking or design-shaping)
================================================================================
 1. SERIAL WIDTH: The spec says a 4-byte serial number (5-byte key total),
    but qmailAddress.js currently parses/formats 3-byte serials (matching
    rest_core qmail_contacts.c). Is the wire format really 4 bytes (uint32,
    values today just fit in 3 bytes), or does qmailAddress.js need a
    4-byte upgrade as part of this work? Plan assumes uint32 on the server
    and no GUI address-format change.
 2. AUTHENTICATION: update_users as specified lets anyone overwrite anyone's
    directory entry. Do we ship that (trusted-alpha) or add proof of
    ownership (e.g., AN-derived token verified server-side / via RAIDA)?
 3. URL CONFIRMATION: user_hints was described as being at the update_users
    URL - assuming https://raida11.cloudcoin.global/user_hints. Correct?
 4. INBOX FEE UNITS: what unit/denomination is inbox_fee expressed in, and
    should the send/compose flow eventually enforce or display it?
 5. LOCAL STORAGE OF NEW FIELDS: contacts/create (core.exe SQLite) has no
    inbox_fee or qcon columns. Options:
       a) extend the backend C schema + API (right place, but touches
          rest_core, a separate codebase);
       b) pack them into the existing user_notes/description field (hacky);
       c) keep a GUI-side sidecar JSON keyed by address (fast to ship,
          data invisible to backend).
    Plan assumes (c) to start, migrating to (a) later. Preference?
 6. QCON SEMANTICS: do user-chosen qcons REPLACE the serial-derived cartouche
    symbols everywhere the avatar appears, or only add a separate "profile
    badge" display? Plan assumes full replacement with fallback.
 7. "FOUR BYTE INDEX NUMBERS": the request says "four byte index numbers of
    up to three qcons", but 256 assets only need one byte (0-255) per index.
    Is each index stored as a 4-byte integer on the wire/DB (future-proofing
    for a larger icon set), or was "four" a slip? Plan assumes indexes are
    logically 0-255 regardless of storage width.
 8. CONTACT UPSERT: contacts/create is create-only. Re-publishing (self) or
    refreshing a contact needs an update/upsert path in rest_core, or the
    GUI must skip the local write when the row exists. Which is preferred
    for v1?
