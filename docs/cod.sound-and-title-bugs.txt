QMail title-bar and alert-sound bug findings
Model prefix: cod (Codex)
Date: 2026-06-29

Scope
-----
This was a read-only investigation of the application code and the running packaged
application. No application code or configuration was changed. The only repository
change is this findings file.

Executive summary
-----------------
1. The Pear default and user-selected title-bar colors are calculated and persisted
   correctly, but the helper that applies them to the native Windows title bar fails
   before it calls the Windows DWM API.
2. The five alert MP3 files are included in both the build output and the ASAR used by
   the running packaged application.
3. Alert previews are silent because a missing saved volume is parsed as numeric zero.
   The current profile has no qmail.sound.volume record, so its effective application
   volume is 0%, despite the source claiming a 30% default.

Bug 1: Pear title bar is dark gray at startup
---------------------------------------------
Expected default: #C9CC3F (Pear).

Relevant code:
- electron.cjs:42 defines DEFAULT_TITLE_BAR_COLOR as #C9CC3F.
- electron.cjs:411-414 loads the saved color or falls back to Pear.
- electron.cjs:440-487 tries to apply the color to the native title bar.
- electron.cjs:1094 and 1164 apply it during window creation/ready-to-show.

Confirmed root cause:
- applyNativeTitleBarColor dynamically compiles a C# P/Invoke wrapper by running
  Windows PowerShell Add-Type.
- runPowerShell inherits the application's complete environment.
- On this machine, LIB contains an invalid entry: ;D:\hla\hlalib.
- Windows PowerShell's Add-Type fails on that invalid compiler search path before
  DwmSetWindowAttribute is called. The observed error is an invalid LIB search-path
  warning promoted to an Add-Type compiler error.
- BrowserWindow.setBackgroundColor does not color the native caption, so Windows keeps
  drawing the normal dark caption after the DWM helper fails.

Verification:
- Running the application's exact PowerShell/DWM script with the inherited LIB value
  failed in Add-Type.
- Running it again with LIB and INCLUDE cleared returned HRESULT 0 for caption, text,
  and border and immediately applied the requested color.
- This Windows 11 build therefore supports the DWM attributes; OS support is not the
  cause on the tested machine.

What would fix it:
- Minimum reliable fix: clear LIB and INCLUDE only in the environment of the
  title-bar PowerShell child before Add-Type runs. Basic framework P/Invoke compilation
  does not need those developer compiler paths.
- Treat a nonzero spawnSync status as failure. The current code checks result.error,
  which only reports failure to launch PowerShell; it does not treat PowerShell exit
  code 1 as an application failure.
- Return an apply result to setTitleBarColor and do not report success to the renderer
  when compilation or any DwmSetWindowAttribute call fails.
- Check all three DWM HRESULT values and log/display a concise actionable error.
- More robust long-term options are a bundled native helper that does not compile C#
  at runtime, or an Electron-rendered title-bar overlay. The latter changes the native
  title-bar design and is unnecessary for fixing this Windows 11 failure.
- If Windows 10 must be supported, add a supported fallback because caption-color DWM
  attributes 34-36 are Windows 11-era behavior.

Bug 2: selected title-bar color blinks but does not remain
----------------------------------------------------------
This has the same visual-application root cause as Bug 1, not a color-picker or
persistence failure.

Confirmed behavior:
- The configuration file next to the portable program already contained:
  { "titleBarColor": "#8000FF" }
- The running window was still dark gray before the diagnostic DWM call.
- Applying that already-saved value through DWM with the clean child environment made
  the native caption purple immediately.
- The brief blink can come from the backing-window/non-client redraw, but the actual
  DWM caption setter never runs when Add-Type fails.

Persistence assessment:
- saveWindowSettings writes qmail-window-settings.json next to the portable executable,
  which is the intended persistent location.
- Startup loads that file after backendDataDir has been assigned, so it reads the same
  location.
- Persistence is therefore functioning on the tested instance. Applying the persisted
  color on every launch is what fails.
- Until the helper is fixed, a restart will generally return to the system dark caption
  even though the selected color remains in the JSON file.

Additional error-handling fix:
- saveWindowSettings returns false on failure, but setTitleBarColor ignores that return
  value and still reports success. Propagate this error so a read-only location or disk
  error cannot masquerade as successful persistence.

Bug 3: Preview Alert Sound is silent
------------------------------------
Are the files included? Yes.

The running application's resources/app.asar contains:
- dist/sounds/default.mp3
- dist/sounds/DingDing.mp3
- dist/sounds/Floraphonic.mp3
- dist/sounds/Notice.mp3
- dist/sounds/Ploops.mp3

The same five nonempty files are present under public/sounds and dist/sounds. The
electron-builder configuration includes dist/**/* in the ASAR. The current relative
URL form, ./sounds/<file>, correctly targets dist/sounds when dist/index.html is loaded.

Confirmed root cause of silence:
- src/api/soundService.js:19-30 reads the volume with:
    Number(window.localStorage.getItem("qmail.sound.volume"))
- localStorage.getItem returns null when the key has never been saved.
- Number(null) is 0, and Number.isFinite(0) is true, so the function accepts 0 instead
  of returning its 0.3 fallback.
- The active q-mail Local Storage records contain sound enabled/file selections but no
  qmail.sound.volume key. The effective volume for this profile is therefore 0%.
- playSource assigns that zero to audio.volume. Preview's force flag bypasses the
  enabled/disabled check, but it does not bypass or repair a zero volume.

What would fix it:
- In readStoredVolume, test the raw storage value before numeric conversion. If it is
  null or blank, return the fallback. Only convert and clamp an actually stored value.
  Conceptually:
    raw = localStorage.getItem(key)
    if raw is null or blank: return fallback
    parsed = Number(raw)
    if parsed is finite: return clamp(parsed, 0, 1)
    return fallback
- Preserve an explicitly stored numeric zero so users can intentionally mute sounds.
- After this correction, profiles with no volume key will start at the intended 30%.
  Whether 30% should be raised is a product choice, but the current defect is not
  merely low volume: it is complete application-level muting.
- For diagnosis and supportability, attach an audio error/load listener to one-shot
  preview Audio objects and surface file/decode failures instead of only relying on
  the play() promise.

Suggested verification after fixes
----------------------------------
1. Remove or temporarily rename qmail-window-settings.json, launch QMail, and verify
   the native caption is Pear (#C9CC3F).
2. Select several title colors, confirm each applies immediately, restart after each,
   and confirm the saved color returns.
3. Reset the title color, restart, and confirm Pear returns.
4. Repeat the title tests with the current invalid LIB value still present. The app
   must no longer depend on the caller's compiler environment.
5. Use a fresh Electron profile with no qmail.sound.volume key. Confirm the Account
   pane shows 30% and Preview Alert Sound is audible for all five packaged MP3s.
6. Set volume to 0 intentionally and restart; confirm it remains muted. Then set a
   nonzero value and confirm that value persists.
7. Select No Sound and verify normal new-mail alerts are disabled while the explicit
   preview behavior matches the intended product policy.

Bug 4: Simplify and stabilize the title-bar text
-------------------------------------------------
Current example:
  QMail Inbox QMail Address: 127.103@Kilo Version: June 26, 2026

Required format:
  QMail Version June 26, 2026                    127.103@Kilo

There must be exactly 20 ordinary space characters between the date and the address.
The folder/view name, unread-count prefix, "QMail Address:" label, and colon after
"Version" are not required.

Cause of the current behavior:
- src/qmail/screens/QMailDashboard.jsx:100-112 builds the native window title.
- It intentionally adds the unread count when nonzero, the current folder (Inbox,
  Sent, Drafts, and so on), the "QMail Address:" label, and "Version:".
- src/qmail/screens/QMailDashboard.jsx:1245-1253 recalculates document.title whenever
  currentFolder, mailCounts, or qmailAddress changes. That is why clicking different
  program sections changes the native title.
- This is a presentation-rule mismatch, not a backend or Electron failure.

What would fix it:
- Reduce buildWindowTitle to the build date and formatted QMail address only.
- Construct the prefix as "QMail Version " plus the formatted build date. Do not put
  a colon after Version.
- When an address is available, append " ".repeat(20) and then the address directly.
- Keep formatTitleQmailAddress so denomination capitalization remains consistent, for
  example 127.103@kilo becomes 127.103@Kilo.
- If the address is temporarily unavailable during startup, show only
  "QMail Version June 26, 2026" and update once when the identity supplies the address.
- Remove folder and unread arguments from buildWindowTitle, and make the title effect
  depend only on qmailAddress. Folder/count navigation will then stop changing it.

Conceptual result:
  prefix = "QMail Version " + formattedBuildDate
  title = formattedAddress
    ? prefix + " ".repeat(20) + formattedAddress
    : prefix

Native-title-bar limitation:
- Twenty spaces gives the requested literal text gap, but the Windows caption uses a
  proportional font and truncates long titles in narrow windows. It does not provide
  independently aligned left/right fields. If the real requirement later becomes a
  right-aligned address rather than exactly 20 spaces, that would require a custom
  rendered title bar instead of a standard native title string.

Suggested verification:
1. With address 127.103@Kilo, confirm the title is exactly
   "QMail Version June 26, 2026" + 20 spaces + "127.103@Kilo".
2. Navigate through Inbox, Sent, Drafts, Trash, Archive, Contacts, and Account; confirm
   the title never changes because of the selected section or unread counts.
3. Confirm denomination capitalization remains @Kilo, @Mega, @Giga, and so on.
4. Confirm startup without an immediately available address does not leave a trailing
   20-space gap and that the address appears once identity data is loaded.
