Direct answers to Opu's 3 questions
-----------------------------------

1. Is the section 3.2 recipe-then-algorithms framing clearer?
   Yes, mostly. It is clearer than splitting the three algorithms out
   with no shared frame. The only part I would change is this:

   - The conceptual recipe currently says numeric values within the 5%
     tolerance bucket to the same canonical form.
   - That muddies "exact canonical signature" and "fuzzy clustering".

   Recommendation:
   - keep the canonical signature exact after normalization-to-token
   - apply 5% tolerance ONLY inside Algorithm 2

   Why:
   - exact duplicates should stay exact
   - fuzzy matches should remain explainable as a second-pass heuristic
   - otherwise the signature table itself starts hiding important deltas

   Relevant section:
   - section 3.2, especially the Step 2/Step 3 wording and Algorithm 2

2. Does the entropy target table conflict with my Phase 5 literal-map?
   No conflict.

   I think the entropy table is helpful and consistent with the
   literal-map idea. It frames the target shape correctly:
   - spacing/typography/radius collapse to a small token scale
   - color collapses to semantic roles, not a flat bucket count

   My only suggestion is wording:
   - make explicit that these are consolidation targets for the raw
     value surface in E1-E7, not guaranteed final token counts for the
     whole app

3. Is P4.5-as-multiple-units the right granularity?
   Yes.

   I prefer:
   - P4.5 after each family
   - plus one final whole-repo audit at the end

   Per-family is the right granularity because it catches newly-visible
   primitive candidates and dead selectors while the family context is
   still fresh. The final all-up audit is still useful as the closing
   snapshot.

   Phase 0.5 exists specifically to scoop the exact repeated

3. "block = first dash-segment of class" is too weak as a heuristic
   In section 3.1 the inventory example says block is guessed from the
   first dash-segment of the class.

   That works for:
   - .dashboard-header -> dashboard

   But fails for multi-word blocks like:
   - .service-selection-screen
   - .wallet-setup-screen
   - .add-contact-modal

   Recommendation:
   - if selector already contains __ or --, take the prefix before that
   - otherwise prefer the component/file-derived block name
   - only fall back to first dash-segment as a last resort

   If we keep the current heuristic, the inventory will mis-group some
   of the most important component namespaces.

4. The 5% rule should NOT alter the canonical signature itself
   This is the main conceptual bug.

   Current risk:
   - if 12px and 12.5px get normalized into the same canonical bucket in
     the signature step, the exact-duplicate pass is no longer exact

   Recommendation:
   - canonical signature = exact normalized declarations
   - fuzzy tolerance = Algorithm 2 only

   This preserves the distinction between:
   - true identical bundles
   - near-identical bundles

5. P5.3 is out of scope for this CSS refactor plan
   P5.3 removes themeService compatibility shims and updates Vitest
   tests. That is not CSS-refactor work; it is ThemeService/runtime
   cleanup.

   Recommendation:
   - move P5.3 to a separate follow-up track
   - OR label it explicitly as a cross-track dependency outside this plan

   Leaving it here makes the CSS plan sprawl into unrelated runtime work.

6. primitives.css needs an explicit wiring step
   Phase 3 says primitives live in src/styles/primitives.css (new).
   Good idea, but the plan never explicitly says where it gets imported.

   Recommendation:
   - add one explicit step:
     - import src/styles/primitives.css from src/index.css
     - or from the agreed top-level style entrypoint

   Otherwise the extraction phase produces primitives that are not
   guaranteed to load.

7. Commit wording should stay aware of user approval
   Multiple phases say "commit" scripts, outputs, or final inventory.
   The repo workflow for this user has been approval-first on commits.

   Recommendation:
   - either leave the plan text as-is but remember the workflow in

   This is not a technical bug, just a workflow nit.

Review of scripts/css-analysis/README.txt + current implementation
------------------------------------------------------------------
Date: 2026-05-23

I read README.txt, inspected the implementation files, and ran:

  npm run css:audit

Run result:
- tool runs cleanly
- inventory rows: 1874
- exact clusters: 123
- fuzzy clusters: 0
- cross-file collisions: 42

Overall:
- README is mostly accurate
- the folder shape is good
- the exact-vs-fuzzy separation is still encoded correctly
- but I found 3 things Opu should know before trusting the outputs too hard


1. numericallyClose is currently LOOSER than the question suggests
   This is the main implementation bug.

   In cluster.mjs, extractNumber() captures an optional unit but then
   discards it. numericallyClose() compares only the numeric scalar.

   Effect:
   - `1rem` and `1em` compare equal
   - `100%` and `100px` compare equal
   - any same-number different-unit pair can be treated as a fuzzy match

   So the current code does NOT implement "same units required";
   it implements "units ignored".

   Recommendation:
   - safer default: require identical units for fuzzy numeric matching
   - special-case `0` ~= `0`
   - if cross-unit comparison is wanted later, do it only for explicit
     compatible conversions (for example px <-> rem, and only if you
     define the conversion rule up front)

   My answer to Opu's question:
   - no, "same units required" is NOT too strict for v1
   - the real problem is that the current implementation is too loose


2. lookupToken / property-aware coverage is not broad enough yet
   The current exact-match approach is okay for:
   - `color`
   - `background-color`
   - `font-size`
   - simple spacing/radius properties

   But it misses several common forms that already exist in this repo:
   - `border: 1px solid rgba(...)`
   - `box-shadow: ... rgba(...)`
   - `outline: 3px solid #ffff00`
   - multi-value spacing shorthands like `padding: 8px 16px`

   Important nuance:
   - not all of these need to be solved in Phase 0
   - but `border` shorthand especially is part of the current colour debt
     surface, and the tool currently does not see it as tokenisable colour

   Recommendation:
   - minimum fix: add a documented limitation in README so reviewers know
     color-family reporting excludes shorthand-embedded colours for now
   - better fix: add parsing for at least `border` shorthand colour
     extraction and maybe outline shorthand too
   - do NOT try to solve every composite value before Phase 0 ships


3. jsx-refs is okay as a lower-bound hint, but too narrow as a true
   blast-radius counter
   The current implementation only walks `.jsx` files and regex-matches
   inside `className=...`.

   That is acceptable for a hint column, but it undercounts:
   - dynamic modifier classes like
     `email-list-pane__coin-badge--${status}`
   - suffix/interpolated families like
     `email-list-pane__tag--${tag}`
   - computed classes like `status-${contact.status}`
   - any future `.js`, `.tsx`, or `.ts` component files

   Recommendation:
   - keep the current approach if the column remains explicitly "hint only"
   - but rename the mental model to "lower-bound usage signal"
   - if Opu wants better accuracy, scan `.js/.jsx/.ts/.tsx` and extract
     static class tokens from string literals / template literals rather
     than trying to match whole attributes with one regex

   My answer to Opu's question:
   - yes, the current JSX-ref pattern is too narrow for exact counts
   - no, it is not too narrow for a rough prioritisation hint


4. Reporting bug: literal-map currently mislabels existing token values as
   "needs decision"
   After running the tool, literal-map.md shows entries like:
   - `var(--text-primary)`
   - `var(--text-secondary)`
   - `var(--accent-primary)`

   ...as "needs decision".

   That is wrong. Those are already tokenized values, not unresolved
   literals.

   Recommendation:
   - in report.mjs, treat existing `var(--...)` values as "already tokenized"
   - or build literal-map from the normalized declaration surface instead of
     the raw-value table

   This is worth fixing because it makes the highest-frequency rows in the
   report look noisier and less trustworthy than they really are.


Bottom line on README + scripts
-------------------------------
- README is broadly fine
- the tool runs
- but I would fix numericallyClose before trusting fuzzy clusters
- and I would fix the literal-map token labelling before using that report
  as a review artifact
- lookupToken/property coverage is acceptable for a first pass only if the
  shorthand blind spots are documented clearly
