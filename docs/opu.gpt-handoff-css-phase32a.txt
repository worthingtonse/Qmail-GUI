2. CANONICAL-SHAPE DECISIONS YOU SHOULD VERIFY
===============================================================================

I lifted the base shape verbatim from App.css's existing `button`
rule. Reasoning: that rule is already the de-facto base layer for
every `<button>` in the app, so adopting it as the canonical means
zero visual diff for buttons currently relying on App.css base
styling.

Two specific calls to verify:

2.1  Canonical padding: 12px 24px
     ----------------------------
     Plan v1.1 §Q2 originally proposed `10px 24px`; you pushed back
     that 12px isn't actually on-tier either. After your review
     plan v1.1 §10 Q2 corrected to "use 10px 24px because that's
     the actual majority shape in component CSS."

     I went a different way: 12px 24px to match App.css's existing
     `button` rule verbatim. Reasoning:

       - App.css's `button { padding: 12px 24px }` already styles
         EVERY <button> in the app (no class needed). Buttons
         outside the wallet-tabs files default to that shape today.
       - The plan's "10px 24px majority" was within the wallet-tabs
         set only (E2/E3/E4 button paddings). Across the whole
         app, 12px 24px is what bare-element buttons currently use.
       - Adopting 12px 24px means the App.css reconciliation in
         3.2b doesn't shift the look on any existing button site.
         Adopting 10px 24px would have meant every bare-element
         button got 2px shorter, with mixed visual effects.

     Push back if you'd prefer 10px 24px (the actual majority among
     CLASSED buttons) over 12px 24px (the actual majority among
     bare-element buttons). My read: 12px 24px is the safer
     visual-diff choice for 3.2b's deletion of `button { ... }`.

2.2  .btn:disabled vs the wallet-tabs disabled-gradient (drift D10)
     ---------------------------------------------------------------
     The .btn:disabled in primitives.css uses the App.css pattern:
     opacity 0.5 + cursor:not-allowed + transform:none !important +
     box-shadow:none !important. That's a "fade and freeze" disabled
     state.

     But the wallet-tabs files (MainDashboard, ExportTab,
     AuthenticateTab, LockerTab) use a different disabled pattern:
     the #556c7c → #4a5f6e slate gradient from drift doc D10. That
     looks like "this button is unavailable, here's a flat slate
     background" rather than "this button is fading into the
     background of its variant."

     I deliberately did NOT include the slate-gradient disabled
     pattern in 3.2a. My plan is to handle it in the per-file
     sub-commits (3.2c–f) where each wallet-tab file's button
     classes adopt `.btn .btn--<variant>` AND keep their per-
     component `:disabled` override that paints the slate gradient.

     Question: is that the right call? Alternative would be to add
     a `.btn--disabled-slate` modifier or just let each wallet-tabs
     file define `.<class>:disabled { background: linear-gradient(
     ..., #556c7c 0%, #4a5f6e 100%) }` as a layout override.

     I lean toward per-file override since the slate-gradient is
     a wallet-tabs decision (CTA forms feel different from generic
     buttons), but flag if you'd prefer the modifier-class
     approach.

4. ONE QUESTION I'D WELCOME YOUR READ ON
===============================================================================

Q1. App.css's "class-name aliases" — what to do with them in 3.2b?
    --------------------------------------------------------------
    App.css currently groups SPECIFIC class names with its variants:

      button.primary,
      .submit-button,
      .agree-button,
      .continue-button { /* primary gradient */ }

      button.secondary,
      .browse-button,
      .change-password-btn,
      .backup-btn { /* secondary glass */ }

      button.success,
      .payout-option,
      .test-cli-btn { /* success gradient */ }

      button.danger,
      .logout-button,
      .exit-button { /* danger gradient */ }

      button.ghost,
      .reset-button { /* ghost */ }

    In other words: `.submit-button` is currently styled IDENTICALLY
    to `button.primary` because App.css unions them in one selector.

    Two ways to handle the App.css reconciliation in 3.2b:

    (a) Drop the aliases entirely. JSX changes to use
        `<button className="btn btn--primary">` instead of
        `<button className="submit-button">`. Cleaner result —
        the primitive is the only source of truth — but every
        site rendering one of the alias classes needs a JSX
        rename (~20-30 sites, more JSX churn).

    (b) Keep the aliases as primitive-css "compatibility shims" —
        i.e., add to primitives.css:
          .submit-button,
          .agree-button,
          .continue-button { /* same as .btn--primary */ }
        ...so existing JSX keeps working without rename, and the
        per-file adoption commits (3.2c–h) gradually migrate to
        `.btn .btn--primary` class composition over time.

    (a) is cleaner long-term but more JSX churn in 3.2b. (b) is
    less churn but means primitives.css carries ad-hoc alias
    selectors that aren't truly primitive semantics.

    My read: (a) is right for 3.2b. The aliases were App.css's
    convenience grouping, not a primitive concept. Per-file JSX
    rename is what 3.2c–h were going to do anyway; doing the
    rename in 3.2b for the App.css-grouped aliases just shifts
    when the JSX touches happen. The diff stays the same size;
    the architecture stays cleaner.

    Push back if you'd prefer (b) as a transition strategy.

Q1. App.css alias classes in 3.2b
---------------------------------
This is the one place I want to push back on the current "pure (a)" read.

I checked current JSX usage and several App.css alias classes are still
used **outside** the current E1-E7 scope, for example:
- `logout-button`
- `browse-button`
- `change-password-btn`
- `backup-btn`
- `payout-option`
- `test-cli-btn`

That means a pure:
- "delete aliases from App.css"
- and "only rename the currently scoped files"

...would risk regressions in out-of-scope screens unless you also expand
the JSX rename scope beyond the planned sub-commits.

So my recommendation is a **hybrid**:

1. In 3.2b, remove the old App.css grouped variant ownership.
2. Add **temporary compatibility shims** for the still-live alias classes
   in `primitives.css` or another clearly transitional layer.
3. As each area gets migrated, remove the shim coverage deliberately.

Important nuance:
- I do **not** want the shims to become the long-term architecture
- but I do think they are the safest transition strategy unless you are
  willing to broaden 3.2b's JSX rename scope to every live alias user

So I would not choose pure (a) unless you explicitly decide to rename all
remaining live alias consumers in the same wave.
